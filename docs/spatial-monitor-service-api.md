# 俯瞰モニター向けサービスAPI案: LARM・ContextStill

作成日: 2026-09-29

状態: 設計案。LARM・ContextStillの現行実装済みAPIを表す文書ではない。URL、認証、値の可用性は各サービスで受け入れ確認が必要。

## 目的と境界

SAAAがLARMとContextStillの状態を低負荷で読み、短時間の異常も履歴へ残せるようにする。各サービスが自分の状態と活動の正本を持ち、SAAAは読み取り専用の利用者となる。通常の確認は1分ごと、変化の遅い値は10分ごと。正常な観測値はSAAAのメモリだけに置き、永続化は`warn`・`danger`・`critical`の異常エピソードに限る。

対象はLARMとContextStillが**提供する**APIの提案である。SAAAの画面向けIPC、サービス設定の変更、ジョブ操作、能動的なモデル診断のAPIは対象外。

## 共通の読み取り契約

| 目的 | LARMの提案URL | ContextStillの提案URL | 呼び方 |
| --- | --- | --- | --- |
| 現在の要約 | `GET /v1/monitor/snapshot` | `GET /api/monitor/v1/snapshot` | SAAAが約1分ごと。1回で通常と低頻度の区画を受け、区画ごとの観測時刻で更新を判断 |
| 異常の差分 | `GET /v1/monitor/changes?after=<cursor>&limit=100` | `GET /api/monitor/v1/changes?after=<cursor>&limit=100` | スナップショットと同じ周期で取得。正常サンプルを列挙しない |
| 対象の詳細 | `GET /v1/monitor/entities/<id>` | `GET /api/monitor/v1/entities/<id>` | 利用者が対象を選んだときだけ。IDはスナップショットに出た不透明IDに限定 |

URLは既存APIとの衝突を避けるための提案であり、実装時に両プロジェクトのルート規約と照合する。スナップショットと差分の2要求を別々に送るか、同じ応答にまとめるかも、実測した負荷に応じて決めてよい。両者の意味上の契約は維持する。

### スナップショットの共通部分

```json
{
  "schemaVersion": "monitor.v1",
  "source": "larm",
  "instanceId": "opaque-runtime-id",
  "generatedAt": "2026-09-29T12:00:00Z",
  "cursor": "opaque-change-cursor",
  "entities": [
    {
      "id": "host:primary",
      "kind": "host",
      "label": "LARM host",
      "readiness": "ready",
      "lastObservedAt": "2026-09-29T11:59:58Z"
    }
  ],
  "sections": {},
  "activeIncidents": []
}
```

`source`は`larm`または`contextstill`。`generatedAt`は応答生成時刻であり、個々の計測時刻ではない。各区画・値は`observedAt`、対象期間、`sampleCount`、単位、取得可否を持つ。更新のなかった10分周期の値は、前回値とその実測時刻を返してよい。`null`または`unavailable`は0とは異なる。状態の種類は`readiness`、直近実処理、SAAAからの到達性、観測の鮮度に分ける。SAAAからの到達性は受信側で判定し、サービス自身が代弁しない。`cursor`と`activeIncidents`は同一の論理時点を表し、その時点より後に起きた変化は必ず`changes`に現れる。初回取得と再同期で取りこぼさないための条件である。

`entity.id`は表示名やプロセスIDから推測せず、サービスが安定して付与する。モデルのファイルパス、プロンプト、音声内容、タスク本文、秘密情報は返さない。件数・文字列長・応答サイズを上限付きにし、`Cache-Control: no-store`を付ける。

### 差分と再同期

差分に含めるのは、異常の開始、`warn`→`danger`→`critical`などの深刻度変化、回復、観測不能への遷移だけとする。イベントは`source`、サービス内で一意な`changeId`と`incidentId`、対象ID、種類、深刻度、発生時刻、検知時刻、短い理由コード、必要最小限の数値根拠を持つ。同じ`changeId`の再取得はSAAAで冪等に扱い、同じ`incidentId`の変化は一つの異常エピソードへ適用する。

```json
{
  "schemaVersion": "monitor.v1",
  "source": "larm",
  "changes": [
    {
      "changeId": "opaque-change-id",
      "incidentId": "opaque-incident-id",
      "change": "opened",
      "entityId": "service:llm:primary",
      "severity": "warn",
      "reasonCode": "queue_wait_high",
      "occurredAt": "2026-09-29T11:59:20Z",
      "observedAt": "2026-09-29T11:59:22Z"
    }
  ],
  "nextCursor": "opaque-next-cursor",
  "hasMore": false
}
```

`after`はサービスが発行した不透明なカーソルであり、SAAAは数値や時刻として解釈しない。初回はスナップショットの`cursor`から開始する。ページ上限を超えた場合は`hasMore`で続け、差分取得中の新しいイベントと重複してもIDで除く。サービス再起動・カーソル期限切れでは明示的な`cursor_expired`を返し、SAAAがスナップショットを取り直す。スナップショットは現在継続中の異常を必ず含める。終了済み異常の完全な再生が必要なら、各サービス側の異常記録の保持期間を決める。保持できない区間を正常として埋めない。

差分取得は長時間接続を前提にしない。1分以内に終わった異常を拾うための小さなポーリングAPIとする。`critical`の即時通知が将来必要になれば、同じイベント契約の配信手段を追加する。通常の毎分スナップショットだけで即時検知を保証しない。

### 詳細の共通部分

詳細応答は選択対象の現在値、取得元、最終観測時刻、短いメモリ上の推移、継続中の異常と根拠、実在する詳細画面への導線を返す。全サービス・全タスクのログや長い生サンプルは返さない。存在しない対象は404、現在取得できない値は項目ごとに`unavailable`と理由コードを示す。画面を閉じたら詳細取得を止める。

## LARMが提供する内容

### ホスト区画

LARMホストがUbuntu上で採取し、次を型付きで返す。

| 項目 | 表現 | 更新の初期案 |
| --- | --- | --- |
| CPU | 使用率の1分要約。内部採取が複数回なら平均・最大・件数 | 毎分 |
| メモリ | 使用可能バイト数、使用量、スワップ | 毎分 |
| GPU | GFX使用率、ドライバーが報告するメモリ割当、温度・電力の取得可能な項目 | 毎分。項目別に取得可否を返す |
| ディスク | 読み書きバイト数の差分による速度、空き容量 | I/Oは毎分、容量は10分 |
| ネットワーク | 送受信バイト数の差分による速度、エラー | 毎分 |

Ryzen AI MaxのGPUメモリ割当を、128GBのシステムメモリとは別の物理容量として合算しない。累積カウンターが再起動・リセットされた期間は速度を`unavailable`にする。GPUの利用率はホスト全体の値であり、特定モデルの利用率と表示しない。AMD SMIとamdgpuで実機から取れた値だけを契約に加える。

### サービス区画

LARM自身がLLM・ASR・TTS・Embeddingなどの実行層から要約を作り、モデル／機能ごとに次を返す。`/health`やCatalogで広告された能力と実処理の結果を混同しない。

| 機能 | 1分窓の値 | 現在値・health |
| --- | --- | --- |
| LLM | 処理件数、失敗件数、総出力トークン数、総生成時間、初回トークン時間と要求時間の分布 | モデルID、実行・待機件数、readiness、直近実処理成功時刻 |
| ASR | 処理件数、失敗件数、入力音声秒数、処理時間、音声終了から確定までの分布 | 実行・待機件数、readiness、直近実処理成功時刻 |
| TTS | 処理件数、失敗件数、生成音声秒数、処理時間、初回音声までの分布 | 実行・待機件数、readiness、直近実処理成功時刻 |
| Embeddingなど | 処理件数、失敗件数、処理時間の分布 | readiness、実行・待機件数 |

tok/sはSAAA側で`総出力トークン数÷総生成時間`から計算する。総生成時間が0、トークン数未取得、標本がない場合は値を返さない。モデル識別子は低基数に制限する。LARM内の処理時間と、SAAAが別途測るネットワーク込みの往復時間は別の値として表示する。要求・失敗の詳細本文はこのAPIに含めない。

## ContextStillが提供する内容

ContextStillの既存キュー台帳・イベントを正本にする。現行の`/api/queue/stats`、`/api/queue/active`、`/api/overview`は利用可能な情報源だが、モニター用途の安定した小型契約としては未完成である。監視用スナップショットはそれらと同じ正本から生成し、別の状態台帳を作らない。

| 対象 | スナップショットに出す値 | 差分に出す出来事 |
| --- | --- | --- |
| キュー | キューID、待機・実行・失敗件数、最古の待機時刻、停止・一時停止状態 | 滞留、失敗の増加、停止、回復 |
| Pipeline／工程 | 段階ID、実行件数、次段階への移管件数、直近の進行時刻 | 停滞、異常終了、回復 |
| LARM依存 | ContextStillから見た待機・再接続・実処理状態 | 依存先待ちの開始・終了 |
| ContextStill自身 | APIの準備状態、台帳参照の可否、最後に生成できた要約の時刻 | 監視要約不能・回復 |

タスクのタイトル・本文、検索対象の知識内容、プロンプト、外部サービスの秘密情報は返さない。クリックしたキューの詳細には件数、最古待機、最近の工程変化、関連する不透明タスクIDなど最小限を返す。タスクの全履歴はContextStillの既存画面・台帳への導線に委ねる。SAAA側でContextStillのジョブ進捗を推測しない。

通常の開始・段階移動・完了は`changes`へ流さず、スナップショットの件数と直近活動の時刻・種類だけに集約する。異常終了は`changes`へ流す。これにより通常の高頻度イベントを監視用の永続履歴へ増幅しない。

## 認証・失敗・負荷

- **LARM**: SAAAが現在使うプライベートネットワークとBearer認証の境界を維持する。監視APIはGETのみで、接続作成・claim・設定変更を行わない。既存のBearerを使えるか、監視専用の読み取り権限が必要かはLARM側の認証実装を確認して決める。
- **ContextStill**: 現行の`/api/*`は公開healthを除き管理者認証が掛かる。監視APIへ管理者キーを広く配る設計にはせず、同一Macからの読み取り専用認証方法を実装時に決める。単なるloopback到達を認証の代わりにしない。
- 両サービスとも`Cache-Control: no-store`、短いタイムアウト、件数・応答サイズ上限、秘密情報を含まない固定のエラーコードを用意する。部分的に値が取れない場合は200で項目別`unavailable`、API全体が機能しない場合は503とする。認証失敗を対象サービスの障害と表示しない。
- 正常な毎分確認でサービス側にもディスク書き込みを生じさせない。ContextStillの既存台帳更新はこの条件から除く。差分は既存台帳または上限付きの異常記録から作り、正常サンプルの新たな履歴表を作らない。
- SAAAは別々の`source`と`incidentId`で冪等に異常を保存する。各サービスの異常記録を丸ごと複製せず、画面に必要な短い根拠と参照IDだけを保持する。

## 検証条件と未決定事項

1. 固定時刻のfixtureで、正常時のスナップショット、1分窓と10分窓の時刻・件数、未取得GPU値、カウンターリセット、無要求時のLLM性能値なしを確認する。
2. 1分以内に発生して回復したwarn、深刻度上昇、重複イベント、カーソル期限切れ、サービス再起動を再現し、取得・再同期・欠測表示を確認する。
3. 認証なし・誤った認証・不正な対象ID・上限超過・部分的取得失敗で、内容漏洩や正常の誤表示がないことを確認する。
4. 実機で1分／10分の通常取得中に、LARM・ContextStillのCPU、メモリ、ネットワーク、ディスク書き込みが許容範囲であることを測る。SAAAの会話と音声遅延も同条件で比較する。

未決定: 各サービスでのルート命名、ContextStillの監視専用認証、LARMの利用可能なGPU値、LARMエンジンごとのトークン・音声時間の計測可否、異常差分の保持期限、HTTP応答の厳密な上限値。これらは実装前に両サービスの所有者と現行契約を照合して確定する。
