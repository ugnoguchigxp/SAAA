# SAAA 俯瞰モニター構想

作成日: 2026-09-28

状態: 構想整理。実装契約・保存期間・閾値は未確定。

## 目的

SAAAで会話や他の作業を続けながら、Mac、SAAA、LARM、ContextStillの状態と活動を一目で把握する。異変に気づいたら上部メニューの「モニター」を開き、対象を選んで数値・経過・根拠を調べる。

`../hono-standard` のDashboard v2で試作中のSpatial Surfaceを表現の参考にする。ただし、現行試作の表示値はMockであり、SAAA・LARM・ContextStillの実測値ではない。実連携は各システムの正本と取得契約を確認してから設計する。

## 範囲と前提

- 対象はSAAAが動くMac、別ホストのLARM、同じMac上のContextStill。
- LARMホストは、ユーザー申告では2026年春のUbuntu Desktop、AMD Ryzen AI Max 395系、メモリ128GB。正確なOS版・製品名・GPUドライバー・ROCm版は実機で確認する。
- ContextStillのホストCPU・メモリを独立した観測系として重複計測せず、ContextStill固有の処理活動を連携する。
- この文書は観測と表示の構想であり、自動復旧、プロセス制御、診断の定期実行、公開APIやDBスキーマの確定を含まない。
- 会話のASRはTTS再生中も継続する。画面切替、背景描画、モニターへの遷移が音声キャプチャや発話割り込みを止めてはならない。

## 利用体験

### 背景表示

会話を選んでいる間、Spatialは操作不能な背景として表示する。会話レイヤーは文字と操作の読みやすさを保つ半透明の面にする。背景は重要な異常や活動の偏りを控えめに伝え、細かな数値や大量の文字を置かない。背景側はクリック・スクロール・キーボード操作を奪わない。

他の画面にも同じ背景を広げる構想がある。ただし設定、単体テスト、診断など文字を読む画面では不透明度・動き・更新頻度を下げる。全画面への適用範囲と既定値は、画面ごとの可読性を見て決める。

### 「モニター」画面

上部メニューの「モニター」を選ぶと会話レイヤーを隠し、Spatialを全面で操作できる。画面切替は会話状態を破棄しない。配置は安定させ、Mac、SAAA、LARM、ContextStillとその依存関係を見失わないようにする。

画面上部には、少なくともMacのCPU・メモリ圧迫、LARMのCPU・GPU・メモリ、異常件数、観測時刻を簡潔に表示する。詳細な時系列や原因調査は選択後のHTMLパネルへ置く。Canvasを使えない場合も、同じ意味情報を一覧と詳細から読めるようにする。

| 視覚要素 | 表す意味 |
| --- | --- |
| ノード | ホスト、サービス、工程、キューなどの対象 |
| 接続線 | SAAA↔LARM、SAAA↔ContextStillなどの通信・依存関係。接続自体の状態を両端の健康状態と分ける |
| 明るさ・短い動き | 実測された活動量・処理中の状態 |
| 途切れ・警告形状 | 切断・失敗。色だけに意味を依存させない |
| 薄さ・時刻表示 | 観測値の古さ。過去の正常値を現在の正常値として見せない |

高負荷は直ちに障害を意味しない。例えば「GPU高負荷でLLMが順調に生成中」と「GPUが空いているのに要求が待機中」は別の状態として示す。

## 信号の採取元

| 所有者 | 最初に扱う信号 | 採取・提供の方針 |
| --- | --- | --- |
| SAAA上のMac | CPU使用率、使用可能メモリ、メモリ圧迫、スワップ、必要に応じディスク・ネットワーク | TauriのRust側がmacOSから採取。Activity Monitorとの差と表示基準を実機で確認する |
| SAAA | SAAAプロセス負荷、会話応答時間、HTTP・音声経路の遅延、キュー、失敗、自己診断 | 既存の実行時計測・診断を利用。WebViewなど別プロセスを合算する範囲は確認する |
| LARMホスト | CPU、GPU、メモリ、ディスク容量・I/O、ネットワーク送受信・エラー | LARMホスト側が採取し、認証付きの読み取り専用要約をSAAAへ渡す |
| LARMサービス | LLM、ASR、TTS、Embeddingなどの準備状態、処理量、待機、遅延、失敗 | サービスを実行する側で計測。SAAAから見た往復時間は別信号として残す |
| ContextStill | キュー別の待機・実行・失敗件数、最古の待機、工程遷移、直近の完了・失敗、LARM待ち | ContextStill自身の台帳・既存APIを正本に、監視用の小さな要約を提供する |

SAAAには既に自己診断と一部のHTTP・音声経路計測がある。ContextStillにはキュー集計、実行中タスク、処理イベントの基盤がある。一方、現時点でSAAAのLARM接続からLARMホストの資源使用率を取得できるとはみなさない。

### LARMの資源信号

- CPU: ホスト全体の使用率と、可能ならLARM関連プロセスの使用率。全体とプロセスで百分率の基準を明示する。
- GPU: GFX使用率、メモリ割当、温度、電力を候補とする。AMD SMIまたはamdgpuの提供値を実機で確認し、未対応項目は`取得不可`にする。
- メモリ: システムの使用可能量とスワップを優先する。Ryzen AI Maxの統合GPUが報告する「GPUメモリ割当」は物理メモリ128GBと独立した容量として足し合わせない。
- ディスク: 空き容量と読み書き速度を別々に示す。ネットワークも送受信速度と接続エラーを分ける。速度は累積カウンターの差から算出し、再起動・カウンターリセットを扱う。
- GPU値はホスト全体の活動であり、特定モデルの使用率と断定しない。プロセス別の値は実機で正確に取れる場合だけ表示する。

### LARMの処理性能

| 機能 | 表示候補 | 計測の定義 |
| --- | --- | --- |
| LLM | モデル別の出力tok/s、最初のトークンまでの時間、要求全体の時間、実行・待機件数、失敗率 | tok/sは出力トークン数÷実際の生成時間。要求全体の時間を分母とする値とは区別する |
| ASR | 音声終了から確定文字起こしまでの時間、入力音声長、処理時間、失敗率 | 音声秒数に対する処理時間を示す。tok/sに置き換えない |
| TTS | 最初の音声までの時間、生成音声長、処理時間、失敗率 | LARMでの生成とSAAAでの受信・再生を別に測る |
| 共通 | 処理件数、実行・待機件数、失敗理由の分類 | コンテンツ本文や音声は計測値に入れない |

期間のLLM tok/sは、各要求のtok/sの単純平均ではなく、計測できた要求の**総出力トークン数÷総生成時間**を基本値とする。併せて件数と要求ごとの中央値・遅い側の分布を示す。トークン数が得られない要求を推測で補完しない。モデル、処理種別、ホストなど必要な低基数の分類だけを持つ。

### healthの意味

次を一つの「健康度」に潰さない。

1. **到達性**: SAAAから接続できるか。
2. **準備状態**: サービスが要求を受けられるか。
3. **実処理**: 直近の実要求が成功し、期待する時間で完了したか。
4. **能動診断**: 明示的に実行した検査の結果。検査モードと実行時刻を付ける。

SAAAのFast診断で能力が見つかったことを、Operational診断の成功として表示しない。重い実要求を短周期で繰り返さず、通常は実トラフィックから3を観測する。無要求の期間は「異常なし」と「実処理未確認」を区別する。

## 収集・集約の流れ

```text
各システムの台帳・計測器
  ├─ Mac / SAAA: Tauri Rustの採取・既存診断と計測
  ├─ LARM: ホスト資源とLLM/ASR/TTSをLARM側で要約
  └─ ContextStill: 自身の台帳から活動を要約
                  ↓
        SAAAの監視用受信・正規化
                  ↓
     観測時刻・鮮度・接続状態を判定
                  ├─ 現在値・毎分履歴・判定用の窓: 上限付きメモリ
                  ├─ 正常値: 保存せず期限で破棄
                  ├─ warn / danger / critical: 発生から回復までをSQLite
                  └─ Spatial / HTML一覧 / 詳細パネル
```

観測値には少なくとも`source`、対象ID、指標ID、値と単位、`observedAt`、`receivedAt`、期待更新間隔、取得状態を持たせる。ホスト時計のずれを考慮し、遠隔時刻とSAAA受信時刻を保存する。接続断で値が来ない場合、最後の値を表示しても鮮度を落とし、期限超過後は現在値として扱わない。復旧時は完全スナップショットで同期してから差分を反映する。

### 確認周期の初期案

**常時の遠隔確認は1分を基本**とし、変化の遅い項目は10分ごとにする。確認結果はまずメモリで受け、正常値は永続化しない。採取周期、SAAAへの転送周期、画面描画周期、異常記録の保存条件は別に決める。

| 区分 | 対象の例 | 通常時の確認案 | 補足 |
| --- | --- | --- | --- |
| 出来事の発生時 | LLM・ASR・TTSの要求完了と失敗、ContextStillの工程遷移、切断と回復 | イベント時にメモリへ反映 | warn以上の異常への遷移を重複を抑えて保存。定期ポーリングだけでは短い失敗を見逃す |
| 毎分 | MacとLARMのCPU・GPU・メモリ、LARMの処理量と待機、軽量な到達性、ContextStillのキュー要約 | 1分ごとに要約を取得 | LARM側は必要なら内部で複数回採取し、1分間の平均・最大・件数を返す。SAAAが生サンプルを毎回受け取らない |
| 10分ごと | ディスク空き容量、モデル・サービス一覧、構成や容量など変化の遅い情報 | 10分ごと | ディスクI/O・ネットワーク速度のような活動量は毎分側に置く。重い能動診断をこの周期で自動実行しない |
| 詳細を開いている間 | 選択したホストのCPU・GPUや短い推移 | 必要な項目だけ数秒～十数秒へ一時的に短縮 | 実機で採取負荷を確認してから有効化。画面を閉じたら通常周期へ戻す |

軽い到達性確認と、LLM・ASR・TTSへ実要求を送るOperational診断は分ける。後者は既存の手動診断を基本とする。1分値や10分値には対象期間・採取回数を付け、前者の1分間に何度も採取した値と、1分間隔の単一観測を同じ「平均」として扱わない。10分周期の値について、測っていない9分間を補間して1分値にしない。

鮮度の期限は信号ごとの期待周期に合わせる。1分周期と10分周期を同じ時間で`古い`にせず、直接の取得失敗・期限超過・サービスが報告した障害も区別する。具体的な期限は実機での応答遅延と揺らぎを見て決める。

### 異常の記録単位

通常の数値はメモリ上の短期履歴から判定する。`warn`、`danger`、`critical`に達したときだけ、対象・指標・根拠・発生時刻を持つ**異常エピソード**を作る。継続中は毎分新しい行を作らず、最大値、持続時間、件数、深刻度の上昇だけを必要に応じて更新する。正常に戻った時刻も同じエピソードに記録する。回復は正常データの常時保存には当たらない。

エピソードには、原因を読むのに必要な範囲で、発生直前のメモリ上の要約を添える。正常時の全サンプルはコピーしない。瞬間的な揺れでwarnを大量に作らないよう、信号ごとに継続条件、回復条件、再発のまとめ方を定義する。`danger`・`critical`は通知と保存を優先し、warnの細かな更新はまとめられるようにする。監視側が取得不能になった場合も、対象の障害と区別した観測不能エピソードにする。

`warn`、`danger`、`critical`は表示と保存のための深刻度であり、到達性・準備状態・実処理といったhealthの種類を置き換えない。閾値と通知方法は指標ごとに後から決める。

## クリックしたときの詳細

共通の詳細パネルは**対象名・役割／現在状態・観測時刻・取得元・メモリ上の直近推移・保存した異常エピソード・次に開ける実在画面**を示す。異常エピソードを選ぶと、発生・深刻度上昇・回復の時刻、継続時間、最大値、判定根拠、直前の短い要約を読める。`正常`、`高負荷`、`劣化`、`切断`、`古い`、`未観測`を別の語として表示する。数値が取れない場合は理由を示す。

| 選択対象 | 詳細に出す項目 |
| --- | --- |
| Mac | CPUとメモリ圧迫の直近推移、使用可能メモリ、スワップ、SAAA負荷。必要に応じディスク・ネットワーク |
| SAAA | 会話・音声経路の現在状態と遅延、キュー、直近の失敗、自己診断の実行時刻・モード・結果。既存診断画面への導線 |
| LARMホスト | CPU、GPU、メモリ、ディスク、ネットワークの現在値と推移。GPUの取得可否、統合メモリの注記、採取時刻 |
| LLMサービス／モデル | 実行・待機件数、出力tok/s、初回トークン時間、要求時間、失敗率、計測件数、直近の実処理確認時刻 |
| ASR／TTS | 準備状態、実行・待機件数、初回結果までの時間、音声長と処理時間、失敗率。SAAAから見た往復・再生との差 |
| ContextStill | キュー別の待機・実行・失敗、最古待機、現在工程、直近の状態遷移。ContextStillの実在する詳細画面への導線 |
| 接続線 | 両端の状態とは独立した到達性、遅延、失敗、最終成功時刻、再接続中かどうか |

パネルに表示する平均や異常判定には、対象期間とサンプル件数を添える。Canvas内の小さな文字に詳細を依存させない。

## 保存と寿命の初期案

個人向けの監視として、常時の表示と早期の異常検知を優先し、正常だった観測値はSQLiteに保存しない。以下は**暫定値**であり、メモリ使用量・実際の書き込み量・DB増分・調査に必要な期間を測って確定する。

| データ | 保存先 | 寿命案 | 用途 |
| --- | --- | --- | --- |
| 現在値と毎分の通常観測 | 上限付きメモリ | 直近24時間を上限候補 | 画面表示とその日の推移、異常判定。期限・再起動・異常終了で消失してよい |
| 詳細表示中だけの細かなサンプル | 上限付きメモリ | 直近15分 | 短いスパイクの確認。通常はSQLiteへ保存しない |
| 正常な毎分値・10分値 | 保存しない | メモリ上の期限まで | SQLiteの行を作らない。再起動後に正常履歴は復元されない |
| warnの異常エピソード | SAAA SQLite | 7日を初期候補 | 発生、根拠、最大値、継続時間、回復。繰り返しはまとめる |
| danger・criticalの異常エピソード | SAAA SQLite | 30日を上限候補 | 重大な異常と回復の追跡。保存件数・容量も上限を設ける |
| 構成情報 | 通常は保存しない | 異常エピソードに必要な範囲だけ | 原因調査に必要な版・モデル識別などを異常発生時の文脈に含める |
| ContextStillの個々の処理記録 | ContextStill自身の台帳 | ContextStill側の規約に従う | 詳細の正本。SAAAへ全件複製しない |
| 既存の監査・技術ログ | 各システムの既存保存先 | 既存の規約に従う | 原因調査。監視の連続数値を毎秒ログに書かない |

メモリ上では平均だけでなく最大、最小、件数、必要な遅延分布を計算し、欠測を0に変換しない。CPUの短いピークとLLMの遅い要求を平均だけで消さず、異常エピソードに判定の根拠を残す。ただし1分間に1回しか測らない信号の最大値は、その観測値を超える意味を持たない。通常観測ではSQLiteトランザクションを作らない。異常終了時にメモリ上の正常履歴を失うことは受け入れる。重要な状態変化は既存台帳の永続イベントを優先し、それがない場合だけ少量を速やかに保存する。

古いデータは定期的に削除し、DB容量とWALの増分に上限・監視を設ける。SAAAの既存SQLiteは単一書き込み担当を持つため、初期案では短い一括書き込みを既存の所有経路に載せる。監視保存の遅れが会話や音声を待たせないよう、有界キューと間引き規則を設ける。削除・チェックポイント・バックアップも書き込みやI/Oを伴うため、会話中の負荷が低い時にまとめて行う方針とする。

SSD寿命への効果は書き込み回数だけでは判断しない。監視なし／ありの同条件で、SAAAとLARMのCPU、メモリ、ネットワーク、DB・WALの増分と書き込みバイト数、会話・音声の遅延を比較する。正常な定期観測に起因するSQLite書き込みが発生しないことを確認する。個人向けの機能として、その差が大きい場合は採取対象・詳細表示の更新・履歴保持をさらに減らす。

ディスク使用量の上限値、バックアップ対象、ユーザーによる履歴削除、イベントと監査ログの重複排除は実装計画で決める。保持期間だけでファイル容量の上限が守られるとはみなさない。

## 安全性と性能の境界

- SAAAの監視受信は読み取り専用にする。LARMやContextStillの設定変更・ジョブ操作を監視画面に暗黙に含めない。
- LARMからの資源・性能APIは既存のプライベートネットワークと認証境界に合わせる。秘密情報、プロンプト、文字起こし本文、音声データをメトリクスに含めない。
- ContextStillのDBをSAAAが直接開かず、ContextStillのAPI・台帳を正本とする。
- 背景描画、採取、SQLite書き込みは会話と音声の応答性を阻害しない。画面非表示・reduced motion・低性能時には描画を抑える。
- 観測側の障害は監視が古い／取得できない状態として示す。対象システムの障害と混同しない。

## 導入順と確認方法

1. **最小の実測版**: MacとSAAAのCPU・メモリ、既存診断、既存の音声・HTTP遅延を表示する。Activity Monitorとの比較で単位と計測範囲を確認する。
2. **LARMホスト**: 実機でUbuntu版、Ryzen AI Maxの正確な型番、ドライバー、AMD SMI／amdgpuの取得可能項目と採取負荷を確認する。CPU・GPU・統合メモリ・ディスク・ネットワークを要約APIで取得する。
3. **LARMサービス**: 実行エンジンでLLM・ASR・TTSの件数と時刻を採り、SAAAの往復時間と突き合わせる。モデル別のtok/s、初回結果時間、待機、失敗を確認する。
4. **ContextStill**: 既存のキュー集計・実行中タスクと照合して活動要約を作る。工程遷移の欠落、切断・再同期、ContextStill停止時の鮮度表示を確認する。
5. **UIと寿命**: 背景の可読性、モニター画面の操作、キーボードとHTML代替、CPU/GPU描画負荷、正常な定期観測に起因するDB書き込み0件、warn・danger・criticalの開始・上昇・回復の記録、連続異常の重複抑制、DB容量、7日・30日の削除を検証する。再起動でメモリ履歴が消えても表示が古い正常値を引き継がないことを確認する。TTSだけではASR発話が発生せず、再生中の人の発話はASRに届くことも確認する。
