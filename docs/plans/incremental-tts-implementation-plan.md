# LLM 応答の逐次 TTS 実装計画

状態: 2026-09-27 に逐次 TTS の初期実装を追加。Qwen の最終回答で SSE 差分から文末優先の片を作り、LLM 完了前に再生を始める。分割閾値と体感品質は実機で未測定。以下には当初の計画と、実装後も残る評価項目を記録する。

現在の実装は `stream_response.rs`、`streaming_speech.rs`、`speech_projection.rs` と既存の音声再生経路を使う。再生は片ごとに直列で、次片の先行合成と片単位の永続化・画面表示は未実装。これらと実機の初回発声時間の比較は P4–P5 の継続課題である。

## 1. 目的と範囲

ユーザー向け回答の全文生成を待たず、確定した文節から合成し、先頭の音声が再生可能になり次第発声する。主な成功指標は、入力確定から最初の可聴サンプルまでの時間である。回答の欠落・重複、順序逆転、不自然な間、取り消した回答の再生を防ぐ。

最初の対象は `ConversationCheckPage` と、その移行先として作業中の Qwen / Ornith / speech キュー経路とする。読み上げるのはユーザー向けの確定可能な Qwen 発言だけとし、Qwen の経路選択 JSON、Ornith の思考・調査結果、ツール制御文、内部思考は対象外にする。短い `quick` 回答は確定後すぐ単一片として読めればよい。逐次化の主な対象は、Ornith 結果を受けた Qwen の長い回答と、今後の長文回答である。

この計画で行うのは、LLM 本文ストリームの取得、音声用の安全な分割、先行合成、順序付き再生、状態記録、割り込みと失敗処理、計測である。ASR 認識方式、Qwen / Ornith の役割分担、Provider 認証、保存済みルーティング設定、既存の TTS Provider 選択は変更しない。一般会話の撤去済み応答ランタイム全体、`role_routing`、`steward` の音声経路をこの段階で復活・移行しない。新しい外部サービスやライブラリの導入も予定しない。

## 3. 採用するデータの流れ

1. Qwen の経路選択 JSON は全体を受け取ってから検証する。`quick` の短い `reply` は確定した回答として単一片で再生する。Ornith の結果は Qwen に渡し、Qwen がユーザー向け自然文を生成するときだけ本文差分を扱う。
2. LLM の本文差分をサーバー側の音声用バッファへ追加する。表示用の差分と音声用の差分は同じ許可済み本文から派生させる。制御フレームや内部思考は両方へ流さない。
3. 文末を優先して分割する。読点は一定の長さに達したときの補助境界とする。句読点がない場合は安全な境界と最大長で分割する。終端では残りを一片として流す。
4. Qwen の自然文生成を始める前に、その回答に対応する speech 仕事を作る。各片を `message_id + generation + ordinal` で特定し、読み上げ可否を確認したうえで合成する。先行合成には小さな上限を設け、再生は `ordinal` 順に一件ずつ行う。HTTP TTS は既存の音声本文ストリーム再生を使い、最初のデコード可能なサンプルから鳴らす。
5. LLM 完了時は音声片の連結結果と最終的な回答本文の一致を検証し、最終回答を `conversation_messages` に確定する。画面は保存済み状態から回答と音声状態を表示する。

### 3.1 音声片の確定境界

- `。！？` と、文末と判断できる `.!?` を強い境界にする。`、,` は弱い境界であり、短すぎる片を単独で発声しない。数値の小数点、略語、括弧内の句読点、URL、Markdown リンク、コード範囲は誤分割しない。
- 初回と継続片の最小長、目標長、最大長、無入力時の flush 時間は、削除前の値を初期候補として fixture と実測で調整する。固定値を製品要件として先に確定しない。無音や文末なしを無期限に待たず、入力終了時は必ず flush する。
- 音声用テキストの正規化は既存の `voice_text::text_for_speech` と発話指示の投影規則を確認してから適用する。表示本文と音声化した本文の対応を ordinal ごとに追跡できるようにする。音声用に削った Markdown 文字列を本文一致判定へ混ぜない。
- LLM 差分から音声片へ渡す前に、分割された `<think>` 等の内部思考タグ、制御フレーム、発話指示を増分で遮断する。最終本文だけの検査では、検査より先に誤発声する。ストリームの途中で後から訂正される可能性がある Provider では、確定済み差分だけを音声化する。完成本文が既送信 prefix と一致しなければ未再生片を止め、既に発声した範囲を「中断」として記録する。全文を黙って読み直さない。

### 3.2 永続状態と再生の安全性

既存の Qwen / Ornith / speech 仕事台帳を正本とし、発話片の順序・本文参照・状態を関連付ける。現行の `queue_runtime.rs` は `commit_answer` が全文保存後に speech 仕事を作るため、そのままでは逐次発声できない。Qwen の自然文生成前に発話単位の仕事を登録し、片の確定ごとに worker を起こす。音声片の保存方式は queue migration の実装時に確定するが、**可聴再生より前に片と世代を永続化**する契約を守る。`conversation_messages` の確定本文は最終回答だけとし、生成途中の内容は別の進行状態として扱う。画面内だけに第二の発話状態を作らない。

再生直前に `generation` と取消し状態を再確認する。古い世代の合成済み音声は破棄する。再起動で再生の成否が不明な片は自動再生せず `interrupted` / `outcome_unknown` として残す。途中で Provider が失敗した場合、既に聞こえた内容を取り消せないため、既発声 prefix と失敗状態を履歴・画面で確認できるようにし、残りを黙って欠落させない。最終本文の確定と音声片の確定を一つの「全文完成」時点に押し込まない。

複数の片の合成は上限付きで重ねられるが、発声順は一つのプレイヤーが守る。片の生成が再生に追いつかなければ自然な短い無音を許容し、無制限の TTS 要求やメモリ蓄積はしない。キュー満杯時は生成側へ backpressure を返し、失敗として記録する。割り込み時は合成リクエスト、未再生片、現在の再生を同じ generation で停止する。

### 3.3 Provider ごとの差

HTTP / LARM TTS は `http_audio` の逐次受信・再生を利用する。ただし Provider が音声本文を最後に一括送信する場合、片の生成開始は早まっても、その片の音が鳴るまでの短縮量は Provider の応答特性に依存する。WAV はヘッダーとデコード可能なサンプルの到着が必要であり、PCM は形式契約を満たす場合に逐次再生する。

System TTS は片単位で既存 renderer を実行して WAV を得てから再生する。片の間の無音が大きい場合は、まず再生プロセス起動や先行レンダリングの時間を測る。別の再生 API への全面移行は測定で必要性が確認された場合の別判断とする。各 Provider の声・速度・スタイルは一つの回答の間で固定し、片ごとに変動させない。

| 段階 | 作業 | 完了条件 |

各段階で targeted test を先に通し、P3 以降は初回発声と最終再生のログを残す。P1 のストリーム化で既存 Provider が SSE を返せない場合は、その Provider だけ完成本文の単一片再生を維持し、能力を明示して段階的に導入する。認証や設定を勝手に変更して回避しない。

## 5. 検証方法

### 5.1 資格情報不要の決定的な試験

| ケース | 判定 |
|---|---|
| LLM の差分が任意のバイト・文字境界で届く | 表示本文と連結後の本文が一致し、句読点を欠かさない。同じ本文と flush 時点なら音声片が差分の切れ目に依存しない。SSE の `[DONE]`、失敗、途中切断を区別する。 |
| `「明日は3.14です。次は…」`、URL、Markdown、コード、句読点なし長文 | 安全な位置でのみ区切り、読み上げ禁止範囲を発声しない。 |
| quick JSON、Ornith 結果、Qwen の最終自然文 | 最初の二つを生成途中に読まず、Qwen の可視本文だけを音声化する。 |
| 片 1 の再生中に片 2・3 の合成が完了 | 再生順は 1→2→3。最大並列数、未再生バイト数、キュー長が上限内。 |
| LLM 完了前に先頭の文と TTS 音声が届く | 最初の音声が LLM 完了イベントより前に再生される。音声本文を小分けで送る HTTP fixture では全バイト到着前に再生する。 |
| 生成途中の失敗、手動停止、新しい世代、画面閉鎖、アプリ再起動 | 古い音声は始まらず、再生済み prefix と失敗・中断状態が正しく残る。自動再読なし。 |
| DB migration | 既存 DB のコピーと空 DB の両方で成功し、保存済み Provider・ユーザー設定・会話履歴が変化しない。 |

テスト用の LLM と TTS はローカル fixture とし、認証情報や実機の音声デバイスを不要にする。可聴開始はプレイヤーの「最初のサンプルを出力キューへ渡した時刻」で機械判定し、実機では実際の聞こえ方も別に確認する。

### 5.2 実行コマンドと失敗時の扱い

| 段階 | コマンド | 期待結果 |
|---|---|---|
| P1–P4 の各変更後 | `cargo test --manifest-path src-tauri/Cargo.toml <追加した対象テスト名>` | 対象の決定的なケースが成功。失敗時は該当段階を修正し同じ fixture で再実行する。 |
| IPC / UI の変更後 | `bun run ipc:check`、`bun run typecheck`、`bun test tests/<追加した会話画面テスト>` | IPC 契約と表示状態が一致し、二重再生しない。 |

| DB 変更後 | コピーした既存 DB と隔離した新規 DB で migration fixture を実行 | 設定・Provider 選択・履歴が保持される。実 DB は試験に使わない。 |

実機確認は、短い quick、長い Qwen 回答、句読点が少ない回答、HTTP / LARM / System TTS、割り込み、TTS 接続失敗を同条件で行う。`inputAccepted → firstLlmDelta → firstSpeechBoundary → ttsRequest → firstDecodableAudio → firstMixerSample → speechEnded` の時刻と、片数・最大キュー長・片間の無音を記録する。p50 / p95、最終回答までの時間、欠落・重複率を P0 と比較する。数値目標は P0 の実測後に固定する。

## 6. 設計判断と留保

句読点ごとの無条件発声は、短片が増えて TTS 起動負荷と不自然な間を増やすため採用しない。文末優先も現時点では採用候補であり、P0 / P5 の実測と聴感で決める。全文完成後に文ごとへ分ける方式は初回発声の遅延を解決しない。非ストリーム JSON の `reply` を途中で構文解析して発声する方式は、経路選択や未確定内容を読む危険があるため採用しない。Qwen の自然文ストリームと、確定後の短い quick 回答を分けて扱う。

残る判断は、キュー移行の確定したスキーマに音声片をどう関連付けるか、Provider ごとの SSE 対応、System TTS の片間の無音許容値、途中生成失敗時の UI 文言である。これらは P0 / P1 の結果と現行キュー実装を見て決める。既に発声した内容は取り消せないことを、状態管理と評価で明示する。

## 7. `qwen-audio-agent` との比較で得た判断

隣接リポジトリの既定構成は Qwen Audio Realtime 等の音声出力可能なリアルタイムモデルを前台に置く。`server/src/voice/realtime-presentation-runtime.mjs` は Provider の `response.audio.delta` を `audio.delta` としてクライアントへ送り、`web/src/realtime/useRealtimeVoice.js` は受けた PCM を順に再生する。Gateway は LLM のテキストを句読点で切って別の TTS に送らない。外部の Hugging Face speech-to-speech を選んだ場合も、Gateway はそのサービスの Realtime インターフェースに接続し、STT / LLM / TTS と文章分割はサービス側が所有する。したがって、このリポジトリから「句読点分割が最適」とは結論できない。

参考にするのは音声境界以降の扱いである。`responseId` で音声と転写を対応させ、再生開始のクライアント通知まで転写表示を保留する。割り込み時は `playback.clear` で残音を消し、完了・中断を区別する。遠隔クライアントでは `web/src/realtime/audio.js` の PCM キューが最初のバッファと再開時のバッファを持ち、通信の揺れによる途切れを抑える。SAAA でも「TTS に要求した時刻」と「実際に音が出た時刻」を分け、発話片の表示・再生状態を音声出力イベントで確定する。

音声を直接生成するリアルタイムモデルへの移行は、SAAA の LLM・TTS Provider 構成と、Qwen が確定した発言だけを読む契約を変えるため、この計画の対象外とする。将来その方式を比較する場合は、初回発声だけでなく事実の保持、指定本文との一致、音色、コスト、割り込み、Provider 選択の自由度を同条件で評価する。
