# ContextWindow 固定プレフィックス再利用計画

状態: レビュー用計画。2026-09-27 の作業ツリーを確認して作成。実装・Provider 設定変更は未実施。

## 1. 目的と判断の前提

会話の各推論で共通する SystemContext とツール定義を安定した入力プレフィックスに置き、Provider が対応する場合に入力キャッシュを再利用する。まず通常の会話で再利用率と応答時間を測り、効果が確認できた場合だけ、SAAA 起動後の非同期先読みを追加する。

この計画でいう `contextWindow` はモデルへ渡せる入力・出力の容量契約であり、キャッシュそのものではない。Chat Completions の現行経路は毎回 `messages` 全体を送る。LARM の `Session` は Provider の接続・リースを管理するが、モデルの過去の入力を保持する会話 ID や KV キャッシュのハンドルを推論リクエストに渡していない。したがって、現行プロトコルで「起動時に固定部分を一度送れば、後続の通信は差分だけでよい」とは扱わない。Provider のプレフィックスキャッシュが有効な場合も、後続リクエストには全入力を送る。

対象は `conversation_check` の Qwen 入口判定、Ornith 思考・ツール利用、Qwen 最終発話の LARM Chat Completions 経路とする。Memory、WorldModel、会話履歴の根拠検証と `contextWindow` の容量制限を維持する。Provider の状態付き推論 API や LARM の契約変更による真の差分送信は別計画とする。

### 成功条件

1. 固定部分が同じ役割・同じ構成の連続リクエストで、バイト列と順序を保った先頭部分になる。現在のユーザー入力と変動する根拠は毎回再構築される。
2. キャッシュ非対応の Provider でも回答、権限、根拠検証、容量制限が現行と同じ結果になる。
3. 対応 Provider では、Provider が報告するキャッシュ使用量と実測の初回出力時間で利益を確認できる。SAAA 側の一致バイト数を Provider のキャッシュヒットと取り違えない。
4. 起動時の先読みは会話受付や起動完了を待たせず、利用しないモデルへの不要な推論を発生させない。

## 2. 現状の根拠

| 対象 | 現在の動作 | 計画への含意 |
|---|---|---|
| `src-tauri/src/memory/context_window/projected_context_message.rs` | 固定の `CONTEXT_POLICY`、Memory 投影、継続・直近履歴、現在の user 発話を順に組み立てる。容量はローカル上限で制限する。 | 固定ポリシーはプレフィックス候補。Memory と履歴は変動し、固定扱いしない。 |
| `src-tauri/src/runtime/conversation_check/queue_context.rs` | Ornith の指示へ ContextWindow の system 文と提示可能な記憶ツール定義を追加し、WorldFrame を履歴へ置く。根拠は応答後と保存前に検証する。 | ツール定義の内容・順序を安定させる。WorldFrame は短命であり、先読み対象にしない。 |
| `src-tauri/src/runtime/conversation_check.rs` | `complete_larm_role_with_events` が LARM の `contextWindow` 上限とローカル予算で履歴を調整し、役割別の指示・履歴・現在の入力を送る。 | プレフィックスの並び替え後も容量計算と必須根拠の保護を維持する。 |
| `src-tauri/src/providers/chat_completions/mod.rs` | リクエストごとに `messages` 全体を JSON 化し、`/chat/completions` に送る。 | この層だけでは差分送信にならない。Provider ごとのキャッシュ機能を調べ、対応がなければ先読みを有効にしない。 |
| `src-tauri/src/runtime/context/usage.rs` | `generation_usage` は `cache_read_tokens`、TTFT 等を保存できる。 | 現行の queue 会話経路へ接続するか、同等の小さな計測経路を用意する。欠測はゼロと区別する。 |

OpenAI の [Prompt caching ガイド](https://developers.openai.com/api/docs/guides/prompt-caching)は、同一プレフィックスの再利用、Provider 側のキャッシュ寿命、先読みの条件を説明している。ただし、SAAA の実際の LARM Provider が OpenAI の機能や同じリクエスト項目を実装しているとは仮定しない。

## 3. 入力の分割契約

| 層 | 内容 | 再利用・更新規則 |
|---|---|---|
| A: 役割別固定プレフィックス | Qwen 入口、Ornith、Qwen 最終発話それぞれの SystemContext、共通の信頼境界、安定したツール定義と順序 | プロンプト版、役割、Provider/モデル、ツールカタログが同じ間だけ同一バイト列にする。役割間でキャッシュを共有したとみなさない。 |
| B: 投影された状態 | Memory、WorldModel、継続履歴、直近履歴、スコープ、ツール結果 | 毎ターン正本から再構築する。Memory の revision、WorldFrame の依存・TTL、会話履歴、権限が変われば更新する。キャッシュヒットのために古い根拠を再使用しない。 |
| C: 現在の入力 | 今回の確定 user 発話、Ornith 結果に基づく Qwen 発話依頼 | 毎回最後の現在指示として渡す。過去履歴やツール結果を現在の指示へ昇格しない。 |

ツールの提示可否は実行時の認可結果を正本とする。固定プレフィックスに置けるのは安定した定義だけであり、利用権限や現在のツール結果を固定化しない。Provider がツール定義を入力プレフィックスに含める場合、定義の並びとシリアライズ方式も版管理する。A の末尾にキャッシュ境界を指定できるかは Provider 別に判定する。指定できない Provider では、A が長いだけでヒットするとは推定しない。

`fit_role_history` による古い履歴の除外、ContextWindow の再投影、WorldFrame の更新は安全性と容量を優先する。これで B の先頭が変わって後方のキャッシュが失われても、根拠を固定してヒット率を上げることはしない。

## 4. 実装段階とゲート

| 段階 | 作業 | 次へ進む条件 |
|---|---|---|
| P0: Provider 能力と基準値 | LARM の実際の `backchannel` / `llm` についてモデル、エンドポイント、キャッシュ応答フィールド、明示的なプレフィックス境界の有無を確認する。現行入力の先頭一致バイト数、送信量、Provider 報告のキャッシュ読み取りトークン、TTFT、完了時間、初回可視・音声時間を役割別に測る。 | 対応・非対応・不明を区別できる。欠測を 0 ヒットとして記録しない。実装前に評価条件と許容劣化幅を固定する。 |
| P1: 固定プレフィックス | 役割別 SystemContext を版付きの決定的な組み立てにし、変動データを後置する。Tool schema の順序を固定する。最終的な送信 JSON の先頭一致を記録する。 | 2 ターン目以降の A が同じ構成で完全一致する。Memory、WorldModel、現行 user 発話が常に最新で、既存の容量・根拠検証・認可テストを通る。 |
| P2: 利用量の計測 | queue 会話経路で Provider の usage を落とさず取得し、`cache_read_tokens`、入力トークン、送信バイト数、TTFT を同一リクエスト ID に結ぶ。Provider が usage を返さない場合は `missing` にする。 | A/B の同条件比較ができる。生の SystemContext、Memory、秘密情報は測定ログに保存しない。 |
| P3: 通常会話で比較 | 先読みなしで固定プレフィックスの効果を測る。冷間・連続会話、短文・調査、履歴増加・圧縮、Memory/World 更新、Provider 切替を分ける。 | 対応 Provider でキャッシュヒットと TTFT 改善を確認する。効果がなければ先読みへ進まず、入力順または Provider 能力を再調査する。 |
| P4: 条件付き先読み | Provider が固定プレフィックスの先読みを明示的に扱えるか、実測で同等の再利用を確認できた場合だけ、SAAA の起動完了後に非同期で実行する。必要な役割だけを対象にし、1 回の起動・Provider 構成につき上限を設ける。 | 後続の実依頼で Provider 報告のヒットと初回出力短縮を確認する。起動 p95、接続容量、費用、不要リクエスト数が設定した上限内。 |

P1–P3 は機能フラグで段階導入する。P4 は独立した既定 OFF のフラグにし、Provider ごとに有効化する。フラグを戻しても会話履歴や設定を削除しない。保存済み Provider 設定を初期化したり、起動失敗の回避に別 Provider へ自動交換したりしない。DB の移行が必要ならコピーまたは隔離 DB で検証する。

### P4 の先読み条件

- 一般の Chat Completions に空の user 発話を送るだけではプレフィックスが再利用される保証はない。Provider の明示的な prefix/prefill API、または実測で再利用が確認できた安全な方式を使う。
- 先読みにはユーザーの会話・Memory・WorldModel・認証情報を入れない。Provider が一定長以上を要求する場合、固定内容を水増しして閾値を越えない。短い固定指示しかない役割は先読み対象から外す。
- 起動完了をブロックしない。最初の実依頼、Provider 切替、アプリ終了が先読みより早ければ中止する。通常の Qwen/Ornith 仕事より低い優先度で、LARM の容量を奪って応答を遅らせない。
- キャッシュの識別子を使う場合は、役割・モデル・プロンプト版・ツール定義版・スコープ／利用者を識別できる非秘密のハッシュから作る。秘密値や本文をキーに埋め込まない。Provider/モデル、権限、SystemContext、ツール定義が変わったら再利用しない。

## 5. 測定と採否

同一 Provider・モデル・構成で、同じ固定シナリオを「現行」「P1–P3」「P4」に分けて比較する。順序効果を避けるため試行順を入れ替え、冷間と温間を別集計にする。起動から最初の応答、2 回目以降の応答、役割別の TTFT/完了時間、入力トークン、キャッシュ読み取り比率、Provider エラー、先読み費用を報告する。ローカルの prefix 一致は診断値とし、Provider の実ヒットは usage または Provider の診断で判定する。

P0 で許容幅を事前に確定する。暫定の採用基準は、温間 TTFT の p50 が 10% 以上改善、p95 が 5% 超悪化しないこと、起動 p95 と最初の実依頼が 5% 超悪化しないこと、正確性・権限・根拠検証の回帰が 0 件であること。P4 ではこれに加え、先読み分を含む費用と無駄なリクエスト数を提示し、ユーザーの速度目標に見合うかを判断する。改善がノイズと区別できない、または Provider がヒットを報告しない場合は P4 を採用しない。

### 決定的な試験

| ケース | 期待結果 |
|---|---|
| 同一役割・同一設定で連続入力 | A の送信バイト列が一致する。B/C は最新の根拠・発話に変わる。 |
| Qwen と Ornith、ツール提示可否・順序の変更 | 異なるプレフィックスとして扱い、利用できないツールを提示・実行しない。 |
| Memory revision、WorldFrame 依存・TTL、スコープ権限の変更 | B を再生成し、既存の応答後・保存前の検証を通る。古い根拠の結果を確定しない。 |
| `contextWindow` の小さい Provider、履歴の圧縮・除外 | 現在の user 指示と必須の Ornith/tool 根拠を維持し、送信前の容量検査を通る。収まらなければ明示的に失敗する。 |
| キャッシュ非対応、usage 欠落、先読み失敗 | 通常会話は動作する。ヒットを推定せず、先読みを無効化できる。 |
| Provider/モデル変更、起動直後の実依頼、アプリ終了 | 旧キャッシュを参照せず、先読みが通常の推論を待たせない。 |

## 6. Opus に確認してほしい点

1. P1 の「固定 SystemContext → 動的根拠 → 現在の入力」の境界で、Qwen・Ornith の信頼境界や振り分け品質を損なう箇所がないか。
2. 現行 Chat Completions 経路と実 Provider 能力を踏まえ、P4 の先読みが本当に再利用可能か。明示的な cache breakpoint がない場合、先読みを見送る判断でよいか。
3. Memory、WorldModel、履歴圧縮、Provider 切替に対する無効化条件に漏れがないか。
4. 役割別 TTFT・Provider 報告 usage・先読み費用で採否を決める設計に、必要な観測値や評価ケースが不足していないか。

レビュー後に P0 の Provider 能力調査と基準値測定から着手する。P4 の実装方式は P0–P3 の実測前に固定しない。
