# 会話からのTTS辞書訂正 実装計画

作成・文書レビュー日: 2026年10月1日
状態: 実装済み。自動検証と実モデル受入の結果は `docs/evals/tts-dictionary-conversation-20261001.md` に記録。実音声でのマイク・スピーカー受入は別途必要。

## 1. 目的と採用判断

普段の会話でユーザーが読み上げを訂正したら、対象の文字と読みを確認し、必要な登録をその場で行う。既存登録が同じなら書き換えずに伝え、違えば維持・変更の会話を続ける。保存完了と実際の発音改善は別々に確認する。

採用方式は、SAAA内蔵の小さな照会・更新ツールを既存の会話キューへ接続する方式とする。SQLiteの辞書を正本とし、既存の索引キャッシュと編集画面を共通利用する。新規ライブラリ、外部MCPサーバー、別の辞書ストアは導入しない。一般Tool発見機構の全面接続を本機能の前提にせず、この二つのツールを明示的に提示する。

正本の[SAAAの全体コンセプト](https://chatgpt.com/space/page_9fc5877949748191b556705128f6a2f5)を確認した。明示訂正の反映、確認への返答を対象へ結び付けること、現行会話へのTool再接続という既存方針を具体化する計画であり、製品概念の変更は行わない。正本との不一致は今回の対象範囲で見つかっていない。

確認対象はHEAD `979cf9780c128aba860df916a007e9cf663d3d37` と2026年10月1日の作業ツリー。既存の文書変更・削除を保持する。以下はコードの接続確認であり、稼働中アプリの状態や実機合格を認定するものではない。

## 3. 会話契約

| ユーザーの依頼と辞書状態 | 処理 | 応答例 |
| --- | --- | --- |
| 「今日を、きょうと読んで」。未登録 | 照会後に追加。明確な訂正への追加確認は不要 | 「『今日』を『きょう』で登録しました」 |
| 指定と同じ読みが登録済み | 書込み・索引再構築を行わない | 「すでに『きょう』で登録されています」 |
| 別の読みが登録済み。上書きの意図が不明 | 現在と候補を示し、確認を保持 | 「現在は『こんにち』です。『きょう』に変更しますか？」 |
| 「今後はきょうに変更して」など変更の意思が明確 | 既存値を照会し、競合検査付きで変更 | 「『こんにち』から『きょう』に変更しました」 |
| 確認への「はい」「今のまま」「別の読みで」 | 一件の保留対象へ結び付けて変更・維持・再提案 | 維持なら書込みせず「現在の読みを維持します」 |
| 「さっきの読みが違う」。対象または読みが不明 | 直前の公開回答から候補を示し、不足部分だけ確認 | 「どの言葉を、どう読むのがよいですか？」 |
| 「今回はこの読みで」 | 恒久辞書へ書き込まない | 「今回だけの指定ですね」。一時読み分けの未対応範囲を説明する |
| 同じ登録があるのに実際の発音がおかしい | 登録の存在を伝える。維持・別の読みへの変更を相談 | 「辞書には『きょう』とあります。この登録を維持しますか？」 |

「登録済み」は辞書状態の事実であり、「誤読は直った」と同義ではない。同じ登録で誤読した場合、より長い見出しの優先、索引取得前後のタイミング、Providerへ渡った文字、Provider自体の発音を調査候補として扱う。実際の音声を確認せず原因を断定しない。自動診断・音声評価Toolの新設は初期版に含めない。

現在の置換は文脈によらず文字列へ適用される。「今日」の登録は「今日び」などの長い語にも影響し得る。同音・多義語、固有名詞、対象の切り分けが不明な場合は確認する。複数の読みを一つのwrittenへ保存する仕様や、漢字の一般的な読みを大量に自動登録する仕様は追加しない。

音声認識は訂正した読みを漢字へ変換することがある。認識文字だけから元の音を確定したとは扱わない。読みが判別できない場合は、かな表記や区切った発話を求める。空のspokenは既存画面では読み飛ばしを表すが、会話の読み訂正Toolでは非空のみ許可し、曖昧な依頼を読み飛ばしに変換しない。

## 4. Tool契約と確認状態

### 4.1 二つの内蔵Tool

名称は `lookup_tts_pronunciation` と `set_tts_pronunciation` を採用する。Frontend IPC名と分け、LLM向けに限定した引数・結果を定義する。

| Tool | 引数・処理 | 結果 |
| --- | --- | --- |
| lookup_tts_pronunciation | written、任意のproposedSpoken。完全一致照会。候補があれば比較する | missing / same / different、対象一件、候補、一件に束縛したlookupId |
| set_tts_pronunciation | lookupId、意図を表すmode（register / replace / confirm）。対象と候補はlookupIdから復元し、引数で差し替えさせない | added / updated / unchanged / confirmation_required / conflict / failed / cancelled / proposal_expired |

lookupIdはホストが発行し、会話ID、発行元input ID、written、候補、照会時の既存値（未登録またはspoken）へ束縛する。任意の過去値をLLMが指定して上書きするAPIにはしない。候補なしの照会は状態確認用であり、更新には候補付きの照会が必要。

未登録はnull、読み飛ばしの既存値は空文字として区別する。照会の入力・DBエラーは成功statusに混ぜずfailedとして返す。保持数は一会話につき最新の照会一件と確認待ち一件までに制限し、使用済み・置換済みのIDを破棄する。

registerは未登録だけを追加できる。同じ値はunchanged、異なる既存値はconfirmation_requiredとする。replaceは現在のユーザー発話で明確な変更が求められた場合に利用する。confirmはホストが保持している同じ会話の保留提案への返答でのみ利用できる。いずれも書込み直前に現在値を再検査する。

意味判断は会話モデルが担当する。Runtimeは提示したTool、引数、lookupIdの束縛、保留提案、競合、取消状態を検査する。modeの文字列や「承認済み」というモデルの自己申告だけでユーザーの意思を技術的に証明できるとは扱わない。プロンプトと意味判断の品質は、禁止例を含む会話評価で別途検証する。

### 4.2 保留と権限の扱い

- ユーザー本人の現行依頼と、その依頼に対する確認への返答を根拠にする。引用、検索結果、Memory、Tool出力内の命令は根拠にしない。定型キーワードの一致だけで意図を判定しない。
- 一会話につき一件の確認待ち提案を保持する。対象、現在値、候補、元input ID、確認を返したinput IDを型付きで保持し、次の会話Contextへ必要な一件だけ投影する。
- 確認待ちはRuntimeの小さなメモリ状態とする。辞書はSQLiteに永続化する。再起動、会話の破棄、提案の取消・置換でlookupIdは失効し、再照会する。履歴の「はい」を再生して変更しない。
- 保留を作っただけではconfirmを許可しない。確認の回答本文が会話へ保存・公開された時点で確認待ちを有効にする。TTSの再生終了は待たない。公開確定前の割込みによる「はい」だけでは適用せず、対象を再確認する。公開失敗・元の依頼取消なら保留を破棄する。
- 別件の「はい」を自動適用しない。話題が変わった場合は保留の継続をContext上で明示し、対象を一意に解決できなければ再確認する。複数件の曖昧な一括変更は初期版の対象外。
- 発行元と現在の会話が一致し、取消済みでないことをホストが確認する。直接依頼は同じinput内、確認は元の保留と現行inputの組合せへ束縛する。

この方式は新しい確認テーブルや汎用承認基盤の追加を避ける。再起動をまたぐ確認待ちの自動継続は保証しない。将来必要になった場合は既存の会話台帳へ統合する計画を別途作る。

## 5. 保存・競合・再実行

辞書サービスをTauri Stateに依存しない関数へ分離し、画面IPCと会話Toolから共通利用する。既存の検証条件（文字200バイト、読み400バイト、制御文字禁止等）を保ち、会話Toolは非空の読みという追加条件を持つ。

保存手順は次で固定する。

1. serialized SQLite writer内でtransactionを開始し、依頼の取消状態と現在の対象行を検査する。
2. 現在の読みが候補と同じならunchangedを返す。書込み、updated_at更新、索引再構築を行わない。
3. 現在値が照会時と違えばconflictとして現在値を返し、変更しない。未登録から新規登録への競合も同様に扱う。
4. 変更する行と、更新後の索引用データをtransaction内で用意する。索引構築まで成功してからcommitする。
5. commit後、同じwriter処理内でキャッシュを公開する。DB保存の後に失敗し得る全件読込みを置かない。公開順序を保存順序と一致させる。
6. 結果を既存の会話監査へ記録し、画面へ更新通知する。Tool結果は一件の変更前後と結果だけを返す。

既存ConversationAuditはbest effortのため、監査記録を保存成功の判定や保留の正本にしない。監査には対象、変更前後、結果、input IDの参照を残し、ユーザー発話全文を重複保存しない。監査書込み失敗は通知・応答失敗と同様に、commit済みの辞書を未保存へ戻す理由にしない。厳密な操作台帳の永続化は初期版では保証しない。

比較対象は読みの値と登録有無とする。変更後に同じ値へ戻った場合も現在値が一致すれば適用可能とする（途中の編集履歴まで排他する契約ではない）。updated_atを秒単位の版番号として使わない。削除・renameを含む画面側の競合検査も同じ共通サービスへ接続する。

再実行時、現在値が候補と同じならunchangedとなる。確認済み提案を別の値で再実行できないようにする。commit後に通知や応答生成が失敗しても保存を自動的に戻さない。次の照会で保存状態を確認し、実行済みの変更を未実施として再適用しない。

取消の順序は、同じwriterで取消状態の確定と辞書更新の検査を直列化する。取消が先なら書かず、commitが先なら保存済みとして扱う。commit済みの登録を、生成回答の取消だけで削除しない。DBとメモリはプロセス障害を含む原子的トランザクションにはできないが、再起動時の初回索引はSQLiteから再構築する。

## 6. 会話キューと読み上げへの接続

`agent_dispatch.rs`で定義提示と実行振分けを追加する。その上で`queue_runtime.rs`のMemory専用フィルタを拡張し、既存Memory Toolと辞書Toolだけを明示した集合へまとめる。生成Tool等を一括で解放しない。

新規の行動は `{"action":"local_tool","name":"…","arguments":{…}}` とする。既存memory_toolは互換性を保つ。両方の行動の実行処理は提示集合との照合と既存execute_agent_toolへ共通化し、誤ったTool名は実行しない。今回の変更対象はこの局所的な接続であり、会話全体のプロトコル移行ではない。

`queue_context.rs`へ、明確な訂正、既存値比較、変更の確認、公開された保留提案、成功結果に基づく返答の指示を追加する。既存上限6 Toolステップを維持し、通常の照会→更新は2回で終える。失敗や競合の無限再試行を禁止し、結果不明を明示する。

現行の「調査」「記憶ツール」専用の案内・失敗文も、辞書操作を含めて意味が通る文面へ対象箇所だけ修正する。失敗時に辞書の更新をWeb検索の失敗として説明しない。

Tool行動、内部引数、確認前の「登録しました」を先行TTSへ流さない。保存結果を受けてから最終answerを生成する。現行の音声索引は最初の音声チャンク初期化時に取得するため、保存後の確認回答は新しい索引を取得できることを検証する。再生中の回答は取得済みArcを保持し、チャンク途中で索引を切り替えない。

既に再生中の誤読は登録だけで差し替わらない。訂正に伴う再生取消は既存の会話取消経路へ従う。ASRの継続キャプチャ、VoiceProcessingIO、PCMによる残響処理は変更しない。音声受入では、TTSのみでASR発話が作られないことと、再生中の本人の訂正がASRへ届くことの両方を確認する。

## 7. 編集画面との整合

共通保存サービスの結果を受け、画面IPCと会話更新の両方から`tts-dictionary-changed`通知を発行する。通知は更新済み状態を取得するきっかけとして扱い、辞書正本にはしない。購読開始後の初回ロードと再表示時の取得で通知取りこぼしを補う。購読解除、連続通知のまとめ処理、取得結果の順序逆転も処理する。

画面は通知後に一覧を再取得する。未保存ドラフト、フォーカス、検索、ページ位置を保持する。対象行の保存済み値がドラフト開始時から変化した場合、ドラフトを残して競合を表示し、自動保存を止める。ユーザーが最新値の採用または自分の編集の適用を選べるようにする。これは必要時だけの行内表示とし、常設の状態列を追加しない。

画面保存にもexpected値を渡し、変更・削除・renameのtransaction内で再検査する。画面からの無条件upsertを残すと会話側だけの競合保護が無効になるため、この追加は本機能の必須範囲とする。IPCの既存呼出しを調査して更新し、必要なら型・fixtureを再生成する。

既存の横並びテーブル（文字・読み方・削除）、小さなタイトル、上部の試し読みを維持する。試し読みはフォーカスした読みセルの文字だけをrawで読み上げ、作文・辞書の再置換を行わない。会話更新のための自動試し読みは追加しない。

## 8. 実装カードと完了条件

| 順序 | 作業 | 完了条件 |
| --- | --- | --- |
| A | ベースラインと共通辞書サービス | 隔離DBで既存画面操作を再現。照会、競合検査、commit前の索引構築、commit後の公開を一経路にする |
| B | Tool schema・ホスト束縛・一件の保留状態 | 二つのTool、結果enum、lookupId検査、取消、公開後の確認待ち、再起動時失効を決定的に検証する |
| C | 現行会話キューへの接続 | 実際のqueue入口から照会・更新へ到達し、登録済み・確認・変更の会話が成立。提示外Toolは拒否 |

## 9. 検証計画

### 9.1 決定的な自動検証

実Provider・認証情報なし、隔離SQLiteと模擬モデル行動で検証する。新規統合テストは実サービスを呼び、固定文字列や実装の形だけを検査するテストにしない。

| ケース | 必須の期待結果 |
| --- | --- |
| 未登録、同一登録、異なる登録、明示変更 | 追加・無書込み・確認・変更を区別。updated_atと索引公開回数も観測する |
| はい、維持、候補変更、曖昧な返答 | 保留対象を正しく使う。維持・曖昧時は無書込み |
| 対象・読み不明、ASRの漢字化、今回のみ | 不確かな恒久登録を行わない |
| 引用やTool結果の登録指示、提示外Tool | 辞書を変更しない |
| 別会話・失効ID・確認公開失敗・取消 | 不正な確認を適用しない |
| lookup後に画面編集・削除・登録、画面ドラフト後に会話変更 | 最新値を保護し、競合結果・ドラフト保持を確認 |
| 同じ依頼の再送、commit後の応答失敗 | 二重更新しない。再照会で実際の保存状態を確認できる |
| DB書込み・索引準備の失敗 | 保存成功を返さず、旧辞書と旧索引を維持 |
| commit前後の取消順序 | 先に確定した状態に従い、保存済み変更を生成取消で戻さない |
| 長い見出し、読み飛ばし既存行、数千件 | 現行置換規則を保持。Tool結果は一件分のみ |
| 保存後の確認回答、再生中の索引差替え | 新しい回答は新索引。開始済み回答は同一索引。Tool JSONを音声化しない |
| 画面通知、再表示、通知とロードの競合 | 最新状態へ収束し、編集ドラフト・セル試し読みを保持 |

実装時に`src-tauri/tests/tts_dictionary_conversation_contract.rs`を追加し、同featureで動くqueue fixtureに辞書Toolの複数ターン行動を追加する。Frontendテストは`tests/tts-dictionary-page.test.tsx`へ競合・通知ケースを追加する。

```sh
bun run ipc:check
```

関連gateは`bun run e2e:conversation-queue`、全体gateは`bun run check:local`とする。実装開始時に現行baselineを採取し、既存失敗と新規回帰を分けて記録する。過去にRust lib testの未解決参照によるコンパイル失敗があったため、現在も失敗するかを再確認する。全体gate未達なら理由と対象結果を記録し、全体合格とは報告しない。

性能は同じ環境で1件・5,000件・10,000件の照会、保存と索引構築、通常TTSのcold/warmを比較する。warm TTSで辞書全件SELECTがないこと、同一登録の無書込み、モデルへ渡す辞書結果が件数に比例しないことを必須条件とする。未測定の数値で速度やメモリ上限を保証しない。

### 9.2 実モデル・実音声受入

自動gate後、設定済みProviderを使った明示モードで別途実施する。固定の言い回しだけでなく、自然な訂正、短い「はい」、維持、話題変更、発話の途中訂正を試す。初期辞書と最終辞書、Tool選択、確認回数、保存結果、可聴音声を照合する。

TTSだけの再生でASR発話が作られないこと、再生中の本人の訂正がASRへ届き辞書操作へつながることを両方確認する。空のASR、聞き違い、Provider失敗時の不適切登録がないことも確認する。本番設定や保存済みProviderを上書きせず、隔離データと既存設定の読み取りで試験する。

## 10. 範囲外と導入・切り戻し

初期版の対象外は、辞書の文脈別読み分け、今回だけの発音制御の新実装、会話からの削除・rename、一括取り込み、アクセント指定、発音の自動採点、一般Tool発見の全面刷新、Memory/Worldへの辞書複製、常設状態列、新しい辞書DBスキーマである。読み訂正をプロンプトの学習待ちにしない。

実装カードA〜Dを通した後に会話Toolを有効化する。切り戻しは二つのToolの提示・受付を停止し、既存の辞書画面と保存済み登録を保持する。辞書を消したりProviderを切り替えたりして復旧しない。スキーマ変更が必要と判明した場合は、この計画の理由と移行・隔離試験を更新してから進める。

## 11. 文書レビュー結果

初案の提案を、現在の接続と障害時の動作へ照らしてレビューし、以下を計画へ反映した。レビューは文書・コード読取りで行い、実装検証は未実施。

| 指摘 | 修正・採用理由 |
| --- | --- |
| Tool登録だけでは現行会話へ提示されない | queueの明示集合・local_tool行動・実行振分けまで必須カードにした |
| 照会と更新の間に値が変わる | ホスト発行lookupIdとtransaction内の値比較を採用した |
| 「はい」の対象が会話履歴だけでは曖昧 | 一会話一件の型付き保留、公開後有効化、失効条件を定めた |
| UIの無条件保存がTool側の保護を上書きする | UIのexpected値、ドラフト保持、競合解決も必須範囲にした |
| 現状はcommit後の全件読込みに失敗すると保存と応答が食い違う | 索引準備をcommit前へ移し、公開はcommit後とした |
| 同じ登録を発音成功と混同しやすい | 登録状態と発音を分け、診断は確認できた証拠に限定した |
| 二つのストアや全面的なツール基盤変更は過大 | SQLite・既存索引・局所的なqueue接続を採用した |
| 保留の永続化や厳密な履歴版管理は初期版を重くする | 保留はメモリ、競合は現在値の比較とし、保証の限界を明記した |
| 音声訂正だけでは読みの表記が確定しない | ASR漢字化、一時指定、長い見出しとの重なりを確認・検証対象へ追加した |
| モデルのmode指定は承認の証明にはならない | 意味判断とRuntime検査の責務を分け、禁止例の会話評価を必須にした |
| 監査はbest effortで、保存の正本として利用できない | SQLiteの保存結果とホストの保留を判定元とし、監査の保証範囲を明記した |
| 確認質問の先行音声と公開確定に時間差がある | 本文の保存・公開後に保留を有効化し、それより早い返答は再確認する |

文書としての未解決な設計分岐は残さず、実装で採用する初期方式を上記に固定した。実モデルの意味判断品質、実音声での訂正反映、性能値は受入時に証拠を得る項目であり、レビュー済みという状態だけで保証しない。

## 12. 実装時の確定事項

- 照会結果は候補なしの既存登録を `found` とし、`same` / `different` と区別した。
- 更新modeに `keep` を設け、確認への維持をホスト側で消費する。維持は保存しない。
- 保留は辞書キャッシュに保持し、公開済みの質問の直後に保存されたユーザー入力だけが確認できる。別の入力、取消、再起動で無効になる。遅れて完了した旧ターンは新しい保留を消せない。
- UIは初回読込み前に変更通知を購読する。通知の順序が逆転しても最新要求を優先し、未保存セルを保持する。競合時はセル付近で最新の読みを採用するか編集を適用する。
- 現行のコンテキスト組立てのlegacy/stable両方式へ接続した。stableでは保留を下位の資料メッセージへ置き、legacyではラベル付きデータとして既存経路へ渡す。
- 実モデルで確認された `action=ツール名` 形式も、提示済みの辞書ツール二つに限って正規化する。引数検査・対象トークン・競合検査は通常のツール経路を通す。
- 監査componentは既存スキーマの `tts` を使用する。辞書スキーマやProvider設定の移行は不要。
