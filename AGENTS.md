# SAAA project instructions

At the start of work in this project, call the `initial_instructions` MCP tool once per conversation. Do not send prompts or messages to another Codex task unless the user explicitly requests it.

Work in the existing checkout by default. Do not create a Git worktree unless the user explicitly requests one. Tests that need temporary worktrees must remove them when finished.

Keep using the current branch unless the user requests a branch change. Do not require a new branch or merge workflow just to save work. Commit and push are checkpoints for saving and sharing work; a successful advance/full gate is not a prerequisite. Run relevant lightweight checks where practical and record passed, failed, and unperformed checks. Requested checkpoints may include incomplete work or known verification failures when those limitations are explicitly recorded in the commit; do not describe such checkpoints as build-ready. Do not launch a whole-project build solely because the user requested commit or push.

Do not reset stored user settings or replace a configured provider to work around a startup failure. Test migrations against a copy or an isolated database.

## Verification commands

- Verification and supported build commands share a process lock across this repository and its Git worktrees. A second invocation waits; do not evade this by changing `CARGO_TARGET_DIR`, using a separate checkout/output directory, or invoking Cargo directly. Use `bun run --silent verify`, `bun run build:desktop`, `bun run ipc:generate`, `bun run toolchain:simulate`, or `bun scripts/serial-command.ts -- <special build command>`. A `start`/`tauri dev` session holds the lock until it exits; stop that session before running separate verification. Internal child commands inherit the lock. This does not serialize rust-analyzer's own indexing.

- Match verification to the change and build scope. For whole-project static verification, use `bun run --silent verify`; it checks TypeScript and every local Rust package: formatting, lint, type/compile checks, generated contexts, and module sizes, without running builds or tests. For a partial change, select the affected packages or language instead of requiring the whole-project gate after every implementation.
- For whole-project build readiness or integration acceptance, require `bun run --silent verify:advance`: the normal gate plus TypeScript/Rust builds, unit/contract tests, quality contracts, and IPC contracts. For partial build readiness, use scoped advance for the changed packages and affected dependents, for example `bun run --silent verify advance --package crates/larm-session`; include `--scope typescript` when the frontend is affected and applicable IPC/quality contracts when crossing those boundaries. These are readiness gates, not prerequisites for checkpoint commit/push. Documentation-only changes require link, command, and factual checks.
- Define the affected scope before verification. Report known whole-project failures and checks not run, and do not claim whole-project success from a scoped pass. Before claiming readiness, fix failures in the affected scope without relaxing checks or resetting baselines. Shared dependency, build-tooling, IPC, or multi-domain changes require verification of their consumers for readiness; use whole-project advance when that impact spans the project. Until domains are extracted into independent crates, `--package src-tauri` still verifies the entire desktop crate; a test filter does not isolate compilation. Generated-context and module-size checks remain project-wide where no scoped entry point exists.
- For version upgrades and major whole-project changes, run `bun run --silent verify:full`: advance plus provider/conversation E2E and desktop smoke. Major domain changes require the relevant integration/E2E checks for that domain and its consumers. Do not run all E2E after every routine partial implementation. Live-service and real microphone/speaker acceptance still require their documented environment and separate evidence.
- All standard checks must go through `scripts/verify.ts`. Use the `bun run` aliases or `verify` subcommands; do not call `oxlint`, `oxfmt`, `tsc`, `bun test`, or Cargo fmt/clippy/check/test/build directly. The `lint`, `typecheck`, `build`, `test`, and `format` package scripts all delegate to verify. Rust-only aliases are `lint:rust`, `typecheck:rust`, `build:rust`, `test:rust`, `format:rust`, and `format:check:rust`.
- Run individual checks with `bun run --silent verify lint|typecheck|build|test|format`. Formatting checks are read-only by default; apply formatting with `bun run --silent verify format --write`.
- Run standalone builds through verify too: `bun run build`, `bun run build:frontend`, `bun run build:rust`, or `bun run build:desktop`. Desktop build arguments follow `--`, for example `bun run build:desktop -- --debug`. Do not add builds back to the normal verify gate.
- Limit a check with `--scope typescript`, `--scope rust`, or `--package crates/larm-session`. Run focused tests with `bun run --silent verify test --scope typescript -- tests/example.test.ts` or `bun run --silent verify test --package src-tauri -- --lib <filter>`. A passing filtered test must actually execute the intended cases.
- Successful verification prints exactly one `OK`. A failure prints the failing command's complete diagnostics and stops immediately. Fix the reported failure and rerun before claiming verification success; do not bypass it, relax checks, reset baselines, or claim that later checks passed. Report failures and checks that did not run. A recorded failed gate does not prevent a requested checkpoint commit/push.
- `bunfig.toml` suppresses Bun's package-script banner by default; `--silent` also makes that explicit, so success output is only `OK` even for `bun run lint` or `bun verify`. Specification, coverage, live-service and manual acceptance checks remain opt-in. Report the gate actually run; never describe normal verify as including unit tests or E2E.

## Voice conversation contract

- ASR is the continuously available microphone-to-text path. It keeps receiving microphone samples during TTS playback so a person can speak or interrupt an answer. Playback must not stop capture, suppress microphone frames by time window, finalize an utterance, or prevent ASR delivery.
- TTS is SAAA's synthesized output played through the speaker. Its audio is a far-end reference for acoustic echo cancellation (AEC), never a user utterance. A TTS playback state flag alone cannot identify what the microphone heard.
- On macOS, route TTS playback and microphone capture through the same VoiceProcessingIO instance. Keep AEC enabled and configure other-audio ducking explicitly. Use the actual rendered PCM samples to identify and remove residual TTS echo from captured PCM; preserve independent and overlapping human speech.
- When changing voice logic, verify both conditions: TTS-only playback does not create an ASR utterance, and human speech during playback still reaches ASR. Do not replace sample-based echo handling with a blanket playback gate.
