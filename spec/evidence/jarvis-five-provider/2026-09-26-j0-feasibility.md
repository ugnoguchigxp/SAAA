The LARM control plane can provision a remote runtime through `POST /v1/agent-connections`; absence of a local model process is not evidence of Provider unavailability. The first connection returned `202 pending`, moved through `probing`, then became `ready`; `POST .../claim` returned all five Providers. A fourth connection provided the claimed-provider concurrent generation result above. A fifth connection reached ready in 64.4 s, but all ten synthetic format probes returned HTTP 401 because the probe appended `/v1/chat/completions` to a claimed base URL that already ended in `/v1`. They are invalid model trials. A sixth diagnostic connection reached ready in 64.6 s: `/v1/v1/chat/completions` reproduced HTTP 401, while the correct `/v1/chat/completions` returned HTTP 200 `text/event-stream` with the claimed credential. The application uses the correct relative `chat/completions` join. A seventh connection for the corrected ten-case pilot stayed `probing` past 279 s and then returned `failed` before the 300 s startup limit; no model trials ran. An eighth connection pinned `expectedCatalogRevision`, reached ready in 267.2 s, completed the ten probes described above, and was released. A ninth connection reached ready in 258.0 s, returned the inspected multi-line record and body, then was released. A tenth connection reached ready in 165.9 s and completed the ten-case JSON-record pilot. All ten temporary connections were explicitly released with `DELETE ...` and HTTP 204. The J1 dispatcher and ASR observation path were verified deterministically. J2b protocol adoption, J3/J5 activation, and live acceptance remain gated by the remaining measurements above. The concurrency observation comes from actual completion requests, not a service health probe.

A direct control-token completion request for the catalog model after releasing the eighth claim returned HTTP 404 `model_not_found`. This confirms that a claimed Provider endpoint and its issued credential must be used for these live acceptance probes; catalog availability or a direct endpoint alone does not supply the same execution context.

In an isolated copy of the application data, listening was enabled without modifying the saved live setting. The enrolled speaker profile was `ready`, filter enabled, with five samples. One spoken synthetic greeting reached ASR with audit `scope=target-speaker` and `commitReason=max-duration`; the user confirmed both visible text and audible reply. The audit recorded commit request to final in 138 ms, final to Qwen send in 24 ms, Qwen send to HTTP headers in 4,703 ms, and final to completed Qwen response in 5,392 ms. The current frontend collects the whole SSE response before using it, so this observed path cannot establish the 2.5 s audible-start target. The exact speech-end and playback-start timestamps were not recorded, and one run cannot yield p95. The process was stopped after the reply; the subsequent ASR stop was caused by that shutdown and is not evidence of a failed automatic resume.

The isolated app was restarted for a spoken overlap check. Audit recorded a new `target-speaker` ASR session, multiple subsequent final utterances, and an automatic ASR restart after the voice run. The user confirmed that the request to read numbers 1–20 succeeded, but did not confirm a successful interruption. The additional ASR finals cannot yet be attributed to user overlap rather than playback pickup. Playback stop time and TTS-only false-input behavior are unmeasured, so J2a barge-in acceptance remains open. The live application database still has `listeningEnabled=false`; test changes remain confined to the isolated copy.

The proposed 1–20 overlap stimulus was unsuitable: Qwen generated the short response before there was a useful generation window. The user observed a green rather than red microphone button and the reading continued, but the capture and playback timelines are insufficient to call this a failed barge-in test. The later spoken request `ジュゲムの名前を発声してください。` was transcribed, and the isolated database recorded a Qwen `nod` result with the assistant reply `待ってください。`; the run then completed. There was no ornith handoff in that run. This is a concrete Qwen classification false close, not evidence that ornith failed to answer. It is retained as a regression case, and the live overlap acceptance remains open.
