MVP 2.6 実装契約 — LARM Provider Integration

0. 文書の役割

  • Status: Proposed; LARM production contract pending
  • Created: 2026-08-28
  • Baseline: d0ba3fd — MVP 2.5 implementation checkpoint
  • Shipping client: macOS版SAAA desktop
  • Production node: gnosis
  • 読者: SAAA実装担当、LARM実装担当、レビュー担当、QA担当、運用担当

この文書は、local-LLM-harness（以下LARM）をSAAAのLocal Model Providerとして統合するための 実装契約である。LARMはmodel、quantization、port、service、Runtime lifecycleを所有し、SAAAはTaskの意味、 Local / Cloud policy、capability、route、allocation lifecycle、Conversation、UIを所有する。

MVP 2.6はLLM canaryを最初のshipping sliceとする。STT / TTSはcontractと実機gateが別であるため、 LLM canaryのproduction gateを通過するまで実装対象に含めない。AI server停止中はcontract、state machine、 fake server、settings migration、security、rollbackを実装し、復旧後にだけgnosis実機canaryを行う。

MVP 2.5はimplementation completeだがmanual acceptance pendingである。MVP 2.6のcontract作業は並行できるが、 MVP 2.5の未完了evidenceを完了扱いにせず、既存計画をarchiveしない。

1. 結論

SAAAはLARMをOpenAI-compatible endpointの別名として登録しない。

SAAA Task / Conversation
  ↓ capability + route + explicit policy
LarmProvider
  ↓ allocate / poll / renew / release
LARM daemon
  ↓ fixed allocation binding
LARM Gateway
  ↓
Selected Local Runtime

既存のOpenAI-compatible Providerはdirect Providerとして維持し、LARM canaryのrollbackに使う。 LARM Providerの設定にはRuntime id、model path、quantization、port、systemd unit、llama-swap情報を保存しない。

最初に有効化するTask mappingは次の一件だけとする。

conversation.respond
  capability: llm.general
  route: llm-default
  allowFallback: false
  deploymentPolicy: existing-only

3. 今回達成すること

  1. LARM固有処理を一つのProvider adapterへ隔離する。
  2. Task intentをRuntime idではなくcapability + routeへ変換する。
  3. allocationのallocate、pending poll、renew、release、expiry、daemon restartを扱う。
  4. allocation id付きLARM GatewayでLLM streamingを実行する。
  5. 最初の出力後に別Providerまたは別Runtimeへ透過的retryしない。
  6. LARM feature flagを既定OFFにし、direct Providerへ即時rollbackできる。
  7. token、prompt、response、resolved endpointをlog、diagnostics、telemetryへ保存しない。
  8. サーバー停止中にfake LARMでcontract testを完了できる。
  9. 復旧後に一つの非critical clientだけでgnosis canaryを行う。

4. Non-goals

  • STT / TTS ProviderのLARM移行
  • Meeting Sessionの複数capability allocation

  • artifact stage、activate、rollback APIの統合

6. LARM production contract gate

次をLARMとSAAAの両projectで固定するまで、実機canaryを開始しない。

  1. OpenAI requestの安定した仮想model名とGateway側のrewrite有無
  2. /v1、health、ready、metrics、legacy endpointの認証範囲
  3. request ID、error envelope、error codeのschema
  4. allocationとoperationの完全なstate transition、保持期間、restart epoch
  5. BUSYをreadyとする意味と推論capacity errorの扱い
  6. client labelとcredentialの関係

LARM側の/v1 allocation、Gateway、authentication、metrics実装がcommitされ、API schemaと gnosis deployment revisionが特定できることをcanary開始条件とする。未commit WIPをproduction contractにしない。

7. Settings contract and v8 migration

7.1 Tagged Provider

type OpenAiCompatibleProvider = {
  kind: "openai-compatible";
  id: string;
  enabled: boolean;
  label: string;
  location: "local" | "cloud";
  endpoint: string;
  model: string;
  credentialStatus: "not-configured" | "configured";
};

type LarmProvider = {
  kind: "larm";
  id: string;
  enabled: boolean;
  label: string;
  location: "local";
  baseUrl: string;
  tokenEnv: string;
  allocationTtlSeconds: number;
  allocationStartupTimeoutSeconds: number;
  allowFallbackByDefault: false;
  deploymentPolicy: "existing-only";
};

kindを必須discriminatorとし、unknown fieldは拒否する。既存v7 Providerはv8 migration時に kind: openai-compatibleを追加するだけで、id、route順、endpoint、modelを変更しない。

7.2 LARM validation

  • baseUrlはcredential、query、fragmentを含まない。
  • HTTPはlocalhost、127.0.0.1、[::1]だけを許可する。
  • remote hostはHTTPSだけを許可する。plain HTTP LANは本計画の対象外とする。
  • tokenEnvはASCII英数字とunderscoreだけ、1〜128文字とする。
  • TTLは60〜3,600秒、既定300秒とする。
  • startup timeoutは1〜300秒、既定300秒とする。
  • allowFallbackByDefaultはfalse以外を拒否する。
  • deploymentPolicyはexisting-only以外を拒否する。

7.3 Feature flag and rollback route

環境変数SAAA_LARM_ENABLEDをprocess-level feature flagとし、既定はfalseとする。 falseの場合、LARM Providerはeffective routeから除外し、明示的に設定済みの次Providerを使う。 feature flag自体をSQLiteへ保存しない。

LARM内部のallowFallbackと、SAAAのfallbackProviderIdsは別policyである。 前者は同一allocation作成時のRuntime候補、後者はLARMとは別のProviderへ移る許可を表す。

8. Rust module boundary

既存direct Providerを大規模移動せず、LARM固有実装だけを次のmoduleへ隔離する。

src-tauri/src/providers/
  mod.rs
  larm/
    mod.rs
    contracts.rs
    session.rs
    client.rs
  • contracts.rs: DTO、bounded enum、error classification。HTTP、SQLite、Tauriへ依存しない。
  • session.rs: monotonic timeをcallerから受けるallocation lifecycle state machine。
  • client.rs: reqwest、Bearer、body limit、HTTP status mapping、Gateway streaming。
  • mod.rs: LarmProvider facadeとmodule外へ公開する最小API。

新しいasync trait dependencyは導入しない。Conversation routerはprovider kindで明示dispatchし、 direct ProviderとLARM Providerが共通のbounded attempt resultを返す構造にする。

9. LarmProvider API

impl LarmProvider {
    async fn health(&self) -> Result<LarmHealth, LarmError>;
    async fn ready(&self) -> Result<LarmReady, LarmError>;
    async fn allocate(&self, request: AllocationRequest) -> Result<AllocationStart, LarmError>;
    async fn get_allocation(&self, id: &str) -> Result<Allocation, LarmError>;
    async fn get_operation(&self, id: &str) -> Result<Operation, LarmError>;
    async fn renew(&self, id: &str, ttl_seconds: u32) -> Result<Allocation, LarmError>;
    async fn chat(&self, id: &str, request: ChatRequest) -> Result<ChatStream, LarmError>;
    async fn release(&self, id: &str) -> Result<(), LarmError>;
}

STT / TTS用のresolve_binding DTOはcontractに定義してよいが、MVP 2.6 LLM sliceから呼ばない。 実際に不要なendpointをSAAAへ露出させない。

10. Task intent to route mapping

mappingはpure functionとし、設定されたRuntime状態やhealthからrouteを変更しない。

Table: MVP 2.6 route mapping
SAAA task Capability LARM route 条件
conversation.respond llm.general llm-default 常にこのmapping。speed / long-contextを推測しない

llm-speed、llm-long-contextは、将来Task contractへ明示intent fieldを追加するまで 選択しない。Coding modeはCodex Agent routeであり、LARMのllm.codingへ暗黙移行しない。

11. Allocation lifecycle

11.1 Scope

LLM allocationはConversation全体ではなく、一回のconversation.respond turn単位で取得する。 allocation idをsettings、Conversation、長期resume tokenとして保存しない。

11.2 State machine

Idle
  ↓ allocate
Allocating
  ├─ 200 → Ready
  ├─ 202 → Pending → poll → Ready
  └─ error → Failed

Ready
  ├─ stream
  ├─ TTL 80% → Renewing → Ready
  ├─ cancel / complete → Releasing → Released
  ├─ 404 / expired → Expired
  └─ error → Failed → Releasing

Released / Expired / Failed
  └─ terminal
  • 200は即時readyとして扱う。
  • 202は失敗にせず、operation idをdeadline付きでpollする。
  • pollは250 msから開始し、500 ms、1 sへ増やし、以降1 s上限とする。
  • pollには20%以下のjitterを加え、全体deadlineを超えたら停止する。
  • renewはallocation TTLの80%到達時に一度開始する。
  • renew失敗後は、stream開始前だけ新allocationを一度取得できる。
  • stream開始後はBindingを変更しない。
  • releaseはsuccess、failure、cancel、deadline、window closeの全terminal pathで一度だけ試行する。

12. Gateway streaming contract

Gateway requestはBearer tokenとallocation idを別headerで送る。

POST /v1/chat/completions
Authorization: Bearer ${LARM_API_TOKEN}
X-LARM-Allocation-ID: alloc_example
Content-Type: application/json

request bodyのmodelはSection 6で固定された仮想名を使う。実Runtime名をSAAAへ返して bodyへ埋め込む方式は採用しない。既存のSSE parser、UTF-8 chunk処理、1 MiB event上限、64,000文字上限を維持する。

12.1 Partial output rule

最初のnon-empty assistant deltaをTauriへ送った時点でoutput_started = trueとする。 以後のtimeout、disconnect、502、capacity error、invalid SSEはpartial failureであり、次のProvider、別allocation、 別Runtimeへ自動retryしない。 

Failure before first delta
  → explicit SAAA Provider fallback may run

Failure after first delta
  → stop
  → mark provider session partial-failed
  → release allocation
  → show bounded recovery
  → user may start a new turn explicitly

このruleはLARM Providerだけでなく既存direct Providerにも適用する。現在のConversation routerがpartial output後も次Providerへ進み得る挙動を、LARM実装より先に修正する。

13. Error mapping

Table: LARM error handling in SAAA
LARM result Internal kind SAAA behavior
400 bad_request contract retryせずclient bugとして停止
401 unauthorized authentication token設定を案内し、bodyをlogしない
404 unknown_route / unsupported_capability contract route mapping不一致として停止
404 not_found allocation-lost stream開始前だけ古いidを捨て、一度だけ再allocate
409 fallback_not_allowed policy 暗黙にfallbackを許可しない
409 resource_exhausted capacity 同一LARMへ自動stormを起こさず、明示済みSAAA Provider policyへ返す
409 allocation_inactive allocation-lost stream開始前だけ再allocate
503 no_candidate_available unavailable healthを確認し、明示済みProvider fallbackだけを許可
503 allocation_not_ready not-ready operation pollを継続しdeadlineを守る
503 draining draining 新規要求を止め、次の明示turnで再試行
502 upstream_unavailable upstream Bindingを変更せず、partial output ruleを適用
413 body_too_large request-too-large 同じpayloadを再送しない

internal kindはbounded enumとし、raw error bodyをSQLiteへ保存しない。MVP 2.6では既存public provider-errorとの互換性を維持し、Provider activityのbounded reasonとrecoveryを改善する。

14. Security and network topology

14.1 Canary transport

推奨canary transportは、SAAA hostからgnosisへのSSH tunnelまたは同等のprivate tunnelである。 SAAAからはhttp://127.0.0.1:<forwarded-port>として見せ、LARM daemonはgnosisのloopback listenを維持する。

remote HTTPSをproduction transportとして採用する場合は、certificate、hostname verification、firewall、 trusted subnet、token rotationを別ADRで固定する。plain HTTP LANのために既存local endpoint validationを緩めない。

14.2 Secret handling

  • token値はenvironmentからだけ読む。
  • token値をSQLite、Settings UI、diagnostics、error、test snapshotへ保存しない。
  • Authorization headerをdebug printしない。
  • 401 response bodyをuser-visible errorまたはtelemetryへ複製しない。
  • redirectは追従しない。
  • resolved endpointはRegistry由来だけを使い、user inputからupstream URLを作らない。

15. Persistence and telemetry

SQLite v8でprovider_sessionsへ次のnullable bounded fieldを追加する。

  • provider_kind
  • route_id
  • allocation_id
  • selected_runtime_id
  • fallback_used
  • selection_reason
  • request_id
  • output_started
  • failure_kind

allocation id、Runtime id、request idは運用相関用であり、選択入力として使わない。resolved endpoint、port、model path、 prompt、response、audio、Authorization headerは保存しない。diagnostics exportではallocation idとrequest idを除外し、 route、bounded runtime label、fallback、failure kindのaggregateだけを含める。

process restart時にrunning provider sessionをinterruptedへreconcileする。allocation idを再利用せず、 LARM側のTTL回収を前提に次のturnで新規allocateする。

16. Settings UI

LARM Provider cardには次だけを表示する。

  • Display name
  • Provider kind: LARM
  • Base URL
  • Credential environment variable name
  • Allocation TTL
  • Startup timeout
  • Feature flag状態
  • health / ready connection test結果

model、Runtime、quantization、port、service、artifact操作は表示・編集しない。Effective RouteにはSAAA Provider順を表示し、 実行後のbounded activityとしてLARM route、selected Runtime、fallback、selection reasonを確認できるようにする。

Test connectionはhealthとreadyまでとし、allocation作成、model起動、推論を開始しない。

17. Fake LARM contract test

新しいproduction server dependencyは追加せず、Rust test内のbounded TCP fixtureでHTTP responseとSSEを制御する。 fake serverはrequest body、header、connection countを上限付きでcaptureし、test終了時に必ずshutdownする。

サーバー停止中に次のscenarioを自動化する。

  1. 200 allocation ready → streaming完走 → release
  2. 202 pending → operation poll → ready
  3. operation deadline超過
  4. cancel中のpoll停止とrelease
  5. TTL 80%でrenew
  6. renew失敗とstream開始前の一回だけ再allocate
  7. daemon restartを模した404 not_found
  8. fallback_not_allowedを暗黙に再要求しない
  9. resource_exhaustedでbounded failure
  10. draining中に新規allocateを反復しない
  11. Gateway cancelがbody readを停止する
  12. 最初のdelta後のdisconnectで次Providerへ移らない
  13. 最初のdelta前の失敗で、明示済みdirect rollback Providerだけを使う
  14. redirectを追従しない
  15. oversized body、SSE event、responseを拒否する
  16. token、prompt、response、resolved endpointがtelemetryとdiagnosticsへ出ない
  17. route mappingにRuntime id、port、model名が含まれない

19. gnosis canary and production gate

実機canaryでは次の順番を変えない。

  1. tunnelまたはHTTPS transportを確立し、SAAAからhealthとreadyを確認する。
  2. Bearerなし、誤token、正tokenの境界を確認する。
  3. llm-defaultで一回の非stream requestまたは短いstream requestを完走する。
  4. 通常stream、user cancel、request timeoutを確認する。
  5. 最初のbyte後のupstream failureで自動retryしないことを確認する。
  6. LARM daemon restart後に古いallocationを捨て、新規allocateできることを確認する。
  7. resource_exhaustedとno_candidate_availableでretry stormがないことを確認する。
  8. default routeからoptional workerまたは未登録Runtimeへ暗黙切替しないことを確認する。
  9. feature flag OFFでdirect Providerへ戻し、SAAA restart後もrollback状態を維持する。
  10. 30分canary、2時間soakの順でallocation leakとmemory増加を確認する。

canary中にprompt、response、Authorization header、resolved endpointがLARMまたはSAAAの通常logへ出た場合は、 即時停止してsecret rotationとlog cleanupの判断を行う。

21. Stop conditions

次のいずれかが発生した場合は次ticketまたはproduction canaryへ進まない。

  • LARM API contractが未commitまたはresponse schemaと実装が不一致
  • 安定した仮想model名が未決定
  • plain HTTP LANを許可しなければ接続できない
  • token、prompt、response、audio、endpointがlogまたはdiagnosticsへ出る
  • 最初のdelta後にProvider fallbackまたはreallocationが発生する
  • cancel、failure、window closeでallocation leakが発生する
  • existing-only以外を通常Taskから送る
  • default routeからspeed、long-context、35Bへ暗黙切替する
  • Resident Runtime停止またはsystemd / llama-swap操作がSAAAから発生する
  • v7→v8 migrationで既存Providerまたはroute順が失われる
  • 既存Codex、Voice、Meeting、Situation contractに回帰がある

22. Acceptance criteria

  1. LARM固有処理がProvider adapter外へ漏れていない。
  2. SAAA設定にRuntime id、model path、quantization、port、service名がない。
  3. conversation.respondが常にllm.general + llm-defaultへmappingされる。
  4. allowFallback: falseとexisting-onlyが通常経路で固定される。
  5. 200、202、poll、TTL、renew、release、404 restartを扱う。
  6. stream開始後にBinding、allocation、Providerを変更しない。
  7. cancel、timeout、failure、shutdownでreleaseを一度だけ試行する。
  8. feature flagが既定OFFで、direct Provider rollbackが検証済みである。
  9. token、prompt、response、resolved endpointがSQLite、log、diagnosticsへ保存されない。
  10. fake LARM suiteと既存全testが成功する。
  11. gnosis canaryでdefault、cancel、partial failure、restart、capacity、rollbackが成功する。
  12. allocation leak、Resident停止、Preferred stop漏れがsoakで検出されない。

23. LLM canary後のfollow-up

MVP 2.6 acceptance後、別計画でVoice pipelineを扱う。LLM、STT、通常TTSをMeetingまたはVoice Session単位の 一つのallocationへまとめ、STT / TTSはLARM Gateway完成まではresolve結果をsession内だけ保持する。

  • speech.stt + stt-default
  • speech.tts + tts-default
  • VOICEVOXを通常TTSとし、creditをUIまたは生成物へ反映する
  • speech.tts.expressive + tts-expressiveは明示intent時だけ
  • LARM STT / TTS Gateway完成後にdirect resolveを廃止する

artifact lifecycle、35B、multi-node、allow-listed deploymentはVoice follow-upにも含めず、operator権限を分離した 独立計画とする。
