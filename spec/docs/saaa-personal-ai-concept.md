# SAAA Personal AI Concept

## ユーザーを理解し、任された仕事を進め、適切なタイミングで関わる

作成日: 2026-09-13  
状態: コンセプト案 v1 / レビュー用

## 1. この文書の位置付け

この文書は、SAAAが長期的に目指す体験と、その実現に向けて守る設計原則を定義する。個別機能の採用や実装順序を判断するための基準として使う。

既存の[Project Concept & Direction](plan.html)にある「Local-first, Situation-aware Ambient Agent Runtime」を、長期的なユーザー理解と継続的な仕事の実行へ発展させる提案である。既存の実装仕様・運用条件を自動的に置き換えるものではない。

本文の「SAAAは〜する」は目標とする設計を表し、実装済みという意味ではない。VoiceMem、ContextStill、NightWorkers、DeepStill、LARM、KV:memは、その責務を担う候補または連携先として記述する。各製品の現在の機能を保証するものではない。

設計原則、実装仮説、未決事項を区別する。特にVoiceMemの導入方式とWorld Modelの具体構造は、この文書を基準に次の設計で決める。

## 2. Vision

> SAAAは、ユーザーを継続的に理解し、目標と委任範囲を保持し、現在の状況に応じて必要な仕事を進め、その結果から理解と計画を更新するPersonal AIである。

目指す存在は、JARVIS / FRIDAYのようなユーザー専属の常駐AIである。必要なことを覚え、状況を察し、任された仕事を進め、適切なときに話しかける。

その価値は、ユーザーが何度も背景を説明したり、細かな実行手順を指示したり、進捗を追い続けたりする負担を減らすことにある。

SAAAは「今、何をするべきか」と同時に「今は何もしないべきか」を判断する。ユーザーが集中している間は静かに仕事を進め、判断が必要なときは必要な情報をそろえて伝える。

高度な単一モデルの完成を待たず、既存のモデル、記憶、ツール、実行基盤を組み合わせて、この体験を段階的に実現する。システムの評価対象は、構成要素の数やモデルの印象的な応答ではなく、実際にユーザーの仕事と生活をどれだけ支えられたかである。

## 3. 目指す利用体験

### 3.1 話が続いている

数日後に「この前の続き」と話しかけても、関連する目標、判断理由、未解決事項を取り出せる。曖昧な場合は候補を絞って確認し、推測を過去の事実として語らない。

ユーザーの好みを応答や提案へ反映する一方、過去の好みにユーザーを固定しない。「今回は違う」「その方針は変えた」という訂正を受け入れる。

### 3.2 状況に合った関わり方をする

会議中、集中作業中、離席中では、使う機能も結果の伝え方も変わる。会議中の音声出力を避ける、完了報告を後でまとめる、といった判断ができる。

観測できていない状態を、理解できているように振る舞わない。常駐していることは、すべてを常時収集することを意味しない。

### 3.3 任せた仕事が途切れない

ユーザーが離席しても、委任された仕事は継続する。再起動や一時的な接続断があっても、実施済みの操作と未完了の仕事を区別し、再開できる。

帰ってきたユーザーには、実施内容、確認できた結果、残っている判断を簡潔に示す。完了できなかった場合も、どこまで進み、何が妨げているかが分かる。

### 3.4 先回りが役に立つ

明示された目標や約束に関係する問題を見つけ、調査や準備を進められる。新しい提案には、なぜ今必要なのか、どの目標に役立つのかを説明できる。

自発的に作業する量を増やすこと自体は目的にしない。提案しない、通知をまとめる、今は着手しない、という判断も価値を持つ。

### 3.5 理解と行動を修正できる

ユーザーは、SAAAが何を覚え、どう理解し、何を進めているかを必要な範囲で確認できる。記憶の訂正、目標の変更、仕事の停止、観測や委任の解除が、以後の判断へ反映される。

## 4. 中核となる循環

SAAAの中核は、観測から行動、その結果の確認までがつながった循環である。

```text
会話・作業・外部サービスから、許可された情報を観測する
                         ↓
              記録と現在の理解を更新する
                         ↓
          目標・約束・制約と現在の差を捉える
                         ↓
           行動候補を作る／何もしないと判断する
                         ↓
         委任範囲・状況・資源から実施可否を決める
                         ↓
             必要な能力を選び、仕事を進める
                         ↓
                結果を観測して検証する
                         ↓
        理解・計画を更新し、適切なタイミングで伝える
```

循環は、ユーザーの発話、状態変化、期限、実行結果、設定された定期確認などを契機に動く。常にLLMへ「何かすることはあるか」と問い続ける構造にはしない。

同じ循環の中に、即時応答、長時間の仕事、バックグラウンドでの振り返りを位置付ける。それぞれの応答時間と計算予算は分ける。

## 5. 情報と責務の分離

以下は論理的な責務であり、それぞれに別のプロセス、DB、サービスが必要という意味ではない。

| 責務 | 答える問い | 扱うもの |
| --- | --- | --- |
| Event / Evidence | 何が発言・観測・実行されたか | 記録、出典、時刻、結果 |
| Personal Memory | このユーザーについて何を覚えているか | 好み、経験、関係、個人史 |
| Knowledge Memory | 何を再利用できるか | 知識、手順、失敗、判断理由 |
| World Model | 現在をどう理解しているか | 関連する実体の状態、関係、不確実性 |
| Intent / Goal Model | どうなってほしいか | 目標、約束、優先順位、制約 |
| Policy / Delegation | 何を、どこまで任されているか | 操作範囲、予算、期限、通知条件 |
| Task Runtime | 何をどこまで進めているか | 計画、依存関係、実行状態、検証 |
| Capability Model | どの能力を利用できるか | 実行先、適用条件、資源、実績 |
| Context Composer | 今回の判断に何が必要か | 関連する情報の選択と構成 |
| Intelligence Runtime | 推論や音声処理をどう動かすか | モデル、計算資源、推論キャッシュ |
| Consolidation | 経験をどう次へ生かすか | 記憶の整理、矛盾の再評価、改善候補 |

World ModelとIntent / Goal Modelは並列の責務とする。前者は現在についての判断、後者は望む未来を保持する。両者を一緒に参照できても、同一の意味として保存しない。

Task Runtimeは実行状態の責任主体である。World ModelにTaskの状態を載せる場合、それは参照用の派生状態とし、別の実行状態を独立管理しない。

## 6. 記録は証拠であり、世界の真実そのものではない

Event Logは、発言、観測、操作、応答が記録されたことについての基礎資料である。「明日会議がある」という発言の記録だけで、会議の開催が確定するわけではない。

```text
Event / Evidence = 発言・観測・実行の記録
Memory           = 根拠を持つ整理と解釈
World Model      = 現時点で採用している判断
Goal             = 望ましい状態とその由来
```

事実についての判断には、可能な範囲で出典、観測時刻、対象時点、確かさ、失効条件を伴わせる。ユーザーの明示発言、外部サービスの応答、モデルの推測を区別する。

同じ情報を複数のMemoryから取り出しても、元が同じ発言なら独立した裏付けとして数えない。生成した要約や以前のWorld Modelを繰り返し読むことで、確信だけが強まることを防ぐ。

記録対象と保持期間は用途とユーザー設定に従う。完全な永久ログを前提にしない。再構築できる範囲は、保持が許可され、現に残っている証拠の範囲に限られる。

## 7. Personal MemoryとKnowledge Memory

Personal Memoryは、ユーザーとの関係が続くための記憶である。好みだけでなく、その理由、適用される状況、過去の経験、変更の履歴を扱う。

Knowledge Memoryは、別の仕事でも利用できる知識と経験を扱う。技術知識、検証結果、手順、失敗原因、プロジェクトの判断理由などが含まれる。

例えば、「この構成では60 tok/sだった。自分には30 tok/s以下だと遅い」という会話には、環境に依存する測定結果と、ユーザーの使用感の両方がある。それぞれの意味を保ち、共通の出典へ戻れるようにする。

VoiceMemはPersonal Memoryの候補、ContextStillはKnowledge Memoryの連携先として検討する。責務の違いを製品の機能だけから決めず、必要な入出力と実際の重複を確認する。

人物への信頼、感情、性格などの解釈を、単一の数値や固定属性で断定しない。利用する場合は、誰の評価か、どの状況での評価か、不確実性は何かを保持する。

## 8. World Model

World Modelは、ユーザーに関係する現在の状況を、判断に使える大きさへまとめたものとする。

世界全体をモデル化する必要はない。現在の仕事、関係する人やサービス、利用可能な端末、進行中の会議など、ユーザーの目標や直近の行動に関わる対象を優先する。

詳細な履歴をすべて抱えず、必要なときは記憶や元の証拠へ戻る。分からないこと、情報が古いこと、複数の説明が競合していることも表現できるようにする。

### 時間の異なる状態を扱う

数か月続く好みと、数分で変わる会議状態は、同じ更新周期にしない。

長期的な理解はバックグラウンドで整理できる。一方、目標の取り消し、会議の開始、Taskの完了など、行動を変える情報は速やかに反映する。外部へ影響する操作の前には、その操作に必要な現在状態を確認する。

Snapshot＋Realtime Overlayは有力な実装仮説である。ただし、公開処理中の新着イベント、訂正、削除、失効を失わずに統合できることを採用条件とする。Snapshotを作り直すだけでは、現在性は保証されない。

### 関連度は用途に応じて使う

Personal Relevanceは、検索やContext配分に利用できる。ただし、関連度、期限の切迫度、重要度、割り込みの必要性は別に評価する。

普段あまり話題にしない約束でも、期限が迫れば重要になる。頻繁に取り上げた対象だけをますます優先する循環を避ける。

## 9. Goalと委任

Goalは達成したい状態であり、Taskはそこへ向かう具体的な仕事である。一つのGoalを複数のTaskで進めたり、失敗した手段を別のTaskへ置き換えたりできる。

Goalには、由来、現在の状態、達成条件、制約、優先順位を持たせる。長期的な願望のように達成条件がまだ曖昧なものは、具体的な実行Goalと区別する。

```text
明示された目標: ユーザーが直接示したもの
導出した目標:   明示目標のために必要だと判断したもの
推測した意向:   まだ採用されていない仮説
```

モデルが導出した手段を、ユーザーが望んだ目的に昇格させない。「Personal Memoryが必要」から「VoiceMemを採用すると決まった」へ飛躍しない。

すべての自主Taskは、採用済みのユーザー目標、約束、または設定された保守目的へたどれるものとする。そのうえで、実行可能な範囲を委任として別に定義する。

委任は、対象、許可操作、予算、期限、実行条件、通知条件を表す。明示的に任された範囲内では自律的に進め、同じ許可を繰り返し求めない。委任を超える必要が生じた場合は、判断に必要な結果をそろえて確認する。

L0「記憶のみ」からL4「外部へ影響する操作」までの段階表現は、説明用として使える。ただし実行可否はレベルの大小だけでは決めない。操作対象や送信先が異なれば、必要な委任も異なる。

目標の中止や委任の撤回は、以後の実行判断へ反映する。実行途中の仕事についても、停止できる地点と既に生じた影響を追跡する。

## 10. 継続的な仕事の実行

Task Runtimeは、行動候補を永続的な仕事へ変換し、実行から検証までを管理する。

候補の採否には、目標への寄与、状態の確かさ、費用、期限、リスク、利用可能な能力を使う。モデルが出した期待値や信頼度を、そのまま客観的な測定値として扱わない。

同じ問題からTaskを繰り返し作らない。実行中、対応済み、再試行待ち、ユーザー判断待ちを区別し、失敗時には回数・時間・費用の上限を設ける。

完了条件は、実行前にできる限り定める。「ツールが正常終了した」と「目標を満たした」を区別し、変更後の状態を確認する。確認できなければ未検証として報告する。

再起動後の再開では、操作が実施済みか不明な場合も想定する。外部への操作を安易に再実行せず、状態照会や操作識別子などで確認する。詳細方式は実行先に合わせて設計する。

SAAAは目標間の調整とMissionの管理を担い、NightWorkersなどの実行先は、そのMissionを達成するための専門的な分解と実行を担う。引き渡しには目的、範囲、制約、完了条件、予算を含める。

## 11. CapabilityとContext

Capabilityは、利用できるツール名の一覧にとどまらず、どの条件で何を実現できるかを表す。対応する仕事、利用可能性、必要な権限、費用、資源、過去の実績を判断材料にする。

初期には、調査、修正、テスト、報告などの小さな既知の手順を組み合わせる。動的な実行グラフや再利用Skillへの昇格は、繰り返し成功し、適用条件と検証方法が説明できる範囲で導入する。

能力を組み合わせても、構成する操作の委任範囲は広がらない。失敗した場合は、どの段階まで実施されたかを追跡できるようにする。

Context Composerは、Personal Memory、Knowledge Memory、World Model、Goal、Task、最近の会話から、今回必要な情報を選ぶ。大量に渡すことより、関連性、現在性、根拠、矛盾の扱いを重視する。

外部から取得した文書や過去の発言は参照情報として扱い、現在の実行権限を決める指示と区別する。Contextへ含まれたことを理由に、操作を許可しない。

## 12. 計算資源と推論キャッシュ

SAAAは必要な能力、応答期限、予算を決める。LARMなどのIntelligence Runtimeは、その要求をどのモデルと計算資源で満たすかを担う。

即時の会話や音声処理には低遅延を優先し、複雑な調査や振り返りには長い時間を割り当てる。バックグラウンド処理は、ユーザーが戻ったときに譲れるようにする。

Local-firstを原則とし、外部処理を使う場合も、送信可能な情報と利用条件をユーザーの設定・委任に従わせる。処理性能を理由に、暗黙に送信範囲を広げない。

会話フロントは2B級モデル、詳細な推論・タスク遂行は27Bモデルが担当する設計とする。中間メモリから2Bへは会話に必要な現在状態・進捗・確認事項を投影し、27Bへは原文に基づく依頼と変更を渡す。実行状態と権限はSAAA Runtimeが管理する。

2026-09-13のユーザー提供情報では、LARMのQwen 3.8 27Bに20M ContextWindow / KVキャッシュが実装済みである。このモデルでは詳細な作業文脈を継続して使う中核として優先活用する。20Mを上限とし、他モデルへのKV共有は前提にしない。中間メモリは現在状態の明示、モデル間の引き継ぎ、容量到達・cache喪失からの回復を補う。具体的な接続・保持保証と実装順序は[Personal Stateロードマップ](personal-state-architecture-roadmap.md)を優先する。

キャッシュの再利用条件と無効化条件は、採用するモデルとRuntimeの仕様に合わせて検証する。訂正、削除、権限変更、Context変更が正しく反映され、元の情報から再生成できることを求める。導入効果は遅延、メモリ、再利用率、出力品質で測る。

## 13. Dream / Sleep Cycle

Dream Cycleは、ユーザーが不在の時間や余剰資源を使い、経験を整理して次の判断を改善する処理である。

会話の整理、重複の解消、実体の照合、矛盾の再評価、Goalの進捗確認、再利用可能な手順の抽出、次の行動候補の作成を行う。

生成した解釈は候補として検証する。明示目標や訂正をモデルの判断だけで消さず、矛盾が解決できない場合は保留する。派生状態の公開には変更内容と根拠を残し、問題があれば以前の状態へ戻せるようにする。ただし、削除・権限撤回を巻き戻してはならない。

再構築可能とは、保持されている証拠から状態を作り直せることである。LLMによる解釈が毎回完全に一致するという保証ではない。比較できるよう、入力範囲と生成方法の版を記録する。

「寝ている間に賢くなる」は検証する仮説である。訂正の反映、想起の正確さ、判断の改善、不要な提案の減少などで確かめる。記憶の件数が増えたことだけを改善とは呼ばない。

日次・週次などの周期や処理の分割は、データ量、変更頻度、資源、効果を測って決める。

## 14. 訂正・削除・忘却

Personal AIでは、覚える能力と同じく、適切に忘れる能力を設計する。

訂正は、その発言を追加保存するだけで終わらせず、現在の理解と以後の検索結果へ反映する。履歴として残す情報と、現在有効な情報を区別する。

削除は、原文、派生記憶、索引、World Model、Context、キャッシュなど、関係する保存先への影響を追跡する。再構築によって削除した情報が復活しないようにする。

外部サービスやバックアップを含む削除範囲と反映時点は、利用者へ説明できるものにする。期限切れの情報を保持し続けるかどうかも、保存目的に応じて決める。

## 15. 成功をどう判断するか

評価は、記憶・World Model・自律実行を導入する前後で、同じ利用シナリオを比較して行う。

| 評価対象 | 確かめたいこと |
| --- | --- |
| 継続性 | 背景の再説明が減り、過去の判断を正しく引き継げるか |
| 記憶 | 必要な経験を取り出し、取り違えや過剰な一般化を抑えられるか |
| 現在性 | 訂正・中止・状態変化を必要な時間内に反映できるか |
| 実行 | 目標を満たしたことを確認し、重複操作や無制限の再試行を防げるか |
| 自発性 | 採用される提案が増え、不要な仕事や通知が増えていないか |
| 制御 | 委任範囲を守り、停止や撤回が実際に機能するか |
| 資源 | 会話の応答性を守り、時間・計算・費用が予算内に収まるか |
| 改善 | 振り返り後に正確さや仕事の成果が改善したか |

数値目標は各PoCの開始時に決める。品質を確認する前に構成を増やさず、効果が確認できない仕組みは簡素化または見送る。

## 16. 段階的な検証方針

### 最初に小さな循環を成立させる

一つの明示Goal、一つの観測対象、一つの実行先で、観測から検証までを通す。

例として「指定されたプロジェクトのテスト失敗を検知し、許可された範囲で原因を調査し、結果を報告する」を使える。最初から自主的なコード修正まで広げる必要はない。

この段階で、重複候補の抑止、実行状態の保存、停止、再開、完了判定を確認する。高度な記憶や大きなWorld Modelがなくても、循環の成立は検証できる。

### 記憶と現在理解の効果を個別に確かめる

VoiceMemのPoCでは、過去の会話から必要な個人情報を取り出し、根拠と訂正を保持できるかを確認する。

World ModelのPoCでは、限られた対象について現在状態を表現し、記憶を直接検索するだけの場合と比べて判断が改善するかを確認する。

両者は連携を想定するが、一方の完成を他方の検証条件にしない。失敗の原因を分けて評価できる規模に保つ。

### その後に振り返りと自発性を広げる

Dream Cycleを加えて、記憶と判断が改善するかを比較する。行動候補の生成は、まず候補だけを記録・評価し、十分な精度が確認できた範囲から実行へ進める。

Capabilityの動的構成、広範な視覚入力、大量Contextのキャッシュは、具体的な不足や性能上の問題が確認された段階で導入する。

## 17. 次に設計すること

### VoiceMem導入

次の検討では、VoiceMemが担うPersonal Memoryの最小契約を決める。

- どの会話・音声情報を、どの条件で渡すか。
- どの形式で観測を渡し、想起結果と根拠を受け取るか。
- ユーザー、話者、第三者、プロジェクトをどう識別するか。
- 訂正・削除・保持期間をどう反映するか。
- ContextStillとの重複、連携の必要性、運用負荷をどう測るか。
- 導入しない場合と比較して、どの利用体験が改善すれば採用するか。

この検討を経て、Adapterの境界、保存先、実行タイミング、PoC対象を決める。音声入力を使うことと、話者認証や個人記憶が成立することは、それぞれ別に検証する。

### World Model

次の検討では、最初の利用シナリオに必要な現在状態を絞る。

- どの判断のために、どの状態が必要か。
- 状態の正本はどこにあり、World Modelは何を派生保持するか。
- 各状態に許容できる古さはどの程度か。
- 不明、矛盾、訂正、失効をどう表現するか。
- Snapshot＋Overlayと、直接参照・単純な状態投影をどう比較するか。
- 再構築・公開・新着更新・削除をどう整合させるか。
- 通常の検索とTask状態管理だけでは不足する価値があるか。

この結果から、SQLiteのテーブル構造や更新方式を決める。大きなGraphや専用DBの導入を出発点にはしない。

## 18. 設計判断の優先順位

設計に迷ったときは、次の順に判断する。

1. ユーザーの目標、訂正、委任範囲と整合しているか。
2. 実際の利用体験と成果を改善するか。
3. 根拠を追え、状態の変更や失敗から回復できるか。
4. 小さな構成で検証できるか。
5. 応答性と計算予算を守れるか。
6. 将来、モデルや連携先を交換できるか。

SAAAが目指すのは、ユーザーが背景と目的を共有し、仕事の続きを安心して任せられる存在である。長期記憶、World Model、自律実行、Dream Cycleは、その関係を成立させるために導入する。
