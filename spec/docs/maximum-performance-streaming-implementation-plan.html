Maximum-Performance Streaming Experience 実装計画

0. 文書の役割

  • Status: Implemented — controlled automated Gate検証済み、operator Gateはrelease evidence待ち
  • Created: 2026-08-31
  • SAAA baseline: 0ec8019 + working tree
  • Shipping client: macOS版SAAA desktop
  • 対象: LLM transport、Conversation Runtime、Chat UI、ASR、TTS、Meeting audio、SQLite
  • Evidence: Maximum-Performance Streaming Release Evidence

本文書は、Provider自身の推論速度ではなく、SAAAの実装上の待ち、再計算、直列化、 queueingを減らし、体感性能を最大化するための統合実装契約である。LLMのstreaming data planeはSSEを廃止してWebSocketへ完全移行し、回答生成中の画面はplain textで表示する。 Markdownは回答が正常に確定した後に一度だけrenderする。

この変更はASRとTTSの作り直しではない。既に実装済みのASR精度向上策と、LLM回答完了を 待たずにTTSを開始するstreaming speechを継承し、その上でhot pathを短くする。 本文書と既存の音声計画が競合する場合、ASR/TTSの正確性、安全性、順序保証については 既存計画を優先し、transportとperformanceの接続点だけを本文書で追加する。

0.1 Normative precedence

  1. ASRの音声形式、話者filter、partial/final、fallback、deliveryは Always-on Streaming ASR Implementation Planを正本とする。
  2. TTSの文境界、speech session、順序、取消、half-duplexは Streaming TTS Sentence-Boundary Pipeline Implementation Planを正本とする。
  3. 本人音声の登録と検証は Target Speaker Enrollment Implementation Planを正本とする。
  4. SQLiteのsingle-writer ownershipは SQLite Single Writer Implementation Planを維持する。本文書はqueryとlock保持時間の性能要件だけを追加する。
  5. ChatGPT subscriptionで利用するCodex second opinionのsession、認証、transportは Codex SDK Realtime Second Opinion実装計画を正本とする。local child processとのstdio JSONLはProvider network transportではないため、 本文書のsaaa.llm-stream.v1 WebSocket-only要件の対象外とする。

2.3 その他の実装bottleneck

  • React stateをdeltaごとに更新し、stream中の本文全体をMarkdown parseしている。
  • stream更新ごとのlayout effectとauto-scrollがmain threadへ重なる。
  • meeting audioの5秒block resampleがUI threadで約22 msを占有する測定例がある。
  • SSE parserはbuffer先頭からの反復走査とdrainにより、大きな受信塊で二次的に悪化する。
  • timestampへのCAST、deep OFFSET、短命reader接続がSQLite readを増幅する。

3. 変更してはならないInvariant

  1. INV-01: ASR、LLM、TTSは別socket、別queue、別取消tokenを持つ。
  2. INV-02: ASRの100 ms audio pathはLLM/UI/DBのbackpressureで待たない。
  3. INV-03: ASR partialは表示だけに使い、conversation送信と永続化はfinalだけにする。
  4. INV-04: target speaker reject前のraw PCMは外部送信、保存、診断出力をしない。
  5. INV-05: TTSは最初の自然境界で開始し、LLM completionを待たない。
  6. INV-06: TTSはcanonical deltaを欠落、重複、逆順なしで一度だけ消費する。
  7. INV-07: Text回答の成功とSpeechの成功を分離し、TTS失敗でTextを失敗へ戻さない。
  8. INV-08: Markdown完了は視覚表示の状態であり、TTS入力の開始条件ではない。
  9. INV-09: tool loopがあるturnは、最終assistant messageだけを完成Markdownとして確定する。
  10. INV-10: cancel / fail後の遅延eventはrun IDとgenerationで破棄する。
  11. INV-11: secret、音声内容、回答本文をperformance logへ出さない。
  12. INV-12: SQLite writerは単一ownerのままとし、UI threadで同期I/Oを行わない。

4.1 saaa.llm-stream.v1 contract

Provider側のnormative wire contractは SAAA Provider LLM WebSocket Protocol v1を正本とする。

endpointごとにProviderが広告するmaxConcurrentRuns本までpersistent wss接続をprewarmし、各接続へactive runを1件だけpinする。idle接続がなければ 新しいturnを待機queueへ入れず、開始前にcapacityで即時失敗させる。active run同士を同一TCP streamへ multiplexしてはならない。LARMのallocation / healthなどcontrol planeのRESTは維持できるが、回答data planeにSSEを残してはならない。Codex app-serverのlocal subprocess JSONLはnetwork SSEではなく、 この移行対象外とする。

Table: Required WebSocket messages
方向 Message 必須field / rule
Client → Server run.start runId、model、input、tools、client capability。idle接続で一度だけ送る
Client → Server run.ack 累積ackSeqとincremental content hash。UI状態を待たない
Client → Server run.cancel idempotent。cancelled terminalまたは既知terminalを返す
Client → Server run.resume runIdと最後に連続受理したseq
Server → Client response.delta binary、run内単調増加seq、append-only UTF-8 text、16 KiB以下
Server → Client tool.call tool ID、名前、bounded arguments。本文sequenceと同じ順序domain
Server → Client response.completed 最終seq、累積UTF-8 byte数、incremental content hash、usage、finish reason
Server → Client response.failed / response.cancelled terminalはrunごとに一度だけ。公開可能なbounded errorだけを含む
  • duplicate seqは無視し、gapは後続へ渡さずresumeする。
  • reconnect後も既にTTSへ渡したdeltaを再発声しない。
  • 出力開始後に別Providerへfallbackしない。重複回答と重複発声を避ける。
  • terminalのcontentBytesとhashを受理済みdelta accumulatorへ照合し、 不一致ならprotocol failureにする。terminalへ全文を重複格納しない。
  • connection queueはmessage 64件または512 KiBの早い方を上限とし、無制限bufferを禁止する。
  • WebSocket serverが未提供のendpointをSSE gatewayで包まない。

4.2 Ordered Turn Event Hub

Provider adapterが生成したeventを直接複数箇所へ送らず、Rust側の TurnEventHubでsequence検証、dedupe、terminal判定を一度行う。検証済みdeltaは、 同じtask内で先にTTS accumulatorへappendし、その後UI coalescerへ渡す。TTS branchがfullでも LLM socket readerを無制限に待たせず、bounded session failureとしてspeechだけを停止する。

ACK可能になるのは、canonical accumulatorへのappendとTTS branchへの配送結果が確定した時点とする。 UI queueへのenqueue、Channel送信、React commit、paintをACK条件へ含めない。UI branchは runごとに未ACK UiDeltaBatch 1件とpending suffix 1件だけを持つ。WebViewはrAFでbatchを Text nodeへappendした後にui.batch.appliedを返し、それまで次batchをChannelへ送らず pending suffixへmergeする。このUI ACKはProvider ACKと完全に別物である。UIが停止しても LLM生成とTTSを停止させてはならず、pending suffixはresponse上限262 KiBを超えない。

現在のTTS event sinkにあるTauri ChannelへのJSON serialize / parse往復は除去し、Rust内の typed eventを直接渡す。WebViewへは表示に必要なeventだけをnative Channelで送る。

4.3 Markdown lifecycle

  1. streaming: Rustで未表示suffixを集約し、visible windowでは最大1回 / 16.7 ms、 backgroundでは最大1回 / 100 msだけplain textへ追記する。 white-space: pre-wrapで表示する。
  2. finalizing: canonical accumulatorのbyte数 / hash、tool loop終了、DB commitの整合を確認する。
  3. completed: Markdownを一度だけparseし、sanitized resultを表示する。
  4. cancelled / failed / length: partial plain textにincomplete表示を付け、Markdownへ移行しない。

streaming本文は4 KiB単位のimmutable chunkと可変tailで保持し、React stateやDOMへ累積全文を 毎回渡さない。既存chunkを再renderせず、tailだけをText nodeへ追記する。完了時にだけcanonical textへ置換する。Markdownは16 KiB未満をmain threadのidle task、16 KiB以上を常駐Workerでparse / sanitizeし、 DOM treeではなくcompactなsanitized HTML stringを返す。cacheはmessage ID / hashをkeyに100件または8 MiBのLRUとする。 完了済みmessage componentはmemoizeし、過去messageを新しいdeltaで再renderしない。auto-scrollは1 animation frameに1回までとし、ユーザーが上へscrollしたら追従を停止する。

4.4 ASR精度施策の継続と追加検証

ASR pipelineはtransport共通化の対象にしない。変更はmetrics、実Harness検証、accuracy corpusの 追加に限定し、既存algorithmの削除や単純化を行わない。Providerごとの差はserver-side adapterで saaa.asr-stream.v1へ正規化する。

  • quiet speech、click、無音、長発話、50 ms境界、Native切断を固定corpusにする。
  • 日本語の固有名詞、数字、句読点、英語混在をgold transcript付きで追加する。
  • target speakerは本人、他人、同時発話、遠距離、環境音を分けてFalse Accept / Rejectを測る。
  • stable textの巻き戻り、final重複、先頭欠落を件数0のhard gateにする。
  • 実mic / 実Harnessについてfirst partial、final、CER、provider failoverを記録する。

現行speaker gateは時間方向の本人判定であり、同時発話のsource separationではない。 同時発話accuracyを上げる場合は、既存gateを削除せず、別ticketとmodel evidenceを持つ source separation前処理として提案し直す。

4.5 TTS hot path

  1. typed Rust eventをaccumulatorへ直接appendし、deltaごとのJSON round-tripを削除する。
  2. protected-range scannerへcursorを持たせ、新規suffixだけを走査する。
  3. idle flushをsessionごとの単一resettable timerにし、世代ごとのsleep taskを作らない。
  4. rendererとplayerを分離し、Cloud / Harnessでは最大3 chunkを並列合成してsequence順に再生する。
  5. synthesis concurrencyは初期値2とし、直近8 chunkの ceil(p95 synthesis time / median audio duration)を1〜3へclampして更新する。ready audioは30秒または16 MiBの早い方、player内は再生中と次の2 chunkに制限する。
  6. System routeもrender-only APIでaudio artifactを作ってplayerへ渡す。artifactを生成できないrouteは maximum-performance profileのauto-speakではunsupportedとし、serial synthesize-and-playへfallbackしない。
  7. SpeechQueued、SynthesisStarted、PlaybackStartedを分離し、 SpeechStartedとASR half-duplex開始は最初のaudio sampleがplayerへ渡った時点とする。
  8. cancel時はtimer、HTTP、renderer、player、temporary fileを同じsession tokenで停止する。

UIのMarkdown確定、DB commit、MessageCompletedはTTS開始をblockしない。 finishReason=stopのresponse.completedは未発声tailの一度だけのflushと byte length / hash確認にだけ使う。finishReason=lengthでは未完成tailをflushしない。

4.6 Meeting audio / SQLite / release build

  • Meetingの48 kHz → 16 kHz resampleとPCM encodingはstateful専用Workerへ移し、100 ms入力を 位相を保ったまま処理して1秒segmentを出力する。5秒分をUI threadに蓄積してから処理しない。 Chat ASRの16 kHz AudioWorklet pathは変更しない。
  • conversation_messagesは (conversation_id, CAST(created_at AS INTEGER) DESC, id DESC)のexpression indexを一件だけ追加し、同じ式とmessage IDのopaque cursorでdeep OFFSETをkeyset paginationへ変える。本文を複製するcovering indexは作らない。Context composeはwriter lock外で行う。
  • read-only operationはsingle-writer契約のReader経路へ寄せ、起動時に開く2本のpersistent read-only connectionとprepare_cachedを使う。UI threadから同期呼出ししない。 read transactionはquery結果のmaterialize直後に閉じる。
  • Rust release profileはopt-level = 3、lto = "fat"、 codegen-units = 1、strip = "symbols"へ固定する。 target-cpu=nativeは配布互換性を壊すため指定しない。

5. Scope / Non-goals

5.1 Scope

  • LLM streaming WebSocket protocol、connection manager、resume、cancel、tool event。
  • Turn Event Hub、TTS direct branch、UI coalescing、final-only Markdown。
  • TTS incremental scanner、timer、render-ahead、playback cancellation。
  • ASR non-regression corpus、実Harness / 実mic accuracy evidence。
  • Meeting audio worker、Chat read query、release buildの測定可能なhot path。

5.2 Non-goals

  • Provider modelの推論速度、精度、料金そのものを比較・改善すること。
  • ASRのpacket format、VAD、reconciler、speaker gate、final queueの再設計。
  • TTSを回答完了後の全文読み上げへ戻すこと。
  • full-duplex barge-inを性能変更と同時に導入すること。
  • Markdownの見た目、prompt内容、memory selection policyを変更すること。
  • WebSocket未対応Providerのために恒久的なSSE互換層を保持すること。

6. 実装Packageと順序

各packageは前packageのexit criteriaを満たしてからmergeする。性能改善を理由に音声の correctness gateをskipしない。

PERF-00 Baselineと観測点の固定

  • 変更: runごとのsocket_receive → first_delta → first_plain_paint → response_completed → markdown_paint、TTSのfirst_boundary → audio_start、ASRの speech_start → partial → finalを本文なしで計測する。
  • 変更: render count、main-thread long task、queue depth、reconnect、sequence gapを記録する。
  • Exit: controlled Harnessを同一machine、同一fixtureで200 run、microbenchmarkを1,000反復、 実Providerを30 run測定し、p50 / p95 / p99、CPU time、allocation、peak / settled RSSを保存する。

PERF-01 Ordered Turn Event Hub

  • 変更: Provider eventの型、run ID、seq、terminal stateをRustで一本化する。
  • 変更: TTSへtyped direct append、UIへcoalesced native Channelを分岐する。
  • Test: duplicate、gap、out-of-order、stale run、cancel race、TTS queue full。
  • Exit: TTSに渡るdeltaのloss / duplicate / reorderがfixture 10,000件で0。

PERF-02 LLM WebSocket server / protocol

  • 変更: LARM / controlled Harnessへsaaa.llm-stream.v1を実装する。
  • 変更: advertised concurrency分のpersistent connection、1 active run / connection、binary delta、 incremental hash、ack / resume、ping / pong、bounded replayを実装する。
  • Test: fragmented frame、10,000 delta burst、別connectionの1 MiB upload stall、disconnect / resume、 cancel、最大4 parallel tool call。
  • Exit: canonical accumulator hash / byte数、append-only、terminal exactly-onceがserver contract testで成立する。

PERF-03 Desktop WebSocket cutover

  • 変更: endpoint capability probeを追加し、必要本数のWebSocketをprewarmできなければturn開始前に明示的にfailする。
  • 変更: LLM adapterをconnection poolへ接続し、SSE parserとSSE routeを削除する。
  • 変更: LARM control RESTとlocal Codex JSONLは維持する。
  • Exit: production targetでSSE response bodyを読むコードとruntime fallbackが0件。

PERF-04 Plain streaming / final Markdown

  • 変更: capacity 1 latest-wins coalescer、append-only chunk / tail bubble、completion state machineを実装する。
  • 変更: final canonical textだけをsize threshold付きでMarkdown parseし、bounded LRUへcacheする。
  • 変更: completed message memoization、list virtualization、rAF auto-scrollを導入する。
  • Test: code fence途中、table途中、cancel、fail、tool loop、履歴100件、64,000文字 / 1文字delta回答。
  • Exit: stream中のMarkdown parser呼出し0、completed messageはcontent変更時だけ1回。

PERF-05 TTS pipeline hardening

  • 変更: JSON往復削除、incremental scanner、単一idle timer、最大3並列synthesizer、ordered playerを実装する。
  • 維持: adaptive threshold、protected boundary、final tail一回、ordered playback、half-duplex。
  • Test: 1文字delta、巨大delta、URL / Markdown / 数値、idle reset、cancel、provider failure。
  • Exit: 最初の実audio sampleがMessageCompletedより前に始まり、SpeechStartedとの誤差20 ms以下、 speech completeness違反が0。

PERF-06 ASR accuracy regression gate

  • 変更: 固定PCM corpus、gold transcript、Native Harness loopback、speaker scenariosを整備する。
  • 維持: exact packet、VAD boundary、whole-prefix、stable / unstable、speaker zeroize、final queue。
  • Test: Native / Batch、Native途中切断、quiet speech、30秒、50 ms boundary、他人音声。
  • Exit: 自動test全件成功、先頭欠落 / final重複 / raw leakage 0、accuracyがbaseline非劣化。

PERF-07 Meeting audio worker

  • 変更: 100 ms入力のstateful resample、PCM encode、1秒segment transferをWorkerへ移す。
  • Test: phase continuity、sample count、clipping、alias suppression、stop race、transfer ownership。
  • Exit: resample中のUI long taskが0、capture終了からnormalized segment配送までp95 20 ms以下。

PERF-08 SQLite read path

  • 変更: persistent read-only connection 2本、statement cache、本文を含まない三列expression index、 opaque keyset pagination、settings snapshot cacheを実装する。
  • 変更: SQL外のcontext composeをwriter lock外へ出す。
  • Test: 100,000行、同時read / write、migration、旧timestamp、deep page。
  • Exit: query planがindexを使用し、p95がSection 7を満たす。

PERF-09 Release evidence / cutover

  • 変更: release profile、canary flag、protocol version telemetry、rollback runbookを固定する。
  • 実施: 30分stream、100 turn、ASR/TTS同時利用、network flap、sleep / wake、app quit。
  • Exit: Section 7の全Gateを満たし、SSE serverを停止してもproduction flowが成功する。

9. Migration / Rollback

  1. Serverへversioned WebSocketを先行配備し、production trafficなしでcontract testを通す。
  2. Desktop canaryをWebSocketだけで動作させ、SSE serverを遮断した試験を行う。
  3. UI final-MarkdownとTTS direct branchをcanaryへ同時投入し、三つの時刻を個別計測する。
  4. ASRは変更せず全regression suiteと実mic testを再実行する。
  5. 全Gate通過後にSSE client、parser、fixture、server routeを削除する。

rollbackはDesktopとServerを直前の互換releaseへ同時に戻す。新Desktop内にSSE fallbackを 残さない。WebSocket障害時にASR sessionと既に確定したTextを巻き戻さず、該当LLM runだけを 明示的にfailedにする。TTSはそのrunの未再生audioをcancelし、他sessionへ影響させない。

11. Definition of Done

  1. PERF-00からPERF-09を依存順に完了している。
  2. 対象LLM data planeにSSE code、fallback、gatewayが残っていない。
  3. stream中の画面はplain textで、finishReason=stopの正常完了時だけMarkdownを一度renderする。
  4. TTSは回答完了前に開始し、先行合成、順序、取消、half-duplexを維持している。
  5. ASRの既存精度・安全策を維持し、自動testと実mic / Harness evidenceが揃っている。
  6. Section 7のperformance、accuracy、correctness、soak Gateをすべて満たしている。
  7. rollback手順がSSE fallbackなしで実地確認されている。
  8. 本文書、既存ASR/TTS計画、release evidence、実装のstatusが一致している。
