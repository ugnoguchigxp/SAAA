本文書は、SAAA Adaptive Learning and Selective Memory Concept のreviewで確認された10件の欠陥だけを修正するための実装契約である。完了の定義は AC-00〜AC-10を依存順に完了し、Section 7のAcceptanceを満たすことである。

本契約はConcept文書とInternal Design Documents索引の2ファイルだけを 変更する。Rust、TypeScript、SQLite schema、Settings、テストを変更しない。Concept文書のStatusを ConceptからPlanへ昇格させず、実装着手を許可しない。

5. 各修正の内容

5.1 F1 — 学習器stateの再構成性を固定する

§1のTable「Concept decisions and hypotheses」へ次の行を追加する。

Table: Added decision row
項目 Status 判断
学習器stateの再構成性 固定 replay可能なexample logと定期checkpointから常に再構成できる状態に保ち、不可逆なonline更新を 主経路にしない

§5.2末尾の「可能な範囲で派生Candidate、Index、学習example、model revisionへのlineageを無効化し」 を、この決定に沿って書き換える。削除は、example logから該当exampleを除去し、直前のcheckpointから replayしてmodel revisionを再生成する手続きとする。「可能な範囲で」という留保を残さない。

§17から「User削除要求に対する派生modelのunlearningを、再学習とrevision rollbackのどちらで保証するか」 を削除する。§13.1の「削除要求はRaw sourceだけでなく、派生物と学習revisionへの影響を表示できる」は この決定により実装可能になるため、そのまま維持する。

5.2 F2 — Sample budgetを新設する

§7.2の後に§7.3として新設する。次の3点を必ず含める。

  1. 測定対象: 既存baselineのlogから、guardで自動決定されず選択が実際に分岐する turn数、§9.1上位2層に該当する強いoutcome件数、および§10が要求するprovider fingerprint別・ revision別・recency window別に分割した後のセルあたり有効標本数を測る。
  2. 測定主体: 学習器の実装前に、既存の投影経路へdecision loggingを追加して測る。 本契約はその実装を含まないが、これがsample budget確定の前提であることを明記する。
  3. 停止条件: セルあたり有効標本が特徴次元数を下回る場合、線形Policyを実装しない。 固定Policyを結論として採用し、§15の仮説1を実装前に棄却する。

§10の第1項目へ、単一userのdesktop clientでは恒久的にcold startである可能性を、棄却可能な選択肢として 追加する。cold startを一時状態とだけ扱う現在の書き方を改める。

5.3 F3 — coverageの操作的定義を入れる

§6の目的関数のpre記述の後に、次の定義を追加する。

  • required information coverageは、Assist intentごとの必須スロットchecklistで表す。スロットは 要求の決定論的パースから導き、主体、時点、制約の対象、出典の要否を含む。
  • coverage failureは、当該スロットを充填できる候補がCandidate Indexに存在するにもかかわらず、 選択後のWorking Setで未充填スロットが残る状態と定義する。
  • この定義は学習器なしでoffline計測できる。§16.1のB0からB4まで同一定義で比較する。

§17から「Candidate setのcoverage、冗長性、矛盾、costをどの独立指標で測るか」のうちcoverageを削除する。 冗長性、矛盾、costは未決のまま残す。

5.4 F4 — PURPLE注記に前提を明記する

§19の第1項目の注記を差し替える。現在の「semantic similarityだけでなくgeneration utilityから profile setを選ぶ検証例」に、次の前提を追加する。

  • rewardはreference responseのlikelihoodであり、正解応答が与えられたbenchmark上で成立する。
  • 学習は9個のpersonalizationタスクを横断し、単一userのonline feedbackではない。
  • 選択機構は線形banditではなく、順序依存を扱うPlackett-Luce ranking modelである。
  • SAAAは§9.1で信号を疎な明示feedbackと機械検証に限り、§10で横断学習を禁じるため、同一条件は 成立しない。本引用は仮説の成立根拠ではなく、成立条件を示す資料として扱う。

5.5 F5 — baselineへ実装差分を追記する

§0の第3段落へ次を追記する。

  • 現行実装のContext Healthはgreenとyellowのみを返し、RED状態は存在しない。
  • minimal rebuildが予算内へ収まらない場合はturn自体が失敗し、REDとして観測されない。
  • Provider requestの開始はContext Health statusでgateされていない。
  • したがって§12の「Context HealthがREDのEnvelopeは送信せず」と§16.3のContext Health違反0件は、 現時点でコード上未強制のinvariantである。§16のbaselineをこの差分の上で組む。

5.9 F9 — userから見た成功条件を書く

§15の冒頭に、仮説表より前に1段落を追加する。次の4点を観測可能な条件として列挙する。

  • 同じ前提をuserが繰り返し説明する回数が減る。
  • 誤った前提に基づく応答が減る。
  • 過去の事実を問う質問に、出典付きで答えられる割合が上がる。
  • foreground latencyとtoken costが悪化しない。

あわせて、これらが観測できない場合はarchitectureの内部的な正しさを採用理由にしないことを明記する。
