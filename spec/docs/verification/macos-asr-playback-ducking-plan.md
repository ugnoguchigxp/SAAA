# macOS: ASR中に他アプリの再生音量が下がる問題の検証計画

## 目的と既知の事実

SAAAでASRを有効にすると、再生中の動画や音楽が毎回小さくなる。`echoCancellation`は、この問題に対する有効な解決策ではない。これらを既知の事実として扱い、再現の有無や同設定の有効性をユーザーに聞き直さない。

本計画の目的は、**どの音声処理段階で他アプリの再生音量が下がるか**を特定し、その段階だけを修正することである。段階試験は原因候補を絞る手段であり、通常のSAAAで同じ現象を再現できなければ判定に使わない。音量が下がらないことの実機確認までを完了条件とし、音声設定値や自動テストの成功だけで修正完了としない。

## コードから確認した経路

1. `src/features/voice/ambientVoiceCaptureActions.ts` の `attachVoiceCapture` はRust側のASRセッションを開始してから、WebView側のマイク取得を開始する。
2. `src/lib/microphone.ts` の `microphoneCaptureConstraints` は `echoCancellation: true`、`noiseSuppression: false`、`autoGainControl: false` を指定し、`requestMicrophoneStream` が `getUserMedia` を呼ぶ。
3. `src/features/voice/ambientVoiceCapture.ts` は16 kHzの `AudioContext` を作り、`MediaStreamAudioSourceNode` → `AudioWorkletNode` → `AudioContext.destination` を接続する。Workletから届くフレームはVADより前に `packetFrame` に渡す。
4. `src/features/voice/VoiceCaptureResources.ts` の `packetVoiceFrame` はフレームをパケット化し、`src/lib/voiceAsrRuntime.ts` のIPC経由でRustへ送る。`src-tauri/src/voice/streaming_asr/` の話者ゲートと認識処理はこの後段にある。
5. `src/features/chat/conversationTurnControls.ts` は通常の会話経路でTTS開始時にマイク取得を停止し、TTS終了時に再開する。したがって、現行コードのTTS中割り込みを本件の既存機能として仮定しない。

上記から、ASR開始時に再生音量へ影響し得る境界は、少なくとも「ASRセッション準備」「WebViewのマイク取得」「AudioContext/Worklet起動」「デバイス切替」に分解できる。現在のRust側ASRはマイクを直接開かない。

## 検証の準備

- 同じMac、同じSAAAビルド、同じ出力デバイス、同じ音量スライダー値を使う。比較中は動画・音楽のプレーヤー側の音量も変えない。試験前に、SAAA以外のマイク利用アプリと音声補正アプリの起動状態を記録する。
- **最初に通常のSAAAのASRを開始・停止し、この試験環境でも報告済みの減音が起きることを確認する。** この確認はユーザーへの再質問ではなく、診断用経路が通常経路を再現できるかを判定するための対照試験である。通常経路で減音しなければ、その試行では段階試験に進まず、機器・SAAAビルド・他の音声利用状態を点検する。
- まずMacBook内蔵マイクと内蔵スピーカーを選ぶ。普段の機器がBluetoothなら、普段の機器での通常経路の結果も先に記録し、内蔵機器での段階試験後に同じ段階試験を繰り返す。内蔵機器で通常経路の減音が起きなければ、内蔵機器の段階試験だけからWebView入力を無罪と判定しない。
- 同一の音源区間をループ再生し、各試行で開始前、開始直後、開始後5秒、開始後30秒、停止直後、停止後5秒の聴感音量、システム音量値、入出力デバイス名を記録する。可能なら独立した音圧計で同じ位置の相対レベルを測る。自動音量調整のあるスマートフォン録音の波形振幅は判定根拠にしない。macOS内の新たな音声キャプチャも診断自体を変えるため、測定用に増やさない。
- 各段階を3回繰り返し、間にASR停止・マイク解放状態の対照試行を入れる。音源、機器、音量を変えた試行は比較に混ぜない。3回で結果が割れたら追加試行し、初発段階を確定扱いにしない。音量スライダーが一定でも聴感音量が下がる場合は減音ありと記録する。
- 開発専用の診断入口を使い、各段階を個別に開始・完全停止できるようにする。通常の会話UI、保存済み設定、プロバイダー設定は変更しない。ログには段階、開始・停止時刻、機器、トラックの実効設定と`readyState`、AudioContextの`state`、Workletのフレーム到着数、ASR送信数だけを残し、生音声や発話内容は保存しない。各段階の構成要素が実際に起動しなかった試行は無効とする。

## 仮説と段階試験

| 段階 | 起動するもの | 音量低下がここで初めて発生した場合 |
| --- | --- | --- |
| S0 | RustのASRセッションだけ。マイクは開かない | 仮説外。ASR開始コマンドの副作用・他の同時マイク取得を調べる |
| S1 | S0に加え、WebViewで `getUserMedia` だけを実行。`MediaStream` は保持し、`AudioContext` は作らない | 仮説1: WebViewのマイク取得またはそれに伴うmacOS音声処理 |
| S2 | S1に加え、16 kHzの `AudioContext` を作って起動。まだマイクを接続しない。`state === "running"` を確認する | 仮説2: `AudioContext` の起動・出力経路 |
| S3 | S2に加え、現行どおりsource、Worklet、destinationを接続。ASRへのパケット送信は止め、Workletからのフレーム到着を確認する | 仮説2: 音声グラフの接続またはWorklet動作 |
| S4 | S3に加え、現行どおりASRへフレームを送る | 仮説外。送信・認識開始に連動する別の動作を追跡する |

主試験では各段階を前段階から連続して追加し、**音量が変わった瞬間と操作を対応付ける**。初発段階を見つけたら、いったん全リソースを解放し、その段階の直前までを起動してから疑わしい操作だけを入れる試行を3回行う。各試行の開始前には音量が基準へ戻っていることを確認する。再起動後に結果が変わる場合は、起動順序またはWebKitの音声処理状態を別要因として記録し、単一原因に確定しない。S1以降は同じマイク・同じ制約を使用する。終了時にはトラック停止、ノード切断、`AudioContext.close()`、ASRセッション停止を確認する。

### 仮説1: WebViewのマイク取得が減音を起こす

S0では音量が維持され、S1で小さくなれば支持される。S1の `MediaStreamTrack.getSettings()` を記録する。ただし、`echoCancellation`の表示値だけを原因の証明に使わない。WebViewのマイク取得はWebKit管理下にあり、アプリ側で別のネイティブ音声ノードを設定しても既存の `getUserMedia` に効くとは限らない。

**次の変更先:** まず現行WebView入力に公開されたダッキング制御方法があるか確認する。なければ、macOS版のマイク取得だけを別経路にする小規模な試作で、**他アプリの音量を下げずに音声フレームを取得できるか**を先に確かめる。成功してから既存ASRへの16 kHz PCM接続、機器選択、停止・再開、話者ゲートとの統合を設計する。AppleのVoice Processingの最小ダッキング設定は完全な無減音を保証しないため、設定値だけで採用を決めない。

### 仮説2: AudioContextまたは音声グラフが減音を起こす

S1では音量が維持され、S2またはS3で小さくなれば支持される。S2で始まれば `AudioContext` の起動・出力経路、S3で始まればsource/Worklet/destination接続へ絞る。Workletを出力から単純に切り離すと処理自体が止まる可能性があるため、「音量が戻った」だけで修正成功としない。音声フレームが引き続き届くことを同時に確認する。

**次の変更先:** 減音が始まるノードまたは接続方式を変更する。まずS3の内部で、source作成、Worklet接続、destination接続を順に加えて初発操作を絞る。16 kHzフレーム取得とASRへの送信、VADの境界判定が維持されることを必須条件とする。

### 仮説3: 入出力デバイスまたはBluetoothの通話モード切替が減音に見える

内蔵マイク＋内蔵スピーカーでは各段階で音量が維持され、普段の機器でだけ減音する場合に支持される。普段の機器でS1前後の出力先、サンプルレート、チャンネル数、macOSの表示上の入力・出力機器を比較する。Bluetooth出力が通話用モードへ切り替わるなら、他アプリのアプリ内Gainの問題とは区別する。

**次の変更先:** 入力を内蔵マイクにしてBluetoothを出力専用にする構成など、入出力機器の選択を修正する。内蔵機器でも同じ減音が起きるなら、この仮説だけでは説明できない。

## 判定と実装への引き渡し

- **S1で初発:** WebViewマイク取得層を第一候補とする。デバイス切替が同時に起きた場合は仮説3も残し、機器別の試験結果で判定する。ASR、話者ゲート、TTS Gainは第一の修正対象にしない。
- **S2/S3で初発:** `AudioContext` または接続グラフを修正対象とする。フレーム到達を確認しながら変更する。
- **機器の組み合わせでだけ発生:** デバイス切替を修正対象とする。
- **S0/S4で初発、または段階試験で再現しない:** 既存の通常経路と診断経路の差分を記録し、他のマイク利用者、開始順序、イベント処理を調査する。仮説1へ決め打ちしない。

実装後は、同じ機器と音源で問題が初発した段階と通常のASR経路を再測定する。合格条件は、**問題を再現した元の機器構成**で、ASR開始中と停止直後に他アプリの再生音量が不必要に変わらず、音声フレームと本人の発話が既存のASRへ届き、話者ゲートの動作が維持されること。通常のTTS再生単独、およびASRを有効にした状態からTTSを開始・終了してマイクが停止・再開する場面でも、他アプリの音量が急変しないか確認する。TTS中のマイク停止という現行挙動の変更は本件の範囲外とする。
