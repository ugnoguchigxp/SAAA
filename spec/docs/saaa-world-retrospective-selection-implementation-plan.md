# World 振り返り選定 Job 実装計画

更新日: 2026-10-01。状態: SAAA内の直列Job・プレビュー・限定適用を実装。最新の検証状況と残る実機・外部受入は[実装記録](../evidence/world-maintenance/retrospective.md)を参照。

## 目的と推奨構成

普段の会話を後から振り返り、再利用できる知識、因果仮説、条件、反例、訂正を選定し、既存 World の登録・更新経路へ渡す。ユーザーがその場で指定する即時登録とは別の入口とし、同じ根拠を二重に評価しない。

推奨は `world.retrospective_review.v1` という論理 Job を既存の継続処理基盤に追加する構成である。全履歴を毎日再解釈する方式や専用の常駐 LLM ワーカーは追加しない。変更のあった根拠と未処理履歴を、小さな有限 Job に分割して継続処理する。LocalLLM だけを使い、会話やユーザー指定の仕事を優先する。

製品概念の正本は [SAAAの全体コンセプト](https://chatgpt.com/space/page_9fc5877949748191b556705128f6a2f5)。本書は同 Page の World・Memory 共通 Job、根拠管理、LocalLLM 限定、単一 Writer の原則を具体化する実装契約であり、概念の複製ではない。

## 入力と選定規則

対象は、登録された所有者・プロジェクト Scope に属する確定会話と、許可された外部根拠である。Scope、権限、ID、版、時刻はホストが決める。assistant の発言は指示対象や代名詞の解決にだけ使い、独立した経験・支持根拠として加点しない。ASR の途中結果、TTS、自分の推測は経験として登録しない。

選定対象は次のとおり。

- 繰り返し使う事実・制約・依存関係。
- 原因と結果の候補、および適用条件・比較対象・交絡要因。
- 予測と実際の結果、反例、訂正、撤回。
- 現在の Objective と関連する知識。ただし Objective との一致を全知識の必須条件にはしない。

「原因」という語の有無だけで候補を落とさない。雑談、一時的な状態、既登録と同じ根拠は優先度を下げるが、決定的な否定・撤回は優先して処理する。相関や単発体験を確定した因果法則へ昇格しない。条件付き仮説は既存の型で保持し、未対応の複合条件は根拠参照付きで保留する。

例えば「キャッシュを消すと速くなった」「ただし初回だけ」「翌日は変わらなかった」は、単純な『キャッシュ削除で高速化』へ統合しない。測定条件と時点を保持し、支持・反証・不明を区別する。過去の Goal が現在も有効かは既存 Objective の状態を確認する。

## 処理フロー

1. ソース確定・更新・撤回イベントで対象 Scope を dirty にする。イベント欠落時は版付きの差分照合で補う。初回履歴はカーソルから有限量を読む。
2. ホストが権限と確定状態を検査し、対象 ID・版・Scope epoch・走査境界を固定する。既処理根拠と即時登録済みの対応を先に確認する。
3. LocalLLM が有限窓から候補を抽出する。候補は型、条件、比較対象、引用範囲、根拠 ID・版を持つ。LLM が登録権限や時刻を決めることはない。
4. 候補ごとに、既登録 World と後続の訂正・撤回を照合する。必要なら関連根拠だけを追加取得して LocalLLM で一度補完する。
5. ホストが引用の UTF-8 範囲、意味、型、Scope、依存版、重複、時点を検証する。登録可能・保留・反例追記・訂正・変更なしに分類する。
6. 検証済み提案を保存し、既存 World 適用層へ渡す。適用直前に権限、Scope epoch、依存版、Job 所有権を再検査する。結果と処理済み境界を同じ Writer transaction で確定する。

初期上限は一窓12件のメタデータ、根拠本文32,000 bytes、候補8件、引用は主根拠と追加3件、条件4件とする。既存パーサーの制限を超える候補は、意味を保って分割できる場合だけ分割する。分割で意味が失われるものは保留する。モデル入力全体は既存48,000 bytes 上限を維持する。

一 Job の LLM 呼出しは原則1回、根拠補完を含め最大2回、各段階30秒を初期値とする。これは測定前の運用案であり、Gemma の実測性能を保証しない。追加根拠を探す無限ループは作らない。

## 後日の訂正と時点

現行の「主発言以前」の補助根拠取得を変更せず使うだけでは成立しない。新アダプターは、対象発言より後の訂正・撤回と、同じ対象に関する既知の変更を取得する。スナップショットの走査上限、根拠版、確認範囲を記録する。

有限窓に訂正が見つからなかったことを、全履歴に反例がない証明にしない。既知の撤回が窓に収まらない、必要な後続根拠を取得できない、関連性を判断できない場合は保留する。適用後に新しい訂正が来た場合は再評価・無効化する。

観測時刻は元ソースの時刻を保持する。現在時刻へ置き換えて stale 検査を回避しない。過去としてのみ成立する知識には過去の有効期間を保持し、現在 active な assertion へ無条件で昇格しない。現行適用 API がこの区別を表現できない型は、歴史記録用の適用契約を拡張するまで保留する。

## 重複、再評価、保存

Job 実行状態の所有者は共通キューとし、振り返りドメインの記録は窓、候補、根拠 manifest、処理境界だけを保持する。World の第二の正本や原文の複製を作らない。テーブル名と migration 番号は実装時の現行 schema を確認して決める。

操作 receipt は Scope、根拠 ID・版集合、選定ポリシー版、正規化した対象からホストが作る。lease generation や試行回数は業務 identity に含めない。検証済み提案を保存した後の再試行は保存済み提案を使い、LLM を再実行して別 patch を作らない。同じ receipt key に異なる正規化内容が来た場合は衝突として扱う。

即時登録・通常抽出・振り返りは共通の World 適用層で、原ソース lineage と意味 identity を照合する。条件・比較対象・有効期間の違いを潰さない。同じ根拠の再解釈、窓の重複、ポリシー改版は独立した支持回数を増やさない。新しい根拠や変更された関連前提がある場合だけ再評価する。無関係な World 全体 revision の更新では再推論しない。

保留には理由と再開条件を保存する。入力不備、外部未取得、モデル待ち、資源待ち、矛盾を区別する。時間経過だけで同じ不明候補を再推論しない。

## SQLite 単一 Writer と中断

SAAA の既存 `SqliteWriter` 所有者を通して、enqueue、claim、lease、候補保存、checkpoint、ack、再試行、再起動復旧、関係更新、削除・撤回反映を行う。別プロセス・別接続による直接 write は追加しない。WAL と busy_timeout は単一 Writer の保証として扱わない。

LLM 呼出し・外部根拠読取り中は DB transaction や Writer の排他ロックを保持しない。短い transaction で claim、外で読取り・推論、短い transaction で版検査と commit を行う。commit は候補 receipt、World 変更、checkpoint、ack を原子的に確定する。キュー所有者が別の場合は transactional outbox と consumer receipt で配送を保証し、二つの DB の同時 commit を仮定しない。この場合、producer の ack は outbox への保存完了だけを意味する。World 適用完了は consumer receipt を確認した後に表示し、適用前の配送済み状態と区別する。

中断・lease 失効・所有権変更後の遅延応答は採用しない。commit 前の停止は再試行、commit 後の停止は receipt で変更なしとなる。忘却・撤回は LLM やキュー容量を待たず既存 invalidation 経路で反映し、候補・引用参照・保存済み提案にも波及させる。

外部 CLI とテストは本番 DB へ直接書き込まない。migration・クラッシュ試験は隔離 DB を使う。ContextStill は許可された read API だけで参照する。

## 実行資源と Gemma 64k

背景枠は LocalLLM の認定済み provider/model/endpoint に限定し、API fallback を設けない。LAN endpoint も単に private IP であるだけでは認定しない。接続・各呼出し前に資源と所有権を検査する。停止時は待機し、設定を置換しない。

Gemma 64k は背景枠の利用想定であり、64k を埋める目標ではない。実際の tokenizer で system prompt、schema、根拠、関連 World、出力予約を含む token 数を検査する。byte 上限と token 上限の両方を守る。モデル名・context 能力・サーバー同時実行数は実機で確認する。

共通資源管理が導入されるまでは現行の直列・低優先度 admission を使い、新しい並列常駐ワーカーを追加しない。導入後は共通 allocator から64k枠を借り、全 Gemma 呼出しが同じ資源所有権を通ることを前提にする。

Gemma セッション計画の「会話開始で独立 Job を一律中断しない」案と、正本 Page の背景 Job 中断・優先順位契約には調整が必要である。本計画はその変更を承認済みと扱わない。並列継続を有効化する前に、競合時の退避条件を正本 Page と共通資源契約で整合させる。ASR 常時捕捉を理由に常時 busy と判定しない一方、実際の発話・会話応答を優先する。

## 容量と進捗

新規と履歴を3:1で公平に処理し、古い履歴が永久に待たないようにする。既存 World Job と振り返り Job を合算して非終端作業1024件以内に制限し、未処理候補も1024件以内とする。新規キューと旧キューが共存する期間にも、共通 admission で合算する。

満杯でも原ソースの保存を止めない。窓の receipt または再開可能な境界を保存する前にカーソルを進めない。容量が空いたらソース境界から補充する。何も変わらない期間は LLM 呼出し0回とする。

終端候補の詳細は初期案として7日・1000件まで保持し、原文は保存しない。冪等性 receipt と未処理例外はこの期限で削除しない。削除できる詳細と再試行に必要な記録を分離し、根拠の忘却では双方を削除・無効化する。処理済み範囲はカーソル、改版・保留は疎な例外記録で表現する。継続運用の DB 増分を測定してから保持期間を確定する。

UI は処理段階、待機理由、最古の未処理時刻、最終成功、選定・追加・統合・反証・保留・変更なし件数を示す。無期限処理に固定の100%表示を付けない。候補の根拠、適用条件、観測時刻、現在性、保留理由を確認できるようにする。

## 実装順序と導入判定

1. **適用契約の共通化**: 原ソース lineage による重複防止、過去の有効期間、版 fencing を既存適用層へ追加する。即時登録と通常抽出の挙動を保つ。
2. **隔離された選定プレビュー**: SAAA 会話の有限窓、後続訂正取得、候補 receipt、カーソルを実装する。このモードでは振り返りから active World を更新しない。既存の通常抽出を停止する意味ではない。
3. **既存 Job 基盤への接続**: 単一 Writer、容量合算、再試行、失効、進捗を接続する。共通資源基盤が未完成なら現行直列運用で受入する。
4. **限定自動適用**: 引用・Scope・版・現在性を検証できた型から既存 World へ適用する。曖昧なものは保留。全件の恒久的な手動承認を前提にしない。
5. **外部と実機受入**: ContextStill 契約成立後に Episode を追加する。Gemma 実機負荷と連続稼働を測定し、初期上限を必要な範囲で調整する。

各段階は独立して受入できる。ContextStill や並列 Gemma 基盤の未完了を理由に、SAAA 会話のプレビュー・直列適用を止めない。

## 必須受入例

| ケース | 合格条件 |
| --- | --- |
| 初回効果・例外・後日反例が別発言にある | 条件と反証を保持し、一般的な確定因果へ変換しない |
| 古い発言が後で撤回されている | 現在 active にしない。訂正取得不能なら保留 |
| 単発の相関 | 仮説として保持し、確定因果へ昇格しない |
| 即時登録済み／重複した窓／再試行 | assertion・支持回数が増えない |
| ポリシー版更新のみ | 再評価は許容するが、独立支持を増やさない |
| 別 Scope、assistant の推測、未確定 ASR | 根拠として登録しない |
| 推論中の忘却・ソース改版・lease 失効 | 遅延応答を捨て、忘却対象が復活しない |
| commit の直前・直後でプロセス停止 | 部分適用なし。再起動で重複なし |
| キュー満杯 | ソース保存が続き、後で抜けなく補充される |
| foreground 優先・モデル切断 | 契約どおり退避・待機し、cloud へ逃がさない |
| 更新なしで再走査 | LLM 呼出し0回 |
| 64k 上限、長文・多数の World | 実 token 検査と byte 上限を守り、意味を壊して切り捨てない |

合格には対象テストが実際に実行されていること、失敗0件を確認する。安全性ケースの誤適用0件、引用・権限・版検査の全件成功を自動適用の必須条件とする。選定品質は人がラベル付けした少量の会話で精度・見逃しを測り、プレビュー時に閾値を決める。現段階で Gemma の精度・速度や24時間稼働を実証済みとは扱わない。

## ドキュメントレビュー記録

本書作成後に1回レビューし、次の修正を反映した。追加のレビュー反復は行っていない。

- 現行 `world_context.rs:11–17` の32,000 bytesを32 KiBと混同しないよう、入力上限の単位を統一した。
- 別 DB キューへの outbox 配送 ack と World 適用完了を区別し、配送のみで完了を表示しない契約を補った。
- `schema.sql:29` の一発言一 Job、`extraction.rs:71` の入力上限、`commit.rs:287` の古い観測検査に合わせ、窓の別記録・有限入力・時刻保持を確認した。
- 後続訂正、共通適用層での重複防止、単一 Writer、忘却、中断後の遅延応答、Gemma 資源方針の整合を導入条件として確認した。ローカル参照先は全て存在を確認した。

**評価:** 現状の制約では、差分駆動の有限 Job を既存適用層へ接続し、プレビューから限定自動適用へ進める案が最も合理的である。全履歴の定期再推論は重複と負荷を増やし、専用常駐ワーカーは資源・Writer の所有権を分散させ、全件手動承認は継続運用を阻害する。ただし、この比較は設計上の評価であり、実測で普遍的な最適性を証明したものではない。Gemma 実機の品質・速度、ContextStill 結合、長期 DB 増分と24時間運用は未検証である。


## 実装時の具体化

有限窓は最後に含まれる実ユーザー発言を主引用とし、以前の発言を補助引用とする。後続発言が窓外にある場合は歴史的な候補として保留し、現在性を偽らない。補完推論は必須とせず、初期実装の呼出しは一窓最大1回。未処理キュー合計1024件に加え、保持する非終端・保留提案を持つ振り返り窓を128件以内とし、候補8件×128窓で1024件を守る。

共通の実行所有者は Personal State の `jobs` と既存背景 scheduler である。`personal_review_work` は同所有者が管理する追加ドメインキューであり、別プロセス・別DB・独立スケジューラではない。将来の汎用背景Job基盤への移行はGemma計画に従い、現段階では既存の直列運用を採用する。

最新と履歴には別のreceiptを持たせ、最新を3回、履歴を1回の割合で選ぶ。最新処理では履歴カーソルを進めず、完了した最新窓の最小receiptは詳細の保持期限を超えて残す。履歴の提案詳細は120窓以内とし、最新候補のために8窓分を確保する。
