2. 対象範囲と維持する境界

主な対象はsrc/features/settings/、src/lib/providerRuntime.ts、src-tauri/src/providers/dynamic_lan/http.rs、src-tauri/src/credentials.rs、README日英版。既存の接続確認と設定UIを拡張し、別の設定経路を増やさない。

  2. 「未設定」「確認中」「利用可能」「認証失敗」「到達不能」「このOSでは非対応」を利用者が区別できる表示にする。既存エラーコードと接続状態を使用する。

  4. キー保存がmacOS以外で利用できない制約を、操作失敗後だけでなく設定時に表示する。新しい保存方式はここでは実装しない。

完了条件: 架空のProviderで各状態と再試行をDOM/IPC境界テストし、古い接続確認結果が新しい設定を上書きしない。READMEの手順だけで新規データディレクトリから会話まで到達する。APIキーをUIログや検証記録へ出さない。

利用者検証の初期目標: 開発に関与していない協力者3名が、準備済み接続先を使い、依存ソフト導入後から10分以内に口頭補助なしでテキスト会話を成功させる。人数不足や未達は未検証/失敗として記録し、一般利用者全体への統計的な保証とはしない。

7. Q04 性能の現状計測と限定改善

対象はsrc/appPages.ts、src/features/chat/、src/features/meeting/audio/、既存ストリーミング計測、scripts/maximum-performance.ts。過去のWebSocket専用手順はそのまま使わず、現行SSE経路への適合を確認する。

  1. 同一ハードウェア・build条件で、起動→操作可能、Provider待ち、最初のテキスト描画、取消→停止、長い履歴表示、Meetingの確定表示を分けて計測する。
  2. 各短時間シナリオ30回以上でp50/p95を記録する。p99の主張はこの標本では行わない。失敗数・timeout数を併記し、成功要求だけで品質を評価しない。
  3. 30分・100 turnの反復に切断、sleep/wake、取消を含め、開始前後の5分間の安定時RSS、残存session/process、クラッシュを確認する。
  4. 約543 kBのメインチャンクは構成を調べ、未使用画面や重量依存が初期読込を悪化させている場合だけ分割する。警告抑制のために上限だけを引き上げない。

完了条件: ベースラインと改善後の条件が一致し、クラッシュ・データ損失・残存処理が0。初期の相対基準としてp95が10%以上悪化、または安定時RSSが10%以上かつ20 MiB以上増加したら原因調査を必須にする。閾値は本計画の暫定値であり、測定ノイズを含む初回計測後に固定し、結果を見て合格させるために変更しない。30分成功を2時間の耐久確認の代替にしない。

8. Q05 AI・記憶品質を実証する

対象はscripts/conversation-quality-eval.ts、scripts/conversation-quality/schema.ts、scripts/personal-state-eval.ts、tests/fixtures/personal-state/ja-corpus.json、Personal Stateの既存live harness。評価器が正しいことと、対象モデルが合格することを分けて報告する。

  • モデル・Provider release・設定・corpus版を固定し、会話品質は既存60シナリオを3周する。既存基準である平均90以上、項目別85%以上、3周中2周以上合格、全体の重大違反0を維持する。
  • 記憶は既存の60件以上・8カテゴリ以上・各カテゴリ5件以上・3反復を維持する。各反復でprecision/recallとも95%以上、未処理率5%以下、違反0、欠測0、人手レビュー済みを認定条件とする。
  • 訂正前後、矛盾、別Scope、期限切れ、忘却直後、遅延結果、再起動のケースが網羅されるかを点検し、不足分だけ追加する。
  • LLMによる採点だけで結論を出さず、重大違反全件と各カテゴリの成功・失敗例を人手で確認する。実会話を無断で評価データへ転用しない。

完了条件: 既存評価器が合格し、使用した環境・反復別結果・欠測・人手確認の記録が残る。サービス不通や認証失敗は実装不良と断定せず環境失敗に分類するが、合格率の分母から黙って除外しない。必要環境がない場合は「評価基盤完了・実機評価未完了」と記録する。

9. Q06 Coding処理の保守性改善

対象はsrc-tauri/src/coding/service.rsと隣接repository・workspace・tests。総行数にはテストも含まれるため、大きいという理由だけで全モジュールを分割しない。

  1. 冪等性、conversation/workspace認可、revision、busy、shutdown、generation fence、call budget、transaction commit後の起動を不変条件としてテストに対応付ける。
  2. 長いSQLと状態遷移を名前付き関数へ抽出し、既存のtransactionを引数で受ける。整形と移動を先に行い、挙動変更が必要なら別変更に分ける。
  3. 認可やbusy判定をtransaction外へ移さず、同一call再送で二重起動しないことを維持する。新しい汎用Repository層やRuntime抽象は導入しない。

完了条件: 二重実行、他会話からの参照、古いrevision、取消と起動の競合、commit失敗後の起動禁止を確認する。公開IPC、DB schema、tool応答は不変。module-size上限を維持し、既存テストと全体検査を通す。

  2. 署名・公証の担当と環境がある場合、固定commitから配布物を作成し、digest、依存lock、同梱物、ライセンス、実行環境を記録する。秘密鍵はリポジトリへ保存しない。

環境変数やlive runnerの引数は実装開始時に現行runnerとrunbookから確認する。古い実行例を推測で補わない。公開IPC変更が別途必要になった場合は生成・fixture更新・ipc:checkを同じ変更で行う。

新しい証拠はspec/evidence/product-readiness/への保存を予定する。公開対象はscenario ID、commit/build digest、OS、匿名化した環境ラベル、所要時間、成否、失敗コード、反復数、検証日時に限定する。認証情報、実会話、音声、個人パス、接続先、完全なHTTPログを保存しない。既存runnerの出力も公開前に点検し、機密を含む元データはリポジトリ外で扱う。

失敗後の再実行は元の結果を残し、原因と変更内容を添える。再実行の成功で最初の失敗を隠さない。docs-only変更はリンク・コマンド・事実・spec検査で確認し、アプリ全体の再buildは不要。

13. 完了と引き継ぎ

  • 各Qの状態は未着手、実装中、自動検証済み、実機検証待ち、完了、対象外のいずれかで記録する。実装コミットと証拠参照を付ける。
  • 完了にはそのQの受入条件が必要。外部待ちは担当・必要条件・次の確認方法を明記し、実装だけで完了へ変更しない。
  • 第1段階の完了はQ01〜Q03による現行状態の明確化と主要操作の確認。第2段階はQ04〜Q07の対象範囲の品質改善。一般配布の完了はQ08の判断まで必要。
  • 受入条件を満たさない変更は独立したcommit単位で戻せるようにする。文書や内部関数整理のためにDB migrationを追加しない。
  • 再評価は点数上昇だけでなく、初回成功率、重大違反、復旧成功、性能、未検証項目の減少で比較する。
