本文書は、SAAAが日常の対話結果から個人に適応しつつ、保存したMemoryを毎TurnすべてLLMへ 渡さないための概念境界を定義する。固定するのは、構造化Memory、制約付きContext選択、 小さなPolicy Learner、検証可能な学習記録を分離するarchitectureである。LinUCBなどの 個別algorithmは、本文書だけでは採用しない。

本文書は実装契約ではない。DB schema、Rust module、依存library、migration、Work Package、導入順序、 固定threshold、verification commandは定義しない。既存の Situation-Aware Ambient Agent Runtimeと SAAA Personal AI Concept、 Capability / Tool Runtime Concept、 MVP 3 Memory Architecture実装契約を自動的に変更せず、後続の検証設計と再baselineで参照するConceptとする。

現行baselineにはfeature gate配下のMemory control planeとactive Memory投影があるが、本文書の 階層的selector、Learning Ledger、学習Policyが実装済みであるとはみなさない。既存挙動とConceptの差は、 後続の検証設計で明示的なbaselineとして扱う。現行実装のContext Healthはgreenとyellowのみを返し、RED状態は存在しない。minimal rebuildが予算内へ収まらない場合はturn自体が失敗し、REDとして観測されない。Provider requestの開始はContext Health statusでgateされていない。したがって§12の「Context HealthがREDのEnvelopeは送信せず」と§16.3のContext Health違反0件は、現時点でコード上未強制のinvariantである。§16のbaselineをこの差分の上で組む。

さらに現行実装は、Memory feature gateが有効な場合にPersonal State専用の会話経路へ分岐する。 その経路は通常のContext Window、Provider routing、最近の会話、Tool構成と同じ統合点を通らない。 これは移行中のbaselineであり、目標architectureではない。本ConceptはMemory専用Runtimeを完成形とせず、 Personal Stateを共通Context Brokerの一つのsourceへ変更する方向を固定する。

1. 結論とDecision Status

SAAAに必要なのは、会話全体を学習する単一modelではない。適応対象を、事実と状態の保持、 Context選択、実行可能な設定、再利用手順、LLM本体の能力に分解する。そのうち軽量学習器が担うのは、 安全な候補の中から今回役立つMemoryPlanを選ぶ限定的なPolicyである。

「普段の会話から学ぶ」という表現には、性質の異なる五つの問題が混在している。これらを一つの 学習器やNeural Networkへ入力しても、責務、正解、失敗時のrollbackを定義できない。

Adaptive Memory Policyは、発話するか、介入するか、外部操作するかを決めない。Situationと Interaction Policyが許したAssist Planningに対して、参照すべきMemoryの計画だけを返す。 MemoryPlanはCapabilityでもPermissionでもなく、外部作用を許可するauthorityを持たない。

Adaptive Memory Policy、Personal / World State、Capability Routerは並列の候補生成器である。 いずれもProvider requestを直接所有しない。共通Context Brokerだけが、現在入力を一度だけ命令位置へ置き、 Memory、State、Tool定義、Task状態を共通予算内へ収めたContextEnvelopeを構成する。

LLMは自然言語の理解と生成を担当する。Memoryの保存可否、source validity、Context予算、 Tool permission、学習revisionのactive化はSAAAが所有する。ContextStillは抽象化された再利用知識を 所有するが、Personal Raw Memory、現在状態、各TurnのContext選択は所有しない。

5. Memory RecordとLifecycle

5.1 Record semantics

Candidate Indexと構造化Memoryは、少なくとも次の意味を区別できなければならない。これはDB schemaの指定ではなく、事実性、時間、削除、適用範囲を混同しないための概念契約である。

  • type、subject、scope、applicability
  • source reference、source trust、source availability、derivation lineage
  • valid timeとrecorded time
  • status、confidence、explicitness、review state
  • sensitivity、retention class、provider / configuration scope
  • 推定utility、解決cost、Context cost、最終利用時刻

valid timeは「いつ真であったか」、recorded timeは「SAAAがいつ知ったか」である。後から訂正された 過去の予定を、最新の事実として扱わない。confidenceはsourceの信頼性を表す補助情報であり、 反復回数だけで事実を確定する投票値ではない。

5.2 Lifecycle

  ↓ admission

  ├─ explicit confirmation / trusted deterministic rule → active
  ├─ insufficient evidence                         → candidateのまま
  └─ rejected / unsafe / irrelevant                → rejected

  ├─ user correction      → retracted
  └─ source deletion      → invalidated / deleted

LLMの要約、Reflection、反復観測はcandidateを作れるが、それだけでconfirmed factやactive Ruleへ 昇格させない。訂正時は過去Evidenceを改変して一つへ溶かさず、関係を保持したまま新しいactive revisionを 指す。削除では先に対象sourceと派生依存を利用停止にし、example logから該当exampleと派生特徴を除く。 対象の影響を含まないcheckpointからreplayし、確認できるcheckpointがなければ初期状態からmodel revisionを再生成する。影響のあるrevisionとcheckpointは再利用・rollbackを禁止し、再構築中は 削除を反映した固定Policyを使う。派生CandidateとIndexも再構成し、旧成果物の削除完了を追跡する。 保持期限により再構築根拠が失われた場合も、残存証拠に限定して再学習またはresetする。

5.3 矛盾とauthority

指示の優先順位と事実の確かさを分離する。trusted policyと委任の境界内で、現在の明示的なUser instructionは今回の希望や作業条件を更新する。過去のPreferenceは、そのScopeと適用期間が有効な場合だけ 使い、今回だけの訂正を恒久的な個人属性へ昇格させない。

同じsubjectとvalid timeについての事実は、対象ごとの正本、観測時刻、sourceの直接性、検証結果で 評価する。User発言もEvidenceであり、外部サービスやTask Runtimeの実行記録を指示だけで上書きしない。 例えば「送信済みとして扱って」は送信成功の証拠にならない。推論候補と再利用知識は個人事実の証明にしない。 解決できない競合はdisputedとして残し、確認・追加観測・abstentionへ進む。

過去Memoryと取得文書はdataであり、current instructionやtrusted policyを上書きできない。 必須制約の有効性が不明な場合、その制約を省いたまま依存する操作を実行しない。

6. Context選択は制約付き集合構築である

一件のMemory typeを選ぶだけでは、直前の会話、複数の制約、正確な引用、Procedureを同時に必要とする Turnを表現できない。そこで、選択を四段階に分ける。

  1. Eligibility guard: current instruction、trusted policy、現在Taskに適用されるcritical constraint、現在Scopeの継続に必要なturn pair、未完了Tool correlationなどの必須Contextを確保する。Scope外、expired、deleted、権限外、機微度違反を先に除外し、 直前という理由だけで会話を持ち込まない。除外で必須correlationが欠ける場合は再計画または保留する。
  2. Route plan: 追加Memoryなし、Personal state、Raw recall、Reusable knowledge、 Procedure support、または許可済みのbounded combinationから計画templateを選ぶ。
  3. Candidate set selection: template内で、予算とtrustを守りながら候補の限界効用を 評価し、必要なcoverageを満たす小さなref集合を選ぶ。
  4. Resolution and health: 選択したrefだけから本文を解決し、deduplicate、serialization、 Context Healthを経てWorking Setを完成させる。

  • required information coverageは、Assist intentごとの必須スロットchecklistで表す。スロットは 既知のintent templateと構造化された要求から導き、主体、時点、制約の対象、出典の要否を含む。自然文を確定できないスロットはunknownとし、充填済みとして扱わない。
  • coverage failureは、当該スロットを充填できる候補がCandidate Indexに存在するにもかかわらず、 選択後のWorking Setで未充填スロットが残る状態と定義する。
  • この定義は学習器なしでoffline計測できる。§16.1のB0からB3まで同一定義で比較する。

coverage failureは選択漏れである。充填候補がCandidate Indexに無い場合はselectorのcoverage failureではない。「最小」は単に短いことではない。Taskを正しく 処理するために必要なcoverageを満たしたうえで、不要な情報がないことを意味する。coverageを満たせない 場合は、薄いContextで断定せず、targeted recall、確認、またはabstentionへ移る。

6.1 MemoryPlanの概念契約

MemoryPlanは本文の寄せ集めではなく、Context Brokerが検証可能な選択理由付きref計画である。少なくとも 次の意味を表現し、ContextEnvelopeのtrusted policyやcurrent instructionを複製しない。

  • 選択したRoute planとpolicy revision
  • mandatory contextとoptional Memory refの区別
  • 各refのsource、trust、validity、sensitivity、選択理由
  • 必要coverage、推定cost、不確実性、除外理由
  • 解決先のProvider境界、deadline、失敗時のfallback

MemoryPlan自身にRaw本文、secret、Tool permission、外部実行命令を保存しない。本文解決後にsourceや validityが変わった場合は、古い計画を送信せず再検査する。

6.2 ContextEnvelopeの統合契約

MemoryPlanはContextEnvelope全体を所有しない。Context Brokerは、MemoryPlan、Personal / World State refs、Capability Plan、Task Runtime snapshot、最近の会話を同じContext予算で調整する。あるsourceが 同じRaw Eventを根拠にする場合、MemoryとWorld Stateの両方から選ばれても独立した裏付けとして数えず、 本文を重複投影しない。

  • trusted policyとcurrent instructionの参照は共通Turn Orchestratorが所有し、Brokerが命令位置へ一度だけ置く。MemoryPlanから供給しない。
  • Scope外、deleted、expired、permission外の候補は、utility scoreより前に除外する。
  • Memory、State、Tool schema、会話履歴は個別上限だけでなく、Envelope全体の共通予算で競合解決する。
  • Learning Ledger、Policy checkpoint、Candidate Index本文はProviderへ投影しない。
  • ToolやProcedureの必須情報を一緒に収容し、満たせない依存は再計画または保留する。最終Tool集合のSelection SnapshotはRuntime検査後に確定する。
  • 選択漏れ、競合、stale、source unavailable、予算超過をContext Healthへ残す。
  • Turn完了後にEnvelopeを継続状態として保存せず、必要な結果だけを各正本へ記録する。

Candidate Indexは本文cacheではなく、各Turnで選択可否を判断するmetadata projectionである。前Turnで選んだMemoryを無条件に持ち越さない。

7. 学習問題の定義

7.1 Bounded target

学習器は、guard通過後のRoute planと候補の限界効用を予測する。個々のMemory refを恒久的なarmにすると、 追加と削除のたびにaction spaceが変わり、集合の組合せが爆発する。そのため、安定したplan templateと type別scorerを学習し、具体的なref集合は制約付きselectorが構築する。

判断前の特徴は、本文を巨大なtext vectorとして直接学習するのではなく、次のboundedな群に分ける。

  • Situation、Assist intent、要求される正確性、時間参照、照応、Task種別
  • 利用可能なMemory type、件数、鮮度、source trust、矛盾、coverage
  • Context予算、推定token、解決latency、provider / model / adapter fingerprint
  • Userが明示した設定、学習停止、sensitivity、Cloud可否
  • 最近のpolicy outcomeとrevision。ただしRaw本文はLearning Ledgerへ複製しない

Feature生成のために追加のblocking provider callを必須にしない。Situationやintentを確定できない場合は LLMに推測させて埋めず、unknownを表現して固定baselineへfallbackする。これにより、Memory routingを 改善するための学習器が、別の高能力LLMへ常時依存する循環を避ける。

7.2 Short-horizon assumption

Contextual banditが妥当なのは、今回の選択の主な価値が今回または近接した結果で観測でき、次Turnの状態を 大きく変えない場合である。数日後の信頼、会話の主導権、長いProcedureの成否など遅延効果が支配するなら、 rewardを無理に今回へ帰属させない。その場合はbandit仮説を棄却し、状態遷移を持つ別Policyとして再設計する。

7.3 Sample budget

単一userのdesktop clientでは、学習に使える分岐が恒久的に不足しうる。線形Policyを実装する前に、次のsample budgetを確定する。

  1. 測定対象: 既存baselineのlogから、guardで自動決定されず選択が実際に分岐する turn数、§9.1上位2層に該当する強いoutcome件数、および§10が要求するprovider fingerprint別・ revision別・recency window別に分割した後のセルあたり有効標本数を測る。
  2. 測定主体: 学習器の実装前に、既存の投影経路へ§9.2が求めるlogged decisionの記録を追加して測る。本文書はその実装を含まない。この計測がsample budget確定の前提である。
  3. 停止条件: セルあたり有効標本が特徴次元数を下回る場合、線形Policyを実装しない。 固定Policyを結論として採用し、§15の仮説1を実装前に棄却する。

8. Guarded Hybrid Policy

8.1 Linear policy candidate

決定論的なrule / semantic selectorを初期active policyとする。§7.3の標本条件を満たした後の学習比較候補はonline linear contextual banditである。少量の個人データから逐次更新しやすく、予測と 不確実性を分けられ、Mac上でforegroundを妨げない計算量に収めやすい。LinUCBまたはBayesian linear policyは候補であり、固定routingより良いことを時系列検証できなければ採用しない。逐次更新するとしても、 example logを学習記録の正本とし、checkpointとメモリ上の更新は再構成可能な派生に留める。 

candidate score
  = calibrated linear expected utility
  + allowed uncertainty term
  - context / latency / risk costs

8.2 Model lifecycle

draft → shadow → candidate → active → superseded
                    │            │
                    └→ rejected  └→ rolled back
  • draftとshadowはUser-facing選択を変えない。
  • candidateはbaselineとの検証を通過しても、active化前にhard invariantを再確認する。
  • revisionは完成前にactive化せず、atomicに切り替える。公開直前に削除・権限変更を再検査する。
  • active revisionとfeature contractを対応付け、削除・権限撤回の影響を含まない有効な旧revisionへrollbackできるようにする。
  • model fileの欠損、schema不一致、数値異常、検証期限切れでは固定Policyへ戻る。

9. 学習Evidenceと因果的な妥当性

9.1 Outcome hierarchy

  • 明示的な承認、拒否、訂正、Memory削除を最も強い信号とする。
  • 機械的に検証できるTask完了、Tool結果、verification失敗を強い結果信号とする。
  • 再質問、言い換え、同じ依頼の繰り返しは低confidenceの補助信号とする。
  • 無反応、無音、会話終了、Provider成功statusをUser満足とみなさない。
  • latency、Context量、不要なRecall、確認負荷をcostとして分離記録する。

一つのscalar rewardだけを正本にせず、観測したoutcome vector、confidence、帰属windowを保持する。 異なる価値を一つの重みへ圧縮する場合、そのreward definitionをversion化する。

9.2 Logged decision

各判断は、後から別Policyを評価できるだけの情報を持つ。

  • 判断前に利用可能だったfeatureとeligible action / plan集合
  • 選択したplan、candidate refs、selection probabilityまたはpropensity
  • guardと除外理由、Context health、選択しなかった候補のbounded metadata
  • policy revision、feature contract、reward definition
  • provider、model、adapter、prompt policy、Capability revisionのfingerprint
  • observed outcome、feedback confidence、遅延、token、失敗class

選んだactionの結果しか観測できないため、単純な過去平均は別Policyの効果を示さない。Safety範囲内の controlled explorationとpropensity記録がある領域だけを、IPS、doubly robust、SWITCH系などの off-policy estimatorで比較する。supportがないaction、個人をまたぐ推測、選択確率が不明な古いlogは、 因果的改善の証拠に使わない。

Explorationは同じSafety、Privacy、authority、必要coverageを満たす等価候補間だけで許可する。機微dataの 追加送信、外部作用、Userが明示したPreferenceへの違反、必須Contextの欠落を試さない。確率化する単位が Route planだけなら、propensityとoff-policy評価もplan判断だけに適用し、決定論的guardやselectorまで 因果評価できたと主張しない。

9.3 自己強化の防止

Policyがよく選んだMemoryは観測機会も増えるため、利用回数やLLMの肯定だけでutilityを上げると self-confirming loopになる。明示feedback、独立verification、反事実評価を優先し、Policy自身が生成した 要約や評価を独立した正解として再投入しない。

10. Cold Start、Drift、Provider変更

  • 学習例がないUser、未知のSituation、未知のproviderでは、決定論的な最小Context baselineから始める。学習しないことと追加Memoryなしを正常状態とする。単一userのdesktop clientでは恒久的にcold startである可能性を、棄却可能な選択肢として扱う。cold startを一時状態とだけ扱わない。
  • Userごとのデータ量を前提にせず、globalな個人情報を共有しない。共有する場合は個人情報を含まない feature priorに限定し、明示的なPrivacy contractを別途必要とする。
  • Userの訂正、設定変更、生活状況の変化をconcept driftとして扱い、recencyだけでなく明示revision境界、 change signal、手動resetを持つ。
  • Provider、model、system policy、Tool revisionが変わると同じContextの価値も変わりうる。 fingerprintを跨いだ学習例は無条件にpoolせず、再検証まではshadowまたはbaselineへ戻す。
  • 過去logの量が多いことを現在の妥当性とみなさない。時間順のweighting、revision分割、stale判定は 検証対象とする。

11. Procedureと権限の分離

Skill全文を毎回LLMへ読ませない。Procedureは、Use when、入力、bounded step、期待結果、verification、 stop conditionを持つ実行候補として扱う。SAAAが現在stepと状態を管理し、LLMには現在の判断または生成に 必要な断片だけを渡す。

断片投影は、versioned Procedureから機械的に必要節を解決でき、必須prerequisite、禁止事項、stop condition、verificationが欠落しない場合に限る。Procedureの整合性を証明できない、versionが変わった、 未知の分岐へ入った場合は、断片を推測で補わず、全文読解または実行停止へfallbackする。

Procedure inductionでは、LLMが説明文を生成できるが、根拠はsource-backed Episode、実際のAction Trace、 結果、verificationである。ただし、成功したAction Traceは将来の権限を付与しない。Procedureは提案または plan templateであり、各外部作用は実行時点のCapability、Permission、Approval、idempotency、verificationを 毎回通る。過去のsecret、credential、Tool output、承認を再生しない。

12. Foreground、idle、失敗時の挙動

Table: Conceptual execution classes
状態 許可する責務 中断条件
Foreground bounded feature生成、Policy inference、MemoryPlan、Context Health、decision記録 失敗時はdeadline内で固定Policyへfallback
Soft idle 確定feedback反映、再構成可能な線形更新、Candidate metadata整理 発話、ASR、TTS、Meeting、Provider実行の開始
Hard idle shadow再学習、reflection、consolidation、Procedure候補生成、offline評価 Foreground需要またはresource pressure
  • Foregroundの候補選択はIndex metadataを使い、本文は選択したrefだけを解決する。全Memory走査やmodel再学習を待たない。
  • idle jobはpreemptibleかつ再開可能で、途中成果物をactive revisionとして公開しない。
  • optionalなMemory、ContextStill、学習器の障害は、必須Contextを検証できる通常Chatでは最小Contextへ縮退する。認可や必須制約を確認できない操作は保留する。
  • Context HealthがREDのEnvelopeは送信せず、minimal rebuild後もREDならProvider requestを開始しない。

共通Runtimeでもrunごとに取消状態と予算を分離する。新入力や忘却は依存sourceと適用Scopeを通して 関連runへ伝播し、無関係なTaskを一律に失効させない。背景jobは公開直前にもsource validityとrevisionを 検査し、古い候補や削除済みsourceからの成果を保存・active化しない。

13. User Agency、Privacy、Security

13.1 User control

  • 保存されたMemoryと根拠を閲覧し、訂正、reject、deleteできる。
  • 今回どのMemoryがなぜ使われたかを確認できる。
  • 学習更新を停止しても、明示設定と必要な継続Memoryは別に利用できる。
  • Memory投影を無効化し、固定Policyへ戻し、個人Policyをresetできる。
  • 削除要求はRaw sourceだけでなく、派生物と学習revisionへの影響を表示できる。

13.2 Privacy

  • Policy Learner、Learning Ledger、Candidate Indexはlocalに所有する。
  • Providerへ送るのはContext Healthを通過したWorking Setだけとする。
  • ContextStillへPersonal Raw conversation、人物、予定、secret、現在状態を送らない。
  • 学習featureやmodel weightも個人情報を漏らしうる派生dataとしてretentionと削除対象に含める。
  • Raw本文をLearning Ledgerへ複製せず、source refとbounded featureを基本にする。

13.3 Security and poisoning

  • Web、Tool result、添付文書、過去会話内の命令文をUser preferenceやtrusted policyへ昇格しない。
  • 外部dataにはauthorityがない。admission時とprojection時の両方でtrust classを検査する。
  • 引用された第三者の発言をUser自身のPreferenceとして学習しない。
  • 異常な反復、急激なpreference変更、source欠落はpoisoningまたは誤帰属候補として隔離する。
  • Memory本文はhistorical dataとしてserializeし、current instructionとの境界を保持する。

15. 検証仮説と棄却条件

Userから見た成功は、次の条件が観測できたときに限る。これらが観測できない場合は、architectureの 内部的な正しさを採用理由にしない。

  • 同じ前提をuserが繰り返し説明する回数が減る。
  • 誤った前提に基づく応答が減る。
  • 過去の事実を問う質問に、出典付きで答えられる割合が上がる。
  • foreground latencyとtoken costが悪化しない。
Table: Falsifiable hypotheses
仮説 比較対象 棄却または縮退条件
Guard付き線形PolicyはContext routingを改善する 固定最小Policy、決定論的heuristic 時系列評価で検証済みoutcomeを改善しない、または重要groupを悪化させる
Candidate set選択は全active投影より良い 全active投影、semantic top-k Context量を減らしても必要情報coverage、訂正率、Task成功を維持できない
短期banditとして扱える 帰属window別の分析 主要価値が遅延・複数Turnの状態遷移に依存し、今回の選択へ安定して帰属できない
暗黙signalが補助情報になる 明示feedbackと機械検証のみ 追加すると誤適応、特定groupの偏り、self-confirmationが増える

仮説が棄却された場合、より複雑なmodelを自動追加しない。固定Policy、明示設定、targeted recall、 full Skill readなど、検証済みの単純な経路へ戻る。§7.3の停止条件に該当する場合、仮説1は実装前に 棄却する。

16. 検証Framework

16.1 Baseline and ablation

  1. B0: 必須Contextだけの固定最小Policy
  2. B1: 現行相当のactive Memory投影
  3. B2: 学習しないrule / semantic selector
  4. B3: Guard + linear Policy

B0からB3は§6のrequired information coverage定義で比較する。保存、候補生成、route selection、set selection、本文解決、Provider生成を別々にablationし、改善源を特定する。

16.2 Test design

  • random splitではなく、未来を過去から予測するchronological holdoutを基本にする。
  • 同一source、近接turn、派生要約がtrainとtestへ跨るleakageを防ぐ。
  • cold start、訂正、topic shift、矛盾、削除、provider変更、ContextStill停止を独立scenarioにする。
  • LongMemEval型のinformation extraction、temporal reasoning、knowledge update、abstentionを分ける。
  • 明示feedback、機械的outcome、暗黙signalを混ぜず、signal別の寄与と誤差を確認する。
  • 期待utilityだけでなく、予測のuncertainty coverageとcalibrationを確認し、過信したPolicyを探索へ使わない。
  • offline replay、supportのあるoff-policy評価、shadow、限定的canaryの順で証拠を強める。

16.3 Acceptance logic

数値thresholdは検証設計で定めるが、判定構造は次を固定する。

  1. hard Safety、Privacy、authority、deleted-source、Context Health違反は0でなければならない。
  2. 固定baselineに対し、明示feedbackまたは独立検証に基づくTask outcomeを改善する。
  3. cold start、訂正、provider変更、機微dataなどの重要groupで重大な回帰がない。
  4. foreground latency、Context cost、memory footprintがRuntime予算内である。
  5. 異常時に固定Policyへfallbackし、active revisionをrollbackできる。

全体平均の改善だけでは採用しない。どれかのhard invariantに違反したPolicyは、平均rewardに関係なく rejectする。support不足や信頼区間が広い場合は「改善なし」ではなく「判断不能」とし、active化しない。

17. Open Questions

以下は実装時の自由項目ではなく、検証設計で解消してから採用判断する未決事項である。学習器stateの 再構成性は§1、required information coverageは§6で決定したため、本節から外す。

  • Route plan templateをどこまで組合せ可能にし、action supportをどう確保するか。
  • Candidate setの冗長性、矛盾、costをどの独立指標で測るか。
  • 自然な会話だけで明示feedbackを得る範囲と、Review UIを必要とする判断はどこか。
  • Soft idleをambient microphoneの無音中まで許可するか、microphone inactiveに限定するか。
  • Personal dataを共有せずにcold-start priorを作れるか。
  • Provider変更後に旧学習例を再利用できる同等性条件をどう検証するか。
  • 遅延rewardがどの程度ならbandit仮説を棄却するか。

18. 非目標

  • 本文書だけを根拠に実装を開始しない。
  • LLMの一般知識、読解力、推論能力を個人会話だけで置き換えない。
  • ユーザー別LoRA、online fine-tuning、neural long-term memoryを初期主経路にしない。
  • Vector DBまたはEmbeddingを必須dependencyにしない。
  • 全Memory、全Skill、全過去会話をContextへ投入しない。
  • Memory有効時だけ別の会話Runtime、Provider routing、Tool loopへ切り替えない。
  • Sessionを継続性の単位として復活させず、適用範囲はScopeとして扱う。
  • 非線形residual補正（Random Forest）を初期主経路にしない。単一userのデータ量では chronological holdoutで増分価値を検証できないため、個人情報を含まない横断学習のPrivacy contractが成立した場合のみ再検討する。
  • ContextStillをPersonal Memory DB、Raw会話検索service、権限管理器へ変更しない。
  • Memory utilityの最大化を、User満足、Safety、真実性の代理として無条件に扱わない。
  • 本Concept内でDB schema、module構成、migration、Work Package、release thresholdを決めない。

20. Concept完了条件

共通Runtimeへの導入順序はPersonal Stateロードマップ§11に従う。 本文書の学習検証は共通経路とWorld Stateの初期gate後に行い、学習なしのContext選択と受入を先に成立させる。

本Conceptの完成状態は、学習器の名前が決まっていることではない。適応対象と非対象、Memoryの正本と lifecycle、Context集合選択、authority、学習Evidence、off-policy評価、drift、User control、fallback、 仮説の棄却条件が一貫しており、実装計画と分離されていることである。

次の成果物は実装計画ではなく、Section 15の仮説をSection 16のbaselineとscenarioで判定する検証設計とする。検証結果により、線形Policy、または学習器を使わない 固定Policyのいずれも正当な結論になりうる。§7.3の停止条件は、後者を実装前に採用する。
