SAAA Generative Inline UI 実装計画

作成日：2026-09-12。状態：初期導入の実装を追加済み。本書は着手時の計画と採用・公開基準を残す。実装方式の変更、実施した検証、未検証項目は実装結果を参照。

1. 到達する体験と対象範囲

ユーザーが「状態をダッシュボードで見せて」と話すと、説明文とUIが会話の同じ流れに表示される。その場で絞り込みや更新を行い、「一覧を右へ」などの依頼で配置を修正できる。「これを保存して」と言えば名前を付けて再利用できる。サイドペインへの移動を必須にしない。

  • LLMは情報の選択・グループ・順序・強調を決める。CSS、DOMの細部、任意のReact／HTML／JavaScriptは生成させない。
  • 外観、余白、文字サイズ、配色、レスポンシブ挙動はSAAA側の責務とする。部品は既存のCSS・翻訳・アクセシビリティの方式に合わせる。
  • 業務データの正本は既存サービスまたは永続ストアとする。LLMが大量データや計測値を創作・転記する経路は作らない。
  • 今回の導入範囲は会話のContent Part、UIの保存、限定したデータ接続、表示・操作・編集・再利用、履歴の性能改善とする。
  • Native Featureへの昇格、NightWorkersへの自動実装依頼、別モデルのComposer、Patch言語、任意MCP接続、外部サービス管理APIの新設は初期導入の対象外。別のCodexタスクへメッセージは送らない。

3. 責務分担と実行経路

User → Conversation Agent → present_ui
  → 定義・source・actionの検証 → SQLiteへ会話とUIを保存
  → Content Part → SAAA Inline UI Host → OpenUI Adapter → SAAA Components

SAAA Components → 許可済みQuery／Action ID → Tauri IPC
  → SAAAの実行境界 → 既存サービス／永続ストア

UI Host → Instance State／Visibility／Data Cache
再表示 → 固定Revision + Instance State + SnapshotまたはLive Data

OpenUIは解析・描画のadapterに閉じ込める。UI定義にはrenderer種別、DSL版、component library版を保存する。OpenUI由来の型を会話・DBの公開契約へ露出させない。初期段階で独自の汎用ASTや第二のDSLは作らず、版付きの定義文字列を保存する。将来別rendererへ移る場合も既存定義の互換adapterまたは明示的な変換を必要とし、自動的に互換になるとは扱わない。

Queryのキャッシュキーはsource ID、正規化した引数、接続先の識別・設定世代とする。複数のUIが同じsourceを利用した場合はin-flight取得と定期更新を共有する。OpenUI内部のpollingとSAAA側のpollingを重複させず、SAAAが購読と取得間隔を管理する。

4. 会話と生成の契約

// 概念契約。Rust定義からIPC用TypeScriptを生成する。
type ContentPart =
  | { type: "text"; text: string }
  | { type: "ui"; instanceId: string; viewId: string;
      revision: number; summary: string };

// 既存contentはテキスト投影として残す。
// partsがない旧メッセージはtext partひとつとして解釈する。
  • partsを表示の正本とし、contentはテキスト部分とUI要約からバックエンドで導出する。二つを独立に更新しない。既存履歴を一括変換しなくても読めるようにする。
  • 要約はTTS、検索、コピー、描画失敗時に使用する。DSLや大量のテーブルデータを読み上げない。履歴のモデル入力も要約と参照を用い、編集対象の定義だけ必要時に追加する。
  • Phase 1はpresent_ui toolの完全な引数を受領・検証してから表示する。toolは定義、要約、source参照を受け、生成済みIDを返す。表示位置はtool結果を会話へ投影する地点で決める。
  • 検証済み定義、初回Revision、Instance、Content Partを同一transactionで保存する。再送時はrun IDとtool call IDで重複作成を防ぐ。旧messageCompleted契約も更新し、UIだけの回答を失わない。
  • 定義の最大サイズ64 KiB、コンポーネント数100、深さ12、source数8、UI数3／messageを初期上限案とする。Phase 0で実例を測定して確定する。エラーは未知部品・型不一致・上限超過などの構造化情報として返す。
  • 不正定義の自動修正は1回まで。失敗時は要約と再試行操作を表示し、正常な文章を消さない。未知版、欠損Revision、renderer例外も同じ境界で処理する。
  • 後続のストリーミングUIは別の構造化eventで追加する。途中定義では外部QueryとMutationを実行しない。完了後に検証し、成功した定義のみ保存・有効化する。キャンセルした断片をSaved Viewにしない。

5. 初期コンポーネントと表示規則

初期語彙はStack、Grid、Cell、Text、Metric、Table、Chart、Status、Actions、ModelStatusの10種類を上限の目安とする。ModelStatusは標準配置で状態を示す高レベル部品とする。Form、Tabs、Timeline、Confirmなどは実ユースケースができた段階で追加する。Chartはまず時系列lineだけとし、系列・単位・取得時刻をsourceの型で定める。

  • Gridは12列、Cellのspanは3／4／6／8／12に制限する。初期は行span・固定高さ・自由な座標指定を許可しない。
  • LLMは単一のspanと表示順序を選ぶ。狭いコンテナでは1列へ落とし、読み上げ順と見た目の順を一致させる。ウィンドウ幅だけでなく会話領域の実幅を使う。
  • 文章の読みやすい最大幅を維持しつつ、UIは会話領域の利用可能幅まで広げる。Tableの横スクロールは部品内に閉じ込める。
  • Tableはsource参照、許可された列、sort／filter／pageを受ける。Chartは実在するデータのみ描画する。未取得・未対応の値は「取得できません」とし、0や架空の系列で埋めない。
  • キーボードで操作できるラベルとフォーカス表示を用意する。生成部品の文字列は既存の日本語／英語UIに対応し、数値の単位・時刻表示はSAAA側で整える。

6. 永続化とRevision

追加する論理テーブルと不変条件
テーブル案 主な項目 規則
conversation_message_parts message_id、ordinal、type、payload_json、schema_version messageとordinalを一意にする。UI payloadはInstanceとRevisionを参照する。ページ取得時に一括で読む。
ui_views id、name、description、tags、status、current_revision、published_revision、timestamps ephemeral／draft／published／archived。再利用一覧に出すのは明示的に保存したView。
ui_view_revisions view_id、revision、renderer、dsl_version、library_version、definition、reason、created_at view_idとrevisionを一意にする。追記専用。過去の定義を書き換えない。
ui_instances id、view_id、revision、mode、state_version、state_json、updated_at 各表示に別IDを割り当てる。stateはタブ・sort・filterなどの操作状態だけで、業務データの正本にしない。
ui_snapshots instance_id、source_id、source_schema_version、captured_at、data_json snapshotの表示データを固定する。liveのキャッシュと混同しない。

これらは論理設計であり、具体的なDDLとmigration番号は実装時点のschemaへ合わせる。外部キー、JSON検証、最大サイズを定める。巨大なSnapshotは無制限にJSONへ詰めず、初期は1 MiB／Instanceを上限案とし、超過時は明示的な件数制限または生成失敗を返す。データを黙って切り捨てない。

Ephemeralも会話に残るため定義を保存する。「保存」は再利用可能なViewへ登録する操作を指す。会話削除時は当該Instance・Snapshotを削除し、どこからも参照されない未保存Viewを回収する。Saved Viewは残す。Archiveは検索の通常結果から除く操作とし、過去の会話参照を壊さない。

編集要求は対象instanceId、base revision、現在の定義、関連sourceの型、直近の変更要求を入力とする。参照先が曖昧なら対象をユーザーが選べるようにする。全会話履歴はUI編集用には再投入しない。初期は定義の全文再生成とし、compare-and-swapで競合を検出する。

編集結果は新Revisionと新しい会話内Instanceとして表示する。過去メッセージのRevisionは変えない。公開済みViewの編集はDraftとし、再保存時だけpublished_revisionを進める。保存済みViewの呼び出しはpublished_revisionを固定して新Instanceを作る。liveでも固定されるのはレイアウトの版であり、データだけ現在値になる。

画面操作状態はinstanceIdとrevisionをキーに外部ストアへ置く。永続化はdebounceし、unmount前にもflushする。フォームを導入する際は保存対象を限定し、認証情報はstate_jsonへ保存しない。revisionが変われば互換なstateだけ移行する。

7. データと操作の境界

source registryはID、引数schema、結果schema、取得関数、許可する更新間隔を持つ。action registryはID、引数schema、対象source、利用条件、実行関数を持つ。LLMがURL・SQL・IPC command名を自由指定する経路は作らない。フロントエンドの検証に加えRust側でもsource、action、引数、現在の設定と操作対象を確認する。

  • Phase 1では読み取りと明示的なRefreshだけを有効にする。LARMの初期画面は実在する接続・実行・割り当て状態から構成する。CPU／memory／tok/sの取得契約がなければその部品を出さない。
  • モデル停止とallocation解放は同じ意味ではない。モデル全体の停止を既存releaseへ読み替えない。管理APIが未提供なら停止機能を未実装として残す。
  • Mutationは明示的なユーザー操作または既存Agentの実行ポリシーに従って開始する。mount、restore、stream更新からは実行しない。ボタンと会話経由の操作は同じ実行サービスへ合流する。
  • 操作はinstance、revision、action、対象ID、期待する状態、request IDを持つ。実行中は重複送信を防ぎ、必要な確認は操作の性質と既存ポリシーに従う。すべてのクリックでLLMや追加確認を呼ばない。
  • 通信切断で結果が不明になったMutationを自動再送しない。backendの冪等性契約または状態再取得で結果を確定する。操作結果は既存audit経路に記録し、会話には実行結果の短い記録を残す。
  • Snapshotは読み取り専用。操作が必要なら現在状態を取得するLive Instanceを新しく開く。Liveには「現在の情報」と最終取得日時を表示する。取得失敗時は前回値と失敗状態を区別する。

8. 表示ライフサイクルと履歴性能

Phase 1からUI Hostを設け、Phase 2で画面内判定と外部stateを導入する。初期はactive／suspended／unmountedの3状態でよい。HOT／WARM／COLDはその説明用の呼称とし、別の状態機械を増やさない。未取得の履歴はSQLiteにだけ存在する。

  • active：画面内のUI。許可されたQueryとユーザー操作を利用できる。
  • suspended：近傍だが画面外。新規Query・polling・購読・animationを止める。共有sourceに別のactive購読者があればその通信は維持する。
  • unmounted：遠いUI。rendererを破棄し、外部stateと高さ推定だけ保持する。画面外になっても送信済みMutationを取り消した扱いにはせず、backendで結果を記録する。
  • アプリが背景になった場合も更新を停止する。最後の購読者が離れた時にin-flight Queryを可能ならcancelし、取消不能なら結果の反映を世代番号で制御する。
  • TanStack Virtualはmessage単位に適用する。過大な単一messageにはUI数・データ数上限を設け、表のページングで抑える。フォーカス中の入力は保持し、入力を失うunmountを避ける。
  • 先頭への履歴追加は安定したmessage IDと先頭可視要素のoffsetでanchorを維持する。末尾追従はユーザーが末尾にいる場合だけ行い、UIの遅延描画・幅変更にも対応する。
  • 高さcacheはinstance、revision、幅bucket、表示に影響するstate世代、theme／font世代をキーにする。実測で補正し、粗い推定が外れても累積してscrollがずれないようにする。
  • DOM仮想化と履歴メモリ上限は別に実装する。初期取得30 messages、保持上限150 messagesを初期案とし、上下の再取得境界を管理する。上限超過時の解放後も新しい側へ戻れるよう、既存cursor APIに必要最小限の方向指定またはanchor取得を追加する。
  • content-visibilityは計測との整合を確認できた場合だけ補助に使う。必須依存にしない。

9. Saved View検索

名前、説明、タグ、更新日時をSQLiteへ保存し、通常の一覧・名前検索から始める。FTS5を導入する場合は日本語の「前に作ったローカルLLMの画面」で目的のViewへ到達できるかをfixtureで検証する。標準tokenizerだけで日本語検索を満たすとは仮定せず、実際に同梱するSQLiteの機能を確認してtrigramや正規化検索を選ぶ。初期に検索基盤を新設しすぎない。ContextStillによるsemantic retrievalは後続候補であり、Viewの正本は引き続きSQLiteとする。

11. OpenUIの採用・撤退条件

OpenUIの公開仕様では独自library、Renderer、Query／Mutation、initialState／onStateUpdateが提供されている。一方、直接的なsuspend propは公開Renderer APIにない。SAAAのHostで取得制御を実現できるかを必須検証とする。パッケージはlatest追従にせず、試作で確認した版とlockfileを固定する。

Phase 0で測る採用基準。数値は製品目標であり実測結果ではない
項目 合格条件 不合格時
制御と互換性 独自libraryだけで描画し、許可外toolは0件実行。Tauriで描画・restore・unmountが成立。必須ケースは全件成功。 依存追加を本採用しない。少数のJSON schemaと同じSAAA部品を使うadapterへ切り替える。
生成と編集 新規20件・編集20件の固定ケースを実利用予定modelごとに3回測定。初回有効率95%以上、修正1回込みで99%以上。未達modelではGenUIを有効化しない。 語彙とlayoutを縮小して再測定。それでも未達ならSemantic View中心のJSON方式と比較する。
状態復元 filter、sort、page、選択状態が再mount・再起動で復元し、同じViewの別Instanceへ漏れない。 自前部品へのstate移管で解決できなければ不採用。
通信停止 10 UIを表示履歴に残しても画面外の新規取得は0。共有sourceは一つの取得周期。同時Mutationの誤再送0。 Query実行をSAAA部品へ移す。runtimeが許可外通信を止められなければ不採用。
総コスト 同じ部品・データ参照を使う最小JSON方式と比較し、入力／出力token、修正回数、生成時間、初回描画時間、bundle差を記録する。 出力tokenだけで採用しない。OpenUIの機能上の利益が運用コストを上回る根拠を記録できなければJSON方式を選ぶ。

候補が不採用でもContent Part、View／Instance、source／action、Snapshotの契約は維持する。代替JSON方式はLLMに任意コードを書かせるものではなく、同じ許可部品の選択・配置を型付きデータで表す。Native Featureへの変換は実装成果の受入後、別計画で評価する。

失敗時は同じ条件で再現し、原因を修正して該当ケースと関連回帰だけを再実行する。既存差分由来の失敗は開始前の結果と比較し、今回の成功に含めない。OpenUI固有の必須条件を満たせなければPhase 0の代替へ戻す。接続不能などの外部要因は未検証項目として残し、合格扱いをしない。

13. 有効化、停止、完了報告

新規生成を制御するfeature flagを既定OFFで導入し、Phase 1Bを通過した環境で試用する。描画機能とQuery／Mutation有効化は分けて制御する。停止時は新規生成・外部操作を止め、既存Content Partは要約表示で読める状態を維持する。DBを逆migrationで破壊しない。旧binaryへのdowngrade互換を保証する場合は別途検証が必要であり、初期の復旧手段は同じbinaryでのflag無効化とする。

実装証跡はspec/evidence/generative-ui/へ、baseline、使用版、fixture、テスト結果、モデル評価、性能結果、画面例をまとめる。完了報告には工程ごとの合否、未対応source／action、未検証の実機条件、残る制約、OpenUI採用または代替の根拠を残す。単に画面が表示できたことだけで保存・通信停止・履歴性能まで完了したとは扱わない。

14. 根拠と関連仕様

  • OpenUI公式リポジトリ：対象プロジェクト、MIT、パッケージ構成。2026-09-12の採用評価で確認。
  • OpenUI Renderer：独自library、stateの復元、toolProvider、error処理。
  • OpenUI Query／Mutation：tool連携と実行契機。SAAA側の実行境界を省略できる根拠にはしない。
  • OpenUI Benchmarks：公式の比較情報。SAAAの総コストは独自測定する。
  • SQLite Single Writer計画：永続化の既存方針。
  • Streaming性能計画：既存の会話表示・音声経路との整合。
  • LARM Operations Runbook：既存の接続・運用境界。
