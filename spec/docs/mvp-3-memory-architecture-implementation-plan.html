1. 結論と固定判断

SAAAとContextStillの責務を次のように固定する。

SAAA
├─ One continuous user-facing Timeline
├─ Raw interaction events and local FTS
├─ User Profile / User Core
├─ Working State / Continuity Capsule
├─ Per-turn Context Projection
├─ Context Health Engine
├─ Idle eligibility
├─ Reflection source window
├─ Pre-egress abstraction
└─ Raw drill-down resolver

ContextStill
├─ EpisodeCard
│  └─ success / failure / mixed / unknown
├─ Rule
├─ Procedure = Skill
├─ Deduplication / consolidation
├─ Rule / Skill induction
├─ Knowledge lifecycle
└─ Episode + Knowledge retrieval

User-facingなSessionの概念を廃止する。通常Chatに「新しい会話」「Sessionを開く」「Sessionを再開する」操作は置かず、 一人のUserとAgentの関係を一つの連続Timelineとして扱う。話題変更、app再起動、Provider変更、日付変更はTimelineを分割しない。

実装内部には処理境界としてTurn、Runtime Run、Reflection Window、 Context Projectionを残す。ただし、いずれもSessionではなく、記憶、検索、関係性の境界に使用しない。 Context Projectionは毎Turn作り直す使い捨て入力であり、Provider側の会話状態へ無期限に追記しない。

Meeting、Coding Task、Document、Runtime RunはTimelineから参照できるresourceとして残せる。resourceを開く操作は表示filterにすぎず、 別の会話履歴、別の人格、別のMemory partitionを作らず、Continuityをresetしない。

Sessionlessは「全履歴を常時Contextへ投入する」ことを意味しない。全Raw履歴はSAAAのTimelineへ保持し、 Context Windowには現在の指示、Policy、User Core、Continuity Capsule、Working State、直近Raw、必要なRecallだけを選択投影する。 投影前後をContext Health Engineで検査し、健全性を満たさないContextはProviderへ送信しない。

ContextStillはPersonal Memory DBにしない。人物、クライアント、予定、現在のプロジェクト進捗、User Preference、会話全文を保存しない。保存するのは、将来の判断または実行へ再利用できる経験、Rule、Skillだけである。

ProcedureとSkillはMemory上では同義とする。既存schemaとCandidate pipelineの互換性を維持するため、永続化typeは procedureを正本とし、UI、Context projection、文書上ではSkillと呼んでよい。 SKILL.md生成は将来のexport形式であり、別のMemory categoryを追加する理由にはしない。

scopeは新設しない。ContextStillに既存のrepositoryとglobalだけを利用する。 repository scopeは再利用知識の適用境界であり、現在のプロジェクト状態を保存する意味ではない。

プロジェクト名、製品名、具体的なクライアント名、人物名、内部endpoint、絶対path、branch、ticketなどは、 ContextStillへ送る前に役割ベースの表現へ抽象化する。ContextStill側でも保存直前に同じ契約を再検証する。

3. 今回達成すること

  1. User-facing Sessionを廃止し、通常Chatを一つの連続Timelineとして提供する。
  2. 既存Conversationを失わず、legacy sourceとして一つのTimelineから横断参照できるようにする。
  3. Raw interaction eventをSAAA SQLiteへSource of Truthとして残す。
  4. Agent Policy、User Core、Continuity Capsule、Working State、Recent Rawをpriority付きでContextへ投影する。
  5. Providerの実効Context上限から出力予約と安全marginを先に引き、残りだけを入力budgetとして使う。
  6. 毎Turn Contextを再構築し、重複、古い情報、矛盾、無関係なMemory、未解決照応を検査する。
  7. 全Timelineを横断するlocal Continuity Recallと、ContextStillのExperience Recallを分離する。
  8. 明示的・永続的Preferenceを構造化し、現在の明示指示より低い優先順位で利用する。
  9. Turn完了時にMemory整理jobをtransactionalにenqueueする。
  10. Agent待機時だけ、Profile候補抽出、Experience Reflection、Working State cleanupをboundedに実行する。
  11. 再利用価値がないConversationへNO_MEMORYを返す。
  12. ContextStillへ送る前に、固有名詞とsensitive valueを抽象化または除去する。
  13. 抽象化済みExperience CandidateをContextStillのEpisode pipelineへ冪等に登録する。
  14. Episode群からRule CandidateとSkill Candidateを自動生成する。
  15. 重いretrievalを毎turn実行せず、必要時だけEpisodeとKnowledgeをrecallする。
  16. Episodeのopaque source referenceから、SAAA内のRaw Timelineへdrill-downできる。
  17. ContextStill停止、Memory worker失敗、抽象化失敗が通常会話を停止させない。

4. 非要件

  • Session廃止を、全Raw履歴の常時Context投入として実装しない。
  • 内部のTurn、Run、Reflection WindowをUser-facing Sessionとして再導入しない。
  • ContextStillをPersonal Memory DBへ変更しない。
  • User Profile、Interest、人物関係、予定、Task、Contact、Fileの現在値をContextStillへ保存しない。
  • SAAAとContextStillでSQLite fileまたはprivate tableを共有しない。
  • user、project等の新scopeを追加しない。
  • Conversation全文、Meeting全文、Tool Result全文をContextStillへ送信しない。
  • 保存前の抽象化に失敗した内容を「後で直す」前提で保存しない。
  • すべてのTurnからEpisodeを生成しない。
  • 一つのEpisodeだけを根拠に、RuleまたはSkillを無条件でactive化しない。
  • Vector SearchをChat起動またはMemory機能の必須dependencyにしない。
  • 巨大Knowledge Graph、人物Graph、Conversation Graphを導入しない。
  • 初期MVPでRaw Conversationの自動削除policyを変更しない。
  • Meetingのexplicit-save / discard policyを変更しない。

2. Current explicit user instruction
3. Explicit scoped preference

7. Recalled raw continuity evidence
8. Recalled Rule / Skill / Episode as evidence

6. Memory Abstraction Contract

次の不変条件を、SAAA pre-egressとContextStill pre-storageの両方で検証する。

  1. Raw ConversationをContextStillへ送信しない。
  2. 固有名詞を含む置換辞書をContextStillへ送信または保存しない。
  3. ContextStillへ届く自然文は、すでに役割ベースの表現へ抽象化済みである。
  4. ContextStillは防御的に再抽象化し、残留を検出した場合は保存せずrejectする。
  5. 抽象化前本文をoutbox、error、audit log、diagnosticsへ保存しない。
  6. source referenceはopaque idだけとし、Conversation titleやclient名を含めない。
  7. 技術的再利用に必要な公開用語は保持する。

実装開始時に現行user_versionが9であることを確認する。9以外ならmigration番号を推測せず、 baselineを更新して本Sectionを改訂する。migration前backup、transaction、reopen検証を既存方式どおり維持する。

8.1 Continuous Timeline

CREATE TABLE continuity_streams (
  id TEXT PRIMARY KEY,
  stream_kind TEXT NOT NULL UNIQUE CHECK(stream_kind = 'primary'),
  status TEXT NOT NULL CHECK(status IN ('active','archived')),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE continuity_turns (
  id TEXT PRIMARY KEY,
  stream_id TEXT NOT NULL,
  turn_status TEXT NOT NULL CHECK(turn_status IN (
    'started','completed','failed','cancelled'
  )),
  started_at TEXT NOT NULL,
  completed_at TEXT,
  FOREIGN KEY(stream_id) REFERENCES continuity_streams(id)
);

CREATE TABLE timeline_events (
  id TEXT PRIMARY KEY,
  stream_id TEXT NOT NULL,
  turn_id TEXT,
  ordinal INTEGER NOT NULL CHECK(ordinal >= 0),
  role TEXT NOT NULL CHECK(role IN (
    'user','assistant','system','tool','transcript'
  )),
  event_kind TEXT NOT NULL CHECK(event_kind IN (
    'message','tool_call','tool_result','runtime_note','import_marker'
  )),
  content_text TEXT NOT NULL,
  content_digest TEXT NOT NULL,
  source_kind TEXT NOT NULL CHECK(source_kind IN ('native','legacy_import')),
  tool_name TEXT,
  tool_call_ref TEXT,
  legacy_conversation_id TEXT,
  legacy_message_id TEXT,
  created_at TEXT NOT NULL,
  FOREIGN KEY(stream_id) REFERENCES continuity_streams(id),
  FOREIGN KEY(turn_id) REFERENCES continuity_turns(id),
  CHECK(
    (
      event_kind IN ('tool_call','tool_result')
      AND tool_name IS NOT NULL
      AND tool_call_ref IS NOT NULL
    ) OR (
      event_kind NOT IN ('tool_call','tool_result')
      AND tool_name IS NULL
      AND tool_call_ref IS NULL
    )
  ),
  UNIQUE(stream_id, ordinal),
  UNIQUE(stream_id, tool_call_ref, event_kind),
  UNIQUE(legacy_message_id)
);

CREATE VIRTUAL TABLE timeline_events_fts USING fts5(
  event_id UNINDEXED,
  content_text,
  tokenize = 'trigram'
);

CREATE INDEX timeline_events_stream_time_ordinal_idx
ON timeline_events(stream_id, created_at, ordinal);
  • primary streamはlocal profile DBごとに一件だけ作る。通常Chatから二件目を作成するAPIを公開しない。
  • v9の全conversation_messagesをcreated_at、既存順序、idの順で安定sortし、 legacy_import eventとしてcopyする。件数、digest、先頭・末尾時刻を検証後、新規Chat書き込み先をTimelineへ切り替える。
  • legacy importではuser eventから次のuser event直前までを一つのTurnへgroup化し、orphan eventにはsynthetic completed Turnを割り当てる。
  • native tool call / resultは同じopaque tool_call_refとbounded tool_nameを持ち、callとresultを各一件に制限する。legacy tool eventに相関情報がない場合は安全に対応できる範囲だけを pair化し、不明な場合は独立したopaque refを付けてContext上で未完了Toolとして保護しない。
  • 既存conversationsとconversation_messagesはmigration直後に削除せずread-only legacy archiveとして残す。 互換adapterは移行期間中だけ利用し、新しいContext、Recall、Reflectionの絞り込み条件にconversation_idを使わない。
  • FTS rowはinsert / update / delete triggerで同期し、migration後にrebuildして件数を検証する。anchor候補にはuser / assistantの messageとUserが保存確定したtranscriptだけをindexする。system、runtime note、tool call / result、Recall receiptはindexせず、必要なTool eventはTurn windowのneighborとしてのみ取得する。 検索結果はevent idとscoreだけを返し、本文と前後eventは通常tableからboundedに取得する。
  • created_atはUTCの固定幅RFC 3339へ正規化して保存する。相対時間はUser timezoneで解決し、UTCの半開区間[from, toExclusive)に変換してから timeline_events_stream_time_ordinal_idxで絞り込む。
  • migration前にSQLiteのtrigram tokenizerをcapability probeする。未対応なら実装を止めて代替tokenizerをADRで決め、短すぎるqueryはbounded LIKE fallbackを使う。
  • Runtime Runはturn_idへ関連づける。TurnとRunは実行単位であり、Userに見えるSessionまたはRecall境界ではない。

8.2 continuity_capsule_items

CREATE TABLE continuity_capsule_items (
  id TEXT PRIMARY KEY,
  stream_id TEXT NOT NULL,
  item_kind TEXT NOT NULL CHECK(item_kind IN (
    'active_referent','constraint','open_loop','commitment','recent_decision'
  )),
  value_json TEXT NOT NULL CHECK(json_valid(value_json)),
  status TEXT NOT NULL CHECK(status IN (
    'active','resolved','superseded','stale','deleted'
  )),
  priority INTEGER NOT NULL DEFAULT 0 CHECK(priority BETWEEN -100 AND 100),
  source_start_event_id TEXT NOT NULL,
  source_end_event_id TEXT NOT NULL,
  valid_from TEXT NOT NULL,
  valid_until TEXT,
  revision INTEGER NOT NULL CHECK(revision > 0),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY(stream_id) REFERENCES continuity_streams(id),
  FOREIGN KEY(source_start_event_id) REFERENCES timeline_events(id),
  FOREIGN KEY(source_end_event_id) REFERENCES timeline_events(id)
);
  • Capsuleは長期記憶ではなく、Recent Rawから外れたactive continuityを保持する短い索引である。
  • 各itemはRaw source rangeを必須とし、sourceが失われたitemは投影しない。
  • 次revisionを前revisionだけから生成するsummary-of-summaryを禁止する。Raw sourceとactive itemを再読して再構築する。
  • 同じkeyの矛盾を黙って上書きせず、旧itemをsupersededにするかunresolved conflictとしてHealth Engineへ渡す。

8.3 user_profile_items

CREATE TABLE user_profile_items (
  id TEXT PRIMARY KEY,
  category TEXT NOT NULL,
  key TEXT NOT NULL,
  value_json TEXT NOT NULL CHECK(json_valid(value_json)),
  scope TEXT NOT NULL CHECK(scope IN (

  source_type TEXT NOT NULL CHECK(source_type IN ('explicit','inferred','observed')),

  status TEXT NOT NULL CHECK(status IN (
    'candidate','active','superseded','rejected','deleted'
  )),
  priority INTEGER NOT NULL DEFAULT 0 CHECK(priority BETWEEN -100 AND 100),
  projection_eligible INTEGER NOT NULL DEFAULT 0 CHECK(projection_eligible IN (0,1)),
  source_event_id TEXT NOT NULL,
  supersedes_id TEXT,
  valid_from TEXT NOT NULL,
  valid_until TEXT,
  expires_at TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  last_confirmed_at TEXT,
  FOREIGN KEY(source_event_id) REFERENCES timeline_events(id),
  FOREIGN KEY(supersedes_id) REFERENCES user_profile_items(id)
);
  • 同じcategory + key + scopeにactive itemを一件だけ許すpartial unique indexを作る。
  • explicitはprovenanceであり、confidence 100を自動設定する理由にはしない。
  • 明示的かつ永続的なPreferenceだけを自動activeかつprojection eligibleにできる。
  • 「今回は」「この回答では」等のtemporary instructionはProfileへ保存しない。
  • inferred / observedはcandidateに留め、初期MVPではUser Coreへ自動投入しない。
  • Settingsからの明示編集は、非表示のlocal runtime_note eventを同じtransactionで作りprovenanceにする。
  • supersedeは旧item更新と新item挿入を同じtransactionで行う。

9. Context Builder

9.1 Per-turn Context Projection

Provider adapterが直接historyを組み立てる処理と、Provider側Sessionへ履歴を追記し続ける処理を廃止する。 全Providerは、SAAAがTimelineから毎Turn新規生成した一つのContextEnvelopeだけを受け取る。 

ContextEnvelope
├─ policy: Agent Policy + version
├─ currentInstruction: exactly once, highest user priority
├─ userCore: bounded projection + profile revision
├─ continuityCapsule: source-backed active continuity
├─ situation: Current Situation
├─ workingState: active bounded items
├─ rawContinuityEvidence: optional local Timeline evidence
├─ experienceEvidence: optional Episode / Rule / Skill evidence
├─ recentRaw: token-budgeted tail from the one Timeline
└─ healthReport: counts and provenance manifest, not prompt prose

Context生成順序を次で固定する。

  1. Policy、Current、User Core、Capsule、Working State、Recent Raw、二種類のRecall候補を収集する。
  2. source id、content digest、semantic keyで正規化・重複排除する。
  3. superseded、expired、stale、無関係なitemを除外し、矛盾と未解決照応を検出する。
  4. Provider profileからdynamic input budgetを計算し、protected itemを先に確保する。
  5. role、trust、source、validityを明示してserializationする。
  6. 完成したEnvelopeを再計測し、Context Healthのhard invariantを検証する。
  • Current user messageはcurrentInstructionへ一回だけ入れ、Recent Rawから同じevent idを除外する。
  • 直前の完全なuser / assistant pairと未完了Tool correlationを途中で分断しない。
  • Topic変更ではTimelineを分割しない。relevanceを下げてinactive topicを投影対象から外すが、Rawと未解決open loopは保持する。
  • 大きなTool Resultは全文を再投入せず、source id、結果種別、必要fragmentだけを投影する。
  • Agent PolicyとUser Coreはversion keyでcacheできるが、最終EnvelopeとHealth判定は毎Turn作り直す。
  • selectable itemの初期relevanceはpriority + active topic match + explicit reference + recency - stale penaltyで決める。 threshold未満は投影せず、Fast PathのためにForeground LLM scoringを必須にしない。

9.2 Dynamic Token Budget

effectiveContext = providerAdvertisedContext - adapterOverhead
outputReserve    = max(requestedMaxOutput, ceil(effectiveContext * 0.20))
safetyMargin     = ceil(effectiveContext * 0.10)
inputBudget      = effectiveContext - outputReserve - safetyMargin
  • Provider上限が取得できない場合は、検証済みprovider profileのうち最小の上限を使う。推測値で上限を広げない。
  • output reserveとsafety marginをMemoryまたはRaw履歴のために消費しない。
  • Policy、Current instruction、直前の完全なturn pair、active critical constraintはprotected itemとする。
  • 初期hard capはUser Core 1,200、Capsule 1,500、Working State 1,000、Raw Recall 3,000、ContextStill Recall 3,000 tokenとする。
  • Recent Rawはprotected itemと各hard capを差し引いた残量を使う。固定12Kを全Providerへ適用しない。
  • token estimatorはProviderごとに交換可能にし、unsupported Providerには保守的な文字数推定と10%追加marginを使う。

9.3 Context Health Engine

Provider送信前に次のhard invariantをすべて満たす。

  1. Current instructionがexactly onceで、他のUser preferenceより高い。
  2. 再計測したprojected tokenがinput budget以下である。
  3. output reserveとsafety marginが100%残っている。
  4. superseded、expired、deleted itemが0件である。
  5. User Core、Capsule、Working State、Recall itemがsource referenceとvalidityを持つ。
  6. 同一factまたはinstructionの重複投影が0件である。
  7. 現在のtopicと無関係なMemoryを投影しない。
  8. 過去のuser message、Raw Recall、ContextStill Recall、Tool Resultをhistorical / untrusted evidenceとして区切る。
  9. 過去の命令文がCurrent instructionまたはPolicyを上書きできない。
  10. 直前の完全なturn pairと未完了Tool correlationを保持する。
Table: Context health state and required action
状態 判定 動作
GREEN input budgetの70%以下、critical conflictなし、source coverage充足 そのまま送信する
YELLOW 70%超85%以下、または非criticalな矛盾・照応不足・重複がある dedup、stale eviction、targeted local Recallを行って再検査する
RED 85%超、reserve不足、instruction conflict、source欠落、prompt injection疑いのいずれか 元Envelopeを破棄し、minimal safe Envelopeを再構築する

REDのEnvelopeは送信しない。Policy、Current、直前pair、critical constraintだけのminimal Envelopeを作り、必要ならlocal Raw Recallを一回だけ行う。 再検査でもREDならProvider requestを開始せず、解決不能な照応またはContext容量不足をUserへ明示する。

9.4 Capsule更新とHealth repair

  • Recent Rawからeventをevictする直前に、active referent、constraint、open loop、commitment、decisionのsource-backed itemを更新する。
  • Capsule全体は1,500 token以内とし、上限超過時はresolved、superseded、inactive topic、低priorityの順で除外する。
  • Context eviction順はstale Recall、低priority Working State、重複Raw、古い非anchor Raw、inactive Capsule itemとする。
  • Policy、Current instruction、直前pair、active critical constraint、未完了Tool correlationは自動evictしない。
  • 照応をCapsuleとRecent Rawで解決できない場合、ContextStillより先にlocal Continuity Recallを行う。
  • CapsuleとRawが矛盾する場合はRawを優先し、Capsuleをstaleまたはsupersededへ遷移させる。

content: ...
[END_RECALLED_EVIDENCE]

10.1 Idle eligibility

次の全条件を満たしたときだけ一件のjobをclaimする。

  • active_runsが空である。
  • 最後のuser inputから30秒以上経過している。
  • Meetingがactive、paused、stoppingではない。
  • STTとTTSがrunningではない。
  • window shutdownが開始されていない。
  • Memory feature flagとUser settingの両方が有効である。
  • local-only policyに反するProvider routeを必要としない。

10.2 Runtime bounds

  • worker concurrencyは1とする。
  • 一回のidle wakeで最大3 job、または合計120秒の早い方で停止する。
  • 一つのreflection source windowは最大16K estimated tokenとする。
  • user activityを検知したら、新しいLLM requestを開始せず、現在の短いtransaction完了後にjobをpauseする。
  • running leaseは30秒ごとにheartbeatし、5分staleでpendingへreconcileする。
  • app restart時にrunning jobをinterrupted扱いにせず、lease expiry後に同じidempotency keyで再開する。

10.3 独立した整理domain

jobの入力はstream_id + event rangeで指定し、ConversationまたはSessionを単位にしない。 Reflection Windowは処理量を制限するための一時的な範囲であり、必要なら旧Conversation境界をまたぐ。

  ↓ apply 3-window / 3,000-token hard cap
typed historical evidence with opaque source refs
  • conversation_id、旧Session、現在の画面をfilter条件にせず、legacy importを含むprimary stream全体を検索する。
  • anchor eventは確定したtime range内を必須とする。anchor Turnは分断せず、隣接Turnはrange外へ拡張しない。
  • 近接hitのTurn rangeが重なる場合は先にmergeし、event idで一回だけ投影する。
  • 過去user message、assistant message、Tool ResultはCurrent instructionではなく、source付き untrusted historical evidenceとして囲む。過去system event、runtime note、保存対象外transcriptは返さない。
  • FTS query、hit本文、固有名詞、cursor内部をnetwork、ContextStill、diagnostic logへ送らない。

Recent RawとCapsuleで照応が解決する場合はtoolを呼ばない。SAAA内部のDual Recall Routerも同じrecall application serviceを使い、model-visibleな二つ目の会話toolは追加しない。 ContextStill Experience Recallは抽象化済み経験が必要な場合だけ、SAAA内部APIとして後段で呼び出す。

15. Privacy、Security、Observability

15.1 Feature gate

  • migrationとcanary用process gate SAAA_SESSIONLESS_ENABLEDを追加し、G2まではdefault OFFとする。
  • Sessionless gate ONではprimary Timeline、single-timeline UI、Context Health Engineを一体で有効にする。

  • User setting memory.enabledをdefault OFFで追加する。
  • Memoryの両gateがONのときだけReflection、outbox送信、ContextStill Experience Recallを有効にする。

17. Stop conditionとRollback

次のいずれかが発生した場合、次のWork Packageへ進まない。

  • SAAA実装開始時のschema versionが9ではない。
  • 通常Chatの作成、表示、再開にConversation / Session idの選択が必要なままである。
  • Context Projection、Continuity Recall、Reflectionのいずれかが現在のconversation_idだけに絞られる。
  • Agentから見える会話履歴toolがrecall_conversation以外に増えるか、任意SQL、raw FTS構文、DB path、table名をmodelが指定できる。
  • 相対時間の解決をLLMが計算するか、続きcursorで確定済みUTC rangeが変わる。
  • recall_conversationのRaw result本文をTimelineへ複製保存するか、次回のFTS候補にRecall receiptが含まれる。
  • legacy importでmessage欠落、重複、順序逆転、digest不一致、FTS未収載が一件でもある。
  • Current instruction重複、output reserve不足、sourceなしCapsule、superseded item投影が一件でもある。
  • RED判定された元EnvelopeがProviderへ送信される。
  • CapsuleがRaw sourceを読まず、前版Capsuleだけからsummary-of-summaryとして更新される。
  • 過去のuser messageまたはRecall中の命令がCurrent instructionかPolicyを上書きする。
  • ContextStillのEpisodeまたはKnowledge schemaがbaselineから互換性なく変更されている。
  • 抽象化前のproject名、client名、人物名、path、endpoint、secretがContextStill側へ到達する。
  • ContextStillがSAAA private DBまたはRaw Conversationへ直接接続する必要が生じる。
  • Idempotency-KeyなしでCandidateを登録する必要が生じる。
  • ContextStill停止が通常Chatの失敗または起動blockerになる。
  • foreground activity開始後も新しいMemory inferenceが開始される。
  • Rule / Skillが既存quality gateを通らずactive化される。
  • User Profileのinferred itemが確認なしにUser Coreへ入る。
  • Meeting discard policyまたはlocal-only policyが緩む。
  • Fast Path p95がSection 18の閾値を超える。

Rollback順序を次で固定する。

  1. User setting memory.enabledをOFFにする。
  2. process gate SAAA_MEMORY_ENABLEDをOFFにして再起動する。
  3. outbox senderとContextStill ingressを停止する。
  4. Experience Recallだけを外し、Timeline、Local Continuity Recall、Context Healthを維持したFast Pathへ戻す。
  5. Sessionless canary自体を停止する場合はSAAA_SESSIONLESS_ENABLEDをOFFにし、 compatibility adapterからprimary Timelineを一つのsynthetic continuity viewとして読む。native eventをlegacy tableへ逆copyしない。
  6. schema v10 tableとlegacy archiveは削除せず、forward-compatible dataとして残す。
  7. migration integrityが破損した場合だけ、write switch前のpre-migration backupからSAAA DBを復元する。

18.3 Required scenarios

  • 初回起動→Session作成なしでprimary Timelineが開き、入力できる。
  • 話題を20回変更→Timelineは分割されず、現在topicへ無関係なMemoryは投影されない。
  • app再起動→Session再開操作なしで直前Turnとactive open loopが復元される。
  • 複数の旧Conversationに分かれた過去発言を尋ねる→全legacy eventを横断してRaw source付きで見つかる。
  • 100,000 messageかつ保存履歴100万token超→Context inputはbudget内、output reserveは維持される。
  • Current messageがRecent tailにも存在→Envelopeには一回だけ入る。
  • CapsuleとRawが矛盾→Rawを優先し、Capsuleをstaleへ遷移して再構築する。
  • 前版Capsuleしか読めない状態→更新を拒否し、Raw sourceから再構築する。
  • ContextがYELLOW→dedupとstale eviction後に再検査してGREENまたはbounded REDへ遷移する。
  • ContextがRED→元Envelopeを送信せず、minimal safe Envelopeを再構築する。
  • 「前に約束した件」→SAAA Continuity Recallを使い、ContextStillを具体的会話検索に使わない。
  • 「昨日SQLiteについて何を話した？」→queryとyesterdayに分離し、確定期間内のanchorと前後Turnを返す。
  • 「先週は何を話した？」→previous_calendar_weekのtime-only searchを行い、未取得分はopaque cursorで続行できる。
  • 「過去7日」と「先週」→前者は168時間のrolling range、後者は前calendar weekとして異なる期間を返す。
  • 日付変更前に「昨日」を検索して日付変更後にcursor続行→初回と同じUTC rangeを使う。
  • 「この前の件」→未定義の相対期間を推測で作らず、keyword RecallまたはUser確認へ戻す。
  • Agent tool schemaを列挙→会話履歴取得はrecall_conversation一件だけで、SQL / FTS / search / window toolは含まれない。
  • 同じqueryを次Turnで再実行→前回のRecall result本文またはreceiptではなく、元のTimeline eventだけが検索候補になる。
  • 「似た失敗の回避手順」→ContextStill Experience RecallからEpisode / Rule / Skillを取得する。
  • 「今後は技術説明を詳しく」→ explicit persistent Profileへ保存される。
  • 「今回は3行で」→ Profileへ保存されず、現在Turnだけに作用する。

  • 失敗原因と回避策がある→failure Episodeが一件作られる。
  • 具体的なclient名を含む成功→client名なしでlessonが保持される。

  • 存在しない過去を尋ねる→「記録が見つからない」と棄却する。
  • Recall Episode内に命令文がある→Policyと現在指示を上書きしない。
  • ContextStill停止中→通常ChatはFast Pathで成功する。
  • Timeline source event削除後→Raw Drill-downはraw-unavailableになる。
