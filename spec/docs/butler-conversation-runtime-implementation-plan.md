# バトラーエージェント会話ランタイム改修計画

状態: 実装前の計画。2026-09-23 時点のリポジトリを確認して作成。

## 1. 目的と成功条件

SAAA の会話を、ユーザーの一発言に対する一回の最終回答から、同じ会話の中でアシスタントが発言・調査・再判断を続けられる形へ改修する。ユーザーも作業中に発言でき、その内容が次の判断へ反映される。応答文、発言の要否、ツールの要否、中間報告の要否は LLM が状況に応じて決める。ランタイムは発言順序、永続化、権限、取消し、予算を保証する。

完了とみなす条件:

- LLM が必要と判断した場合、自然な第一声を会話に表示・保存してからツールを開始できる。不要なら第一声を強制せず即答できる。
- 一つの `run_id` から複数のアシスタント発言を確定でき、各発言を `conversation_id` の履歴で正しい順序に復元できる。
- 実行中のユーザー発言を同じ会話に受理し、次の安全な判断境界で LLM に渡せる。必要なら現在の作業を修正・中止できる。
- 長い作業では根拠のある中間報告を行い、その後もツール使用と判断を続けられる。無意味な定期実況は行わない。
- 関連メモリと短い作業状態を継続判断に使い、古い情報やツール出力をユーザーの新しい指示と取り違えない。
- クラッシュ、再接続、音声再生、プロバイダー切替時に、発言の重複や未確認ツール操作を起こさない。

## 2. 現状と改修理由

| 領域 | 現状 | 改修上の結論 |
|---|---|---|
| 会話履歴 | `conversation_messages` は複数発言を保存できるが、通常の応答経路は実行完了時の回答一件を中心に扱う。 | 中間発言を最終回答と別に確定する経路が必要。 |
| UI 契約 | `RuntimeEvent::Delta` と `MessageCompleted` は一つの実行中テキストと一つの完了回答を想定する。 | 発言 ID ごとの開始・差分・確定を導入する。 |
| LLM ツール往復 | Chat Completions は結果を会話に加えて再呼び出す。外部の Agent Session API 用アダプターにも上限付きの継続ラウンドがある。 | 往復機構は再利用し、複数の可視発言を扱う意味契約を追加する。 |
| ツール選択 | SQLite の `tool_selection_catalog`、revision、grant、decision と discovery 経路がある。組込みツールは別に提供される。 | カタログを唯一のツール台帳と誤認しない。両方から認可済み候補を提示し、使用判断は LLM に任せる。 |
| 入力 | UI は実行中の通常入力を止める。音声は一部を後続要求としてキューに積む。役割ルーティングには `rr_inputs` がある。 | 全会話共通の追加入力受付と消費記録が必要。役割ルーティングの台帳は置き換えない。 |
| メモリ | 関連記憶の検索、context window、continuation がある。`context_segments` は条件付き経路。 | 検索メモリは再利用する。進行中の作業状態には経路に依存しない小さな正本を設ける。 |
| 音声 | 確認・進捗・最終回答のキューや TTS がある。 | 可視発言と音声を同じ発言 ID に結び、古い発言の再生を制御する。ASR 経路は変更しない。 |

主な参照: `src-tauri/src/runtime/turns/execute_turn.rs`、`src-tauri/src/providers/chat_completions/mod.rs`、`src-tauri/src/providers/agent_session/sse.d/01.rs`、`src-tauri/src/providers/stream/agent_dispatch.rs`、`src-tauri/src/runtime/conversation_prepare.rs`、`src-tauri/src/ipc_contract.rs`、`src/features/chat/useConversationTurn.ts`、`src/features/chat/conversationTurnControls.ts`。

## 3. 境界と設計判断

### 3.1 新しいセッションを導入しない

`conversation_id` が会話の継続単位、`run_id` が有限の実行単位、`message_id` がユーザーまたはアシスタントの可視発言単位である。長い依頼を複数の実行に分ける場合は作業記録の `work_id` で引き継ぐ。`work_id` は会話の代替単位ではなく、その依頼の状態を指す ID である。`AgentSession` は既存の外部プロバイダー API 名であり、SAAA の会話単位ではない。プロバイダー内部の `provider_sessions` も対話の正本にしない。後続ユーザー発言は同じ会話に属し、進行中の作業に取り込まれた場合だけその `run_id` と関連付ける。

### 3.2 自然さを LLM に、順序をランタイムに置く

「最初は必ず挨拶」「15 秒ごとに報告」などの台本は作らない。LLM は答える、発言して続ける、ツールを使う、質問して待つ、完了する、を選ぶ。ランタイムは LLM が選んだ可視発言を確定してから対応するツールを始める。第一声とツール利用の組合せは任意であり、不要な予告を作らない。

### 3.3 プロバイダー共通の意味契約

プロバイダーごとの wire 形式を UI に漏らさず、内部に次の行動を表す型を設ける。

| 行動 | 意味 | ランタイムの処理 |
|---|---|---|
| `SpeakAndContinue(text)` | ユーザーへ発言し、作業を続ける。 | 発言を確定し、次の LLM 判断へ進む。 |
| `UseTool(call, optional_preface)` | ツールを使う。必要なら先に発言する。 | 発言があれば確定後にツールを認可・実行し、結果を次の判断へ渡す。 |
| `Answer(text)` | 今回の回答を完了する。 | 最終発言を確定し、実行を完了する。 |
| `AskAndWait(text)` | ユーザーの返答が必要。 | 質問を確定し、実行を待機または完了して入力を待つ。 |

これは文章テンプレートではなく、出力の用途と制御の区別である。まず既存の Chat Completions と Agent Session の出力をこの契約へ変換できるか fixture で確かめる。Chat Completions の `content + tool_calls` は `optional_preface` にできる。ツール専用出力を要求する経路では、LLM が選んだ発言を独立した `SpeakAndContinue` ラウンドとして確定し、次ラウンドでツールを使う。ランタイムが勝手に定型の予告を捏造しない。プロバイダーがどちらも安定して表現できない場合は、その経路を対応済みと扱わず、実機評価で契約を調整する。

### 3.4 正本と権限

確定済みユーザー・アシスタント発言は `conversation_messages` を正本とする。新しい会話イベント台帳は発言、実行、ツールの順序と配信再開位置を記録するが、発言本文の第二の正本にしない。`rr_events` と `context_entries` はそれぞれ役割ルーティングとコンテキスト投影の用途を維持する。ツールを実行する直前には、提示時の grant だけで済ませず現在の権限・schema revision・scope を再検証する。承認が必要な操作は既存の承認境界を通す。

### 3.5 比較した案と採用理由

| 案 | 評価 |
|---|---|
| SystemContext だけで第一声と継続を指示する | 変更は小さいが、ツール専用出力、複数発言の永続化、実行中入力を保証できないため不採用。 |
| 固定の確認文と時間ごとの中間報告をホストが生成する | 発言順序は簡単だが、不要な予告と空疎な実況を生むため不採用。障害などの事実通知には限定利用する。 |
| すべてを役割ルーティングの recipe に載せる | 既存 recipe は有限の既知形であり、会話全経路の任意継続には合わないため不採用。既存の権限・監査・音声機能は再利用する。 |
| LLM の行動選択と共通の会話記録を組み合わせる | 自然な応対と検証可能な順序を両立できる。プロバイダー差と移行の負担があるため段階的に実装する。 |

## 4. データとイベントの実装案

新規または拡張する最小の永続契約:

1. `conversation_events`: `conversation_id` と単調増加する `seq`、`run_id`、イベント種別、関連 `message_id` / tool invocation ID、時刻を記録する。UI の再接続時は `seq` から再生する。可視発言確定イベントと `conversation_messages` の INSERT は同じ SQLite transaction で行う。
2. `conversation_run_inputs`: 実行中に受理したユーザー `message_id`、対象 `run_id`、受理順、状態（未処理・取り込み済み・後続作業へ移管）を記録する。ユーザー本文は複製しない。複数の発言が届いても順番を失わない。
3. `conversation_work_state`: `work_id`、`conversation_id`、現在の `run_id`、revision、現在の目的、確認済み事実の参照、未解決点、次の判断候補、状態を持つ小さな JSON。非公開の chain of thought を保存しない。ツール結果本文や永続的権限も保存しない。更新は revision 条件付きで行う。
4. `conversation_messages` には必要最小限の `run_id` / 発言用途の関連を加えるか、イベント台帳から参照する。既存の会話ページ取得、メモリ投影、移行済みデータを壊さない方式を migration 試験で選ぶ。

IPC は発言単位の `messageStarted`、`messageDelta`、`messageCommitted` と、ツール・待機・実行完了の状態イベントへ拡張する。`MessageCompleted` をいきなり削除せず、既存 UI と互換な移行期間を設ける。UI は受信イベントを一時表示するが、復元と確定状態は SQLite に問い合わせる。イベント再送には `(conversation_id, seq)` と `message_id` で重複排除を行う。

## 5. 一回の作業の流れ

1. 入力を会話に永続化する。現在の設定、関連履歴・メモリ、組込みツールと SQLite discovery の認可済み候補を集める。候補選定が失敗した場合は利用できる範囲を明示し、使えないツールを使えたものとして続けない。
2. LLM が最初の行動を選ぶ。即答でも、可視発言でも、確認質問でもよい。`UseTool` の予告があれば発言を先に transaction で確定する。前面 UI が接続している場合は `messageCommitted` を描画した受領通知を待ってからツールを始める。音声応答では当該発言の再生開始を確認する。受領通知には短い上限を設け、切断・非表示・TTS 障害では「保存済みだが提示未確認」を記録してツールを続けるか、発言が不可欠な操作なら待機する。再生終了までは待たない。これにより通常時はユーザーが第一声を受け取ってからツールに進み、切断時に無期限停止しない。
3. ツール結果を監査記録に結び、次の LLM 判断へ戻る。次ラウンドの直前には `conversation_run_inputs` の新着、権限・scope、残り時間と予算を読み直す。
4. LLM が中間報告を選べば可視発言として確定する。ランタイムは長時間無言や新着入力を「再判断すべき情報」として渡すが、固定文を自動挿入しない。必要な情報がない、ツールが失敗した、ユーザーの判断待ち、といった事実を LLM が説明できるようにする。
5. `Answer`、`AskAndWait`、取消し、失敗のいずれかで今回の `run_id` を終える。`AskAndWait` は作業状態を `awaiting_user` にして現在の実行を終え、次のユーザー発言から新しい実行を開始する。作業状態の終端と最終発言の確定を整合させる。待機・失敗時に実行済みの操作を未実行と偽らない。

時間またはツール予算が近づいた場合、LLM に残り予算と作業状態を渡して報告・完了・継続の判断機会を与える。継続を選んだら、作業記録を確定して今回の `run_id` を終え、同じ `conversation_id` と `work_id` を参照する次の `run_id` を起動する。起動は永続的な一回限りの継続予約から行い、アプリ再起動で重複起動しない。継続全体にも累積の時間・費用上限を設け、上限を超えたら現在までの結果と必要な次の判断を報告して止まる。ユーザーからの新着指示は継続起動前に取り込む。

実行中のユーザー発言は、少なくとも「新しい依頼」「現作業の変更」「状況質問」「中止」を区別して扱う。ただし分類だけで破壊的な操作を許可しない。文意が曖昧なら LLM が確認する。処理中のツールを止めるかはそのツールの取消し可能性で決める。完了済みの結果と新着指示が競合したら、新しい指示を次のラウンドへ渡し、既存の副作用を明示する。

## 6. メモリと中間報告の基準

- 関連メモリは現在の依頼との関係で検索し、出典・時点・信頼境界を付けて渡す。検索結果は指示ではなくデータである。
- 作業状態は事実と仮説を分ける。事実にはツール結果や会話発言の参照を付ける。再起動後は参照の有効性を検証し、未確認の作業を自動再実行しない。
- SystemContext は「ユーザーに役立つ変化を短く報告し、進捗のない定期実況はしない」「今のユーザー指示を優先する」「必要に応じて再検索する」を規定する。報告頻度の上限、timeout、予算はコードで規定する。
- LLM の中間報告判断が遅い場合、ランタイムは経過時間・未解決点・新着入力を次の判断に含める。表示文面を機械的に生成する最終手段は障害・待機の事実通知に限定し、LLM 発言と区別する。
- 音声では TTS のキューを発言 ID に結び、最終回答が先に確定した場合は古い進捗音声を再生しない。文字表示と音声が異なる作業状態を示さないようにする。

## 7. 実装フェーズと各ゲート

| フェーズ | 変更の中心 | 完了ゲート |
|---|---|---|
| P0: ベースライン | 既存の短い質問、検索、複数ツール、音声、途中入力、失敗・取消しを fixture と実機で記録する。 | 現状の発言順序、初回表示時間、失敗時の保存状態を再現できる。 |
| P1: 永続契約 | 会話イベント、複数発言、入力関連、作業状態の migration と repository。 | 旧 DB をコピーした migration、逆順・重複・クラッシュ境界のテストが通る。 |
| P2: 行動変換 | provider adapter が `SpeakAndContinue` 等へ変換し、発言確定後にツールを実行する。 | 即答・発言→ツール・ツール→再判断・確認待ちを資格情報不要の fixture で検証する。 |
| P3: 実行中入力 | 同じ会話に追加入力を保存し、LLM 呼出し境界で取り込む。 | 複数入力、取消し、同時到着、処理中ツール、role routing 有効・無効を検証する。 |
| P4: UI と音声 | 発言 ID 別の表示、再生、再接続、TTS キューを実装する。 | 複数発言が別吹き出しとなり、リロード後も順序が一致する。音声が重複しない。 |
| P5: メモリと報告 | 関連メモリ、作業状態、長時間タスクの再判断を接続する。 | 中間報告が事実に基づき、進捗のない連呼をせず、復旧後の状態が一致する。 |
| P6: 既定化 | プロバイダー別の実機評価、品質比較、段階的な既定化。 | 下記の全ゲートに合格し、劣化時は旧経路へ戻せる。 |

P1 から P5 は小さな縦断実装に分ける。新機能は設定ではなく内部 feature flag で閉じた状態から始め、既存の一問一答経路を P6 まで維持する。role routing の有限 recipe を無理に任意ループへ拡張せず、共通会話イベントと入力受理で接続する。新規ライブラリ、全 provider の一括書き換え、無制限の常駐推論は行わない。

## 8. 検証計画

### 決定的な試験

| ケース | 観測する合格条件 |
|---|---|
| 検索不要 | 不要な予告やツール呼出しがなく回答する。 |
| LLM が予告して検索 | 発言の SQLite commit とイベント seq が tool dispatch より前。前面 UI の描画受領後に dispatch し、発言は最終回答に重複しない。 |
| 表示・音声の障害 | 描画受領または音声開始が得られない場合に上限時間で収束し、提示未確認を記録する。発言が不可欠な操作は勝手に進めない。 |
| LLM が予告せず検索 | 台本による定型発言を捏造しない。ツール実行は契約・権限内。 |
| 結果不足 | 追加ツールを選べる。結果が十分なら停止する。 |
| 長時間タスク | 作業状態に基づく中間報告後も実行が続く。既知の事実と未確認事項を混同しない。 |
| ユーザー追加入力 | 同じ会話に直ちに記録され、一度だけ LLM に渡る。変更・状況質問・中止を区別できる。 |
| 権限・scope 変更 | 古い tool offer で実行しない。失敗と継続判断を記録する。 |
| 切断・再起動 | 同じ message/tool operation を二重確定・二重実行しない。未確定操作は unknown として扱う。 |
| 予算を超える長い作業 | 作業記録と累積予算を引き継いで次の `run_id` に一度だけ継続する。上限時は報告して止まる。 |
| メモリ競合 | 古いメモリより現在のユーザー発言と新しい根拠を優先する。 |
| 音声 | 第一声・中間報告・最終回答の順序を守り、遅れた進捗を再生しない。 |

失敗した試験は同条件で一度再現し、イベント seq・DB 状態・provider request/response を照合して修正する。flaky な実機試験だけで判定せず、対応する deterministic fixture を追加する。live provider は P6 の独立した評価レーンとし、資格情報なしのテストを通すために設定を消したりプロバイダーを置き換えたりしない。

### 実行コマンドと期待結果

- 各縦断変更: `bun test tests/system-context.test.ts`、該当する frontend / Rust の targeted tests、`bun run s11tnext:check`。生成物と行動契約が一致すること。
- 初回応答を変更するフェーズ: `bun run quality:check` と macOS の `bun run desktop:smoke`。後者には読み込まれた snapshot と primary conversation が必要。初回表示・予告→ツールの順序と通常回答の劣化がないこと。
- 音声に触れるフェーズ: 関連する会話・TTS 試験を実行する。ASR 保護ファイルを変更する必要が生じた場合だけ、AGENTS.md 指定の ASR 試験と freeze 手順を追加する。
- 統合完了: `bun run check`、旧 DB のコピーで migration、実機のテキストと音声の短い依頼・長い依頼・追加入力を確認する。失敗時は P6 の既定化を止め、記録した契約違反を修正して同条件で再実行する。

`critical-path-freeze.json` の初回応答ドメインに保護されたファイルを変更する際は、対象回帰試験後に変更理由を記録し、`bun run freeze:accept:initial-response --reason "..."` でそのドメインだけを更新する。freeze check は常に通す。ASR は無関係な変更として触れない。

## 9. 設計評価と残るリスク

| 評価観点 | 判定 | 理由と対応 |
|---|---|---|
| LLM の自然さ | 良好 | 発言・ツール・報告を固定順序にせず、LLM の行動選択に置いた。行動別の出力品質を fixture と実機で評価する。 |
| 第一声の順序 | 実現可能 | DB commit とイベント送信に加え、接続中 UI の描画受領または音声再生開始を tool dispatch 前に確認する。切断時は提示未確認を記録し、操作の性質に応じて継続・待機を分ける。 |
| プロバイダー差 | 主要リスク | ツール専用形式では「発言して続行」に別ラウンドが必要。P2 で経路別 fixture を先に作り、未対応経路を黙って成功扱いしない。 |
| 途中入力 | 主要リスク | 現在の UI は一実行前提。DB 受理と消費の exactly-once、取消し可能性、role routing との整合を P3 の独立ゲートにする。 |
| メモリ | 良好だが節度が必要 | 作業状態に検証可能な事実と参照のみを持たせる。古いメモリによる指示上書きと長い非公開思考の保存を避ける。 |
| 移行・復旧 | 主要リスク | 新台帳と既存履歴の二重正本を避け、旧 DB コピーとクラッシュ境界を検証する。 |
| 性能 | 要測定 | 別ラウンドの第一声は初回表示を早めても総遅延と費用を増やし得る。P0 の実測と P6 の比較で判断する。 |

この案の評価は「実装可能で、現在の要求に対して最も整合的。ただし provider 差・入力競合・移行が未検証」である。P0/P2/P3 の結果で契約を調整する余地を残す。SystemContext の追加だけで達成したと判定しない。

### 計画を見直す判定点

P0 では既存の短い回答の初回表示時間・総完了時間・ツール回数を固定シナリオで採取する。P2 では同じシナリオについて、予告の適切さ、発言とツールの順序、回答の正確さ、総時間、provider ごとの失敗率を比較する。P3 では追加入力の取り込み遅延と重複・取りこぼしを測る。短い回答の品質や速度を大きく損なう、または複数経路で行動変換が安定しない場合は P6 の既定化を行わず、プロトコルを見直す。数値の許容幅は P0 の実測分布を見て P2 着手前に固定し、結果を見た後で都合よく変更しない。
