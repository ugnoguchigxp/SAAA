会話ランタイム + MCP推論サービス MVP実装計画

作成日: 2026-09-12。状態: 実装前の提案。基準: 5a91753 と作成時のworking tree。本書の作成は機能の実装・性能検証・リリース完了を意味しない。

1. MVPで確かめること

音声要求を受けたら短く反応し、MCP経由の推論結果を正しく読み上げる。ユーザーの停止操作や追加入力で古い処理を中断し、古い回答を再生しない。最初に定型相槌版を成立させ、その後に2B程度の分類モデルを比較評価する。大型モデルの回答を小型モデルで言い換える工程は設けない。

最初の利用例は「この会話で説明した条件を踏まえて、SQLiteとPostgreSQLを比較して」のような、渡された文脈だけで判断できる依頼とする。「今のDB構成」など、実際に取得していない情報を知っている前提で回答しない。

MVP-B: 比較実験 2B程度の意味分類を追加 CR-06の採否条件で採用または不採用を決定。不採用でもMVP-Aは成立

3. 実装範囲と責務

  ├─ 文脈の投影、版管理、結果検証、履歴保存
  ├─ 任意の小型分類モデル（MVP-B）
  └─ MCP tools/call: reasoning.answer
       ↓
     Reasoning Service（独立プロセス）
       ↓
     設定済みのLocal LLM Harness / Provider
       ↓
     検証済みResponse Plan + speechText
       ↓

  • SAAAが決めるもの: 発話開始と停止、委譲、締切、文脈、結果採用、保存、再試行。小型モデルは助言のみ。
  • Reasoning Serviceが決めるもの: 指定された制約下での回答、確認質問、不足情報の明示。モデル選択と常駐はProvider側の運用責務。
  • 対象: 明示的に有効化した音声会話。通常のテキスト会話、Coding、Meeting、Situationの自動介入は既存経路を維持する。
  • 範囲外: DB移行、新たな長期記憶、汎用MCP設定画面、モデル起動管理、Cloud自動フォールバック、任意ツール実行、音声認識方式の置換、生成UIとの統合。
  • 2Bへの自由回答許可、数値confidenceによる自動承認、相槌の繰返し生成、推論内部テキストの読み上げは行わない。

「検索・操作を含む要求を従来と同等に処理する」ことはMVP-Aの保証に含めない。Serviceは外部ツールを持たず、渡された文脈で足りなければ確認または不足を返す。実験経路であることを表示し、必要な場合は利用者が通常経路へ切り替えられるようにする。

4. 配置と有効化

提案する配置は、SAAA側にsrc-tauri/src/runtime/conversation_controller/とsrc-tauri/src/providers/reasoning_mcp/、独立サービスにservices/reasoning-mcp/である。いずれも新設候補であり、存在する実装を示すものではない。サービスは独立Rust crateを基本とし、MCP SDKの版と必要な依存はCR-01で疎通確認して固定する。SAAA本体からサービスやモデルを起動しない。

5. reasoning.answer v1契約

新規の推論接続ではMCP 2025-06-18を最初の相互運用プロファイルとし、Streamable HTTPでinitialize、initialized通知、tools/list、tools/call、キャンセルを確認する。これは最新版の指定ではなく、本MVPの固定した検証対象である。対応しないServiceは接続検証で失敗させる。既存ContextStill接続の版は維持する。

出力はMCPのoutputSchemaとstructuredContentで契約化し、互換用のtext blockには同じオブジェクトをJSONで格納する。SAAAはstructuredContentだけを回答の正本として検証する。これらはMCPの構造化出力機能であり、モデル生成の正しさを保証するものではない。MCP Tools仕様

5.1 入力例

{
  "schemaVersion": "reasoning-answer-v1",
  "conversationId": "conversation-1",
  "turnId": "run-2",
  "requestId": "request-3",
  "contextRevision": 4,
  "request": "この会話で説明した用途ならSQLiteとPostgreSQLのどちらが適切？",
  "context": {
    "messages": [{"role": "user", "content": "単一ユーザーでローカル運用です"}],
    "evidence": [],
    "truncated": false
  },
  "constraints": {"language": "ja", "localOnly": true, "maxSpeechChars": 240},
  "budget": {"timeoutMs": 15000}
}

turnIdは既存run_idを利用し、新しい永続ターンID体系を作らない。requestIdは各呼び出しで新規発行する。contextRevisionは会話ごとのランタイム内カウンタとし、追加入力、停止、会話切替で採用権を失効させる。再起動をまたぐ結果受理はしない。

文脈は既存の投影と制約を再利用し、現在要求はrequestに一度だけ入れる。履歴内の同一要求は重複させない。最新の明示条件を優先し、取得済み根拠にはIDと由来を付ける。MVP-Aは新しい検索を開始しない。根拠は命令へ昇格させず、system方針はServiceの固定テンプレートとして別管理する。

5.2 正常出力例

{
  "schemaVersion": "reasoning-answer-v1",
  "conversationId": "conversation-1",
  "turnId": "run-2",
  "requestId": "request-3",
  "contextRevision": 4,
  "intent": "answer",
  "speechText": "この会話で挙げた条件なら、SQLiteが候補です。単一ユーザーのローカル用途で、運用を簡単にできます。同時書き込みなどの要件は別途確認が必要です。",
  "keyPoints": ["単一ユーザー", "ローカル運用"],
  "evidenceIds": [],
  "limitations": ["実際のDB構成は取得していない"]
}

intentはanswer、clarify、insufficient_contextの3種類。clarifyのspeechTextは一つの確認質問、insufficient_contextは不足事項を伝える文章とする。confidenceとcanSpeakImmediatelyは設けない。これら3種類は成功した回答結果であり、接続障害とは区別する。

初期上限は入力全体64KiB、応答全体16KiB、履歴32件、evidence8件、speechText240 Unicode文字、keyPoints5件・各160文字、limitations5件・各160文字とする。文字数とUTF-8 byte上限は別々に検証する。さらにProviderの実context windowから出力枠を差し引いたtoken予算で入力を制限する。現在要求だけで上限を超える場合は黙って切らずinput_too_largeとする。

全objectで未知フィールドを拒否し、必須値・enum・各上限・空本文・ID一致・evidenceIdsの参照先を検証する。Providerの完了理由が途中打切り、終端欠落、tool callの場合は成功にしない。Serviceはモデル出力を検証し、不正JSONを最大1回だけ同じ締切内で再生成できる。SAAAは壊れたJSONから本文を抽出して読み上げない。

初期版のChat本文はspeechTextと同一とし、別の要約生成はしない。keyPoints等は検証・評価用のメモリ内情報とする。長い説明や途中のトークン読み上げは後続とし、最初の版では完全な結果検証後にTTSへ渡す。

6. 会話・発話ライフサイクル

推論状態と再生状態を分ける。推論はidle、pending、accepted、failed、cancelled。再生はsilent、ack_pending、ack_playing、answer_pending、answer_playing。並行する相槌を一つの排他的action enumに押し込まない。状態更新と結果採用は既存run管理に結び付けた一つの直列化された更新経路で行う。

  1. 確定ASRのutteranceを一度だけ受理・保存し、runと版を確定する。文脈構築と並行して相槌のタイマーを予約する。相槌生成のためにLLMを待たない。
  2. 既存の発話権・Meeting・mute制約を確認する。受理後250msで未完了なら「確認します」を最大1回だけ再生する。実音響の安定性を確認するまではキャッシュ音声を必須にしない。
  3. 本回答が相槌開始前に届けば相槌を取り消す。再生中なら未再生の相槌を取り除き、既に始まった短い相槌の終了後に本回答を流す。二重再生しない。
  4. 結果採用時、TTS enqueue時、実再生開始直前の各時点でrun・request・版・発話権を確認する。result到着とcancelが競合しても失効した音声を開始しない。
  5. 停止または追加入力では、先に旧版を失効させ、相槌タイマー・TTSキュー・再生を停止する。その後にMCPキャンセルを送る。サーバーの停止応答を待って画面や音声を止める設計にしない。
  6. 追加入力を旧要求の次のuser messageとして保持し、新runで会話全体を再投影する。旧要求の文字列を推測で上書きしない。旧runはcancelled、新runは独立した終端を持つ。
  7. 表示・保存済みの回答への割り込みでは履歴を消さず、再生だけを停止する。採用前に失効した結果はassistant回答として保存しない。

MCPキャンセルは進行中requestのIDを指定する通知として送り、ServiceからProviderの生成キャンセルと接続解放へ伝える。遅着結果の採用禁止はSAAA側でも保証する。MCP Cancellation仕様

相槌は通常のassistant Deltaに混ぜず、一時的なspeech itemとして扱う。通常のmessageCompletedやrun終了を発行しない。TTSのspeechStarted/Endedと入力休止・再開は既存の管理を通す。親runの下で相槌と本回答を識別するspeech item IDを追加し、生成IPC型が変わる場合は型生成とUI consumerを同時に更新する。

MVP-AではTTS中の音声割り込みを保証しない。停止ボタン・テキスト追加入力は必須とし、音声入力が再開している推論待ち期間の確定発話も処理する。相槌中に声を重ねたケースは実機評価で取りこぼしとして記録する。入力休止を外す変更には、エコー・誤VAD・話者照合を含む独立した検証が必要になる。

7. 締切・障害・保存

初期値として推論全体の締切を要求受理から15秒、接続検証を3秒とする。Providerの待ち行列と再生成も15秒に含め、SAAAの単調時計を最終判定に使う。1会話につき有効な推論は1件、MVP-Aではアプリ全体も同時1件とし、Serviceはcancel後も残る旧計算を無制限に積まない。

入力例のtimeoutMsは上限値であり、実際の送信時には文脈構築などの経過時間を差し引いた残り時間を渡す。Serviceで生成を開始する時点でも待ち行列の経過時間を差し引く。MCP接続のやり直しによって締切を延長しない。

9. 検証・採否基準

A0は現在の単一モデル経路、A1は定型相槌+MCP、A2は分類モデル+MCPとする。A0/A1の推論モデル、量子化、sampling、入力文脈、出力長上限を揃え、起動直後とwarmを分離する。warmは50固定ケースを3回ずつ実行し、順序を交互にする。既存の品質評価60ケースも回帰確認に使い、MCPを通らない既存runnerだけで新経路の品質を証明しない。

10. MVP-B: 小型モデルの追加条件

2B程度のモデルをProvider側で常駐させ、最初はshadowで分類結果だけを記録する。出力はroute: delegate | simple_replyとreplyKey: greeting | acknowledgement | nullに限定し、自由文とツール呼び出しを受け取らない。相槌は引き続きランタイムが予約する。

simple_replyを採用できるのは、ランタイムの厳格な全体一致ルールで既に許可された挨拶・受領応答だけとする。条件追加や質問が混在する場合はdelegateへ戻す。小型モデルによる未許可要求の格下げを認めないため、この段階の分類による速度改善は限定的であることを明示する。

分類の上限は受理から150ms。不正出力・切断・期限超過はdelegateへ戻す。比較試験では意味が紛らわしい100例を3回実行し、委譲漏れ0件、回答品質の重大回帰0件、最初の音声p95のA1比増加100ms以内を要求する。同じGPUで大型モデルが稼働中の条件も測る。

採用には、上記に加えて50組の会話比較を順序を伏せて利用者が評価し、A2が好ましい割合60%以上となることを初期基準とする。改善がなければA1を維持する。2Bを導入したという事実をMVPの成功条件にしない。自由回答や広い意味ルーティングへ拡張する場合は、別途許可範囲と誤分類の評価を設計する。
