# SAAA Role Routing 実装計画

更新日: 2026-09-20
状態: 計画。ランタイム未実装。

## 目的

会話を維持しながら、応答・思考・ツール利用・発話を適切な担当に振り分ける。Semantic Routerは導入しない。役割と物理モデルを分離し、既存メモリー、ツール管理、ワールドモデルを利用する。

| 役割 | 初期担当 | 境界 |
| --- | --- | --- |
| 会話維持 | 1.2B | 相槌、受付、実際の状態に基づく進捗。実行権限や最終結論を独自に追加しない |
| 通常推論 | Qwen 27B | 調査、判断、回答作成、許可されたツールの利用 |
| 高難度処理 | Codex SDK経由のSol | 能力、設定、送信先制約を満たす依頼を委任 |
| ツール専門処理 | 将来の任意モデル | 限定した目的の呼び出し提案。既存の実行ゲートを迂回しない |
| 発話 | 共通TTS | 思考担当が確定した回答を同じ音声で再生 |

モデル名はユーザー指定の役割割当であり、有効な接続モデルID、API能力、常駐可否は実装時に確認する。

## 既存コードから分かった境界

- `src-tauri/src/runtime/conversation_controller/mod.rs`: 推論と遅延付き相槌を並行実行する既存経路がある。現行の送信契約はlocal-onlyで、コーディング実行不可を明示している。
- `src-tauri/src/runtime/reasoning_ack.rs`: 相槌の再生期限、親キャンセル、最終回答との発話順序を扱う。
- `src-tauri/src/runtime/turns.rs`: 通常会話、音声推論、Codexの分岐がある。役割Routingは既存経路の責務を整理して接続する。
- `src-tauri/src/runtime/codex_turn.rs`: 現行Codex経路は有効設定とワークスペースを必要とする。一般の難問すべてに使えると仮定しない。
- `src-tauri/src/tool_selection/gateway.rs`: ツール検索、説明、実行の入口がある。専門モデルもこの実行管理へ接続する。
- `crates/personal-state-core/src/world/runtime_frame.rs`: WorldFrameは時点の観測であり、実行管理の正本ではない。Routingの権限付与や完了判定を観測だけで行わない。

上記には作業中の未コミット変更を含む。実装時は最新の契約を再確認し、他の変更を上書きしない。

## Routingが所有する判断

1. 送信先制約、必要能力、設定状態から担当候補を限定する。
2. 通常はQwenへ委ね、明確な簡易応答のみ会話側で完了する。不明な入力を1.2Bの自由回答で完了しない。
3. 明示的な高度処理要求、既知のタスク種別、Qwenの構造化した委任要求を高難度処理の候補にする。Qwen自身の確信度だけで決めない。
4. Solが利用不可またはクラウド送信不可なら、許可されたQwen経路か実行不能の説明へ戻す。禁止された送信先へ自動迂回しない。
5. 作業継続中は担当を維持する。委任回数と時間に上限を設け、担当の往復を防ぐ。
6. 音声出力の所有者を一つにし、相槌と最終回答を重ねない。最終回答は思考担当が作り、共通TTSへ渡す。

## 引き継ぎと並行処理の契約

会話ID、依頼ID、実行ID、委任ID、入力の改訂番号で結果を関連付ける。目的、ユーザーの条件、決定事項、未完了作業、参照する記憶、ツール実行結果を既存の正本から組み立てる。モデルごとの内部思考やKVキャッシュの移植は行わない。

追加発言は条件追加、別依頼、中止、会話継続に分ける。曖昧な場合は確認する。更新を受け入れたら改訂番号を進め、古い結果は最新回答として発話しない。実行済みの副作用は破棄せず記録し、更新後の処理へ引き継ぐ。

親の中止は子処理と発話へ伝播する。中止要求と上流の停止確認を区別する。結果保存、発話開始、中止の競合を既存ランタイムの所有者で直列化する。再試行で副作用を伴うツールを無条件に再実行しない。

## 可変な定義と将来の学習ランキング

役割名とモデルIDを分離する。初期の1.2B / Qwen / Solは設定上の割当であり、モデル名によるコード分岐は作らない。役割、接続先、能力、委任可能な組合せ、発話方針、時間・費用上限をバージョン付き設定として管理する。定義変更は検証後に反映し、実行中の依頼は開始時の設定版を維持する。ただし権限撤回や送信禁止などの制約変更は実行直前にも再確認する。

選択は候補生成、制約適用、ランキング、継続性の判断、実行と観測に分離する。ランキングの上位でも権限、送信先、文脈容量、ツール契約を満たさない候補は実行しない。現担当の維持、切り替えコスト、作業中の固定も明示的に扱う。

ランキング対象はモデル単体だけでなく、事前定義した有限の実行手順を含める。例えばQwen単独、QwenからSolへの委任、Qwenとツール専門担当の組合せ。MLが任意の実行グラフや権限を生成する方式にはしない。

ランカーの境界は候補一覧、必要最小限の状況特徴、候補別スコア、不確実性、判断理由、ランカー版で定義する。初期は決定的なルールを実装し、将来は統計やMLに差し替える。ランカー停止、未知のモデル、データ不足では初期ルールへ戻す。設定変更と学習モデル更新は別々に検証・ロールバックできるようにする。

### 後ろで保持する情報

- 利用傾向: 依頼の種類、明示的な速度・品質の好み、音声かテキストか。利用回数を品質評価と同一視しない。
- 結果の評価: 課題達成、ツール結果の検証、修正要求、再実行、待ち時間、費用。API成功だけを課題成功としない。
- 選択時点の証跡: 候補と除外理由、選択担当・手順、方針版、改訂番号、担当維持の理由。選んだ候補の結果しか得られない偏りを明示する。

特徴と結果は依頼・委任のIDで紐付ける。中止は一律に失敗とせず、理由を区別する。複数担当の結果を最終担当だけの成績にしない。会話本文を学習ログへ無制限に複製せず、既存の保存・削除・送信先制約に従う。WorldFrameは現在の特徴の一部として利用し、過去の観測を実行許可の根拠にしない。

### 学習の導入順序

R1で設定契約と差し替え可能なランカー境界、R2で委任も含む評価イベント、R3で集計と推薦のみのシャドー比較を用意する。学習モデルの訓練と本番適用は、データが揃った後の追加段階とする。

バックグラウンド集計、オフライン学習、シャドー評価、限定適用の順で進める。固定ルールとの比較で品質・遅延・制約遵守を確認してから実経路へ反映する。実トラフィック上の探索は別途設計し、副作用のあるツール実行を無条件に探索対象にしない。安全に再現できるタスクや検証環境で比較して選択バイアスを補う。品質・速度・費用の重みは可変にし、「ベスト」を単一の固定指標にしない。

## 3段階の実装

### R1: 会話維持と通常推論

役割設定、純粋なRouting判断、委任の識別情報を追加し、1.2BとQwenを実際の会話経路へ接続する。既存相槌を障害時の代替として利用する。Qwenの最終回答は1.2Bで再要約せず共通TTSへ渡す。

完了条件: 受付から推論、結果保存、発話まで一つの依頼として動作する。会話側の失敗が推論結果を失わせず、重複発話や二重保存を起こさない。固定モデル経路へ設定で戻せる。

### R2: Sol委任と会話中の更新

既存Codexアダプターの能力とワークスペース条件を明示し、許可された依頼を委任する。追加条件、中止、タイムアウト、古い結果の抑止、実行済みツール結果の引き継ぎを実装する。既存の別Codexタスクへメッセージを送る方式は使わない。

完了条件: 高難度依頼の実経路が動作し、処理中の追加発言を受け付ける。権限制約を守り、古い結果を最新回答として発話せず、ツールを二重実行しない。

### R3: 継続性と遅延の評価

日本語会話で、短い追加指示、言い直し、中止、ツール待ち、担当障害、クラウド禁止を検証する。Routing理由、担当、改訂番号、受付時間、最終回答開始時間、委任回数を記録する。本文の追加ログは既存のプライバシー方針に従う。

固定Qwen経路と比較して品質、最初の相槌までの時間、最終回答までのp50/p95、リソース使用量を測る。相槌の速さと回答の速さを混同しない。速度の受け入れ値はベースライン測定後に固定し、測定なしでシームレスさを保証しない。

完了条件: 主要な会話シナリオが通り、改訂済み回答の誤発話、二重実行、禁止送信先への転送がテストで防止され、実機測定結果と制限が残る。

## 検証方法

各段階でRoutingの判定表を単体テストし、制御可能な模擬Providerで結果到着とキャンセルの順序を入れ替える統合テストを行う。音声再生失敗、モデル応答遅延、追加条件の同時到着を含める。該当Rustテスト、`bun run check:local`、`bun run test:rust-packages`を変更範囲に合わせて実行する。実Providerの確認はオフライン検証と分け、モデルIDと接続能力を確認してから行う。

## 追加検証と対象外

Needle3等のツール専門モデルはR1〜R3の完成条件に含めず、同じ実行ゲートに接続する比較実験として追加する。成功率、引数の正確さ、総遅延をQwenの直接利用と比較する。

生成中のトークン列のモデル間移植、任意のエージェント内部状態の移植、オンライン学習、Semantic Router自体の組み込みは対象外。Semantic Routerの設計を参考にする場合は、判定材料の分離、担当維持、切り替えコスト、判断理由の観測を中心にする。コードを転用する場合は該当版の実装とライセンスを確認する。

## 会話反応による再検討と夜間学習

### 定型行動と柔軟な解釈

会話反応の解釈と実行行動を分離する。解釈には対象の回答ID、根拠となる発言箇所、説明不足・条件訂正・結論への疑問・担当変更要求・曖昧という区分と不確実性を残す。「本当に？」だけで誤答やモデル能力不足と確定しない。

初期の行動集合は、根拠説明、確認質問、同担当で再検討、別担当で再検討、独立評価、指摘に基づく修正、上位モデル利用の提案、回答確定とする。行動の定義と許可する遷移はバージョン付き設定で拡張可能にする。解釈モデルからの自由な指示を直接実行しない。

Qwen回答への疑問からSolへ再検討を委ねる、Sol回答をQwenに評価させてから修正する、未解決点を明示してAstra利用を提案する、といった手順を登録する。Astraの実利用は有効なモデルID・接続能力・送信先制約・費用方針を確認してから行い、提案を利用の許可と混同しない。評価担当の指摘は根拠付きの仮説として扱い、無条件に元回答を上書きしない。

### SQLiteに残す学習契約

既存のツールフィードバック処理には、発言根拠と提案の分離、曖昧な反応の保持、重複除去がある。この考え方をRoutingにも利用する。全アクションが保存されていても学習に必要な関連付けが揃っているとは限らないため、実装時に既存スキーマを照合する。

依頼・回答・判断・委任・親子関係のID、入力改訂、当時の候補と除外理由、選択行動、担当、設定・モデル・ランカー版、結果、時間・費用、ユーザー反応の対象を関連付ける。観測された事実、ユーザーの明示評価、LLMによる推定ラベルを区別し、推定に根拠・推定器版・不確実性を残す。無反応を成功、中止を失敗として自動確定しない。

### 夜間バッチの処理

1. 終了済みの処理を確定した読み取り境界で抽出する。後日到着した反応は次回の更新対象とする。
2. 会話単位で判断から結果・反応までを再構成し、重複、途中終了、関連付け不明を区別する。
3. 必要最小限の特徴とラベル候補を生成する。LLMによる補助評価は検証済み事実と分ける。
4. データセット版、抽出境界、生成コード版、ラベル生成器版を保存する。
5. まず集計とルールの評価を行い、十分なデータが集まれば候補ランカーを訓練する。基盤LLMの再学習は初期対象にしない。
6. 会話・依頼を分割単位にして時系列の検証データで評価する。同じ会話を訓練・評価双方へ混ぜない。判断後の反応はラベルに利用しても、その判断時点の入力特徴には混ぜない。
7. 候補をシャドー評価に登録し、品質・遅延・費用・制約遵守を比較する。夜間処理の完了だけで本番方針を自動更新しない。

通常ログでは未選択モデルの成績は観測できない。未実行の手順に成功ラベルを付けない。手順の優劣は安全に再現可能な評価タスクで補い、オフライン再生で副作用のあるツールを再実行しない。探索を導入する場合は選択確率も記録し、その評価手法を別途定義する。

### 実行・保存・評価

バッチはチェックポイントと冪等キーで再開可能にし、同じ入力と版から重複データを作らない。読み取りスナップショットを長時間保持して通常会話を妨げず、メインDBへの書き込みは既存SqliteWriterへ集約する。スリープやアプリ終了で未実行の場合は次回のアイドル時に再開し、会話開始時は計算負荷を抑える。具体的な時刻とスケジューラーは実装段階で設定可能にする。本計画は定期実行の登録ではない。

データセットと学習成果物は元記録との来歴を保持し、削除要求時に派生データと影響モデルを特定できるようにする。外部モデルによるログ評価にも既存の送信制約を適用する。

バッチの単体・統合検証には、再実行、途中停止、遅れて届く評価、削除済み記録、曖昧な反応、異なる依頼への誤った評価紐付け、時系列リーク、モデル更新前後の分離を含める。会話が快適かという評価と、回答が正しいかという評価を別々に計測する。

### 段階への配置

R1で行動と記録の契約、R2で回答後の再検討・独立評価・上位モデル提案、R3で夜間の抽出・集計・データセット生成とシャドー評価への接続を扱う。学習ランカーの訓練と本番適用は追加段階とし、最初の3回の実装でML品質まで保証しない。
