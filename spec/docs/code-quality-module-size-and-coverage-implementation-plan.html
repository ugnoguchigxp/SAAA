コード品質実装契約 — Module size budgets and test coverage

0. 文書の役割

  • Status: Reviewed; ready for implementation
  • Created: 2026-08-29
  • SAAA baseline: 68a8142 + working tree
  • Shipping client: macOS版SAAA desktop
  • 対象: Runtime、Frontend、QA

本文書は、ユーザー機能を増やさず、巨大モジュールの分割とテストの移動・補強を行うための実装契約である。 完了の定義はCQ-00〜CQ-12を依存関係に従って完了し、Section 11のAcceptanceを満たすことである。

MVP 0の計画は、lib.rsを「stateとcommand wiringのみ」へ縮小する大規模refactorを、 境界が安定してから別作業とすると先送りした。その先送り分が本契約である。 本文書を追加するTurnでは、Runtime、SQLite、UIの実装を変更しない。

1. 結論と固定判断

lib.rs (11,476 lines today)
  ├─ keep: AppState, run(), generate_handler, shutdown
  ├─ move: persistence / settings validation / SSE streaming
  ├─ move: conversation orchestration / Codex turn / diagnostics
  └─ move: tests with the production code they pin

App.tsx (949 lines today)
  ├─ keep: shell, surface switch, snapshot wiring
  └─ extract: chat page, voice capture hook, pure helpers

Coverage
  ├─ no new behavior without a test in the same change
  ├─ moved tests must not decrease in count or assertion
  └─ line-coverage % is a report, not a ship gate
  1. 分割はmove-firstである。公開IPC、SQLite schema、Settings JSON、LARM/Gnosis契約、イベント camelCaseを変えない。
  2. テストはコードと一緒に移す。lib.rsのmod testsを空にしてから分割しない。
  3. 1ファイルの本番行数（#[cfg(test)]より前）に予算を置く。超過は CQ-00の機械チェックで失敗させる。
  4. 行カバレッジ100%を目標にしない。未テストの挙動を特定し、抽出した純関数とfake HTTP/SQLiteで埋める。
  5. 本契約のコミットに、MVP 3 Memory、Target Speaker、Voice Behavior、LARM canaryの機能追加を混ぜない。同じファイルを触る場合は、機能側を先に完了またはfreezeする。
  6. bun run checkとbun run ipc:checkが各ticketの完了条件である。

3. Non-goals

  • 新しいユーザー機能、新しいTauri command、新しいSettings namespace
  • エラー型をResult<T, String>から全面置換すること
  • React Testing LibraryやE2Eフレームワークの新規導入（Wave 1では禁止）
  • 行カバレッジの数値目標をbun run checkの失敗条件にすること
  • live_canary.rsのignored testを通常suiteへ入れること
  • Windows / Linux向けSituationの新規実装
  • デフォルトProviderの宅内LAN定数削除（別作業）
  • 1ターンですべての800行超ファイルを予算内へ収めること

4. Stop conditions

  • IPC bind、Settings schema、SQLite user_version、イベントshapeが変わる
  • 既存の#[test]またはbun test件数が、ignoredを除いて減る
  • clippy -D warnings、fmt、typecheck、ipc:checkのいずれかが失敗する
  • 同じPRにMemory write経路、Speaker verification、LARM live、Voice Behaviorの機能差分が混ざる
  • 循環依存を解消するためにpub useのbarrelを無制限に増やす。公開は pub(crate)に留める

8. カバレッジ契約

8.1 原則

  1. 分割ticketは、移したテストが同じ名前・同じ断言で通ることを完了条件にする。新規テストは歓迎するが、 分割PRの必須条件は「減らさない」である。
  2. 穴を埋めるticket（CQ-10〜CQ-11）だけが新規テストを必須とする。 実マイク、実LARM、実Codex、30分soakは既存どおり#[ignore]のままとする。
  3. ソース走査テスト（readFileSync + toContain）を新規追加しない。 CQ-08で純関数テストへ置換した行は、対応するソース走査を削除してよい。
  4. test:coverageは報告用である。checkには入れない。HTML artifactはgitignoreし、リポジトリへコミットしない。

8.3 Tooling

  • bun run test:coverage: bun test --coverage testsと cargo llvm-cov --manifest-path src-tauri/Cargo.toml --html --output-dir coverage/rust
  • cargo-llvm-covは開発者マシンとCI（導入するなら別ticket）の任意依存である。 未インストールならscriptは案内を出してexit 0とするか、明示flagで失敗させる。Wave 1の必須は「scriptが存在する」まで。
  • coverage/を.gitignoreへ追加する。

10. 順序とfreeze

CQ-00 size ratchet
  ├─ CQ-01 redact/diagnostics
  ├─ CQ-02 persistence          ← schemaを触る他計画と同時にしない
  ├─ CQ-03 openai-compatible
  ├─ CQ-04 turns                ← MVP 3 が tool/recall を編集中なら待つ
  ├─ CQ-05 codex turn
  ├─ CQ-06 lib.rs wiring only
  └─ CQ-07 test helpers
CQ-00 ─┬─ CQ-08 App.tsx split（Rustと並列可）
       └─ CQ-09 coverage script（並列可）
CQ-02 + CQ-08 → CQ-10 fill gaps
CQ-06 + feature freeze → CQ-11
CQ-11 → CQ-12 optional

1 ticket = 1つのレビュー可能なPRを基本とする。CQ-02のようにmigrationテストが長い場合は、 schemaとsettingsでPRを分けてよいが、中間状態でcheckが落ちてはならない。
