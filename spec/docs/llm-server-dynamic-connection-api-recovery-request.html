SAAA DesktopからLAN LLM HostのAgent Connection APIを認証付きで利用できる状態へ復旧し、 profile取得、Connection作成、claim、推論、releaseまでのREST lifecycleを完走させたい。 現在の失敗は推論モデル自体ではなく、SAAA processへ長期control credentialが注入されていないため、 動的設定取得のHTTP requestを送る前に発生している。

3. LAN LLM Host側への依頼事項

3.1 SAAA用API tokenの発行と安全な受け渡し

  1. client saaa-desktop、audience saaa-desktop、profile deep-reasoning-35bのlifecycleを実行できる有効なAPI tokenを発行する。
  2. token値は本文書、チケット、chat、通常logへ記載せず、承認済みsecret channelでSAAA運用者へ渡す。
  3. token値を含めず、発行状態、activation時刻、expiry、rotation方法、失効手順を回答する。
  4. 無効・期限切れtokenに対するHTTP statusと安全なerror codeを回答する。

3.2 REST contractのready確認

  1. 認証済みGET /v1/agent-profilesが200 application/jsonを返し、 x-larm-config-revisionが64桁の小文字16進数であることを確認する。
  2. profileがcontractVersion: agent-connection.v1、provider llm、capability llm.reasoning、protocol openai.chat-completions.v1、model deep-reasoning-35b、audience saaa-desktopをadvertiseすることを確認する。
  3. POST /v1/agent-connections、bounded poll、claim、semantic health、 OpenAI-compatible SSE、DELETE releaseが利用可能であることを確認する。
  4. SAAA adapterはttlSeconds: 300、allowFallback: false、 deploymentPolicy: existing-onlyを送る。この条件で既存deploymentがreadyになることを確認する。
  5. claimされたProvider data planeはSAAA MacからLAN到達可能で、loopback addressではないことを確認する。 現行adapterはremote descriptorのportを9810として検証するため、Gatewayが同portで OpenAI-compatible data planeを公開するcontractかを明示回答する。異なるportを返す設計なら、 SAAA側修正が必要なcontract差分として回答する。

3.3 Secretを含まない完走証跡

host側のcanaryまたはSAAAとの合同canaryについて、次のbounded metadataを提示する。

  • 実行timestampとrelease/config revision
  • client、profile、audience
  • 各routeのHTTP method、status、duration
  • Connectionのpending、probing、ready状態遷移
  • semantic healthのready判定、SSEの非空completionと[DONE]確認
  • releaseのHTTP statusと、release後にConnectionおよびworkerが残っていないこと

証跡にはAPI token、Authorization header、claim response、Provider短期token、base URL、prompt、 completion本文を含めない。必要なら値を含まないserver correlation IDだけを共有する。

3.4 認証設定切り分け用のliveness

認証情報がない場合、SAAAはhost到達不能とcredential不在を別々に判定する必要がある。 model、profile、設定値、secretを返さないboundedなliveness endpointを未認証で提供できるか回答する。 提供しない方針の場合は、認証済みprofile取得以外でhost readinessを確認する承認済み手順を提示する。

4. LAN LLM Host側から回答してほしい内容

  1. Control APIのready状態と稼働release
  2. API tokenの発行状態と、値を含まない受け渡しchannelの案内
  3. x-larm-config-revisionとadvertise中のprofile・audience
  4. remote Provider data planeのport contract
  5. canary実施可能な時間帯と、host側で照合できる担当
  6. secretを含まない証跡またはcorrelation情報の形式
  7. 現在readyでない項目がある場合、その項目、復旧予定、暫定回避ではなく恒久対応のowner

5. 受入条件

  1. SAAA processへLARM_API_TOKENが安全に注入される。
  2. 認証済みGET /v1/agent-profilesが200と有効な x-larm-config-revisionを返す。
  3. POST /v1/agent-connectionsが201または202とLocationを返す。
  4. Connectionがbounded time内にreadyへ遷移する。
  5. claim responseがcontract検証を通り、semantic healthがreadyになる。
  6. OpenAI-compatible SSEが非空completionと[DONE]で完走する。
  7. DELETEが204を返し、host側でもresource残留がない。
  8. 証跡がsecret boundaryを守り、SAAA実行結果にauthentication failureが残らない。

6. Rollbackと対象外

SAAAは復旧までの可用性確保として、LAN内の直結Qwen http://<private-ip>:8080/v1を一時的なlocal rollback routeに設定している。 動的lifecycleの受入後はDynamic LAN Provider routeをprimaryとして利用する。

  • 認証を無効化しない。
  • SAAAからLAN LLM HostへSSH、SFTP、SCP、SSH tunnel、port forwardingを行わない。
  • tokenやclaim結果をSAAAのSQLite、設定JSON、diagnostics、logへ保存しない。
  • 本依頼ではmodel deploymentの変更やcloud Providerへのfallbackを要求しない。

7. LAN LLM Host側回答後のSAAA作業

  1. 承認済みchannelで受領したtokenをSAAA process起動環境へ注入する。
  2. profile取得からreleaseまでのLAN canaryを実行する。
  3. SAAA側とhost側のbounded evidenceを照合し、受入条件を判定する。
  4. 成功後、dynamic routeをprimaryとして実行し、直結Qwen routeはlocal rollbackとして保持する。
