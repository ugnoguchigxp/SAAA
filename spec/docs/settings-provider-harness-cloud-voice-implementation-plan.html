Provider Harness / 個別Cloud / 常時待ち受け設定 再構成実装計画

0. 文書の役割

  • Status: Proposed。実装未着手
  • Created: 2026-08-30
  • SAAA baseline: 41636c0 + working tree
  • Database baseline: PRAGMA user_version = 12
  • Settings document baseline: schema_version = 11
  • Shipping client: macOS版SAAA desktop
  • 対象: Settings、Provider Runtime、LLM / ASR / TTS routing、API key secret boundary、Chat常時待ち受け、SQLite migration、QA
  • Design reference: spec/docs/saaa-settings-harness-concept-v1.png、 spec/docs/saaa-settings-individual-cloud-services-concept-v1.png

本文書は、LLM Provider harness addressを一つ設定するとLLM、ASR、TTSを自動解決でき、 必要なサービスだけ個別Cloud Providerへ上書きできる設定構成を、現行SAAAへ安全に導入するための 実装契約である。API keyは画面から登録できるが再表示せず、常時待ち受けはPush-to-talkではなく SAAAの基本動作として扱う。

今回の作業は計画書の作成だけであり、本文書作成TurnではTypeScript、Rust、SQLite、Settings JSON、Runtimeの製品コードを変更しない。実装完了はSection 15の全Gateを通過した時点とし、 UIを描画しただけ、schemaを追加しただけ、または単体テストを追加しただけでは完了としない。

1. 確定方針

  1. Settingsの最上位接続としてLLM Provider harness addressを一つだけ保存する。 保存後にBackendがLLM、ASR、TTSを個別に解決し、各capabilityの状態と実効設定を返す。
  2. LLM、ASR、TTSはそれぞれHarnessまたはIndividual Providerを独立して選べる。 一つのサービスをCloudへ切り替えても、他のサービスの接続元は変えない。
  3. 個別Cloud Providerの初期対応は、型付きのOpenAI-compatible HTTP adapterとする。 任意JSON、任意header、任意scriptを設定画面から注入する仕組みは作らない。
  4. API key本体はmacOS Keychainへ保存する。SQLiteにはProvider metadataと認証方式だけを保存し、 secret、masked secret、Keychainから読み出した値を保存しない。
  5. Settings UIにcredential保存元の選択肢は置かない。API key欄、設定状態、更新、削除、 接続確認だけを表示し、保存方式はアプリの安全な既定動作とする。
  6. maxOutputTokensはUIと永続Settings contractから削除する。 Provider protocolが上限値を必須とする場合だけadapter-ownedな内部値を使い、ユーザー設定へ戻さない。
  7. Chat音声入力は常時待ち受けを基本とする。初回同意とmacOS permission取得後はアプリ起動時に再開し、 ユーザーは一時停止できる。Push-to-talkのmode選択は表示しない。
  8. 常時待ち受け中もRAW audioをCloudへ常時streamしない。Local VADで確定した発話区間だけを、 選択中のASR adapterへ一回送信する。
  9. UIの接続状態はFrontendの楽観状態ではなく、Backendが返すcredential availability、probe結果、 resolved service routeを正本にする。

2. Scopeと非目標

2.1 In scope

  • Harness addressの保存、解決、再解決、capability別status表示
  • LLM、ASR、TTSの独立したHarness / Individual Provider切り替え
  • LLM / ASR / TTS用OpenAI-compatible Cloud adapter
  • API keyの登録、置換、削除、Keychain availability表示
  • Settings schema 11から12へのmigration
  • maxOutputTokensの永続SettingsとUIからの削除
  • 常時待ち受け、Local VAD、発話区間送信、一時停止と自動再開
  • 入力デバイス、利用可能な出力デバイス、VAD設定、Auto speak、Target Speaker Filterへの導線
  • backup、diagnostics、log、IPCのsecret非露出検証

2.2 Non-goals

  • Provider課金、利用量、請求、アカウント管理
  • 任意Provider plugin marketplaceまたは任意code実行
  • API keyのCloud同期、export、backupへの同梱
  • RAW audioの常時Cloud streaming
  • Wake word必須化
  • Meetingへの常時VAD導入、system audio、speaker diarization、翻訳
  • LLM temperature、top-p、seed、max output tokenのUI追加
  • 現時点でadapterを持たないProvider固有のRegion、Project、Deployment設定
  • Settings再構成に便乗したConversation、Situation、Memory UIの刷新

6. API key / Keychain Contract

6.1 保存方式

  • Keychain service: com.saaa.provider-api-key
  • Keychain account: immutable Provider ID
  • Keychain value: API key bytes only
  • SQLite: authentication=api-keyとProvider metadataだけ
  • Frontend: 保存操作中の入力値だけを一時保持し、保存後に即時clearする
  • Rust: Zeroizing<String>または同等のzeroize boundaryを使う

6.2 Typed IPC

set_provider_api_key({ providerId, apiKey })
  → { providerId, state: "configured" }

delete_provider_api_key({ providerId })
  → { providerId, state: "not-configured" }

list_provider_credential_states()
  → [{ providerId, state: "configured" | "not-configured" | "unavailable" }]
  • API key設定commandは1〜4096 byte、control characterなし、header-safeを検証する。
  • command result、error、event、snapshotへAPI key値を含めない。
  • API keyのread commandは作らない。Backend adapterだけがKeychainから読み出せる。
  • 接続テストもProvider metadataだけをFrontendから受け、BackendがKeychainからkeyを取得する。
  • Provider削除はKeychain item削除成功後にSQLite metadataを削除する。
  • Keychain削除後にSQLite保存が失敗した場合、Providerは残るがcredentialなしとしてfail-closedにする。 Secretを復元して成功表示しない。

6.3 Secret非露出Gate

  • SQLiteとそのbackupにfixture API key byte列が存在しない。
  • Diagnostics JSON、Rust log、Frontend console、IPC outputにfixture API keyが存在しない。
  • Settings再読込後は設定済みだけを表示し、元値または末尾文字を表示しない。
  • Keychain unavailable / locked / deniedはunavailableとして表示し、認証なし実行へfallbackしない。

7. Harness Resolution Contract

7.1 Address validation

  • 絶対HTTP(S) URLを受け取る。
  • loopback、private LAN、.localはHTTPを許可する。
  • public hostはHTTPSを必須とする。
  • userinfo、query、fragment、credential埋め込みは禁止する。
  • URLは最大2048 byte。保存前に末尾slashを正規化する。
  • redirect、system proxy、DNS rebinding対策は既存dynamic LANと同じfail-closed方針を使う。

7.2 Versioned descriptor

{
  "contractVersion": "saaa-service-harness.v1",
  "revision": "sha256-hex",
  "services": [
    {
      "capability": "llm",
      "protocol": "openai.chat-completions.v1",
      "baseURL": "http://provider.local:8080/v1",
      "model": "deep-reasoning-35b",
      "healthURL": "http://provider.local:8080/health"
    },
    {
      "capability": "asr",
      "protocol": "openai.audio-transcriptions.v1",
      "baseURL": "http://provider.local:8081/v1",
      "model": "qwen3-asr-1.7b",
      "language": "auto",
      "healthURL": "http://provider.local:8081/health"
    },
    {
      "capability": "tts",
      "protocol": "openai.audio-speech.v1",
      "baseURL": "http://provider.local:8082/v1",
      "model": "text-to-speech",
      "voice": "Japanese Voice",
      "healthURL": "http://provider.local:8082/health"
    }
  ]
}
  • 同一capabilityの重複、未知protocol、空model、unsafe URLはcontract error。
  • 選択中のcapabilityが欠ける場合、そのserviceだけをunavailableにする。
  • 三つのうち一つが失敗しても、成功したdescriptorを虚偽の失敗にしない。
  • 短期credentialを返す場合はmemory内のZeroizing値とし、SQLiteへ保存しない。
  • 解決結果はaddress + revisionをkeyにbounded cacheし、再接続またはexpiryで破棄する。
  • 旧agent-connection.v1はLLM capabilityだけとして扱い、ASR/TTSがあるように見せない。

7.3 UIへ返す状態

unchecked
  → resolving
  → ready
  → degraded（選択していないcapabilityだけ欠落）
  → failed（選択中capabilityを利用不能）

Snapshotはcapability、provider label、model / voice、location、state、latency、updatedAt、 bounded reason codeだけを返す。endpoint、credential、raw server bodyは通常UIへ返さない。

8. Individual Provider Contract

Table: Initial typed provider fields
Capability 必須項目 固定する項目
LLM Label、Endpoint、Model、Authentication、API key状態 Chat Completions protocol、streaming、finish reason検証
ASR Label、Endpoint、Model、Language、Authentication、API key状態 WAV upload、JSON response、Local VAD後の一発話一request
TTS Label、Endpoint、Model、Voice、Authentication、API key状態 Speech endpoint、bounded audio response、既存playback queue
  • Provider作成時にimmutable IDをBackendで発行する。Label変更でKeychain accountを変えない。
  • Cloud endpointはHTTPS、Local endpointはloopback / private HTTPだけを許可する。
  • 接続テストは各capabilityの実protocolを使い、単なるTCP connectを成功扱いしない。
  • ASR接続テストは無音fixtureまたはmodel/health probeを使い、ユーザー音声を送らない。
  • TTS接続テストは短い固定文を生成して再生前に破棄できるpreview結果とする。
  • Provider固有追加項目はadapter実装時にdiscriminated unionへ追加し、汎用mapで逃がさない。

9. Effective Service Routing

Persisted source selection
  ↓
Validate selected capability
  ├─ Harness → resolve descriptor → validate health / credential expiry
  └─ Provider → load typed metadata → check Keychain → semantic probe
  ↓
EffectiveServiceRoute
  capability / source / providerId / modelOrVoice / location / state / reasonCode
  ↓
Runtime adapter factory
  • LLM、ASR、TTSは同じsource選択規則を使うが、adapter型は混ぜない。
  • ASR ProviderをLLM routeへ指定するなどのcapability mismatchは保存時に拒否する。
  • Settings保存成功後にresolver cacheをinvalidateし、新しいrouteを一度probeする。
  • Probe失敗を理由に保存済み設定を別Providerへ書き換えない。
  • Runtime開始時にsnapshotの表示値ではなくBackendの最新effective routeを再確認する。
  • Cloud失敗時にHarnessへ、Harness失敗時にCloudへ暗黙fallbackしない。

10. 常時待ち受けVoice Contract

10.1 State machine

disabled
  └─ user enables / startup preference
       ↓
permission-required ── deny ──→ blocked
       ↓ grant
starting
       ↓
listening-local-vad
  ├─ speech candidate → speech-detected → segment-finalizing
  │                         ↓
  │                    transcribing → listening-local-vad
  ├─ TTS starts       → suspended-for-tts → listening-local-vad
  ├─ Meeting starts   → suspended-for-meeting → listening-local-vad
  ├─ user pauses      → paused
  └─ device failure   → error → explicit retry
  • 初回だけユーザー操作からmicrophone permissionを要求する。
  • permission取得済みかつlisteningEnabled=trueなら、app snapshot読込後に自動開始する。
  • Pauseは設定値へ反映し、再起動後も停止を尊重する。
  • Meeting、Enrollment、Chatは既存audio capture coordinatorで排他する。
  • TTS half-duplex中はASRへ送信せず、停止完了後に同じ入力deviceで再開する。
  • Target Speaker Filterが有効な場合は、ASR送信前のlocal gateを維持する。
  • 空segment、speech未検出segment、queue overflow時のPCMはzeroizeして破棄する。

10.2 Local VAD boundary

  • Microphone streamは待ち受け中に保持する。
  • RMS threshold、speech confirmation、silence timeoutはLocal処理だけに使う。
  • Cloud ASRへ送るのはspeech confirmed後に確定したbounded PCM segmentだけ。
  • ASR処理中も次segmentをbounded queueへ入れ、無制限bufferを作らない。
  • VAD値、raw RMS、PCMをSQLite、diagnostics、logへ保存しない。

10.3 Naming cleanup

  • usePushToTalk.tsをuseContinuousVoice.tsへ変更する。
  • captureMode: "push-to-talk"を削除し、単一の常時待ち受けcontractへ統一する。
  • Composerのmicrophone buttonは「音声入力開始」ではなく「待ち受けを一時停止 / 再開」にする。
  • 表示状態は「待ち受け中」「発話を検出」「文字起こし中」「一時停止」「利用不可」を使う。

11. Settings UI Information Architecture

11.1 接続

  • LLM Provider harness address
  • 接続して解決 / 再解決
  • LLM、ASR、TTSのresolved summaryとcapability別status
  • 保存する値はaddressだけであることの説明
  • 選択中capability欠落時の具体的なrecovery

11.2 個別サービス

一覧では三つのservice summaryを表示し、一つを選ぶと詳細panelを開く。 三つの完全なformを常時展開して小さな入力欄を並べない。

  • ServiceごとのHarness / Individual Provider切り替え
  • Provider選択または新規作成
  • Endpoint、Model / Voice、Language、Authentication
  • API keyの設定状態、更新、削除
  • 接続確認、直近latency、bounded error reason
  • LLMだけReasoning effortを表示する
  • Maximum output tokensは表示しない

11.3 音声とデバイス

  • 常時待ち受け ON / 一時停止
  • 現在状態とmicrophone permission
  • 入力device
  • 対応adapterだけ出力device
  • 発話検出感度 preset
  • 発話確定までの無音時間
  • Auto speak
  • Target Speaker Profileへの既存導線
  • Cloud ASRへ送るのはLocal VADで確定した発話区間だけという説明

11.4 保存とdirty state

  • Provider metadata / route / voice preferenceは既存Save Settings barで一括保存する。
  • API keyはSettings documentへ混ぜず、専用mutationとして即時保存する。
  • API key保存後にmetadataが未保存なら、そのProvider cardに明示する。
  • Settings保存成功後のprobe結果が失敗しても、保存成功と接続失敗を混同しない。

12. Migration and Compatibility

12.1 Version

  • Settings document schemaを11から12へ上げる。
  • Database user_versionは既存migration系列の次versionへ上げる。
  • TypeScript、Zod、Rust serde、IPC bindingを同じcommitで更新する。
  • Unknown field拒否を維持し、migration後の旧field残存を許可しない。

12.2 Existing data mapping

Table: Settings 11 to 12 mapping
旧値 新値
dynamic-lan.host harness.address = http://<host>:9810
Dynamic LANがconversation primary conversationRespond.source = harness
voice.sttHostがHarness hostと同じ voiceTranscribe.source = harness
voice.sttHostがHarness hostと異なる 既存LAN ASR Providerを生成してsource = provider
ttsProviderId = system-tts System TTS Providerを生成してvoiceSpeak.source = provider
captureMode = push-to-talk listeningEnabled = falseで移行し、初回同意後に有効化
maxOutputTokens 削除。値を別fieldへ移さない
credentialStorage = environment 削除。既存environment credentialは移動・複製しない

Migrationは既存利用者のマイクを無断で起動しないため、旧設定からの listeningEnabledをfalseにする。新規installと、常時待ち受けの説明に同意した利用者だけを trueにする。これは常時待ち受けという製品既定と、OS permissionの明示同意を両立するための一回限りの境界である。

12.3 Backup and rollback

  • 既存のmigration前SQLite backupを維持する。
  • BackupにはAPI keyが含まれないことを自動testで証明する。
  • Schema 12から旧binaryへdowngradeして起動することはsupportしない。
  • Rollbackは旧binary + migration前backupで行う。Keychain itemは自動削除しない。
  • Rollback後の未参照Keychain itemは専用cleanup commandまたは再upgrade後に削除する。

14. Test Plan

14.1 Settings / Contract

  • Settings 11 fixtureが12へ移行し、旧fieldが残らない
  • 二回migrationしても結果が変わらない
  • Cloud HTTP、userinfo、credential入りURL、capability mismatchを拒否
  • Provider ID変更、重複、削除中route参照を拒否
  • maxOutputTokensを送るSchema 12 documentをunknown fieldとして拒否
  • Frontend ZodとRust validationが同じfixture集合をPass / Failする

14.2 Credential

  • API key create / replace / delete / missing / denied
  • 設定済みProviderがrestart後もKeychainから利用できる
  • Provider削除後にKeychain itemが残らない
  • Keychain削除後のSQLite failureでProviderが認証なしへfail-closedする
  • SQLite、backup、diagnostics、log、snapshotへfixture secretが出ない
  • Frontendが保存後にAPI key input stateをclearする

14.3 Harness

  • 3 capability ready
  • LLMだけready、ASR / TTS missing
  • duplicate capability、unknown protocol、unsafe endpoint、invalid revision
  • timeout、redirect、oversized body、invalid JSON、health failure
  • cache hit、address変更、revision変更、expiry、explicit re-resolve
  • 旧LLM-only contractをASR / TTS readyとして表示しない

14.4 Individual Provider

  • LLMのstream terminal、length、auth failure、timeout
  • ASRのbounded WAV、一発話一request、language、空transcript
  • TTSのbounded response、voice、cancel、playback failure
  • Cloud ProviderがKeychain missing時にnetwork requestを開始しない
  • Harness / Cloud混在で選択外Providerを呼ばない

14.5 Continuous Voice

  • 初回permission同意前に自動captureしない
  • 同意済み + enabledでstartup後に一度だけcapture開始
  • Pauseがstream、AudioContext、bufferを解放し、restart後も停止
  • VAD確定後もmicrophoneを保持し、次segmentを受け付ける
  • Cloud ASRへspeech-confirmed segment以外を送らない
  • TTS中、Meeting中、Enrollment中の排他とresume
  • Target Speaker Filter failure時にASRへ送らない
  • queue overflow、ASR timeout、device disconnectでPCMをzeroizeする

14.6 UI

  • Harness addressから3 statusへ情報階層が読める
  • LLMだけCloudへ変更してもASR / TTS sourceが変わらない
  • API keyを保存後に元値を再表示しない
  • 保存成功とprobe失敗を別statusで表示する
  • Maximum output tokensとPush-to-talkがSettingsから消えている
  • Keyboard操作、focus、aria-live、error associationが機能する

17. 実装順序とPR境界

  2. PR-2: SPV-02。Keychain / IPC / secret testsだけ
  3. PR-3: SPV-03。Harness resolverとfixture serverだけ

18. Definition of Done

  1. Harness addressを設定すると、LLM、ASR、TTSの解決結果をservice別に確認できる。
  2. 三つのserviceを独立してHarnessまたはIndividual Providerへ切り替えられる。
  3. API keyをUIから登録、更新、削除でき、値はKeychain以外へ永続化されない。
  4. Maximum output tokensとPush-to-talkがSettings contractとUIから消えている。
  5. 同意済み環境ではSAAA起動後に常時待ち受けが始まり、ユーザーが一時停止できる。
  6. Cloud ASRへ送るのはLocal VADで確定した発話区間だけである。
  7. Harness / Cloud / System serviceの混在routeがrestart後も同じ実効設定で動作する。
  8. 全自動Gateと実Harness、実Keychain、実microphoneによるSection 15 GateがPassする。
