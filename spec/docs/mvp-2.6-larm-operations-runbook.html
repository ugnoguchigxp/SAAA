MVP 2.6 Release Evidence

このrunbookは、隔離されたmacOS版SAAAからprivate tunnel経由でLARM canaryを実行し、 障害時にdirect Providerへ戻すための唯一の運用手順である。G1とG2が通過するまでは、 以下のlive command、health / ready、allocation、Gateway、metrics requestを実行しない。

1. Safety boundary

  • 通常profile、通常application-data、既存の会話をcanaryへ使わない。
  • LARM originはSAAA host上のnumeric loopbackだけを使い、LAN上のplain HTTPへ接続しない。
  • token、credential、endpoint、prompt、response、identifier、raw log、raw metricsを証跡へ記録しない。
  • runnerからSSH、remote shell、systemctl、llama-swap、LARM fault commandを実行しない。
  • 一つのreport directoryではpreflightからaggregateまでを一回だけ実行し、fileを上書きしない。
  • 進行中streamのProvider bindingを変更しない。cancelまたは既存bindingでterminalへ進めてからrollbackする。
  • G3がpassedになるまで通常profileのprimary Providerとfeature flag既定値を変更しない。

2. Roles and handoff

Table: Required operator responsibilities
Role Responsibility Evidence
SAAA operator isolated directory、manifest、launcher、UI workload、local rollback operator名、UTC execution window、manual result
LARM operator deployment revision、private tunnel、metrics scope、one-shot fixture、restart、server log audit revision、contract一致、監査結果の件数、UTC時刻
Reviewer report identity、threshold、security、rollback、runbook rehearsal、deviationを照合 判断者、reviewed at、G3 decision

tokenやhost detailを役割間のhandoff文書へ貼り付けない。秘密情報はoperator-owned launcherまたは secret storeからprocess environmentへ渡し、SAAA repositoryとshell historyへ保存しない。

3. G1 — Frozen contract

live trafficを許可する前に、SAAA実装担当とLARM実装担当が同じchange setで次を完了する。

  1. LARM repositoryのcommit、API schema、daemon testを確認する。
  2. virtual modelとrewrite、effective TTL、Gateway request / response上限を含む全contract decisionを確定する。
  3. SAAAのCONTRACT_COMMIT、FROZEN_LARM_CONTRACT_COMMIT、DTO、bounds、 Runtime category、commit由来fixtureを同じcommitへ更新する。
  4. release evidenceのG1欄へsource commit、fixture source、reviewer、UTC reviewed atを記録する。
  5. 未決定値、仮値、未commit WIPが0件であることを別reviewerが確認する。

一件でも未確定ならG1はblockedのままとし、loopback listenerが存在していても larm:preflightを実行しない。

4. G2 — Isolated canary environment

4.1 Private paths

SAAA operatorは、互いにancestor / descendantではない次の三つを用意する。

  • 空のreport directory: current user所有、mode 0700、repository外
  • 空のapplication-data directory: current user所有、mode 0700、通常profile外
  • manifest file: current user所有、mode 0600、上記directoryとrepositoryの外

symlink、hard link、共有directory、通常profileのinode再利用を禁止する。失敗または中断後は report directoryとapplication-data directoryを再利用せず、新しい空directoryと新しいmanifestで preflightをやり直す。

4.2 Manifest

credential値を含めず、次のstrict JSONをoperator-owned manifestへ保存する。

{
  "format": "saaa-larm-canary-manifest-v1",
  "saaaCommit": "reviewed-clean-saaa-commit",
  "larmContractCommit": "reviewed-g1-larm-commit",
  "deploymentRevision": "reviewed-LLM server-revision",
  "dataDirectory": "/absolute/operator-owned/canary-data",
  "metricsScope": "exclusive-window",
  "larmProvider": {
    "baseUrl": "http://127.0.0.1:port",
    "allocationTtlSeconds": 300,
    "allocationStartupTimeoutSeconds": 300,
    "allowFallbackByDefault": false,
    "deploymentPolicy": "existing-only"
  },
  "rollbackProvider": {
    "id": "local-openai-compatible",
    "location": "local",
    "endpoint": "operator-approved-endpoint",
    "model": "operator-approved-model",
    "credentialEnv": "SAAA_PROVIDER_LOCAL_OPENAI_COMPATIBLE_API_KEY",
    "credentialRequired": true
  }
}

metricsScopeはexclusive-windowまたはclient-scopedだけを使う。 placeholderを実行値として残さない。manifest確定後は全modeが終了するまで変更しない。

4.3 Operator-owned launcher

launcherは次のenvironmentだけをrunnerへ渡し、値をterminalへ表示しない。

Table: Required live environment
Name Required value
SAAA_LARM_CANARY 1
SAAA_LARM_ENABLED 1
LARM_API_TOKEN secret storeから取得した1〜4,096 byteのheader-safe値
SAAA_LARM_CANARY_BASE_URL manifestと同じnumeric loopback origin
SAAA_LARM_DEPLOYED_COMMIT G1と同じlowercase hex commit

proxy、Codex credential、無関係な*_TOKEN / *_API_KEY、runner-owned SAAA_LARM_CANARY_RESULT_FILEなどをcaller environmentへ設定しない。

4.4 G2 approval

  1. LLM server deployment revisionがG1 commitを含むことをLARM operatorが確認する。
  2. private tunnelがmanifestのloopback portでlistenしていることだけを確認する。HTTP requestは送らない。
  3. 排他的観測windowまたはclient-scoped metricsを予約する。
  4. rollback Provider credentialが存在することだけを確認し、G2中に推論しない。
  5. deterministic one-shot create-response遮断、release-response遮断fixtureをこの順で準備する。
  6. operator、manifest SHA-256、revision、metrics scope、manual isolation結果をrelease evidenceへ記録する。

5. Fixed execution sequence

同じclean SAAA commit、manifest、report directory、deployment revisionで次を順番どおり実行する。 

bun run larm:preflight -- --report-dir /absolute/operator-owned/report-dir
bun run larm:canary -- --report-dir /absolute/operator-owned/report-dir
bun run larm:soak -- --report-dir /absolute/operator-owned/report-dir --duration 30m
bun run larm:soak -- --report-dir /absolute/operator-owned/report-dir --duration 2h
bun run larm:report -- --report-dir /absolute/operator-owned/report-dir

exit code 0だけをpassedとして扱う。2はfailed、3はblocked、 64はusage error、70はinternal errorである。failedまたはblockedを手編集で passedへ変更しない。後続modeを開始せず、原因を解消して新しいreport directory、空の application-data directory、新しいmanifestからやり直す。

6. Functional canary checkpoints

runnerは自由記述の入力を受け取らない。stderrへ次の固定codeが出たら、SAAA operatorとLARM operatorは5分以内に対応する。runnerがSQLiteまたはmetricsで結果を観測すると自動的に次へ進む。

Table: Functional operator checkpoints
Progress code Operator action Completion signal
waiting-for-isolated-settings flag OFFのpackaged appでmanifestどおりの二Providerを保存し、directをprimaryにして1 turn完走する。 direct session一件がcompleted
enabling-larm-canary LARMをprimary、directを唯一のfallbackに保存する。新しいturnは開始しない。 SQLite上のrouteがmanifestと一致
waiting-for-ui-workload 固定promptでnormal 1 turnと、非empty delta後のcancel 1 turnを実行する。 LARM completed一件、cancelled一件
checkpoint-timeout-fixture-ready pre-output latency fixtureを一回だけ有効化し、timeout後のexplicit direct fallbackを完走して解除する。 LARM timeout一件、direct completed一件
checkpoint-tunnel-interruption-ready non-empty delta後にtunnelを一回遮断する。terminal後にtunnelを復旧し、normal 1 turnを完走する。 partial-output一件、復旧後completed一件
checkpoint-larm-restart-ready active run 0件を確認してLARMを一回restartし、復旧後normal 1 turnを完走する。 新規allocationによるcompleted一件
checkpoint-capacity-fixture-ready capacity rejectionを一回だけ発生させ、explicit direct fallbackを完走してfixtureを解除する。 LARM capacity一件、direct completed一件

packaged UIとlive suiteは次のfixed promptだけを使う。実会話、workspace内容、秘密情報を入力しない。 

Reply with exactly: CANARY_OK
List the numbers 1 through 5.
Write one short greeting in Japanese.
Write ten numbered words, one at a time.
Reply with exactly: READY

live suite用のone-shot TTL fixtureはcreate-response遮断、release-response遮断の順で一度ずつ自動解除され、 三件目は専用test client終了で検証される。

7. Canary and soak operation

7.1 30-minute canary

  • 同時active turnを一件以下に保ち、normal completed 20件以上、cancel 5件以上を実行する。
  • runnerが5秒間隔でSAAA RSS、SQLite、LARM metricsを観測している間、appとterminalを閉じない。
  • unexpected failure、implicit fallback、duplicate terminal、allocation leakが一件でもあれば停止する。

7.2 2-hour soak

  • normal completed 60件以上、cancel 10件以上を、同時active turn一件以下で実行する。
  • minute 30〜40でcheckpoint-larm-restart-readyが出た後、active run 0件でLARMを一回restartする。
  • minute 70以降のcheckpoint-saaa-restartでは操作せず、runnerによるlocal app restartを待つ。
  • restart後にSettings保持と新しいallocationを確認できるnormal turnを実行する。
  • samplingを妨げるsleep、network切替、terminal suspendを行わない。

8. Incident procedures

8.1 LARM unavailable or tunnel failure

  1. 新しいLARM turnを開始せず、実行中runをfailedまたはblockedとして終了させる。
  2. non-empty delta後はProvider fallbackや同一request retryを行わず、cancelまたはterminalを待つ。
  3. Settings rollbackを実施し、新しいturnをdirect Providerだけへ送る。
  4. LARM network accessが続く、またはSettingsを操作できない場合はkill-switch rollbackを実施する。
  5. LARM operatorがserviceとtunnelを復旧し、active allocationがbaselineへ戻ったことを確認する。
  6. 復旧確認は新しいempty report / application-data directoryと新しいmanifestのpreflightから開始する。

8.2 Token rotation

  1. canaryを停止し、active runとallocationが0件になるまで待つ。
  2. LARM operatorがserver側tokenを更新し、旧tokenを失効させる。
  3. SAAA operatorがsecret storeまたはoperator-owned launcherを更新する。値を表示・記録しない。
  4. 新しいempty report / application-data directoryを用意し、両pathを反映した新しいmanifestとlauncherで SAAAをrestartしてpreflightを実行する。
  5. 旧token拒否、新token成功、allocation baseline不変をrelease evidenceへ件数だけ記録する。

8.3 Capacity rejection

  1. allowFallback: falseとexisting-onlyを変更しない。
  2. 同じLARM requestをretryせず、output前のcapacity確定時だけ明示済みdirect Providerへ一回進む。
  3. Resident Runtime停止、model切替、optional Runtimeへの暗黙切替を行わない。
  4. retry storm、implicit fallback、active allocation増加があれば直ちにrunをfailedとして停止する。

8.4 TTL cleanup

  1. allocate結果が不明な場合はblind retryしない。
  2. server-confirmed effective TTL + 30秒までmetricsだけで回収を待つ。
  3. active allocationがbaselineへ戻らなければ新しいscenarioを開始せず、runをfailedにする。
  4. allocation idやrequest idをrunbook、terminal、release evidenceへ転記しない。

9. Two-stage rollback

9.1 Settings rollback

  1. active streamをcancelまたはterminalへ進める。
  2. Settingsでconversation routeのprimaryをlocal-openai-compatibleへ変更し、fallbackを空にする。
  3. 新しいturnを3件実行し、すべてdirect Providerでcompletedになることを確認する。
  4. 新しいLARM session、allocation、requestが0件であることをSQLiteとallowlist metricsで確認する。

9.2 Kill-switch rollback

  1. active streamをcancelまたはterminalへ進め、SAAAを停止する。
  2. operator-owned launcherのSAAA_LARM_ENABLEDをOFFにしてSAAAを再起動する。
  3. UIがLARM disabledを示すことを確認する。
  4. 新しいdirect Provider turnを3件完走する。
  5. Connection Testを含むLARM network accessが0件であることを確認する。

rollback後にLARMへ戻す場合は、障害原因を解消し、G1 / G2 identityが変わっていないことを確認してから、 新しいempty report / application-data directoryと新しいmanifestのpreflightから再開する。 緊急復旧を理由に既存failed reportやcanary dataを再利用しない。

10. Security and privacy review

  1. SAAA runner、app、diagnosticsにtoken、prompt、response、identifier、endpointが0件であることを確認する。
  2. LARM operatorはserver上で同じ監査を実行し、raw logをSAAA hostへ転送しない。
  3. raw metricsを保存せず、allowlist済みnumeric aggregateだけがreportにあることを確認する。
  4. report fileがcurrent user所有、mode 0600、regular file、hard linkなしであることを確認する。
  5. release evidenceには各検出件数、監査UTC時刻、reviewerだけを記録する。

検出件数が一件でも0でなければG3をfailedとし、証跡から値を削除しただけでpassedにしない。

11. Evidence finalization and G3

  1. aggregate.jsonがpassedで、四modeのidentityとallocation baselineが一致することを確認する。
  2. bounded summaryだけをrelease evidenceのautomated欄へ転記する。
  3. manual UI、security、rollback、soak、runbook rehearsalをそれぞれの欄へ分離して記録する。
  4. 別operatorがこのrunbookだけでSettings rollbackとkill-switch rollbackを再現する。
  5. 未解決deviationとwaiverが0件であることをreviewerが確認する。
  6. G3をpassed | failed | blockedのいずれかで記録し、判断者とUTC時刻を埋める。
  7. passedの場合も、初期利用profile、operator、rollback windowを別の明示的判断として記録する。

G3 passedは全体有効化を意味しない。限定enablement中はoperatorが/readyとallowlist metricsを監視し、異常時はSection 9の二段階rollbackを実施する。

Table: Limited enablement monitoring
Timing Observation Action
enablement前 /ready、active allocation baseline、direct rollback credential 一件でも確認できなければ開始しない
限定利用中 /ready、active allocation、capacity、release、Runtime category raw labelを保存せず、承認済みallowlist aggregateだけを監視する
異常時 unready、allocation leak、implicit fallback、unknown Runtime、secret/content leak 新しいturnを止め、Section 9のSettings rollback、必要ならkill switchを実行する
window終了時 active allocationがbaselineへ復帰し、未完了runが0件 UTC window、件数、rollback有無だけをevidenceへ記録する

12. Immediate stop conditions

  • contract、deployment revision、manifest hash、artifact hashの不一致
  • 通常profile、Settings、SQLite、environmentとの共有
  • secret、本文、identifier、endpointの露出
  • health / readyによるallocationまたはRuntime起動
  • non-empty delta後のfallback、retry、reallocation
  • optional Runtimeへの暗黙切替、Resident停止、SAAAからのRuntime運用操作
  • duplicate terminal、unexpected failure、allocation leak
  • sampling gap、RSS、cleanupがimplementation contractのthresholdを超過

stop condition発生後は後続gateへ進まない。機密値を含まないfailure code、UTC時刻、影響modeだけを release evidenceへ記録し、原因を解消して新しいreport / application-data directoryとmanifestから再開する。
