Target Speaker Enrollment and Transcription Gate 実装計画

0. 文書の役割

  • Status: Proposed implementation plan。実装開始はGate G0通過後
  • Created: 2026-08-29
  • SAAA baseline: ae9b84a + working tree
  • Database baseline: PRAGMA user_version = 10
  • Settings document baseline: schema_version = 9
  • Shipping client: macOS版SAAA desktop
  • 対象: Voice Settings、Audio Capture、Voice Runtime、SQLite、File Store、QA、運用

本文書は、Settings画面から本人音声を複数回サンプリングし、その音声ファイルを端末内へ永続保存し、 通常Chatでは登録話者と判定された音声だけをgnosis ASRへ送って文字起こしするための実装契約である。 ユーザーは登録音声の保存を明示的に許可している。本機能はその許可を製品上でも確認可能にし、 保存、再生、追加、再評価、削除のlifecycleをSettingsから管理できるようにする。

完了の定義はTS-00〜TS-10を順に完了し、Section 20の自動検証、 isolated audio fixture、実機canaryがすべてSection 21のGateを通過することである。 Speaker verificationは本人認証ではなく、文字起こし対象を選ぶためのprivacy filterとして扱う。

1. 結論と固定判断

Settings / Voice / My voice profile
  ↓ explicit enrollment
Shared microphone lease
  ↓ bounded PCM capture
Canonical 16 kHz mono WAV
  ├─ encrypted persistent sample file
  └─ local speaker embedding
       ↓ multiple enrollment references
Local Target Speaker Verifier

Normal Chat microphone
  ↓ WebView audio processing and bounded pre-roll
Candidate VAD
  ↓ local speaker verification before ASR
  ├─ verified-user → user utterance buffer → endpoint → gnosis ASR
  ├─ non-user     → discard; never preview or transcribe
  └─ uncertain    → wait for more audio, then fail closed
  1. AECだけでは本人と他者を区別できないため、STTの前に登録話者のspeaker verification gateを置く。
  2. 話者判定はMac上で実行する。判定前の音声、非本人音声、判定不能音声をgnosisへ送らない。
  3. 登録音声は一つの平均値に潰さず、複数の暗号化音声ファイルと複数embeddingを保持する。 これにより、model更新時に保存音声からembeddingを再生成できる。
  4. 音声ファイルはSQLite BLOBに入れず、Tauriのapp_data_dir配下へ暗号化して保存する。 SQLiteはprofile、sample metadata、model provenance、状態の正本とする。
  5. 暗号鍵は音声ファイルとSQLiteへ保存せず、macOS Keychainへ保存する。 plaintext WAVを一時fileとして書き出さない。
  6. Target Speaker Filterは登録完了後も自動でONにしない。Settingsでユーザーが明示的に有効化する。
  7. FilterがONのとき、model、Keychain、profile、inferenceのいずれかが利用不能ならfail-closedにする。 既存の未filter音声経路へ自動fallbackしない。
  8. FilterがOFFのときだけ現行の音声入力経路を維持する。rollbackで登録音声を自動削除しない。
  9. 通常Chatだけを対象とし、Meetingの複数話者文字起こしへ同じfilterを適用しない。
  10. 保存音声、embedding、similarity scoreを本人認証、決済、権限昇格、security decisionへ使用しない。

2. User Contract

2.1 登録

  1. SettingsのVoiceから「本人の声を登録」を選ぶ。
  2. 保存される内容、保存場所、用途、削除方法を確認して開始する。
  3. 異なる文章を5回、各6〜10秒話す。
  4. 各sampleの品質結果を確認し、再生、録り直し、削除を行える。
  5. 4件以上かつ合計20秒以上の有効発話が揃うとprofileを構築できる。
  6. holdout確認用の追加発話で本人一致を確認する。
  7. Target Speaker Filterを明示的にONにする。

2.2 日常利用

  1. 本人の声は通常の無音区間で確定し、文字起こしとLLM送信へ進む。
  2. 他者、テレビ、通知、SAAAのTTSだけが聞こえてもChatへ文字を追加しない。
  3. 判定不能な短文または重畳音声は送信せず、必要なら「本人確認できませんでした」と状態表示する。
  4. Filter状態、登録sample数、model状態をSettingsとChatのVoice statusで確認できる。
  5. FilterをOFFにしても登録音声は保持され、再度ONにできる。

2.3 保守

  • 保存sampleをローカル再生できる。
  • sampleを追加、個別削除、録り直しできる。
  • 全profileを削除すると、音声file、embedding、metadata、Keychain keyを削除する。
  • 入力device変更またはmodel更新後に、短い再確認またはembedding再構築を実行できる。

3. 達成すること

  1. Settings内で完結する、明示的で再開可能な本人音声登録flowを提供する。
  2. 登録音声fileをlocal-only、暗号化、bounded、原子的に永続保存する。
  3. 複数sampleからmodel-version付きspeaker embeddingを構築する。
  4. Filter ON時はspeaker verification成功後にだけpreview ASRとfinal ASRを許可する。
  5. 非本人音声がVAD endpointまたは自動送信を発火させないようにする。
  6. TTS中もcaptureを継続し、本人barge-inとTTS自己音声を可能な範囲で区別する。
  7. restart、model更新、file欠落、Keychain失敗、削除途中から整合した状態へ復旧する。
  8. 保存と判定の状態を、raw audioまたはbiometric値をlogせず観測できるようにする。

4. 非要件

  • 声紋による本人認証、login、権限付与、anti-spoof保証。
  • 本人の録音再生またはvoice cloneを攻撃として防ぐliveness detection。
  • 複数人が同時に話す音声から本人だけを完全分離するtarget-speaker extraction。
  • Meeting transcriptを一人の話者だけへ限定すること。
  • Cloud speaker verificationまたは判定前音声のLAN送信。
  • 登録音声のCloud backup、同期、共有、export package。
  • globalなRetention期限による登録音声の自動削除。
  • 保存音声をLLM Context、Memory、diagnostics、analyticsへ入力すること。
  • 音声による設定変更toolの実装。これは別計画で扱う。

8. Enrollment Capture Contract

not-enrolled
  ↓ begin
requesting-permission
  ↓ microphone ready
recording
  ├─ cancel → not-enrolled / existing-ready
  ↓ explicit stop or bounded maximum
analyzing
  ├─ quality rejected → review-rejected → retry / discard
  ↓ quality passed
encrypting-and-saving
  ├─ failure → failed; no completed row
  ↓ file + metadata committed
sample-ready
  ↓ enough samples
building-profile
  ├─ failure → degraded; filter remains OFF
  ↓ holdout verification passed
profile-ready
  ↓ explicit enable
filter-enabled

Capture invariant:

  • 一回のsampleは6〜10秒を推奨し、3〜12秒だけを受理する。
  • 保存可能なsampleは最大10件、合計120秒、暗号化file合計32 MiB以下とする。
  • canonical formatはPCM signed 16-bit、16 kHz、mono WAVとする。
  • capture元sample rate、effective AEC、noise suppression、input device hashをmetadataへ残す。
  • promptは5種類以上用意し、同じ文だけの反復登録を既定flowにしない。
  • TTS中、Meeting active / paused中、Chat capture中はEnrollmentを開始しない。
  • Settings離脱、app close、permission revokeでcaptureを停止し、未保存PCMを破棄する。

Quality gateの初期値:

  • 有効発話3秒以上。
  • voiced ratio 40%以上。
  • clipping sample比率0.5%未満。
  • 無音、DC offset、過小RMS、過大RMSをreason code付きで拒否する。
  • 既存sampleとのembedding重複が過度に高い場合も、同一録音の再送として拒否する。

RMS detectorはcheap prefilterに限定し、保存可否のspeech segmentationとembedding readinessは native VAD / speaker model側で判定する。thresholdはfixtureと実機dataを使ってSection 21のGateで固定する。

現行のChatとMeetingはそれぞれWebView側にcapture lifecycleを持つ。Settingsへ第三の独立した getUserMediaを直接追加すると競合するため、FrontendにAudioCaptureCoordinatorを追加する。

  one owner at a time

  1. Leaseはrandom tokenとownerを持ち、releaseはidempotentにする。
  2. Frontend leaseに加え、Backend commandもMeetingとTTS状態を再検証する。
  3. Settings captureはChatまたはMeetingを暗黙停止せず、競合理由と復旧操作を表示する。

  5. Track取得後にgetSettings()を読み、要求値ではなくeffective処理状態をsnapshotへ返す。

10. Audio File Storage and Encryption

10.1 Layout

app_data_dir/
└─ voice-profiles/
   └─ <opaque-profile-id>/
      └─ samples/
         └─ <opaque-sample-id>.wav.enc
  • directoryはowner-only、fileはowner read/writeだけのpermissionにする。
  • profile IDとsample IDはBackend生成のopaque IDだけを使用する。
  • DBにはfilenameだけを保存し、absolute pathとUser入力pathを保存しない。
  • symlink component、hard-link置換、root外canonical pathを拒否する。
  • model fileはsample directoryと分離し、profile削除でmodel artifactを消さない。

10.2 Encrypted container

SAAA-VOICE-SAMPLE
├─ magic + container version
├─ cipher suite = AES-256-GCM
├─ random 96-bit nonce
├─ authenticated metadata version
└─ ciphertext
   └─ canonical PCM WAV bytes

AADへprofile ID、sample ID、container version、canonical formatを含め、別profileまたは別rowへのfile差し替えを拒否する。 nonceを再利用せず、profileごとに生成した256-bit master keyは com.saaa.desktop.voice-profile.v1のservice identityとprofile ID accountでmacOS Keychainへ保存する。 HKDF-SHA-256の用途別contextからsample file用keyとembedding用keyをderiveし、keyを使い回さない。 Keychain itemへ音声file本体を保存しない。

Rust dependency候補はaes-gcm、hkdf、sha2、 zeroize、macOS Keychain bindingとする。採用version、license、security advisoryを TS-00で固定し、独自暗号を実装しない。

10.3 Atomic save

  1. PCM bounds、sample rate、qualityをmemory上で検証する。
  2. canonical WAVとembeddingをmemory上で生成する。
  3. random nonceでWAVを暗号化し、同一directoryのrandom temporary fileへ書く。
  4. flush、permission検査、authenticated read-back、ciphertext SHA-256を確認する。
  5. temporary fileをfinal filenameへatomic renameする。
  6. SQLite transactionでsample、encrypted embedding、profile revisionをcommitする。
  7. DB commit失敗時はfinal fileを削除する。削除失敗はorphan reconciliation対象として記録する。

plaintext WAVをdisk、diagnostics、stdout、temporary directoryへ書かない。

10.4 Playback and deletion

  • PlaybackはBackendで認証付き復号し、bounded memory bufferとしてFrontendへ返す。
  • 再生終了または取消時にFrontendのobject URLとbuffer参照を破棄する。
  • 個別削除はsampleをdeletingにし、filter参照から外してからfileを削除する。
  • 全profile削除はFilterを先にOFFにしてprofileをdelete-pendingにし、Keychain keyを削除して crypto-shredを成立させた後、ciphertext fileとDB rowを削除する。
  • Keychain key削除に失敗した場合は削除完了を表示せず、fileとrowを保持したまま再試行可能にする。
  • 削除失敗は成功表示せず、delete-pendingとして再試行できる。

Backendのplaintext WAV、PCM、embedding、key bufferは使用後に可能な範囲でzeroizeする。 JavaScript memoryの完全消去は保証できないため、bufferを上書きして参照とobject URLを速やかに破棄し、 Settings playback中のmemory residencyをboundedにする。

12. Speaker Model and Native Runtime

12.1 Model selection spike

TS-00でsherpa-onnxのspeaker embedding C APIを利用し、少なくともWeSpeaker系と 3D-Speakerの日本語利用候補を比較する。model名だけで選ばず、同じholdout corpusで次を測定する。

  • 本人accept率、他者false accept率、TTS false accept率。
  • 短文、通常文、小声、距離、入力device差、雑音、TTS重畳。
  • model load時間、embedding latency、memory、binary / model size。
  • arm64 macOS bundle、codesign、notarization、offline startup。
  • source、runtime、model weight、training dataに関するlicenseとNOTICE。

sherpa-onnx source licenseだけでmodel weightの再配布可否を推定しない。 選定modelに明示的な再配布根拠がない場合はG0を通過させず、別modelまたはuser-provided artifactへ切り替える。

12.2 Native boundary

  1. sherpa-onnx C APIをRustの専用wrapperから呼ぶ。PythonまたはNode runtimeをshipping dependencyにしない。
  2. App setupで専用worker threadを開始し、そのthreadだけがmodel instanceと全C handleを所有する。 AppStateはbounded request channelとhealth snapshotだけを保持する。
  3. Inference requestはrequest ID、deadline、profile revisionを持ち、UI threadとasync executorをblockしない。
  4. 一度に一件のembedding jobを実行し、bounded queueを越えたcandidateはfail-closedにする。
  5. C pointer、length、dimension、lifecycleをwrapperで検証し、panicをTauri command境界へ漏らさない。
  6. model artifactはversionとSHA-256をpinし、checksum不一致時はloadしない。
  7. app shutdownで新規requestを拒否し、queueを取消し、C handleをowner thread上で破棄してthreadをjoinする。

12.3 Reference and score

  • 各sampleから複数のvoiced window embeddingを生成し、外れ値を除外する。
  • queryは複数referenceとのcosine similarity上位値とrobust aggregateから算出する。
  • 固定sample codeにある例示thresholdをproduction defaultとして流用しない。
  • Enrollment sample同士のleave-one-out scoreと独立holdoutから二閾値を校正する。
  • score >= accept_at_or_aboveだけを本人として受理する。
  • score < reject_belowは非本人として破棄する。
  • 二閾値の間は追加音声を待ち、期限後も中間なら破棄する。

13. Normal Chat Target Speaker Gate

IDLE
  ↓ energy / candidate VAD
CANDIDATE
  ├─ keep 500 ms pre-roll
  ├─ collect at least model-ready voiced audio
  ↓ verify locally
VERIFYING
  ├─ accept    → VERIFIED_USER
  ├─ reject    → DISCARDING → IDLE
  └─ uncertain → CANDIDATE until maximum, then DISCARDING

VERIFIED_USER
  ├─ append accepted PCM
  ├─ re-verify sliding windows
  ├─ start preview only from accepted PCM
  └─ verified-user silence timeout → FINALIZING

FINALIZING
  ↓ final ASR with accepted PCM only
SUBMITTING
  ↓
IDLE

Gate invariant:

  1. Filter ON時、previewAudioとtranscribeAudioの直前にverified receiptを必須にする。
  2. Receiptはprofile revision、model checksum、candidate ID、accepted rangeを含み、別candidateへ再利用できない。
  3. Endpoint silence timerはverified user speech後にだけ進む。
  4. 非本人の発話終了はauto-finalizeまたはLLM queryを発生させない。
  5. 長い発話は1〜2秒ごとにsliding re-verificationし、speaker switch後の未確認tailを送らない。
  6. Filter ON中にprofile revisionが変わったcandidateは取消し、新しいprofileで再判定する。
  7. Verifier timeout、queue full、model unavailable、Keychain failureではASRを呼ばない。
  8. 短すぎる発話は本人と推定して通さず、再発話を促す。

Filter OFF時は現行経路を維持するが、共通capture coordinatorとresource releaseの改善は両経路へ適用する。 Speaker gateを追加するためにMeetingのsegment contractを変更しない。

14. TTS重畳、AEC、Barge-in

  1. Enrollment中はTTSを開始せず、TTS中はEnrollment開始を拒否する。
  2. 通常ChatはTTS中もcaptureを継続し、TTS lifecycleをspeaker gateへ入力する。
  3. echoCancellation: trueの要求だけで成功扱いにせず、trackのeffective settingを取得する。
  4. TTS-only candidateはspeaker mismatchとして破棄し、endpoint timerへ数えない。
  5. TTS中に本人scoreがaccept thresholdを越えたらbarge-inとし、TTSをfade / stopしてpre-rollから収録を継続する。
  6. TTSと本人が重なってuncertainならASRへ送らない。TTS停止後の追加発話を待つ。
  7. 実機評価でbarge-in gateを満たせない場合、system sayの直接再生を見直し、playback referenceを持てるaudio pathを別spikeする。

Speaker verificationはAECの代替ではない。AECは既知の再生音を減らし、speaker verificationは残った音声が 登録話者に一致するか判断する。単一microphoneへ複数音源が同時に強く入った場合の完全分離は本計画の保証外である。

提案command:

Contract rules:

  • Profile IDとfile pathをFrontendから指定させない。
  • Chunkはsequence、sample rate、sample count、total bytesをstrictに検証する。
  • Capture tokenは一回のsessionとownerに限定し、restart後に無効とする。
  • 一回のcaptureは最大12秒でBackendからも強制停止する。
  • Snapshotはfile path、embedding、Keychain identifier、exact scoreを返さない。
  • Decisionはverified-user、non-user、uncertainとbounded reason codeを返す。
  • Exact similarityはdebug buildの明示診断以外でFrontendまたはlogへ返さない。

Table: Failure behavior
Failure Required behavior

Startup reconciliation:

  1. DBにあるReady sampleのfile存在、root containment、permission、cipher authenticationをboundedに検査する。
  2. DBにないsafe-format fileはorphanとして隔離し、active profileが使用しない。
  3. deletingとdelete-pendingを再実行する。
  4. Model provenance不一致では保存WAVから新embeddingを別revisionへ構築する。
  5. 新revisionが完全にreadyになるまで旧revisionをatomicに切り替えない。

Stop condition:

  • 選定model weightの再配布licenseまたはNOTICEを確定できない。
  • 非本人音声が判定前にpreview / final ASRへ到達する経路が残る。
  • Keychain failure時にplaintext fileまたは未filter fallbackが発生する。
  • Meeting、Chat、Enrollmentが同時にmicrophoneを所有できる。
  • Section 20のnegative corpusでfalse accept gateを満たせない。
  • TTS中の自己応答loopを0件にできない。

20. Verification and Acceptance Criteria

20.1 Unit and property tests

  • 全state transition、cancel、restart、stale token、profile revision race。
  • PCM sample count、sample rate、sequence、duration、total byte bounds。
  • Resampling、WAV header、clipping、RMS、voiced duration、quality reason。
  • AES-GCM nonce uniqueness、AAD swap、bit tamper、wrong key、truncated file。
  • Safe path、symlink、unexpected extension、oversized file、duplicate ID。
  • Migration re-entry、old v10 fixture、newer version stop、foreign key cascade。
  • Model checksum、dimension mismatch、NaN embedding、empty output、native error。
  • Two-threshold decision、uncertain retry、timeout、queue full、profile revision change。
  • Filter ONでreceiptなしのpreview / final ASRを拒否する。

20.2 Integration and failure injection

  • 5sample登録、app再起動、再生、追加、個別削除、profile削除。
  • file rename直後、DB commit直前、DB commit直後、削除途中のcrash recovery。
  • Keychain locked / denied / missing、model missing / corrupt、disk full、read-only directory。
  • Chat、Meeting、Enrollmentの同時開始競合と全release path。
  • 非本人fixtureでgnosis mock request countが0、本人fixtureで一回だけ。
  • Previewが本人判定前に開始せず、accepted PCM以外を含まない。
  • Filter OFFで既存microphone、VAD、自動送信、ASR testが回帰しない。
  • Diagnosticsとbackup manifestにaudio、path、embedding、exact scoreが含まれない。

20.3 Model evaluation

Enrollmentに使っていない独立holdoutを使う。最低構成は本人200 utterancesを3日以上、2距離以上、 2voice level以上で収録し、negative 1,000 utterancesを5人以上、system TTS、media音声、通知音から構成する。 Corpusの利用許諾とprovenanceを記録する。

Table: Initial quality thresholds
Metric Gate

Non-target false accept rate 0.1%以下
TTS-only query submission 0件
Quoted / media speech query submission 0.1%以下
Uncertain fail-open 0件
TTS中の本人barge-in accept 90%以上
Verification latency p95 250 ms以下

20.4 Manual desktop acceptance

  1. Settingsで5sampleを登録し、全fileが再起動後も一覧と再生に残る。
  2. app data上のfileがplaintext WAVとして再生できず、UIからだけ再生できる。
  3. 本人が通常声、小声、少し離れた位置から話し、文字起こしと自動送信が成立する。
  4. 別人、テレビ、system TTSが話してもtranscriptとqueryが作られない。
  5. TTS中に本人が割り込み、TTS停止後にpre-rollを失わず本人発話が文字起こしされる。
  6. 短すぎる発話は誤って通過せず、再発話案内が表示される。
  7. Keychain accessを失った状態でFilterが未filter経路へfallbackしない。
  8. 個別sample削除後にprofileが再構築され、必要件数未満ならFilterがOFFになる。
  9. 全profile削除後にfile、row、embedding、Keychain itemが残らない。
  10. Meetingの複数話者captureが従来どおり動作し、Target Speaker Filterに影響されない。
