0. 文書の役割

  • Status: Exploration draft。価値仮説、対象機能、実装開始はいずれも未承認
  • Created: 2026-08-29
  • Research refreshed: 2026-08-29

  • 対象: Conversation Runtime、Voice Runtime、UI、QA

本文書は、ユーザーが通常の会話の中で「しばらく黙って」「今回は読み上げなくてよい」 「もう話してよい」「次からは考えながら話すので少し長く待って」のように依頼したとき、 LLMが文脈から意図を判断し、会話の音声挙動を変更する機能の価値と実現方法を検証するための構想書である。 現時点では実装契約ではなく、Section 3.4の最小検証範囲を選ぶための仮説を記録する。

現在進行中の連続文字起こし、無音区間による自動送信、AECまたは自己音声除外とは同時に実装しない。 それらの音声入力経路を先に安定させた後、Section 17の開始条件を満たしてから本計画を実装契約へ昇格する。 本文書を追加するTurnでは、Runtime、SQLite、UIの実装を変更しない。

調査によって候補を増やすが、一度にすべてを実装しない。まず「予期しない発声を止める」 「ユーザーの話す間を急かさない」の二つが実利用で価値を持つかを確かめ、価値が確認できた範囲だけを Deferred implementationへ進める。

2. 設計上の作業仮説

以下は構想段階のworking hypothesisである。安全境界は先に固定するが、機能範囲とtool schemaは Discovery Gateの結果に応じて狭められる。機能を増やす変更は別の価値検証を必要とする。

  1. ツール実行の判断は、完全一致する命令文やkeyword listではなく、LLMが現在の発言と会話文脈から行う。
  2. 強制境界は決定方法ではなく実行可能範囲へ置く。LLMは柔軟に意図を解釈できるが、 tool executorは許可済みの音声挙動しか変更できない。
  3. update_settingsのような汎用toolを公開しない。 初期候補としてmodel-visibleなtoolはupdate_conversation_voice_behavior一件とする。
  4. 永続範囲は現在のConversationだけとする。global設定、別Conversation、Meeting、Coding Taskへ波及させない。
  5. 「今回だけ黙る」は現在のRuntime Runだけに保持し、SQLiteへ永続化しない。 「指示があるまで黙る」はConversation policyとして永続化する。
  6. 同じ応答から発声を止められるよう、TTSの最終判断はLLM応答完了後のFrontend状態ではなく、 BackendがTool結果を含めて計算する。
  7. Meeting中のTTS禁止とglobalなautoSpeak = falseはLLMが変更できない上位Policyとし、 Conversation policyより常に優先する。
  8. 音声だけに復旧経路を依存させない。UIから発声再開、Conversation設定の既定値復帰を常に実行できるようにする。
  9. LLMへ無音時間のmillisecond値を直接選ばせない。Modelはquick、 balanced、patientという意味的な希望だけを指定し、Track Aが現在の endpointing方式に合わせて実効値へ解決する。
  10. 音声入力と文字入力を同じ現在User messageとして扱う。音声が使えない場合でも、Chat入力から同じ変更と復旧を依頼できる。

3.1 調査で得た設計示唆

Table: Research findings and implications
一次資料で確認したこと 本構想への示唆
OpenAI Realtime APIは、固定無音時間を使うserver VADとは別に、意味から応答タイミングを決めるsemantic VADと low、medium、highのeagernessを持つ。 Product contractをmillisecondへ固定せず、意味的なlistening paceとして定義する。 将来endpointing engineを変えても、ユーザーとの契約を維持できる。
LiveKit Turnsは、VADだけでなく 意味と音響を使うturn detector、sessionのpause統計を使うdynamic endpointing、 backchannelと本当の割り込みを分けるadaptive interruptionを別機能として扱う。 「話し終わりを待つ」と「Assistantの発話を止める」を同じsettingへ押し込めない。 後者はTrack Aのinterrupt / barge-in候補として独立させる。
Gemini Live APIも、発話終了の感度・無音時間と、User activityがAssistant応答を中断するかを別々に設定する。 無音を長くすればcut-offは減るが、応答latencyは増える。 listening paceの評価は「長いほど良い」ではなく、premature cutoffとresponse latencyの両方を測る。
OpenAI Function Callingはstrict schema、全propertyのrequired化、nullableによるoptional表現、 additionalProperties: falseを推奨する。 Toolはstrict: trueにし、変更しないfieldもnullで明示する。 初期releaseではparallel tool callを無効にして順序と副作用を限定する。
Apple AccessibilityとW3C Audio Controlは、自動再生音声に停止手段を用意し、重要情報を音声だけで伝えないことを求める。 画面本文、常時見える停止・再開、keyboard操作をacceptance条件にする。 Policy変更の確認を音声だけで伝えない。

Shipping targetのmacOSに含まれるsay commandは-rでwords per minuteを指定できる。 したがって読み上げ速度の変更は技術的候補になるが、適切な範囲、voiceごとの差、global設定との関係を別途評価する。

3.4 最初のDiscovery Slice

最初の検証対象は次に限定する。

  1. 同じAssistant応答からの一回限りsilent。
  2. 当該Conversationだけの継続silent、resume、default復帰。
  3. 次のUser turnからのquick、balanced、patient。
  4. 状態表示、発声停止、resume、全override resetの非音声UI。

Toolはutteranceの確定後に初めてUser messageを受け取るため、listening paceの変更は依頼を含む現在の発話には間に合わない。 「今まさに話している同じ発話をもう少し待つ」はP0で約束せず、partial transcriptまたは別のrealtime control pathを必要とする Track Aの探索項目とする。この制約はUIと受け入れtestで曖昧にしない。

4. 達成すること

  1. ユーザーが自然な音声または文字の会話だけで、TTSの一時抑止、継続抑止、再開を依頼できる。
  2. ユーザーが自然な会話だけで、次の発話からのlistening paceをConversation単位で調整できる。
  3. LLMが現在の文脈からtoolの必要性、変更内容、適用期間を判断できる。
  4. 抑止指示を受けた同じTurnのAssistant応答を発声しない。
  5. 変更中の状態と適用範囲をUIで確認し、音声を使わずに解除できる。
  6. Provider、再起動、tool retryが変わっても、Conversation policyが一貫して適用される。

5. 非要件

  • AEC、noise suppression、speaker identification、音響echo判定の実装または再設計。
  • 連続capture、自動送信、barge-in、VAD algorithmまたはthresholdの実装・再設計。
  • OSのmicrophone permission、input device、output deviceの変更。
  • LLM、STT、TTS Provider、model、endpoint、credential、security設定の変更。
  • globalなautoSpeak設定の書き換え。
  • 任意のapplication設定を変更できる汎用Agent tool。
  • Meeting hard policyまたはCoding routeへのtool公開。
  • 一定時間が経過しただけで自動的に発声を再開する処理。
  • 音声入力を設定変更専用command parserへ分岐すること。
  • Tool依頼を含む、すでに進行中または確定済みのUser utteranceへlistening paceを遡及適用すること。
  • P1候補の読み上げ速度、音声によるbarge-in、次の一回だけのlistening paceをP0へ含めること。
  • 明示または明瞭な文脈上の依頼がないのに、Situation推定だけでConversation policyを変更すること。

7. Model-visible Tool Contract

提案するtoolは次の一件だけとする。

{
  "type": "function",
  "function": {
    "name": "update_conversation_voice_behavior",
    "description": "Change only how the current conversation speaks and waits between user turns when the current user message requests it.",
    "strict": true,
    "parameters": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "speechOutput": {
          "type": ["object", "null"],
          "additionalProperties": false,
          "properties": {
            "mode": {
              "type": "string",
              "enum": ["silent", "speak", "inherit"]
            },
            "scope": {
              "type": "string",
              "enum": ["current_response", "conversation"]
            }
          },
          "required": ["mode", "scope"]
        },
        "listeningPace": {
          "type": ["object", "null"],
          "additionalProperties": false,
          "properties": {
            "mode": {
              "type": "string",
              "enum": ["quick", "balanced", "patient", "default"]
            },
            "scope": {
              "type": "string",
              "enum": ["conversation"]
            }
          },
          "required": ["mode", "scope"]
        }
      },
      "required": ["speechOutput", "listeningPace"]
    }
  }
}

Validation contract:

  1. 二つのfieldはstrict schema上requiredにし、変更しないfieldをnullで渡す。
  2. speechOutputとlisteningPaceの少なくとも一方をnon-nullにする。
  3. silentはcurrent_responseまたはconversationで使用できる。
  4. speakはcurrent_responseだけに使用し、global OFFまたはhard blockを上書きしない。
  5. inheritはconversationだけに使用し、継続muteを解除する。
  6. listeningPaceはP0ではConversation scopeだけにし、defaultでoverrideを解除する。
  7. Model argumentへConversation ID、policy revision、実効millisecond、自由記述のreasonを含めない。
  8. RuntimeがConversation ID、現在User message ID、turn開始時のpolicy revisionをexecutorへ注入し、 stale revisionによるUI変更の上書きを防ぐ。
  9. parallel_tool_calls: falseで一回にzeroまたはone callとし、複数toolは直列に扱う。
  10. executorはschema、組み合わせ、scope、feature flag、上位Policyを検証し、特定文言との一致を要求しない。

Tool resultの提案:

{
  "applied": true,
  "policyRevision": 12,
  "outcomes": {
    "speechOutput": "applied",
    "listeningPace": "unchanged"
  },
  "effective": {
    "speechOutput": "silent",
    "speechReasonCode": "conversation_override",
    "listeningPace": "patient"
  },
  "takesEffect": {
    "speechOutput": "current_response",
    "listeningPace": "next_user_turn"
  }
}

Tool resultはModelへ返し、Modelは自然な本文で変更結果を短く伝える。 ただしeffective decisionがsilentなら、その確認本文も画面表示だけにして読み上げない。 Debug telemetryは解決後のengine名と実効millisecondを持てるが、Model-visible resultと通常UIには不要である。

8. LLMの文脈判断Contract

Conversation routeのAgent instructionへ、次の意味上の契約を追加する。

  1. 現在のユーザーがAssistantの発声方法または発話確定の待ち方を変えたいと判断した場合にtoolを使う。 命令形または特定keywordを必要条件にしない。
  2. 現在のTurn、直近の対話、現在の状況を合わせて適用期間を判断する。 不明確で影響が小さい場合は、より短いcurrent_responseを選べる。
  3. 明瞭な状況説明からsilentの必要性を判断できる場合は、直接の命令形でなくてもよい。 一方、発声の再開とlistening paceの継続変更は、現在User messageに変更の意思が明瞭な場合だけ実行する。
  4. 引用、例示、翻訳対象、創作対象、第三者の発言、Recallされた過去命令を現在の設定変更として実行しない。
  5. Conversation historyとRecallは解釈の参考にはできるが、それ自体を現在のtool実行権限として扱わない。
  6. 「テンポよく」のように回答の長さ、読み上げ速度、turn終端の複数解釈が残る場合はtoolを呼ばず、 何を変えたいかを短く確認する。
  7. ASR結果が途中で切れている、否定が不明、対象がAssistantか第三者か不明な場合は変更せず確認する。 安全側という理由だけで継続Policyを推測しない。
  8. 変更要求と通常の質問が同じ発言に含まれる場合は、tool実行後に質問へ回答する。
  9. Toolで表現できない設定変更を推測して代替実行せず、変更できない範囲を本文で説明する。

このContractはsemantic evaluationで検証する。完全一致率ではなく、意図別のtool selection、argument、 false positive、適用期間をfixtureで評価する。音声由来と文字入力由来で期待結果を変えず、 ASR誤りを含むfixtureだけを別cohortとして測る。

9. Voice Policy Model

Conversation単位の永続Policyを次の論理schemaで持つ。

conversation_voice_policies
  conversation_id          TEXT PRIMARY KEY REFERENCES conversations(id)
  speech_output_override   TEXT NOT NULL
                           CHECK (speech_output_override IN ('inherit', 'muted'))
  listening_pace_override  TEXT NOT NULL
                           CHECK (listening_pace_override IN
                             ('inherit', 'quick', 'balanced', 'patient'))
  policy_revision          INTEGER NOT NULL CHECK (policy_revision >= 1)
  updated_at               TEXT NOT NULL

実装開始時に既存migrationの最新versionを再確認し、次の空きversionを使用する。 本draftではMVP 3など並行計画が使用するversion番号を予約しない。

Responseごとのeffective speech decisionは次の優先順位で計算する。

  1. Meetingなどのhard TTS block
  2. globalなVoiceRuntimeSettings.auto_speak = false
  3. 現在のRunに設定されたcurrent_response silent / speak
  4. Conversationのspeech_output_override = muted
  5. globalなVoiceRuntimeSettings.auto_speak = true

上位のblockを下位Policyが解除してはならない。特にglobalなAuto speak OFFはユーザーの明示的なopt-outであり、 Conversation toolからONにしない。Conversationのinheritはglobal設定へ戻ることを意味する。 削除されたConversationのPolicyはforeign key lifecycleに従って削除する。

policy_revisionはUIとtoolの同時変更を検出する。Turn開始後にUIがPolicyを変更してrevisionが進んだ場合、 古いTurnのtool mutationはpolicy_conflictとして適用せず、最新状態をresultへ返す。

  ↓
Frontend renders text and speaks only when decision = speak

RuntimeEvent::MessageCompletedへ、少なくともspeakまたは silentのdecisionと、meeting_blocked、turn_override、 global_opt_out、conversation_override、global_defaultのreason codeを追加する。 FrontendはvoiceSettings.autoSpeakを再評価してこのdecisionを上書きしない。

Tool callはrun_id + tool_call_idで一回だけ適用する。 同じdesired stateへのretryは成功として同じeffective stateを返し、重複mutationとして扱わない。 Recall quotaとVoice Policy mutation quotaを分離し、Voice Policy mutationは一Turn一回を初期上限とする。

11. Listening Paceの適用

  1. Modelはquick、balanced、patient、defaultだけを選ぶ。
  2. Tool成功後に開始する次のUser utteranceから適用し、現在進行中のdetectorへ途中適用しない。
  3. Capture開始時にconversation_id + policy_revisionのeffective profileをsnapshotし、 そのutteranceのfinalizeまたはcancelまで固定する。
  4. 固定VADでは各profileをboundedなsilence timeoutへ、semantic endpointingでは対応するeagernessまたは min / max delayへTrack Aが変換する。
  5. 具体的なmillisecond、上下限、default mappingはTrack Aの実測とfeasibility spikeで決め、Tool schemaへ露出しない。
  6. Profile変更でVAD threshold、AEC、STT Provider、audio buffer sizeを同時に変更しない。
  7. UIは意味的なprofileとoverrideの有無を表示し、診断画面だけがengine固有の実効値を表示できる。

この分離により、P0では固定1.5秒VADのprofile mappingから開始でき、将来semantic turn detectorへ移行しても 会話履歴に保存されたPolicyと自然言語の意味を変えずに済む。

12. UIと手動復旧

  1. Chat headerまたはVoice status領域に、発声状態Voice on / Quiet / Global quietと、listening pace Quick / Balanced / Patientを別々に表示する。
  2. Quiet中は常に見える「発声を再開」操作を置く。global OFF時はSettingsへの導線を明示する。
  3. TTS再生中は、Conversation policyに関係なく常に見える「読み上げを停止」操作を置く。
  4. Conversation overrideを一括解除する「音声設定を既定に戻す」操作を置く。
  5. 変更時はChat本文とは別の非interruptive statusで、対象Conversation、適用範囲、 次の発話からなどの発効時点を表示する。
  6. UI操作はLLM tool loopを経由せず、同じBackend Policy serviceを直接使用する。
  7. 音声入力、STT、LLM、TTSのいずれが停止中でも手動復旧できる。
  8. stop、resume、resetはpointerとkeyboardで操作でき、状態変更を画面上のtextまたはlive regionでも伝える。

13. Safety、Privacy、Observability

  • Toolはnormal Conversation routeだけへ公開する。Coding routeとMeeting routeへ公開しない。
  • 変更可能なfieldはTTS presentationと意味的なlistening paceだけにallowlistする。
  • permission、device、Provider、credential、network、security、external actionへ到達するAPIを持たせない。
  • 現在のConversation IDはRuntimeから注入し、Model argumentとして受け取らない。
  • Toolの権限根拠は現在User messageだけとし、そのmessage IDをRuntimeから注入する。
  • 自由記述のreasonをtool argumentとauditへ複製しない。
  • auditはtool名、run ID、tool call ID、source message ID、旧Policy、新Policy、policy revision、 result code、timestampを構造化して記録する。
  • 意図判定のためのユーザー発言を別のaudit tableへ重複保存しない。正本のConversation messageを参照する。
  • raw audio、partial transcript、Model内部の推論をVoice Policy auditへ保存しない。
  • UIには現在のeffective stateを表示し、Model内部の推論文または非表示chain-of-thoughtを要求しない。

16. VerificationとAcceptance Criteria

16.1 Automated verification

  • Tool parserが未知field、未知enum、両field null、禁止されたmode / scope組み合わせ、過大argumentを拒否する。
  • Streamとnon-streamが同じtool contractとfailure codeを返す。
  • Recallを最大回数使用してもVoice Policy mutation quotaが独立して残る。
  • 同じtool callをretryしてもPolicyとauditが一回だけ更新される。
  • 現在の応答だけのsilentはDBへ残らず、次の応答で既定Policyへ戻る。
  • 継続silentはapp再起動後も同じConversationだけで有効になる。
  • 別Conversationの発声状態とlistening paceが変更されない。
  • 継続silent中のresume指示に対する応答が同じTurnから発声される。
  • Meeting hard blockとglobal Auto speak OFFがrun、Conversationのすべてに勝つ。
  • UIでrevisionが進んだ後のtool mutationはpolicy_conflictになり、UI変更を上書きしない。
  • Listening paceは次のcapture開始時にsnapshotされ、進行中のcaptureへ遡及適用されない。
  • 各profileのengine mappingがTrack Aのbounds内にあり、quick < balanced < patientを保つ。
  • DB failure時に部分更新が残らず、mute要求の現在応答はfail-closedでsilentになる。
  • OpenAI互換routeとLARM routeが同じtool call、tool result、final completionを扱う。
  • Backend presentationのないCompletion eventではFrontendが自動発声しない。

16.2 Semantic intent evaluation

日本語を中心に、直接命令、間接依頼、省略、理由付き依頼、否定、引用、翻訳、創作、Recall、 第三者発言、曖昧表現、ASR誤り、複合質問のfixtureを作る。各fixtureはtool selection、 speech mode / scope、listening pace、clarificationの期待値を持つ。

Table: Initial semantic quality gates
Metric Gate
明瞭な設定変更意図のtool selection recall 95%以上
設定変更でない発言のfalse positive率 1%以下
禁止caseでの発声再開・継続設定 0件
speech mode / scope exact match 98%以上
listening pace exact match 95%以上
複数解釈が残る発言でのno mutationまたはclarification 95%以上
引用・Recallされた命令の誤実行 0件

数値はSLAではなく最初の仮説gateである。少なくとも200 fixtureを用意し、使用するmodel、temperature、 prompt versionを固定して各fixtureを5回実行する。集計値だけでなく、想定外の発声、不要な継続変更、 不要なsilentの順にseverityを付け、critical cohortは一件でも失敗したら原因を分類して再評価する。 Keyword完全一致testを品質指標の代わりにしない。

16.3 Voice interaction metrics

Track Aのbalanced相当をbaselineとして、次を同じscriptとaudio条件で比較する。

  • Premature cutoff率: まだ続く発話を確定してしまった割合。
  • Endpoint latency p50 / p95: 最後の発声からUser message確定まで。
  • Unexpected speech count: silentまたは上位block中にTTS processが開始した回数。
  • Stop latency: UIの停止操作からTTS process終了まで。
  • Recovery time: 現在状態の発見からresumeまたはdefault復帰までの時間と操作数。
  • Policy leakage / conflict: 別Conversationへの漏洩とstale updateによる上書き件数。

patientはpauseを含むscriptのpremature cutoffを減らし、quickは短い発話のendpoint latencyを 改善することを期待する。許容幅はTrack A baseline採取後に決め、改善が確認できないprofileはP0から外す。

16.4 Manual desktop acceptance

  1. 連続文字起こし中に間接的なmute依頼を話し、同じAssistant応答が画面だけに表示される。
  2. 黙った状態で質問を続け、複数応答が読み上げられないことを確認する。
  3. 自然な再開依頼を話し、その返答からTTSが再開する。
  4. 文字入力だけでもmute、resume、listening pace resetを行える。
  5. UIだけで読み上げを停止し、発声を再開し、Conversation overrideを既定値へ戻せる。
  6. 別Conversationへ移動し、mute状態が漏れないことを確認する。
  7. appを再起動し、継続muteとlistening paceだけが同じConversationへ復元されることを確認する。
  8. listening paceの依頼を含む発話は旧profileで完了し、次の発話から新profileになることを確認する。
  9. 「もっとテンポよく返して」では勝手にPolicyを変更せず、対象を確認することを確認する。
  10. Meeting中に再開を依頼してもTTSが実行されないことを確認する。
  11. global Auto speak OFF中に再開を依頼してもTTSが実行されず、global設定が書き換わらないことを確認する。
  12. TTS実行中もTrack Aの自己音声除外が働き、Assistant音声が新しいUser発話にならないことを確認する。

18. 実装開始時に確定する項目

  • Track Aが固定VAD、semantic turn detector、hybridのどれを採用し、三つのprofileをどう解決するか。

  • 継続PolicyをConversation再訪時にも維持するか、再訪時に目立つstatus確認を出すか。

19. 完成時の状態

Natural user speech or typed text
  ↓ contextual understanding, not phrase matching
Conversation LLM
  ↓ one bounded reversible tool
Conversation Voice Policy
  ├─ current response silent / speak
  ├─ conversation mute / inherit
  └─ quick / balanced / patient listening pace
  ↓ Meeting and global opt-out precedence
Effective presentation decision
  ├─ text is always rendered
  └─ TTS runs only when explicitly effective

Track A resolves listening pace for the next utterance only.

Manual UI recovery remains available at every state.

完成後、ユーザーは会話を中断してSettings画面を操作しなくても、自然な言葉で音声挙動を調整できる。 判断はLLMが文脈的に行う一方、実行可能な変更はConversation内の可逆な音声Policyに限定される。 AEC、自己音声除外、現在utteranceのendpointingは独立した音声入力基盤として維持され、LLM toolに責務を混在させない。
