5. Fixed implementation decisions

5.1 One operator-only runner

readiness toolingはscripts/larm-readiness.tsへ集約し、次のsubcommandを持つ。

  • preflight: local validationとhealth / readyだけを実行する
  • canary: bounded functional scenarioとmanual checkpointを実行する
  • soak: 30分または2時間のbounded workloadと観測を実行する
  • report: raw captureを持たず、allowlist済みsummaryだけを出力する

runnerはSSH command、remote shell、systemctl、llama-swap APIを実行しない。private tunnelと LARM restart、capacity fixtureは運用担当がrunner外で準備する。runnerはloopback originの到達性と checkpoint結果だけを検証する。

runner自身はLARMへHTTP requestを送らない。preflight、metrics取得、allocation、Gateway、releaseを含む すべてのLARM通信はSection 5.3のRust live suiteを通し、production clientと同じno-proxy、no-redirect、 timeout、body limitを使用する。TypeScript側に二つ目のLARM protocol implementationを作らない。

local child processはすべてargument arrayを使うBun.spawnで起動し、shell、command interpolation、caller-provided executableを使用しない。working directoryはrepository rootへ固定する。

networkへ接続できるRust live childとpackaged appにはcaller environment全体を渡さない。Rust childはtoolchain / temporary-directory / certificate variable、canary / enable flag、base URL、deployed commit、revision、runner-owned result / hash / metrics scope variable、LARM_API_TOKENだけ、packaged appはOS 起動に必要なvariable、canary / enable flag、runner-owned marker、data directory、 LARM_API_TOKEN、固定rollback Providerのcredentialだけを明示的に渡す。proxy variable、Codex credential、無関係な*_TOKEN / *_API_KEYは除外する。release build childもcredential-shaped variableを除外し、渡すenvironment key名をunit testで固定する。

5.1.1 CLI contract

package scriptはすべて同じrunnerへ委譲する。

{
  "larm:preflight": "bun scripts/larm-readiness.ts preflight",
  "larm:canary": "bun scripts/larm-readiness.ts canary",
  "larm:soak": "bun scripts/larm-readiness.ts soak",
  "larm:report": "bun scripts/larm-readiness.ts report"
}
  • --report-dir <absolute-path>を全subcommandで必須にする。
  • soakだけが--duration 30m | 2hを必須で受け取る。
  • reportは同じdirectoryにある四つのfinal mode reportだけを入力にする。
  • base URL、token、prompt、turn count、remote commandをCLI argumentとして受け取らない。
  • unknown argument、重複argument、symlink、既存fileの上書きを拒否する。

canaryはpassed preflight report、soak --duration 30mはpassed functional report、soak --duration 2hはpassed soak-30m reportを同じdirectoryに要求する。commit、artifact SHA-256、manifest SHA-256、deployment revisionのいずれかが現在値と一致しないreportは前提として使わない。各predecessorの finalActiveAllocationsがpreflightの baselineActiveAllocationsと一致しない場合も、後続modeを開始しない。

runnerがmonotonic clockで測るhard deadlineは次に固定する。

  • preflight: 30分
  • canary: 60分

stdoutはformat、mode、resultだけを持つ一行JSONに限定する。 stderrは固定progress codeまたは固定error codeだけを一行ずつ出し、path、environment、HTTP body、identifierを含めない。

5.2 Triple opt-in for live traffic

G3前のreadiness runでは、health / readyを含むlive requestを次がすべて成立する場合だけ許可する。 SAAA_LARM_CANARYはoperator toolingの追加gateであり、G3後の通常production runtimeへ新しい必須flagとして追加しない。

  1. SAAA_LARM_CANARY=1
  2. SAAA_LARM_ENABLED=1
  3. LARM_API_TOKENがprocess environmentに存在する

これらはrunner processの開始条件である。functional bootstrapで最初に起動するpackaged app childだけは、Settings作成とdirect rollback test中のLARM通信を構造的に禁止するため SAAA_LARM_ENABLED=0を渡す。LARMをprimaryへ保存した後、runnerが同じartifactを SAAA_LARM_ENABLED=1で再起動してからlive UI scenarioを開始する。

runnerとtest-only live suiteのbase URLはSAAA_LARM_CANARY_BASE_URLから読み、packaged appはisolated Settingsに保存された同じoriginを使う。preflightはenvironmentとG2 manifestの一致を検証し、functional canaryは最初のLARM request前、soakはapp起動前にSQLite上のSettingsとの一致を検証する。MVP 2.6と同じnumeric loopback originだけを受理する。flag不足、token不足、relative URL、hostname、credential付きURL、path、query、fragmentはnetwork access前に失敗させる。token値をcommand line argumentとして受け取らない。

live runでは、triple opt-inに加えて次のmetadataを必須にする。

  • SAAA_LARM_DEPLOYED_COMMIT: G1 commitと一致する7〜64文字のlowercase hex
  • SAAA_LARM_DEPLOYMENT_REVISION: 1〜64文字のASCII [A-Za-z0-9._-]
  • SAAA_LARM_CANARY_REPORT_DIR: CLIの--report-dirと同じabsolute path
  • SAAA_SMOKE_DATA_DIR: G2で確定したcanary専用application-data directoryのabsolute path
  • SAAA_LARM_CANARY_MANIFEST_FILE: Section 5.2.1のoperator-owned manifestへの absolute path

metadataの値は対応するreport allowlist fieldがある場合だけ複製する。manifest path、data path、base URLはreportへ出力しない。CLIとenvironmentのreport directoryが canonical pathとして一致しない場合は、file作成とnetwork accessの前に失敗させる。 SAAA_SMOKE_MARKER_IDとSAAA_SMOKE_EXERCISE_SITUATIONがcaller environmentに存在する場合も拒否し、runnerが必要な値だけをchildへ設定する。

LARM_API_TOKENと、manifestでrequiredになったrollback credentialは1〜4,096 byte、HTTP headerへ安全に変換でき、whitespaceとcontrol characterを含まないことをmemory上で検証する。 値同士の比較、hash化、report出力は行わない。

5.3 Test-only live suite

実際のLarmProvider、allocation lifecycle、Gateway parserを再利用するlive testは、 src-tauri/src/providers/larm/live_canary.rsへtest-only moduleとして置く。すべてのtestを #[ignore]にし、通常のcargo test、bun run check、CIから実行しない。 production Tauri command、hidden UI flag、通常buildで呼べるremote control surfaceは追加しない。

functional UI確認は隔離packaged appで手動実施し、live suiteは反復可能なadapter lifecycle、 workload、timing、cleanup観測を担当する。この二つを同じ結果として扱わない。

ただしsoak modeではRust suiteからallocationまたはGateway requestを送らない。runnerが隔離packaged appを起動し、operatorが通常UIから固定promptとcancelを実行する。TypeScript runnerはlocal SAAA processのRSSとisolated SQLiteだけを観測し、Rust suiteはLARM metricsのread-only observerとして動く。 これによりmemory、persistence、route、cleanupを実際のshipping processで測定する。

runnerはmodeごとに一つの完全修飾test名を指定し、 cargo test --manifest-path src-tauri/Cargo.toml <exact-name> -- --ignored --exact --test-threads=1で起動する。 --ignoredだけでrepository内の他のignored testを一括実行しない。Rust suiteは SAAA_LARM_CANARY_RESULT_FILEで指定された新規fileへredacted fragmentをatomic writeし、 runnerはschema検証後にだけaggregate reportへ取り込む。result fileはreport directory直下の regular fileに限定し、symlinkと既存fileを拒否する。 

.preflight-rust.json
.functional-rust.json
.soak-30m-rust.json
.soak-2h-rust.json

runnerはmodeから上記以外のresult filenameを生成しない。Rust側のatomic writeに使うtemporary fileも 同じdirectoryでexclusive createし、mode 0600、symlinkなしとする。runnerまたはchildが 途中終了してinternal fileが残ったrun directoryは再利用せず、新しい空directoryで再実行する。

三件目のTTL recoveryでは、functional test binary自身をexact test名で専用子processとして一回だけ 起動する。子processはallocation後、Gatewayとreleaseを呼ばずに終了する。親へ渡す一時file .ttl-client-exit.txtはeffective TTLのdecimal一行だけ、16 byte以下、mode 0600とし、allocation idなどのidentifierを含めない。親は子processの終了を確認してから fileを削除し、metricsによるTTL回収を待つ。timeout時は同じ子PIDだけを終了する。

SAAA_LARM_CANARY_RESULT_FILEはrunnerがmodeから導出してchild processだけへ設定する内部値である。 caller environmentに同名variableが存在する場合は開始前に拒否し、任意pathへの書き込みを許可しない。

artifact hashとmanifest hashはrunnerが SAAA_LARM_CANARY_ARTIFACT_SHA256と SAAA_LARM_CANARY_MANIFEST_SHA256としてchildへ渡す内部値である。caller environmentに同名variableがあれば拒否する。Rust fragment、local observation、前mode reportのhashが一致しなければmergeまたは後続modeを開始しない。

child cargo testのstdoutとstderrはrunnerが各1 MiBを上限にcaptureし、terminalへ転送しない。captureはforbidden-data scannerへ逐次渡し、検出時は redaction-failedとする。上限超過時はchildをcancelしてinternal failureとし、capture内容を保存せず破棄する。test failure時もrunnerは Section 5.1.1の固定errorだけを返すため、Rust assertion messageにはraw responseを含めない。

  • providers::larm::live_canary::live_functional
  • providers::larm::live_canary::observe_soak_30m
  • providers::larm::live_canary::observe_soak_2h

reportはRust live testを起動せず、既存fragmentの検証と集計だけを行う。

5.4 Canary isolation

live evidenceにはclean SAAA commitから作ったrelease-mode macOS app bundleを使う。runnerは固定bundle path src-tauri/target/release/bundle/macos/SAAA.appと、その内部の固定executable Contents/MacOS/saaaだけを受理する。bundle directoryと全entryのsymlinkを拒否し、main executableがregularかつexecutable、build開始時と同じGit commitであることを確認する。debug binary、 cargo test process、任意の--app pathをshipping artifactとして扱わない。

saaaArtifactSha256はmain executable単体ではなく、bundle内の全regular fileから作る canonical bundle digestとする。relative pathのUTF-8 byte列で昇順sortし、ASCII SAAA-BUNDLE-V1\0、path byte lengthのunsigned 32-bit big-endian、path bytes、file sizeのunsigned 64-bit big-endian、各fileのraw 32-byte SHA-256を順にouter SHA-256へ入力する。directory 自体はhash materialに含めず、regular file以外のentry、hard link、bundle外へ解決するentryを拒否する。

release buildはpreflightだけが実行し、後続modeはartifactを再buildせずcanonical digest一致を確認する。build childのstdoutとstderrは各8 MiBを上限にcaptureしてterminalへ転送せず、forbidden-data scannerへ逐次渡す。検出、失敗、または 上限超過時はnetwork access前に終了する。各fileとouter digestはbundle全体をmemoryへ全読込せずstreamingで計算する。

一つのcanary runは次を専有する。

  • 絶対pathで指定された一時application-data directory
  • canary専用SettingsとSQLite
  • canary専用environment
  • 一つのlocal loopback tunnel
  • 一人のoperator
  • 一つのdirect rollback Provider

通常profileのapplication-data directory、Settings、SQLite、process environmentを再利用しない。 data directoryがrepository root、home directory、filesystem root、既存の通常profileを指す場合は拒否する。 data directoryとreport directoryはcanonical pathで異なり、一方が他方のancestorでもdescendantでも ないことを要求する。 runnerはdirectoryを自動削除せず、run終了時に保存・破棄対象をoperatorへ表示する。

packaged appの隔離起動には、既存desktop:smokeと同じ SAAA_SMOKE_MARKER_ID / SAAA_SMOKE_DATA_DIR契約を再利用する。marker idはcryptographically secure random 128 bitから作る canary-<32 lowercase hex>としてprocess起動ごとに新規生成する。起動前に同名markerが 存在しないこと、ready時にregular fileでsymlinkではないことを確認し、ready確認後にmarker fileを削除する。 SAAA_SMOKE_EXERCISE_SITUATIONは設定しない。新しいproduction用 data-directory overrideやhidden Tauri commandは追加しない。

packaged appのstdoutとstderrも各1 MiBを上限にrunnerがcaptureし、terminalやreportへ転送しない。 captureはforbidden-data scannerへ逐次渡し、該当があればappを停止して redaction-failedとする。上限超過もfailedとし、capture内容はrun終了時に破棄する。

G2ではcanary時間帯をLARMの排他的な観測windowとして予約する。LARM metricsが client: saaa-desktopを安全に集計できる場合はclient-scoped countを使い、できない場合は 他のallocationが0件であることをoperatorが確認してからbaselineを取得する。どちらも満たせない場合は allocation leakとRuntime selectionを判定できないためG2をblockedとする。

direct rollback Providerは、LARMとは別の既存OpenAI-compatible Provider local-openai-compatibleとしてisolated Settingsへ登録する。credentialが必要な場合は 固有のSAAA_PROVIDER_LOCAL_OPENAI_COMPATIBLE_API_KEYだけをpackaged appへ渡し、 OPENAI_API_KEYの暗黙fallbackを使わない。non-mutating LARM preflight後は、最初にdirect Providerだけをrouteへ置き、feature flag OFFのpackaged appで一回完走させる。 完走後にoperatorがLARMをprimary、direct Providerを直後のfallbackへ設定し、保存結果を再読込してからrunnerがappを停止する。次に同じartifactと data directoryをfeature flag ONで再起動し、Settingsを再読込してから最初のLARM allocationへ進む。 このbootstrap restartはsaaaRestartsへ数えない。この遷移中にLARM requestが一件でも発生した場合はfailedとする。 direct Provider testでは、 endpoint、model、credentialが有効であることを確認する。この事前確認はLARM failureによる自動fallbackではなく operator testとして実施する。 Section 8.2と同じ固定canary prompt catalogを使う。promptとresponseは通常のshipping経路どおりisolated SQLiteにだけ保存し、 report、log、release evidenceへ複製しない。local-only policyが有効な場合はCloud Providerをrollback先にしない。このturnは rollbackPreflightTurnsへ一件だけ計上し、通常stream 5件へ含めない。

このdirect ProviderはMVP 2.6 Section 7.3で許可したoperator-owned移行例外であり、LARM route selectionの入力、Runtime policyの正本、恒久的な二重設定として扱わない。撤去時期はG3後のenablement decisionで別途決める。

8. Readiness runner contract

8.1 Preflight

preflightは次の順で実行する。

  1. repositoryとSAAA commitを確認する。dirty treeは記録し、production evidence runでは拒否する。
  2. triple opt-in、numeric loopback origin、absolute isolated data directoryを検証する。
  3. G2 manifestをstrict検証し、environmentと一致するSHA-256を確定する。
  4. report directoryのowner permissionを検証する。
  5. Git commitを再確認してからbunx tauri build --bundles appでrelease appをbuildし、build後も commitとclean treeが変わっていないことを確認する。
  6. fixed release app bundleのcanonical digestを計算し、後続mode用のartifact hashを確定する。
  7. compiled CONTRACT_COMMIT、SAAA_LARM_DEPLOYED_COMMIT、G1 target commitが一致し、LLM server deployment revisionが指定されていることを検証する。
  8. G2 manifestのdirect rollback Provider値と必要credentialの存在だけを検証し、推論は開始しない。
  9. preflight前のactive allocation baselineを取得し、0であることを要求する。
  10. /healthを一回呼ぶ。
  11. /readyを一回呼ぶ。
  12. G1で固定した非mutating probeを使い、Bearerなし、誤token、正tokenの境界を各一回確認する。 既定probeはsynthetic idへのGET /v1/allocations/:idとし、正tokenでは not_found、不正credentialではunauthorizedを期待する。
  13. 誤tokenはmemory上で32 byte以上のrandom値を生成し、一回のprobe後に保持しない。
  14. response content type、body上限、timeout、redirect禁止を検証する。
  15. active allocation countがpreflight前のbaselineから変化していないことを確認する。
  16. redacted preflight reportをatomic writeする。

preflightはallocation、operation、Gateway、resolve、renew、releaseを呼ばない。health / ready失敗時は bounded failureとし、自動反復しない。

  1. serverがallocationを作成した後にcreate responseを遮断し、blind retryせずTTL回収を待つ。
  2. completed Gateway turnのrelease送信直前にtransportを遮断し、一回のrelease attempt失敗後に再送せず TTL回収を待つ。
  3. allocation取得後、Gateway前にtest clientを終了し、process消失後のTTL回収を待つ。

一件目と二件目は、live suite開始前にLARM operatorがcanary clientだけを対象とするone-shot failure sequenceとして準備する。順序はcreate-response遮断、release-response遮断に固定し、各条件は 一度発火したら自動解除する。captureされたRust childから対話的な合図を出したり、runnerからremote fault commandを送ったりしない。G2でこのdeterministic fixtureを用意できない場合はfunctional runを 開始しない。

8.3 Soak

runnerはSection 5.4の隔離contractでpackaged SAAAを起動し、operatorはSection 8.2の固定prompt catalogを繰り返し使用する。turnとcancelの実績はisolated SQLiteのterminal stateから数え、UI操作回数の 自己申告だけでminimum workloadを満たしたことにしない。Rust metrics observerはsoak中にallocation、 Gateway、releaseを呼ばない。

runnerはpackaged appのready確認後、UI workload開始前に対応するRust metrics observerを起動する。 observerの最初のsampleがpreflight baselineと一致してからworkloadを開始し、最後のturnのcleanup後に final baselineを取得するまでobserverを終了しない。runnerはlocal RSS / SQLite samplingとobserverを 同時に監視し、どちらか一方の早期終了またはdeadline超過をrun全体のfailedとして扱う。

raw metricsはreportへ保存せず、allowlist済みnumeric sampleだけをmemory上で集計する。 metrics labelにprompt、response、token、identifier、endpointが一件でも見つかった場合は即時停止する。

一回のmetrics responseは1 MiB、1行は16 KiB、sampleは4,096件をSAAA側のhard limitとする。 connect timeoutは5秒、request全体deadlineは10秒とし、同時に複数scrapeを実行しない。 G1で固定したcontent typeとallowlist metric名以外を判定材料にせず、必要metricの欠落、duplicate series、 非finite value、cardinality上限超過はcontract-mismatchとしてrunをfailedにする。

durationとdeadlineはmonotonic clockで測る。RSS、SQLite、allocation countは5秒間隔で取得する。 RSSまたはSQLiteの最大sampling gapが15秒を超えたrunはmemory / persistence gateを評価せずfailedとする。 LARM metricsも通常gapは15秒以下を要求するが、2-hour modeの30〜40分に一回だけ、operatorが実施する LARM restartに伴う1〜120秒の観測済みgapを一回だけ許可し、gapが0のrunをrestart実施済みとみなさない。 metrics responseは一行ずつallowlist parserへ渡し、sampleへ変換した直後にraw textを破棄する。

elapsedMsはmonotonic clock由来とし、30-minute modeは1,800,000 ms以上、2-hour modeは7,200,000 ms以上を要求する。RFC 3339のwall-clock timestamp差をduration判定へ使わない。

30-minute modeのrssRangeMiBはminute 10〜30から計算し、二つのRSS median fieldは0とする。 2-hour modeだけが次の60分memory windowでrangeとmedian差の両方を評価する。

2-hour soakでは、最初のSAAA processを70分以上連続稼働させる。最初の10分をwarm-upとして除外し、 minute 10〜40をprevious、minute 40〜70をlastとする二つの重複しない30分windowを使う。 rssRangeMiBはminute 10〜70全体、二つのmedian fieldはそれぞれのwindowから計算し、 評価完了後にSAAAを一回restartする。 LARM restartは最初の30〜40分、SAAA restartは70分のmemory window完了後に実施する。 LARM restartもactive runが0件であることをSQLiteで確認してからoperator checkpointへ進み、復旧後の 最初のturnで新しいallocationを確認する。restart後は残り時間でroute、allocation、rollback configurationの保持を確認し、restart前後のRSS sampleを 一つのseriesへ混在させない。

functional、soak-30m、soak-2hは同じisolated SQLiteを継続利用する。各mode開始時に既存 runtime_runsとprovider_sessionsのbounded identifier集合をmemory上へsnapshotし、 そのmodeで新規作成されたrowだけをworkload countと結果判定へ使う。snapshotとidentifierはreportへ 保存せず、mode終了時に破棄する。wall-clock timestampだけでmode境界を判定しない。

SAAA restartはactive runが0件であることをSQLiteで確認してからrunnerがlocal processだけを停止し、同じ isolated data directoryと更新後environment、新しいmarker idで再起動する。10秒以内にfrontend ready markerとSQLite reopenを確認できなければrestart recoveryをfailedとする。LARM daemonやtunnelはこのlocal restartに 連動して操作しない。

8.4 Report finalization

reportは次を行う。

  1. runごとのschema version、commit、artifact SHA-256、manifest SHA-256、revision、modeを検証する。
  2. preflight、functional、soak-30m、soak-2hが各一件あり、commit、artifact SHA-256、manifest SHA-256、revisionがすべて一致することを要求する。
  3. 各input fileのSHA-256をmemory上で計算し、同じmode reportを重複集計しない。
  4. 必須scenario countとthresholdをpure functionで評価する。
  5. forbidden key、credential pattern、本文候補、identifier候補を再走査する。
  6. failedまたはblockedをpassedへ手動上書きしない。
  7. release evidenceへ転記するbounded summaryを生成する。

report commandは四つのfinal mode reportからmode: aggregateのfinal reportを一件だけ作り、HTML文書を 自動編集しない。生成したsummaryをoperatorがrelease evidenceへ転記し、 reviewerがcommit、revision、mode、resultを照合する。gate stateは pending | passed | failed | blockedのいずれかとし、failedまたはblocked evidenceを waiverでpassedへ変更しない。

aggregateではscenario / result countを加算し、timingは最大値、failure codeは和集合にする。 各modeのbaselineActiveAllocationsが一致し、各modeのfinalがそのbaselineへ戻ることを要求し、 maxActiveAllocationsは全modeの最大値を使う。RSS三fieldはsoak-2h、lease summaryはfunctionalから 引き継ぐ。これらのsource modeがfailed、blocked、欠落の場合はaggregateをpassedにしない。

10. Security and privacy

  • transportはSAAA host上のnumeric loopback originだけを許可する。
  • LAN上のplain HTTP originへ接続しない。
  • runnerはsystem / environment proxyを使用しない。
  • redirectを追従しない。
  • Bearer tokenをSQLite、Settings、report、log、command historyへ保存しない。
  • runnerのerrorはbounded codeと固定文言に正規化し、raw response bodyを表示しない。
  • promptには固定の非機密canary textだけを使い、実会話または実workspace contextを送らない。
  • Rust live suiteのresponseはassertionと文字数上限の評価後に破棄する。packaged UIのpromptとresponseはisolated SQLiteだけに保存し、report、log、release evidenceへ複製しない。
  • report directoryはrepositoryとapplication-data directoryの外に置き、reportを自動追加または 自動commitしない。
  • runnerはgit add、git commit、git pushを実行しない。
  • machine-readable mode reportからはaggregate summaryだけをrelease evidenceへ転記する。G1、G2、manual、 security、runbook evidenceはそれぞれの専用欄に記録する。

live suiteはcanary / enable flag、base URL、deployed commit、revision、G2で固定したmetrics scope、LARM_API_TOKEN、 runner-owned SAAA_LARM_CANARY_RESULT_FILE / SAAA_LARM_CANARY_ARTIFACT_SHA256 / SAAA_LARM_CANARY_MANIFEST_SHA256だけを明示的に読み、process environmentを enumerateしない。report directory、data directory、manifest path、rollback credentialは渡さない。 token rotationではcanaryを停止し、LARM側tokenを更新し、operator-owned launcherのenvironmentを更新してSAAAをrestartする。LARM operatorは旧tokenの失効だけをattestし、新tokenは 新しい空のreport directoryでSection 8.1のpreflightを通す。旧tokenと新tokenをreportまたはrunbookへ 記録しない。

LLM server上のLARM log auditはLARM operatorがserver側で実施し、raw logをSAAA hostへ転送しない。 release evidenceにはtoken、prompt、response、identifier、endpointの検出件数と監査時刻だけを記録し、 すべて0件でなければG3をfailedとする。

streaming forbidden-data scannerは4,095 byteのrolling overlapを保持し、chunk境界をまたぐ最大4,096 byteのcredentialも検出する。検出対象はmemory上のcredential exact value、manifestのendpoint、固定prompt literal、既知identifier、Authorization / Bearer patternとし、match内容自体はerrorまたはreportへ出さない。

11. Error, retry, and interruption policy

  • authentication、contract、protocol、413、internalはretryしない。
  • health / readyは一回だけ呼び、自動pollしない。
  • allocation pending pollは既存LARM Providerのdeadlineとbackoffを使う。
  • allocate outcome unknownはblind retryせず、TTL回収scenarioへ記録する。
  • 最初のnon-empty delta後はProvider fallback、reallocation、同一request retryを禁止する。
  • capacity failureはretry stormを起こさず、明示されたcanary scenario一件として終了する。
  • runner interruption時は進行中requestをcancelし、bounded releaseを一回だけ試行する。
  • release failureはinference結果を上書きせず、cleanup resultへ分離する。

17. Release and rollback policy

M261-00〜08の完了だけでは通常profileを変更しない。M261-09でG3 passedとなった場合に、初期利用範囲を operator-owned profileまたは明示的に選ばれた少数profileへ限定する。段階的有効化中もdirect Providerを rollback routeとして維持する。

rollbackは二段階とする。

  1. Settings rollback: LARMをrouteから外し、新しいturnをdirect Providerへ送る。
  2. Kill switch: SAAA_LARM_ENABLEDをOFFにしてprocessを再起動する。

rollbackは進行中streamのBindingを変更しない。進行中turnはcancelまたは既存bindingでterminalへ進め、 新しいturnからroute変更を適用する。
