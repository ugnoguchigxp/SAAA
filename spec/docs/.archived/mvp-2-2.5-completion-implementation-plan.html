1. 結論と固定判断

  1. MVP 2のshipping scopeはmicrophone-only Meetingのまま固定する。System Audio、Translation、 Floating Overlayを本closeoutへ追加しない。
  2. Meetingの残作業は、real microphone、real LLM server ASR、permission lifecycle、partial/final表示、 Save/Discard、TTS guard、30分・2時間soakの実機証跡である。
  3. Input Activityの残作業は、実時間category遷移、lock/sleep lifecycle、monitoring off時のOS API call 0件、development/署名済みbundleでpermission prompt 0件を記録することである。
  4. Agent Run Supervisorの自動contractは作り直さない。残作業はshipping UIからの到達性を確定し、 実Codexでlong reasoning、Cancel連打、app close、restart reconcile、read-only violationを検証することである。
  5. 現行UIは通常ChatをSessionlessにした一方、coding.assistの操作、Codex状態、workspace選択を 削除している。既存のMVP 0／2.5 contractを維持する場合、通常Chatとは別resourceとして最小Coding Surfaceを復元する。復元しない場合は実装前にconcept、README、MVP 0 acceptance、MVP 2.5 acceptanceを 明示的に改訂し、Agent Runをshipping scopeから外す承認を必要とする。
  6. 推奨判断は最小Coding Surfaceの復元である。過去実装e4fbb53を参考にできるが、現在の Sessionless normal Chat、Voice、Meeting、Memory baselineへ古いConversation UIを戻さない。
  7. 未確認、実行不能、証跡欠落、署名identity欠落はPassとして扱わない。該当Gateをpendingまたは blockedに保つ。

4. SafetyとEvidence境界

reportへ保存してよい情報:

schemaVersion
suite / mode / caseId
SAAA commit and canonical bundle digest
OS version / architecture / signing class
operator pseudonym
startedAt / completedAt in UTC
pass | fail | blocked and bounded reason code
event type counts and relative timing
RSS samples and bounded resource counters
SQLite row counts and terminal status counts
permission prompt count and indicator release latency

report、release evidence、consoleへ保存してはならない情報:

credential / token / Authorization header
provider endpoint / SSH host / private IP
prompt / response / transcript text
raw or encoded audio
workspace path / database path / home directory
Codex thread id / turn id / runtime request id
window title / application identifier / raw input duration
raw provider event / raw system log / screenshot containing user data
  • 検証は専用の空app-data directoryと専用の一時workspaceだけを使い、ユーザーの通常DBを開かない。
  • Meetingでは人工音声または公開利用可能な短文だけを発話し、reportへ内容を残さない。
  • Codex workspaceは検証用fixtureから作り、実repositoryや未commit user worktreeを渡さない。
  • report directoryは絶対pathの空directoryを要求し、mode 0700、file 0600、上書き禁止とする。
  • runnerはcredential、endpoint、prompt、remote commandをCLI argumentとして受け取らない。

6. Validation runner contract

2026-08-29 implementation checkpoint: 下記CLI、strict schema、case matrix、bounded threshold、MeetingとInput ActivityのRSS median sampling、forbidden-data scan、実行前後の commit／bundle／Apple署名chain整合、fixture workspace自動digest確認、mode 0600 atomic report、report set digest、上書き拒否を実装し、contract testを追加した。各functional/manual caseはbuild class別にまとめ、開始前に対象PIDがdebugまたは署名済みbundleの実行ファイルと完全一致することを確認する。専用app-data環境変数は runtime自身が検証し、DB、voice profile、diagnostics、backupを通常data directoryへ書かない。実機reportはまだ作成しておらず、Gate G2〜G6は未通過である。

  • preflightはclean tree、commit、bundle digest、bundle identifier、architecture、署名検証、専用data directoryを確認する。
  • verifyはoperatorのcase入力をstrict enumとして受け、自由記述のprompt、transcript、pathを受けない。
  • resource samplingは外部processからRSSとprocess existenceだけを取得し、app内部へdiagnostic bypassを追加しない。
  • 各caseは一度だけterminal resultを書き、既存reportを上書きしない。
  • reportは全suiteのcommit、bundle digest、OS、signing class一致を要求し、一つでもmissing/failedならAcceptedを返さない。
  • manual checkboxだけではPassにしない。対応するtimestamp、bounded observation、artifact digestを必須にする。

C25-00 — Contract alignment and clean baseline

  1. 未commit WIPをreview可能なcommitへ確定するか、本検証から除外したclean refを選ぶ。
  2. bun run check、bun run build、bun run spec:check、bun run desktop:smokeを実行する。
  3. coding.assistをshipping scopeへ維持するかを決定する。
  4. 維持する場合は最小Coding Surfaceを復元し、通常Chatのcanonical conversation、Voice continuous listening、Meeting capture ownershipを変更しない。
  5. 廃止する場合は本書を停止し、concept、README、MVP 0 evidence、MVP 2.5 acceptanceを同時に改訂してreviewを受ける。

Gate G0: clean commitから全自動検証が成功し、Agent Run acceptanceがshipping UIまたは承認済みの改訂contractから 実行可能であること。

C25-01 — Evidence runner and isolated environment

  1. Section 6のCLI、strict schema、atomic file contractを実装する。
  2. dedicated app-data、fixture workspace、report directoryの分離をpreflightで確認する。
  3. reportのforbidden-data scannerを実装し、全fileをaggregate前に走査する。
  4. 実行中appと子processのPIDだけを保持し、終了後に存在しないことを確認する。
  5. bundle署名とdigestの不一致、dirty tree、report再利用を開始前に拒否する。

Gate G1: fake report fixtureでunknown field、content leak、digest mismatch、missing case、overwriteがすべて拒否されること。

C25-02 — Meeting functional desktop matrix

development buildと同一commitの署名済みpackaged buildで、次をそれぞれ実施する。

  1. microphone permissionを未決定状態に戻し、初回許可でpreflight後のtrackが解放されること。
  2. permission拒否でcapture 0、Start disabled、recovery表示になること。
  3. active中のpermission revokeまたはdevice lossでFailed/Pausedへ安全に遷移し、bufferとtrackを解放すること。
  4. real LLM server ASRへ人工音声を送り、同じlane/sequenceのPartialがFinalへ置換されること。
  5. pause 5分でtranscriptが増えず、microphone indicatorが5秒以内に消えること。
  6. resumeで新しいcapture tokenを使い、sequenceの重複や逆行がないこと。
  7. Stopを連打しても一つのCompleted snapshotになり、indicatorが5秒以内に消えること。
  8. Meeting active/paused中にChat TTSが開始されず、既に再生中ならMeeting開始前に停止されること。
  9. Surface移動、window unmount、通常のapp closeでtrack、AudioContext、in-flight ASR、queueが残らないこと。

表示証跡はevent type、lane、sequence、相対時刻だけをreportへ保存する。transcript textを保存せず、screenshotを使う場合は transcriptとhost情報を不可逆にマスクする。

Gate G2: 全caseが両buildでPassし、permission/indicator/cleanupの未確認項目が0件であること。

C25-03 — Meeting persistence and resource soak

  1. 専用DBでMeeting開始前、Completed後Save前、Save後、reopen後、Discard後のrow countを採取する。
  2. Save reviewに保存先、final件数、検出言語、raw audio非保存が表示されることを確認する。
  3. Save後はFinalだけが保存され、件数とoriginal_languageのnon-null/null状態がUI reviewと一致することを確認する。
  4. DiscardとSaveしないapp closeではtranscript body 0件であることを確認する。
  5. 30分soakでは5秒segment、in-flight ASR最大1、queue最大2を維持し、pause/resume/stopを各1回含める。
  6. 2時間soakではreal ASRを継続し、45分と90分でpause/resume、終了前にStopを実施する。

resource threshold:

  • 30分: warm-up後最初の5分と最後の5分のRSS中央値差が48 MiB以下。
  • 2時間: warm-up後最初の15分と最後の15分のRSS中央値差が64 MiB以下。
  • 全mode: queue 2以下、in-flight ASR 1以下、未回収child/task 0、unexpected transcript persistence 0。
  • pause/stop/app close後: microphone indicator 5秒以内消灯、app child process 5秒以内終了。

thresholdを超えた場合、単発の最大値だけでwaiveしない。RSS sample、queue bound、処理件数を用いて原因を修正し、 新しいreport directoryで全soakを再実行する。

Gate G3: functionalと両soakが同一commit/bundleで成功し、Save/DiscardのDB差分がcontractと一致すること。

C25-04 — Input Activity lifecycle and privacy

development buildと署名済みpackaged buildの両方で実施する。

  1. Situation monitoring offでsymbolic breakpointのOS API hitが10秒間0件であること。
  2. monitoring onでsampleが開始し、UIとcontractにはcategory/healthだけが現れること。
  3. keyboard、mouse、trackpadの各操作後30秒以内にactiveへresetすること。
  4. 30秒超から5分以内にrecent、5分超でidleへ遷移すること。
  5. screen lock/unlock、sleep/resume後にpanicせず、bounded categoryまたはdegraded fallbackへ戻ること。
  6. Accessibility/Input Monitoring permission promptが両buildで0件であること。
  7. 最終commitで30分sampling soakを再実行し、890 sample以上、RSS増加32 MiB以下を維持すること。
  8. SQLite、diagnostics、Tauri payload、frontend state、console、reportにraw duration/last-input timestampが0件であること。

Gate G4: lifecycle 8項目がPassし、permission prompt 0件、privacy leak 0件であること。このGate通過後だけADR 0003をAcceptedへ変更できる。

C25-05 — Agent Run reachability and lifecycle

認証済みのpackaged Codexと専用fixture workspaceを使い、次を実施する。

  1. SettingsでCodex enabled/authenticated/read-only状態を確認し、Coding Surfaceへ到達する。
  2. normal read-only turnがstreamし、terminal event 1件、SQLite completedになること。
  3. 複数のmeaningful progressを伴うlong reasoningがprogress timeoutを誤発火させず完了すること。
  4. turn開始後の単一Cancelと10回の連続Cancelを実施し、interrupt最大1、child/task残存0を確認する。
  5. active run中の通常window closeでcancel/cleanupが完了し、app processとCodex childが5秒以内に終了すること。
  6. 専用data directoryのappを強制終了し、restartで残存running rowがinterrupted/app-restartedになること。
  7. workspace変更を要求するread-only violationで変更0、承認UI 0、Network/Web Search/write MCP 0を確認する。
  8. 各case後にgit status --shortとfixture digestが開始前と一致することを確認する。

prompt、response、workspace path、thread/turn idはreportへ保存しない。case ID、event count、terminal status、 interrupt count、workspace digest一致だけを保存する。

Gate G5: 全case成功、workspace差分0、child残存0、terminal event重複0、raw provider data leak 0。

C25-06 — Regression, signed package, and aggregate

  1. 全修正後のclean commitからSection 11のcommandを実行する。
  2. 同じcommitからdebugとrelease相当の署名済みbundleを作り、canonical digestを記録する。
  3. G2〜G5を最終bundleで再実行し、古いreportを再利用しない。
  4. forbidden-data scanner、report schema、commit/digest identityを検証する。
  5. aggregateはmissing/blocked/failed caseが一件でもあればnot-acceptedを返す。

Gate G6: 全reportが同一identityでPassし、自動検証、実機検証、privacy scanの欠落が0件。

C25-07 — Evidence closeout

  1. MVP 2 evidenceへMeeting functional、soak、persistence、cleanupの結果とreport digestを転記する。
  2. MVP 2.5 evidenceへInput Activity、Agent Run、MVP 2 Accepted参照、report digestを転記する。
  3. Input Activity spikeへmanual resultを追記し、ADR 0003を条件成立時だけAcceptedにする。
  4. test件数、commit、bundle digest、OS、signing class、operator、UTC実行期間、既知制限を記録する。
  5. 全条件成立時だけ両release evidenceをAcceptedへ変更する。

9. Defect handling

  1. caseがFailしたら同じreportを編集せず、failure reasonを確定して終了する。
  2. 再現testを可能な限り自動suiteへ追加してからproduction codeを最小修正する。
  3. 関連するbun run checkとfocused testを実行する。
  4. 新しいclean commitと空report directoryで、そのGateの全caseを最初から再実行する。
  5. 修正が他のGateのidentityまたは挙動へ影響する場合、G2〜G6を再実行する。

reportの手編集、failed caseだけの削除、古い成功reportとのmerge、thresholdの実行後変更を禁止する。

10. Stop conditions

次のいずれかが発生したら次Gateへ進まず、issue、ADR、または本書の改訂を行う。

  • coding.assistを維持するか廃止するか未決定で、Agent Run acceptanceが実行不能
  • clean commitまたはproduction相当の署名identityを用意できない
  • real LLM server ASRが利用不能でPartial/Finalを確認できない
  • microphone indicatorがpause/stop/app close後も残る、またはraw audioがfileへ残る
  • Meeting queue 2、in-flight ASR 1、RSS thresholdのいずれかを超える
  • Input ActivityだけでAccessibility/Input Monitoring permission promptが出る
  • raw input duration、prompt、transcript、credential、private endpointがreportまたはlogへ出る
  • Agent Runがfixture workspaceを変更する、approvalを要求する、Network/Web Search/write MCPを実行する
  • Cancel/app close後にCodex child、reader thread、async task、running SQLite rowが残る
  • release evidenceのPass判断にoperatorの推測または未保存の口頭確認が必要になる

13. Acceptance criteria

13.1 MVP 2

  1. real microphoneのgrant、deny、revoke/device lossが安全に処理される。
  2. real LLM server ASRでPartialが同じlane/sequenceのFinalへ置換される。
  3. pause、resume、stop、surface移動、app closeでcapture resourceがbounded time内に解放される。
  4. Meeting active/paused中はTTS、notification、Agent/Application actionが起動しない。
  5. Save前のtranscript bodyは0件で、明示Save後だけFinalがtransaction保存される。
  6. DiscardとSaveなしcloseではtranscript bodyが残らない。
  7. 30分・2時間soakでqueue、in-flight、RSS、process cleanup thresholdを満たす。
  8. development buildと署名済みpackaged buildの両方に証跡がある。

13.2 MVP 2.5

  1. MVP 2がAcceptedである。
  2. Input Activityの実時間category、lock/sleep recovery、monitoring off call 0が確認される。
  3. Input Activityによるpermission prompt、raw duration persistence、policy境界違反が0件である。
  4. shipping Coding Surfaceから実Codex normal/long/cancel/close/restart/violationを実行できる。
  5. Agent Runのinterruptは最大1、terminal eventは1、child/task/running row残存は0である。
  6. read-only fixture workspaceの変更、Network、Web Search、write MCP、approval要求が0件である。
  7. 最終clean commitの全verification commandが成功する。

13.3 Evidence

  1. 全reportが同じSAAA commit、bundle digest、OS、architecture、signing classを参照する。
  2. 全caseに開始・終了UTC、operator、bounded observation、terminal resultがある。
  3. forbidden-data scannerの検出件数が0である。
  4. missing、ignored、blocked、failed、waivedをPassへ変換していない。
  5. MVP 2と2.5のrelease evidenceが各acceptanceとartifact digestを相互参照できる。
