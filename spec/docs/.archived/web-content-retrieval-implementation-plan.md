# Web 本文取得の改修計画

作成日: 2026-09-23。状態: **実装済み（固定テスト確認済み）**。


レビュー追補: 短い本文・値を保持し、表の値を項目と期間ごとに分離した。長い表セルでも項目・期間を各候補へ繰り返して保持する。質問と異なる会計区分・期間の値を候補から外し、自然文の四半期・会計年度表現を正規化した。長いタイトルでも返却上限を超えないようにした。公開 HTTP URL を契約どおり扱い、HTML 解析を期限で中断可能な実行枠へ移した。sidecar への変換前にも Rust 経路と同じ入力検証を行う。

## 1. 目的と成功条件

公開 Web ページから質問に必要な根拠を、少ない通信量・短い待ち時間・小さい LLM Context で取得する。HTML の構造は本文の選択と意味の復元にだけ使い、モデルへは読みやすいテキストと引用に必要な既存メタデータを渡す。数値と項目名・期間の対応を失わない。

次ラウンドの成功条件は、固定評価ケースで現行実装より根拠取得率を改善し、取得できたケースのモデル向け文字数中央値を増やさず、公開 URL 制限・キャンセル・総期限を維持すること。実際に失敗した Nvidia URL が特定できれば必須ケースに追加する。特定できなければ Nvidia の公開決算ページを代表例にするが、元の失敗を再現したとは主張しない。

## 2. 現状と問題

現行の macOS 経路は `src-tauri/src/runtime/web_fetch/content.rs` から、先に `static_content.rs` の HTML 取得を試し、本文が短いか検索語が一つもないとき WebView へ進む。`static_content.rs` は `main` / `article` 内の `h1`・`p`・`li`・`td`・`th` 等を個別の文字列にし、先頭 1,000 件を対象に語の一致数で並べる。既定返却上限は 2,500 文字。モデル向け契約は `web_fetch/mod.rs` と `contracts.rs` にある。

現状では、共通語一つの一致で取得成功になり、目的の数値が無くても WebView に進まない。表のセルを個別に並べるため指標・期間・数値の対応が壊れる。対象候補は順位付け前に切られ、静的取得に使った最大 8 秒は WebView の残り期限を減らす。`text/plain` は全文先頭を返し、質問に応じた選択がない。取得品質の実ページ評価もまだない。

## 3. 範囲と非目標

### 範囲

- `fetch_content` の静的 HTML 抽出、本文選択、WebView 移行条件、返却テキストを改善する。
- URL・DNS・リダイレクト検査、応答サイズ、期限、キャンセル、セキュリティ判定を維持・検証する。
- `web_search` の結果から別 URL を試すべき状態をモデルが識別できるようにする。検索プロバイダー自体の順位付けは変更しない。
- 固定 HTML フィクスチャと任意の live canary による取得品質・速度・文字数評価を追加する。

### 非目標

- DOM、HTML タグ、CSS、JavaScript、属性一覧を LLM に送らない。
- 本文の要約・正誤判定のために追加の LLM 呼び出しを行わない。
- サイト全体のクロール、リンク追跡、ログイン、クリック、フォーム操作を追加しない。
- DB スキーマ、記録の保存方式、ASR と初回会話応答の凍結領域を変更しない。
- Bun sidecar を全面改修しない。互換性を保ち、macOS の Rust 経路を主な実装・評価対象とする。

## 4. 提案する取得フロー

### 4-1. Stage A: HTML 一回取得

既存の公開 URL 制限と DNS 接続先固定を維持し、HTML 本体だけを上限付きで取得する。CSS・JS・画像は取得しない。リダイレクトごとに URL と接続先を再検査する。HTTP 状態、Content-Type、文字コード、ページタイトル、最終 URL、通信・解析に要した時間を内部結果として記録する。圧縮された応答と宣言文字コードは正しく復号する。異常なサイズや未対応形式は WebView 候補とする。

静的取得の時間上限は総期限から動的に決める。まず短い接続・応答予算を与え、WebView に必要な最低残時間を確保する。固定 8 秒を常に消費してから移行する形はやめる。キャンセルは DNS、送信、受信、解析のどの段階でも効かせる。

### 4-2. Stage B: ページ内の証拠候補を作る

HTML を内部の軽量な証拠単位へ変換する。各単位には、見出し階層、本文段落、箇条書き、表の行、DOM 順序、可視性、文字数を保持する。`main` / `article` は優先するが、そこが空・短い・質問と無関係なら `body` の候補も評価する。ナビゲーション、フッター、広告、重複、非表示、script/style は候補から除く。

表は `th` と `td` を独立させず、行見出し・列見出し・値を一つの単位にする。例えば `FY2026 Q2 | Data Center revenue | $...` のように、表の見出しと値を結び付ける。見出しから離れた段落には直近の見出しを内部情報として付ける。長文を単一の候補として保持せず、安全な文字数で分割し、隣接候補を参照できるようにする。候補数は上限を設けるが、DOM の先頭だけで使い切らず、ページ全体を有界に走査して選ぶ。`text/plain` も行・段落に分け、先頭から機械的に切る代わりに同じ質問対応の選択を行う。

### 4-3. Stage C: 決定的な候補選択と段階的拡張

`query` を日本語・英語の双方で扱える形に正規化する。社名などの一般的な主語だけより、指標・製品・期間・固有名詞を高く評価する。同じ単位または近接単位で複数の重要語が揃う候補を優先し、表の項目名と値は必ずセットで選ぶ。日付・数値を求める質問では、対応する値がある候補を優先する。ただし語の一致は「回答の真偽」の保証には使わない。

同じ HTML を再取得せず、まず高順位の数単位を選び、足りなければ隣接段落・同じ節・次順位の節へ探索範囲を広げる。初期候補・拡張候補を内部で評価してから、モデルには必要な最小量を一度で返す。候補が不十分なら静的取得を成功扱いせず WebView へ進む。モデルが再取得する必要がある場合だけ `maxCharacters` を増やす。返却文字数の初期上限 2,500 は暫定値とし、実測で調整する。

### 4-4. Stage D: WebView と別の検索結果

静的 HTML が空、チャレンジページ、本文不足、要求した値の候補不足、または JS 描画依存なら WebView に進む。WebView の結果にも同じテキスト選択規則を適用できる範囲で適用する。現行プラグインは DOM 関係を平坦化して返すため、動的ページの表に必要な関係が失われるケースは固定フィクスチャで確認する。必要な関係を復元できない場合は、依存する LLM-fetch プラグインの抽出契約を最小限拡張して固定リビジョンを更新し、同じ評価ケースを再実行する。数値の対応を推測して補わず、このケースを未解決のまま品質完了としない。

WebView でも根拠候補が無ければ `insufficient` を返し、モデルに次の検索結果を試すようツール説明で指示する。同一 URL への無制限再試行は避ける。検索スニペットだけで質問を満たす場合は、従来どおりページ取得を省略できる。

## 5. モデルに渡す契約

`document.text` はプレーンテキストを基本とする。HTML タグや DOM 記述、装飾目的の Markdown を含めない。意味を保つため、見出しは短い行、表は `項目: 値（期間: ...）` のような短い行に変換する。見出しの `#` や強調の `**` を既定では使わず、同じ固定ケースをプレーンテキスト版と最小限の Markdown 版で比較し、回答根拠の読み取り精度が上がり、Token 増分が許容できると確認できた場合にだけ採用する。

既存の `url`・`fetchedAt`・`truncated`・`security` を保持する。追加が必要なら最小限の `retrievalStatus`（`relevant` / `partial` / `insufficient`）と `retrievalMethod`（`html` / `webview`）だけを検討する。`partial` は根拠候補があるが、質問に必要な対象・指標・期間・値の一部を確認できない状態とする。`query` がない場合は関連性を判定できないため、本文を返しても `relevant` と断定しない。ページ本文を取れたことと、回答に必要な根拠を取れたことを区別する。これらは内部判定の説明であり、モデルに「事実は確定した」と主張するものではない。

返却の例:

```text
NVIDIA 決算発表 — FY2026 Q2
売上高: $...（FY2026 Q2）
データセンター売上高: $...（FY2026 Q2）
```

例中の値は書式を示す仮値であり、実際のデータを意味しない。

## 7. 検証と受入基準

### 固定ケース

ネットワークに依存しないフィクスチャを用意する。最低限、(1) Nvidia 型の決算表、(2) 長いナビの後にある本文、(3) `main` が空で `body` に本文があるページ、(4) JS 描画前の空 HTML、(5) チャレンジページ、(6) 日本語の質問と本文、(7) 英語の質問と本文、(8) 長い一段落、(9) `text/plain`、(10) リダイレクト・非公開 DNS・巨大応答・キャンセルを含める。各ケースに「返すべき根拠の文字列」「返してはいけない値」「期待する段階」を明記する。ローカルの模擬 HTTP 応答では、HTML 段階が CSS・JS・画像の URL を追加要求しないこと、WebView に進む条件と残り期限も確認する。

### 比較指標

同じ入力・同じ保存 HTML を変更前後で実行し、**必要な指標と値と期間が対応した形で返った割合**、根拠欠落を成功とした割合、モデル向け文字数と JSON payload bytes、取得時間（中央値と遅いケース）、HTML→WebView 移行率、エラー率を比較する。Provider が usage を返す live レーンでは入力 Token 数も記録する。固定ケースは全件で期待した根拠を返し、誤った数値の対応付けと根拠欠落の成功扱いをゼロにする。動的ページのフォールバックは同条件の現行経路より 2 秒以上遅くしないことを目標にし、超えた場合は HTML 段階の時間配分を見直す。live ケースはページ変動を記録して参考値とし、固定ケースの合否に混ぜない。モデル向け文字数中央値は現行以下を目標とするが、根拠取得率を犠牲にして達成しない。

### 実行コマンドと期待結果

| コマンド | 目的・期待結果 | 失敗時 |
| --- | --- | --- |
| `cargo test --manifest-path src-tauri/Cargo.toml runtime::web_fetch --lib --no-default-features` | 抽出・順位付け・状態・契約の固定ケースが全件成功 | ケースを再現して原因を修正、同条件で再実行 |

実ページ canary はネットワーク依存の任意レーンとし、URL・日時・応答状態を記録する。元の Nvidia 失敗 URL が分かった場合は同じ URL と質問で再測定する。live が落ちても固定テストの結果をごまかさず、再試行は一度までとする。実装完了時には比較表、残る失敗、実行したコマンドと結果を報告する。

計画作成時点の `bun run spec:check` は、新規の本計画書以外にある既存文書のリンク切れ（`REF003`）で失敗する。この既存失敗を改修の合否と混同せず、本計画書に新たな指摘がないことを確認する。

## 8. 主要な設計判断

- プレーンテキスト返却を選ぶ理由: HTML 構造の大半はモデルに不要で Token を消費する。意味関係だけを短い文章として残す。
- 追加 LLM 判定を使わない理由: 取得のたびに Token と遅延が増え、判定の再現性も下がる。決定的な候補選択と結果状態で十分性を近似し、最終的な読解は既存の回答モデルに任せる。
- WebView を残す理由: JS 描画に依存する公開ページを静的 HTML だけでは扱えない。
- `relevant` 判定を事実確認に使わない理由: 語と値の近さだけでは答えの正しさを証明できない。モデルには引用可能な証拠として提示し、候補不足は明示する。
