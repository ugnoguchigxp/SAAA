1. 結論

SAAAはLARMをOpenAI-compatible endpointの別名として登録しない。

SAAA Task / Conversation
  ↓ capability + route + explicit policy
LarmProvider
  ↓ allocate / poll / renew / release
LARM daemon
  ↓ fixed allocation binding
LARM Gateway
  ↓
Selected Local Runtime

既存のOpenAI-compatible Providerはdirect Providerとして維持し、LARM canaryのrollbackに使う。 LARM Providerの設定にはRuntime id、model path、quantization、port、systemd unit、llama-swap情報を保存しない。

7. Settings contract and v8 migration

7.1 Tagged Provider

type OpenAiCompatibleProvider = {
  kind: "openai-compatible";
  id: string;
  enabled: boolean;
  label: string;
  location: "local" | "cloud";
  endpoint: string;
  model: string;
  credentialStatus: "not-configured" | "configured";
};

type LarmProvider = {
  kind: "larm";
  id: string;
  enabled: boolean;
  label: string;
  location: "local";
  baseUrl: string;
  tokenEnv: "LARM_API_TOKEN";
  allocationTtlSeconds: number;
  allocationStartupTimeoutSeconds: number;
  allowFallbackByDefault: false;
  deploymentPolicy: "existing-only";
};

kindを必須discriminatorとし、unknown fieldは拒否する。既存v7 Providerはv8 migration時に kind: openai-compatibleを追加するだけで、id、route順、endpoint、modelを変更しない。

settings documentは既存のproviders.model:defaultを維持し、新しいnamespaceまたはkeyを増やさない。 Provider idはkindをまたいで一意とし、enabledなLARM ProviderはMVP 2.6で最大一件とする。 LARM credential statusは保存せず、connection test時にLARM_API_TOKENの存在だけをbounded statusへ投影する。

新規LARM Providerはenabled: false、http://127.0.0.1:9810、TTL 300秒、startup timeout 300秒で作る。追加・enableだけではprimaryやfallback順を変更せず、route変更は別操作で 明示保存する。

7.2 LARM validation

  • baseUrlはcredential、query、fragmentを含まず、pathは空または/だけとする。
  • HTTPはDNS解決を伴わない127.0.0.1または[::1]と、明示portだけを許可する。 localhostを含むhostnameは拒否する。
  • remote HTTP / HTTPSはMVP 2.6では拒否する。remote transportは別ADRの後に追加する。
  • tokenEnvはliteral LARM_API_TOKEN以外を拒否する。
  • token値はrequest直前に1〜4,096 bytes、ASCII control characterなしを検証する。空、改行を含む値、 HTTP headerへ変換できない値はnetwork access前にauthenticationで停止し、値を表示しない。
  • TTLは60〜3,600秒、既定300秒とする。
  • startup timeoutは1〜300秒、既定300秒とする。
  • allowFallbackByDefaultはfalse以外を拒否する。
  • deploymentPolicyはexisting-only以外を拒否する。

7.3 Feature flag and rollback route

環境変数SAAA_LARM_ENABLEDをprocess-level feature flagとし、既定はfalseとする。 値はexactな1だけをtrueとし、未設定、空、その他の値はfalseとする。flagはApp起動時に一度読み、 immutable runtime gateとして保持する。falseの場合、LARM Providerはeffective routeから除外し、 明示的に設定済みの次Providerを使う。次Providerがなければnetwork accessを行わずconfiguration errorにする。 feature flag自体をSQLiteへ保存しない。変更を反映するにはApp restartを必要とする。

LARM内部のallowFallbackと、SAAAのfallbackProviderIdsは別policyである。 前者は同一allocation作成時のRuntime候補、後者はLARMとは別のProviderへ移る許可を表す。

運用中のrollbackは二段階とする。Settingsでprimary Providerをdirect Providerへ変更する操作は新しいturnから 即時反映し、active turnのBindingは変更しない。process-level flagは全LARM経路を閉じるoperator kill switchであり、 App restart後に反映する。active turnを止める場合は、先にuser cancelを実行する。

conversation.respond開始時にprimary、fallback順、Provider設定、local-only policy、timeoutを 一つのvalidated route snapshotとして固定する。実行中にSettingsを再読込せず、Providerの追加、削除、並べ替え、 enable変更は次turnから反映する。

canary用direct Providerは移行期間だけ許可するoperator-owned例外である。LARM Providerの設定へdirect Runtimeのmodel、port、endpointを複製せず、独立した既存openai-compatible Providerとして維持する。

7.4 v8 migration order

  1. v7 databaseを検出したら、既存のpre-migration backup機構でreopen可能なbackupを作る。
  2. fresh schemaのprovider_sessions定義へSection 15のfieldとCHECKを追加する。
  3. migrate_v6_to_v7の後にmigrate_v7_to_v8を実行する。
  4. 既存Provider JSONへkind: openai-compatibleだけを追加し、unknown legacy fieldを残さない。
  5. 既存provider session rowへnullable fieldとrelease_status: not-applicableを追加する。
  6. 6件すべてのsettings documentをschema version 8へ更新し、strict validatorで再読込する。
  7. transaction commit後にdatabaseをclose / reopenし、SettingsとConversationを検証する。

migration失敗時はtransactionをrollbackし、v7 databaseを変更しない。旧binaryへのrollbackはv8 databaseを直接開かず、 自動作成されたv7 backupを復元する手順で検証する。v3、v5、v6、v7 fixtureのすべてが最終的にv8へ到達するtestを持つ。

8. Rust module boundary

既存direct Providerを大規模移動せず、LARM固有実装だけを次のmoduleへ隔離する。

src-tauri/src/providers/
  mod.rs
  larm/
    mod.rs
    contracts.rs
    session.rs
    client.rs
  • contracts.rs: DTO、bounded enum、error classification。HTTP、SQLite、Tauriへ依存しない。
  • session.rs: monotonic timeをcallerから受けるallocation lifecycle state machine。
  • client.rs: reqwest、Bearer、body limit、HTTP status mapping、Gateway streaming。
  • mod.rs: LarmProvider facadeとmodule外へ公開する最小API。

新しいasync trait dependencyは導入しない。Conversation routerはprovider kindで明示dispatchし、 direct ProviderとLARM Providerが共通のbounded attempt resultを返す構造にする。 

enum ProviderAttemptOutcome {
    Completed { content: String, cleanup: CleanupOutcome },
    Cancelled { output_started: bool, cleanup: CleanupOutcome },
    Failed {
        kind: ProviderFailureKind,
        public_message: BoundedProviderMessage,
        output_started: bool,
        cleanup: CleanupOutcome,
    },
}

enum CleanupOutcome {
    NotApplicable,
    NotStarted,
    Released,
    DeferredToTtl { kind: ProviderFailureKind },
}

current implementationのProviderAttemptError::Failed(String)を上記bounded outcomeへ置換する。direct Providerはcleanup: NotApplicable、allocation作成前のLARM failureはNotStarted、allocate outcome unknownはDeferredToTtl、それ以外のLARM Providerはrelease結果を返す。fallback判定は error textではなくoutput_startedとexplicit route policyだけを使う。

BoundedProviderMessageは固定catalogから生成する300文字以下のuser-safe文字列であり、 HTTP body、URL、header、prompt、response、OS errorのraw文字列から構築しない。詳細な分類は ProviderFailureKindで行う。

AppStateはLARM runtime gateをDisabled、Ready(shared reqwest::Client)、 Unavailable(bounded initialization error)のいずれかで所有する。feature flag OFFは Disabled、ONでclient構築成功ならReadyとする。client構築失敗でもSAAA起動、direct Provider、 Codex、Voice、Meeting、Situationをblockせず、LARMだけをUnavailableとして劣化させる。

LarmProvider facadeはvalidated Settingsと共有clientを一回のattemptで借り、Provider id別のclient cacheまたは Settings cacheを新設しない。clientはproxyを使わず、redirectを追従しない。Bearer tokenはclientまたはAppStateへ保持しない。Provider attempt開始時にLARM_API_TOKENを一度だけ 読み、non-Debugのephemeral credentialとしてrelease完了またはattempt終了まで使う。同じallocationの allocate、poll、renew、Gateway、releaseでcredentialを途中変更しない。新しいattemptは環境変数を読み直すため、 process内でcredentialを長期cacheしない。

STT / TTS用のresolve_binding DTOはMVP 2.6で定義、生成、公開しない。 実際に不要なendpointをSAAAへ露出させず、Voice follow-upで実contractから追加する。

10.2 Allocation response invariants

実際のJSON field名とHTTP status別DTOはG1のAPI schemaから生成または転記する。G1前にfield名を 推測してproduction contractへ固定しない。一方、SAAAが受理する意味上のinvariantは次に固定する。

  • allocation、operation、request、selected RuntimeのidentifierはSection 15のboundを満たす。
  • ready allocationはllm.generalのBindingを正確に一件だけ持つ。
  • routeがresponseに含まれる場合はllm-defaultと一致する。
  • ready responseはselected Runtime、fallback結果、selection reasonを含み、fallback結果はfalseである。
  • readyとrenewのresponseはserver-confirmed effective TTLを含み、60〜3,600秒の範囲にある。SAAAは request値ではなくこの値からmonotonic renew scheduleを作る。
  • selected Runtimeとselection reasonはSection 15のboundを満たし、次のrequestまたはroute選択へ戻さない。
  • pollとrenewのresponseは同じallocation idとBindingを維持し、別Bindingへの変更を受理しない。
  • required field欠落、重複Binding、capability / route不一致、unknown stateはprotocolとする。

invariant違反時はGatewayへ進まない。cleanup可能なallocation idを検証済みの場合だけbounded releaseを一度試行し、Provider attemptをprotocolで停止する。未検証文字列をrelease pathへ連結せず、次Providerへfallbackしない。

11. Allocation lifecycle

11.1 Scope

LLM allocationはConversation全体ではなく、一回のconversation.respond turn単位で取得する。 allocation idをsettings、Conversation、長期resume tokenとして保存しない。

11.2 State machine

Idle
  ↓ allocate
Allocating
  ├─ 200 → Ready
  ├─ 202 → Pending → poll → Ready
  └─ error → Failed

Ready
  ├─ stream
  ├─ TTL 80% → Renewing → Ready
  ├─ cancel / complete → Releasing → Released
  ├─ 404 / expired → Expired
  └─ error → Failed → Releasing

Released / Expired / Failed
  └─ terminal
  • 200は即時readyとして扱う。
  • 202は失敗にせず、operation idをdeadline付きでpollする。
  • pollは250 msから開始し、500 ms、1 sへ増やし、以降1 s上限とする。
  • pollには20%以下のjitterを加え、全体deadlineを超えたら停止する。
  • pollのjitter sourceとmonotonic clockはtestから注入し、unit testを決定的にする。
  • renew scheduleはwall clockのexpiresAtではなく、allocation response受信時のmonotonic timeとserver-confirmed effective TTLから80%地点を計算する。server expiryはtelemetryと整合性確認だけに使う。
  • renewのnetwork、timeout、5xx、allocation-lost後は、stream開始前だけ新allocationを一度取得できる。 authentication、contract、protocol、allocation-lost以外の4xxでは再allocateしない。
  • stream開始後のrenewは同じallocationに対して最大2回、1秒間隔かつexpiry前だけ試行する。両方失敗しても Bindingを変更せず、進行中streamを継続する。Gatewayが失敗した場合はpartial output ruleで停止する。
  • renewの二回目を許可するのはnetwork、timeout、5xxだけとする。authentication、contract、protocol、 4xxは再試行せず、同じBindingのstreamをexpiryまで継続する。
  • stream開始後はBindingを変更しない。
  • 検証済みallocation idが分かる場合、releaseはsuccess、failure、cancel、deadline、window closeの 全terminal pathで一度だけ試行する。outcome unknownでidがない場合はSection 11.3を適用する。

11.3 Unknown allocation outcome

allocate request送信後、response受信前にtimeoutまたはconnection lossが起きた場合、server側でallocationが作成されたかを SAAAは判断できない。LARMがidempotency keyをcontract化するまでは同じturn内でallocateをblind retryせず、attemptを allocation-outcome-unknownとして失敗させる。server側に残った可能性があるallocationはTTL回収へ委ねる。

202 responseは、cancel時にcleanupできるallocation idまたは同等のoperation cancel / ownership contractを 必須とする。どちらも提供されない場合はG1を通過させない。

11.4 Release semantics

  • releaseの200、204、対象消失を示す404 not_foundはcleanup成功とする。
  • release timeoutまたは5xxを同一turnで繰り返さず、一回の2秒attempt後はTTL回収へ委ねる。
  • 404以外の4xx、unknown status、invalid responseも再試行せず、bounded failure kindを記録してTTL回収へ委ねる。
  • chat成功後のrelease失敗はassistant messageの成功を失敗へ変更しない。
  • release失敗はseparate cleanup statusへboundedに記録し、userへ本文を含まない非blocking warningを出せる。
  • App shutdownはreleaseをbest effortで試行するが、process終了を無期限に止めない。TTLを最終回収手段とする。

12. Gateway streaming contract

Gateway requestはBearer tokenとallocation idを別headerで送る。

POST /v1/chat/completions
Authorization: Bearer ${LARM_API_TOKEN}
X-LARM-Allocation-ID: alloc_example
Content-Type: application/json

request bodyのmodelはSection 6で固定された仮想名を使う。実Runtime名をSAAAへ返して bodyへ埋め込む方式は採用しない。既存のSSE parser、UTF-8 chunk処理、1 MiB event上限、64,000文字上限を維持する。

12.1 Partial output rule

最初のnon-empty assistant deltaを受信し、Tauriへ送る直前にSQLiteへcommitした時点でoutput_started = trueとする。 その直後にchannel送信が失敗した場合もtrueのままとする。 以後のtimeout、disconnect、502、capacity error、invalid SSEはpartial failureであり、次のProvider、別allocation、 別Runtimeへ自動retryしない。 

Failure before first non-empty assistant delta
  → explicit SAAA Provider fallback may run

Failure after first non-empty assistant delta
  → stop
  → mark provider session partial-failed
  → release allocation
  → show bounded recovery
  → user may start a new turn explicitly

このruleはLARM Providerだけでなく既存direct Providerにも適用する。現在のConversation routerがpartial output後も次Providerへ進み得る挙動を、LARM実装より先に修正する。

Tauri channelへのdelta送信が失敗した場合はfrontend consumer消失としてbody readを停止し、 client-disconnected failureでcleanupする。channel消失後に推論を継続したり、別Providerへfallbackしたりしない。 このruleもdirect ProviderとLARM Providerの両方へ適用する。

12.2 Persistence and event ordering

  1. Provider attempt開始時にruntime_run_id付きsession rowを作り、commit後に既存started eventを送る。このeventはallocation readyを意味しない。
  2. allocation ready後、route、allocation、selection結果をcommitしてからProvider selected eventを送る。
  3. 最初のnon-empty deltaでは、同じattemptのoutput_started = 1をcommitしてからdelta eventを送る。
  4. stream成功後にbounded release attemptを行い、inference statusとcleanup statusを分離して確定する。
  5. assistant message、Conversation更新、runtime_runs完了を既存transactionでcommitしてから messageCompletedを送る。release失敗だけでこのtransactionを失敗させない。
  6. partial failureではassistant completed messageを保存せず、provider sessionとruntime runをfailedへ確定してから terminal failure eventを送る。既に表示したdeltaは再送または別Providerで補完しない。

12.3 Persistence failure

  • attempt rowの作成失敗時は、LARMを含むProvider network requestを開始せず、eventを送らない。
  • allocation selectionのcommit失敗時はGatewayへ進まず、検証済みallocationをbounded releaseして internalで停止する。
  • output_startedのcommit失敗時は受信中bodyを停止し、releaseして internalで停止する。deltaをTauriへ送らない。
  • terminal transactionのcommit失敗時はmessageCompletedを送らず、bounded recoveryを表示する。 既に表示済みのdeltaを再送せず、別Providerへfallbackしない。

persistence failureはすべてinternalであり、error本文をSQLite、event、diagnosticsへ複製しない。 cleanup failureはSection 11.4どおり別結果として扱い、database復旧前にnetwork inferenceを再開しない。

12.4 Terminal race

cancel、stream EOF、timeout、channel disconnectが競合しても、pure sessionが最初に受理したsignalだけを inference terminal resultとする。stream EOFを先に受理した場合はCompletedを維持し、その後のcancelはcleanupを 促進してもassistant結果を破棄しない。cancelを先に受理した場合は残りのbodyを読まず、EOFを成功へ昇格しない。 provider sessionとruntime runを一度だけ確定し、terminal eventも一度だけ送る。

13. Error mapping

Table: LARM error handling in SAAA
LARM result Internal kind SAAA behavior
400 bad_request contract retryせずclient bugとして停止
401 unauthorized authentication token設定を案内し、bodyをlogしない
404 unknown_route / unsupported_capability contract route mapping不一致として停止
404 not_found allocation-lost stream開始前だけ古いidを捨て、一度だけ再allocate
409 fallback_not_allowed policy 暗黙にfallbackを許可しない
409 resource_exhausted capacity 同一LARMへ自動stormを起こさず、明示済みSAAA Provider policyへ返す
409 allocation_inactive allocation-lost stream開始前だけ再allocate
503 no_candidate_available unavailable healthを確認し、明示済みProvider fallbackだけを許可
503 allocation_not_ready not-ready operation pollを継続しdeadlineを守る
503 draining draining 同一LARMへの新規要求を止め、明示済みSAAA Provider policyへ返す。LARM再試行は次turn
502 upstream_unavailable upstream Bindingを変更せず、partial output ruleを適用
413 body_too_large request-too-large 同じpayloadを再送しない
allocate response受信前のtimeout / disconnect allocation-outcome-unknown blind retryせずTTL回収へ委ね、明示済みSAAA Provider policyへ返す
unknown HTTP status / error code / state protocol raw bodyを表示せず、retryしない

internal kindはbounded enumとし、raw error bodyをSQLiteへ保存しない。MVP 2.6では既存public provider-errorとの互換性を維持し、Provider activityのbounded reasonとrecoveryを改善する。

13.1 SAAA Provider fallback eligibility

output_startedがfalseでも、すべての失敗を次Providerへ渡してはならない。 fallback判定は次のfixed policyをpure functionとして実装し、error message本文から推測しない。

Table: Provider fallback eligibility before first output
Failure kind Explicit SAAA Provider fallback Reason
authentication、contract、protocol、request-too-large、internal 禁止 設定またはpayloadを直すべきで、別Providerへ同じ内容を送らない
client-disconnected、cancelled、partial-output 禁止 consumerまたはuserが停止している
policy 明示済みrouteに限り許可 LARMのallowFallbackを変更せず、上位policyだけを使う
capacity、unavailable、draining、upstream、network、timeout 明示済みrouteに限り許可 Provider availability failure
allocation-lost 一回のreallocate失敗後、明示済みrouteに限り許可 daemon restartまたはexpiry
allocation-outcome-unknown 明示済みrouteに限り許可 LARMへblind retryせず、TTL回収へ委ねる
not-ready startup deadlineまではpollし、deadline後はtimeout policyを適用 202 lifecycleの途中

fallback eligibleでも、既存localOnlyWhenSelectedがCloud Providerを除外する境界を維持する。 LARM統合を理由にCloud fallbackを追加、有効化、並べ替えしない。

14. Security and network topology

14.1 Canary transport

MVP 2.6のcanary transportは、SAAA hostからgnosisへのSSH tunnelまたは同等のloopback private tunnelに固定する。 SAAAからはhttp://127.0.0.1:<forwarded-port>として見せ、LARM daemonはgnosisのloopback listenを維持する。

MVP 2.6 Settingsはloopback URLだけを受け入れる。remote HTTPSを将来採用する場合は、certificate、hostname verification、firewall、trusted subnet、token rotationを別ADRで固定してからschemaを拡張する。plain HTTP LANのために既存local endpoint validationを緩めない。

14.2 Secret handling

  • token値はenvironmentからだけ読む。
  • attempt用Authorization headerはsensitiveとしてmarkし、Debugを実装しないwrapper内でだけ保持する。
  • token値をSQLite、Settings UI、diagnostics、error、test snapshotへ保存しない。
  • Authorization headerをdebug printしない。
  • 401 response bodyをuser-visible errorまたはtelemetryへ複製しない。
  • redirectは追従しない。
  • LARM clientはsystem proxyとenvironment proxyを使わない。
  • health / readyへのBearer適用はG1で固定した認証範囲に従い、推測で付与または省略しない。
  • resolved endpointはRegistry由来だけを使い、user inputからupstream URLを作らない。

environmentはrunning processの外から安全に差し替えられないため、token rotationはactive turnを完了または cancelし、releaseを確認してからSAAAを新しいLARM_API_TOKENでrestartする。旧tokenはactive allocationが0件になるまでLARM側でoverlapさせ、先に失効させない。この手順をM26-10 runbookで実機検証する。

15. Persistence and telemetry

SQLite v8でprovider_sessionsへ次のnullable bounded fieldを追加する。

  • runtime_run_id
  • provider_kind
  • route_id
  • allocation_id
  • selected_runtime_id
  • fallback_used
  • selection_reason
  • request_id
  • output_started
  • failure_kind
  • release_status
  • release_failure_kind

allocation id、Runtime id、request idは運用相関用であり、選択入力として使わない。resolved endpoint、port、model path、 prompt、response、audio、Authorization headerはprovider session、runtime telemetry、error recordへ保存しない。Conversationのuser messageとassistant messageは既存のConversation storeへ従来どおり保存するが、LARM統合用columnへ本文を 複製しない。diagnostics exportではallocation idとrequest idを除外し、route、bounded runtime label、fallback、failure kindのaggregateだけを含める。

runtime_run_idは既存rowでnullable、新規attemptで必須とし、lookup indexを追加する。 inferenceのstatusとallocation cleanupのrelease_statusを分離し、chat成功・release失敗を Provider失敗として誤表示しない。direct Providerのrelease statusはnot-applicableとする。

release_statusはnot-applicable、not-started、pending、 released、failed、deferred-to-ttlの固定enumとする。 failure_kindはSection 13のinternal kindにnetwork、timeout、 partial-output、client-disconnected、internalを加えた固定enumとする。

release開始前にpending、成功時にreleasedをcommitする。timeout、network、5xxは deferred-to-ttlとし、release_failure_kindを記録する。failedはLARMが cleanup不能を明示した場合、またはSAAAが起動中にTTL + 30秒を超える残存をmetricsで確認した場合だけ使う。

Table: Provider telemetry bounds
Field Bound
run / allocation / Runtime / request identifiers 1〜160文字、ASCII英数字、hyphen、underscore
route id 1〜80文字、ASCII英数字、dot、hyphen、underscore
selection reason primaryまたはother。LARMのraw説明文は保存しない
status / failure / release kind 固定enum以外を拒否

process restart時にrunning provider sessionをinterruptedへreconcileする。allocation idを再利用せず、 LARM側のTTL回収を前提に次のturnで新規allocateする。

  6. outcome不明のallocateをblind retryせず、release失敗とinference結果を分離する。
  7. stream開始後にBinding、allocation、Providerを変更しない。
  8. cancel、timeout、failureでreleaseを一度だけ試行し、shutdownではbounded best effortとTTL回収を使う。
  9. feature flagが既定OFFで、direct Provider rollbackが検証済みである。
  10. token、prompt、response、resolved endpointがprovider telemetry、error、log、diagnosticsへ複製されない。 Conversation本文は既存Conversation storeだけに保存される。
  11. fake LARM suiteと既存全testが成功する。
  12. gnosis canaryでdefault、cancel、partial failure、restart、capacity、rollbackが成功する。
  13. allocation leak、Resident停止、Preferred stop漏れがsoakで検出されない。
  14. isolated canary instanceと通常利用profileのSettings、SQLite、environmentが共有されない。
  15. /ready、/metrics、主要error、token、transportのoperator runbookがある。

23. LLM canary後のfollow-up

MVP 2.6 acceptance後、別計画でVoice pipelineを扱う。LLM、STT、通常TTSをMeetingまたはVoice Session単位の 一つのallocationへまとめ、STT / TTSはLARM Gateway完成まではresolve結果をsession内だけ保持する。

  • speech.stt + stt-default
  • speech.tts + tts-default
  • VOICEVOXを通常TTSとし、creditをUIまたは生成物へ反映する
  • speech.tts.expressive + tts-expressiveは明示intent時だけ
  • LARM STT / TTS Gateway完成後にdirect resolveを廃止する

artifact lifecycle、35B、multi-node、allow-listed deploymentはVoice follow-upにも含めず、operator権限を分離した 独立計画とする。
