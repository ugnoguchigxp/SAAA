1. 実装したこと

  • crates/reasoning-contract/: SAAAとServiceが共有するv1入出力型、JSON Schema、文字数・byte上限、参照根拠と相関IDの検証。
  • services/reasoning-mcp/: 独立したRustサービス。Streamable HTTPのJSON応答を使い、initialize、tools/list、reasoning.answer、通知によるキャンセルを提供。LARMモードではアプリ内loopbackで起動し、共有Sessionのclaimからモデル名・接続先・tokenを取得する。
  • src-tauri/src/providers/reasoning_mcp/: モデル名を持たない専用クライアント。初回handshakeの再利用、JSON/SSE応答受信、総量上限、15秒以内の締切、キャンセル通知、応答検証。
  • src-tauri/src/runtime/conversation_controller/: 既存の確定音声入力から会話文脈を投影し、検証したspeechTextだけを既存の保存処理とTTSへ渡す。キャンセルと回答採用を直列化する。
  • src-tauri/src/runtime/reasoning_ack.rs: 250ms後も未完了なら一度だけ定型相槌。独立した一時speech sessionで既存TTSを使い、履歴には保存しない。相槌終了後に本回答を再生する。
  • 追加入力: 有効な推論runだけを中断し、既存の最大2件の待ち行列で次の入力を保持。通常の会話経路の待ち方は変えない。

LARM接続契約（2026-09-12受領）

今後の接続実装は以下を正とする。接続先はhttp://gnosis.local:9810。 ユーザー提供のLARMリリース識別子はbe5e86272165f4e13e69f4da204b1425486c6070。 4 Provider同時readyと解放後のtoken失効はLARM側の報告であり、SAAA側の実接続検証は未実施。

  1. SAAA音声会話セッションの開始時に一つのAgent Connectionを作成し、ASR・TTS・Decision・推論で共有する。 POST /v1/agent-connectionsに下記JSONと一意なIdempotency-Key: saaa-session-<ID>を送る。 現行LANのライフサイクルAPIには長期Bearerは不要。201または202を成功として扱う。
  2. 返却idでGET /v1/agent-connections/{id}を1秒間隔、最大300秒pollする。 pending・probingは待機、readyでclaimへ進み、failed・released・expiredは終了する。他Providerを強制preemptしない。
  3. POST /v1/agent-connections/{id}/claimへ{"format":"openai-provider-v1"}を送る。 providersはnameで対応付ける。全4 Providerの設定とhealth検証が揃うまでセッションを利用可能にしない。
  4. 各呼び出しはconfiguration.fields.baseURL、configuration.fields.model、 credential.tokenを使う。tokenはProvider専用Bearerであり、他Providerへ流用しない。 バックエンドportとモデル名を呼び出しコードに固定しない。
  5. health.urlを当該Providerのtokenで確認する。ready・acceptingRequests・probe.validatedがすべてtrue、 probe.protocolがProviderのprotocolと一致することを要求し、結果の有効期間はhealth.maxAgeMsに従う。
  6. expiresAt前にPOST /v1/agent-connections/{id}/renewへ{"ttlSeconds":600}と 一意なIdempotency-Key: saaa-renew-<ID>を送る。 renewで旧tokenが即失効するため、新規Provider要求の受付を止め、実行中要求の終了またはキャンセルを待つ。 同じConnectionを再claimし、health検証後に4 Providerの設定を原子的に差し替えて受付を再開する。 更新失敗時に旧tokenへ戻さず、セッションを失敗として解放する。
  7. 正常終了・途中失敗・起動タイムアウト・キャンセルのいずれでも、取得済みidに対してfinally相当で DELETE /v1/agent-connections/{id}を実行する。正常応答は204。 解放失敗を記録し、解放確認なしに成功扱いにしない。

ASRはfile・model・response_format=jsonのmultipart。TTSはmodel・input・voice=Kasukabe_Tsumugi・response_format=wavのJSON。 LLMとDecisionはmessagesを持つChat Completionsで、stream=trueでは互換SSEを使う。 本プリセットのASRを既存のWebSocket音声入力protocolに対応していると仮定しない。

KV:memの通常Chat Completionsではsnapshotを使用しない。作成済みContext Viewを利用する場合のみ、 x-larm-allocation-idにclaim.allocationId、x-larm-context-view-idに当該View IDを渡す。 Viewがない場合は通常推論とする。現行MCP adapterが要求するJSON Schema出力は今回の接続仕様だけでは保証されず、実接続で別途検証する。

LARMモードの起動と所有期間

SAAA_CONVERSATION_REASONING_MODE=larm bun run start

接続先の既定値はgnosis.local:9810。必要ならSAAA_LARM_CONTROL_URLでローカルの制御APIを指定する。 接続URL・モデル・Provider tokenを個別に環境変数へ設定する必要はない。モデルと認証はclaim値のみを使う。 新モードはopt-inで、既定のoffと既存のテキスト会話経路は維持する。

  • crates/larm-session/: 接続作成・poll・4 Providerの検証・health cache・renew・release。要求中のread guardと更新時のwrite lockでtokenの世代混在を防ぐ。
  • src-tauri/src/providers/larm_voice/: 音声会話のownerを管理し、同じSessionをASR・TTS・軽量応答・27B推論に渡す。Provider tokenはRust側のメモリ内に保持する。ツール実行とMCP利用経路はSAAAが所有し、LARMはLLM Providerとしてだけ扱う。
  • 音声ONの最初のASR開始前に4 Providerを準備する。ASRの一時停止・相槌・発話ごとの再開では接続を作り直さない。
  • 音声OFFでは確定済み音声の配送とTTS完了を待って解放する。会話切替・画面破棄・アプリ正常終了・起動失敗でも解放処理を実行する。解放失敗は成功扱いにせず通知またはログに残す。
  • 有効期限の90秒前からrenewを開始し、実行中のProvider要求が終わるまで待つ。renew待ちの呼び出し元がキャンセルされても再claimと更新処理は完了させる。
  • Managed ContextのView作成は今回の範囲に含めない。作成済みViewを渡す経路がない現在は通常推論を使い、snapshot使用を表示・計測上も主張しない。

2026-09-16以降の音声経路では、decision-defaultを軽量応答モデルとして使う。軽量モデルは相槌、長時間推論中の通知、SAAAが把握したtool phase、最終回答の読み上げ用文面だけを生成し、tool call・推論結果・保存内容を決定しない。llmの27B Providerが会話本文とtool callを生成し、SAAAがtoolを実行して結果を27Bへ返す。画面表示と履歴には27Bの本文を保存し、軽量モデルの文面は同じTTS queueへだけ配送する。軽量モデルが失敗・timeout・不正JSONになった場合も推論は失敗させず、最終発話は27B本文へ戻す。

設定は起動時に固定する。有効化後の最初の要求で接続を検証し、warm pathでは再利用する。失敗時はそのrunを失敗として表示し、自動で別Providerへ送らない。無効化は停止操作後にmodeをoffへ戻し、SAAAを再起動する。履歴やDBを削除する必要はない。

UIの経路名はReasoning MCPとなり、既存Providerの失敗によるfallback扱いにはしない。テキスト会話、Coding、Meeting、既存のContextStill接続のprotocolVersionは変更していない。

4. LARM側との境界と残作業

  • LARMモードは共有Agent Connection経由、従来のdeterministicモードは固定接続によるfixture経路として区別する。実機での4 Provider応答とJSON Schema対応は接続可能な環境で確認が必要。
  • 2B Decisionの分類は引き続きshadowであり、回答経路を変更しない。これとは別に軽量応答を最大1〜2秒・応答16KiB以内の厳格なJSON契約で受け取り、相槌・思考中・tool進捗・読み上げ用最終文面へ使う。軽量応答は27Bの回答本文、tool選択、保存内容を変更しない。
  • 上流HTTP要求のdropによる切断までは伝播する。GPU上の生成が実際に停止すること、残留計算が増えないことはLARM側の動作に依存し、実接続試験が必要。
  • Serviceの上流入力は24KiB、出力予算は1024 tokensの初期制限。モデル固有のtokenizer・context window検証と予算調整は未接続。小さいcontextや推論tokenを多く消費するモデルで完了できるとは保証しない。
  • 既存の会話投影からuser/assistant履歴と利用可能なtool定義を27Bへ渡す。tool callは全件を先に検証し、検索・記憶参照・Coding・Generative UIを既存SAAA実装で実行する。軽量応答モデルにはtool定義・引数・結果を渡さず、SAAAが選んだ安全な進捗文だけを渡す。
  • 相槌・思考中通知は27B完了時に打ち切る。軽量モデルが生成した最終文面は音声専用であり、27Bの本回答を書き換えたり履歴へ保存したりしない。
  • 実音声のVADからの自然な割り込みは未対応。TTS中に音声入力を休止する既存方針を維持する。停止操作と入力受付中の追加入力を対象とする。
  • 文脈構築前を含む発話終了からの全区間測定、実音響のfirst audio、A0/A1比較、30分soak、実接続のrelease判定は未完了。

2026-09-12 コードレビューと修正

修正後はRUST_TEST_THREADS=1 bun run check成功。Frontend 264件、Rust単体508件成功・12件ignore、IPC・品質契約・Clippy・ドキュメントテストも成功。 接続管理11件、共有契約3件、Service 6件と各crateのClippyを確認した。build、desktop:smoke、spec:checkも成功。 buildには既存の500kB超chunk警告が残る。ビルドとcheckの並行実行では成果物が競合したため、最終checkは単独で再実行している。 確認した範囲で未修正のコード指摘はない。gnosis.localの名前解決、実ProviderのJSON Schema対応、実音響・長時間運転は引き続き実機での検証対象。

  • Connection作成応答の待機を打ち切っても、返却されたidの解放を継続する。closeの呼び出し元が消えても解放を続け、解放失敗時のSession参照を保持して再試行できるようにした。
  • 音声ON直後のOFF、会話切替、開始・終了IPCの到着順逆転を処理する。終了未確認のownerがある間は次のConnectionを作成しない。起動中のOFFは直ちに中止し、通常のUI終了待機には60秒の上限を設けた。
  • TTSには開始時のSession参照を直接渡す。Provider応答の受信後は再生完了を待たずにtokenの使用guardを解放する。音声出力の待ち行列が停止した場合も受信の締切でguardを解放する。ASRの締切には接続取得を含める。renew応答のConnection idも検証する。
  • 相槌の2秒制限に準備時間を含め、停止操作で準備待ちも中断する。回答検証までのメトリクスから相槌終了待ちを除いた。
  • 会話履歴を共有の24KiBモデル入力予算に合わせて古い順に減らす。現在の質問を切り詰めず、質問だけで超過する場合は明示的に失敗させる。追加入力は同じ会話のrunだけを置換対象とする。
  • claim由来のASR・TTS専用tokenを送るHTTPクライアントではproxyを無効にする。通常のCloud設定への影響がないこともloopback試験で確認する。
