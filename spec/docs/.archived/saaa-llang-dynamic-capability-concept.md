# SAAA × L-Lang — 必要な能力を、その場で作り変える

作成日: 2026-09-19  
状態: コンセプト案 v0.1

SAAAが目指すのは、ユーザーの意図と状況を理解し、任された仕事を進めるJarvisのような存在である。その実現に向けて、必要になった機能をLLMがその場で作り、SAAAの能力として使えるようにする。L-Langを、この動的拡張機能の実装コアに据える。

Iron Manが状況に合わせてスーツの形状を変え、その場で必要な装備を生み出し、強力なビームを放つ。その関係をSAAAとL-Langにも持たせたい。SAAAが目的と状況を捉え、L-Langによって必要な機能を形にし、実際の行動へつなげる。「即座に形を変える」は目指す利用体験であり、生成時間や実行性能の保証値ではない。

この文書は、そのための構想と判断の軸をまとめる。記載する機能は到達目標であり、実装済みであることを示さない。何から作るか、どの順序で検証するかは、コンセプトを踏まえて別途決める。

**動的に作った機能を、SAAA自身が使えるようにする**

SAAAは、目的に合う既存の能力を利用し、不足があれば機能を生成する。生成した機能には、処理の実体に加えて、何に使うのか、どんな入力を渡すのか、何が返るのか、どんな条件や権限が必要なのかを対応付ける。登録後は、SAAAが用途を理解し、必要な場面で発見して呼び出せる状態にする。

L-Langが担うのは、処理の意味を表すSemantic Coreと、それに対応する実行成果物である。Semantic Coreは、機能がどのような計算・判断・状態変化を行うのかを保持する核として位置付ける。WebAssembly（Wasm）は、その意味を機械が実行するための成果物として扱う。

SAAAは、生成物の検証、ツール登録、使い方の提示、実行、権限制御、結果の記録をつなぐ。生成されたファイルが存在するだけでは、この構想における「能力が増えた」状態には達していない。SAAAがその使い方を知り、実際の仕事で呼び出せることまでを一つの流れとする。

```text
目的と状況を理解する
        ↓
必要な能力を探す
        ↓ 不足や改善余地がある
LLMが機能を構想し、L-Langで実装する
        ↓
生成物と利用条件を検証する
        ↓
使い方とともにツールとして登録する
        ↓
SAAA内・MCP経由で利用する
        ↓
結果を確かめ、継続利用・更新・置換・廃棄を判断する
```

**ツール、MCP、画面を同じ能力へつなぐ**

生成した機能は、そのままMCP経由でも動的に利用できることを目指す。MCPは、AIやアプリケーションからツールを発見し、呼び出すための接続口として位置付ける。機能を作るたびに、人が別の連携コードや使い方を用意する負担を減らしたい。

SAAA内のツール呼び出しとMCP経由の呼び出しは、同じ機能の契約と実行成果物へ結び付ける。どの経路から使っても、対象となる版、入力と出力、必要な権限を特定できるようにする。MCPとして利用可能にすることは、無条件で外部へ公開したり、すべての呼び出し元に同じ権限を与えたりすることを意味しない。公開先と接続方式は後の設計で決める。

画面が必要な機能には、SAAAの既存OpenUI基盤を表示・操作の窓口として利用する。会話内のフォーム、表、可視化、ゲームなどから、同じ機能を呼び出せるようにする。画面を持たない計算処理や変換ツールも、動的拡張の対象である。

L-Langは処理の意味と実行を、OpenUIは表示と操作を、SAAAは能力の登録・選択・実行管理を担う。画面だけを変える場合と処理を変える場合を区別し、互換性のある範囲でそれぞれを更新できるようにする。

**普段は機械が進め、違和感があれば人が検証できる**

LLMが動的に機能を作り、利用することを通常の運用として認める。機能を作るたびに、人がコードを読み、実行を承認することを必須にはしない。生成物の検証とテスト、実行時の制限、HostであるSAAAの認可を、その運用を支える条件とする。

その一方で、ユーザーが「この結果はおかしい」「内部で何をしているのか」と感じたときには、対象の機能をTypeScriptとして出力し、処理を読んで検証できることを期待する。

このTypeScriptは、実行後にLLMが推測して作る説明用コードではなく、実際に使われた版のSemantic Coreに対応する、人が読める表現として扱う。実行したWasm、Semantic Core、TypeScriptの対応を追跡し、何を検証しているのかが分かるようにする。出力を読めることと実行結果の正しさを確認できることは区別し、テストや実行記録と照合するための対応情報も残す。その検証方法と表現上の制約は、後の設計で具体化する。

外部へのアクセス権限はSAAAが管理する。生成した機能が要求する権限と、実際に認可された権限を分け、コードレビューを省略できることを権限拡大の根拠にしない。動的に能力を増やしながら、人がその振る舞いを調べ、停止し、修正できる関係を維持する。

**作った機能は、使いながら変えてよい**

生成機能の寿命は用途によって異なる。一度の作業で役割を終えるものもあれば、長く使い続けるものもある。よりよい機能ができれば置き換え、不要になれば利用対象から外す。すべてを恒久的な資産として残すことは目的にしない。

小さな仕様変更や最適化のアイディアがあれば、日常の作業の中で気軽に更新できるようにする。例えば、入力形式への対応を増やす、計算方法を変える、繰り返す処理を一つのツールへまとめる、といった変更を想定する。これは目指す利用例であり、現在の対応範囲を示すものではない。

更新した版は検証を経て利用対象にする。新しい版ができても、進行中の呼び出しや過去の結果が、どの版に基づくものか分からなくなってはならない。実行中の版を特定できること、問題のある版を停止できること、必要に応じて以前の版へ戻せることを重視する。

利用対象から外すことと、検証に必要な来歴を削除することは区別する。何をどの期間残すかは、機密性、保存コスト、ユーザーの削除意図に応じて決める。会話から保存済みの画面や結果を開き直すことも、外部への送信や書き込みを再実行することとは分ける。

**あらゆるエンジニアリングへ広げるための基盤**

対象領域は、世界時計や会話内の小さなアプリに限定しない。計算、変換、検証、シミュレーション、開発支援、外部システムとの連携など、あらゆるエンジニアリングへ広げられる基盤を目指す。世界時計やゲームは、表示・状態・操作・実行の関係を確かめるための例として扱う。

長期的には、必要な能力を作り、その結果を確かめ、能力の構成を更新する仕組みを、AGIの基盤として利用することも視野に入れる。この構想がAGIの成立を保証するわけではない。まず目指す存在はJarvisであり、評価の中心は、SAAAがユーザーから任された仕事をどこまで遂行できるようになるかに置く。

L-Langが現時点で表現・実行できる範囲と、この長期的な対象範囲は分けて扱う。既存ツールやCoding Agentも利用手段として残し、L-Langで扱えなかった要求は、将来の拡張を考える材料にする。モデルやコンパイラがどこまで担うか、自己改善をどの範囲まで許すかは、実装計画で検討する。

**既存構想との関係**

[Personal AI Concept](saaa-personal-ai-concept.md)が定めるJarvisの目標に対し、この文書は「必要な能力そのものを動的に作り変える」という方向を加える。[Capability / Tool Runtime Concept](saaa-capability-tool-runtime-concept.md)の登録・発見・選択・実行へ、L-Langによる生成と更新を接続し、画面や成果物は[Interface / Artifact Runtime Concept](saaa-interface-artifact-runtime-concept.md)へつなぐ。新たな独立会話Runtimeを設けることは意図しない。

先に整理したGenerated App Runtimeの構想とPhase 1案は、Wasm実行、OpenUI連携、権限、復元、検証を具体化する材料として保持する。この文書では、それらの実装順序や最初の対象アプリを確定しない。次の計画では、動的な生成から登録、利用、更新、事後検証までの関係を踏まえて、何を最初に実証するかを選ぶ。
