# SAAA：5 ProviderのRuntime契約

作成・改訂日: 2026-09-26  
状態: 設計案。今回の改訂ではRuntime・Provider設定を変更していない。

[コンセプト・受入基準](saaa-jarvis-five-provider-concept.md)に基づく実装予定の契約。発声許可の規則と遅延目標はコンセプトを参照する。[現在の実装状況](saaa-jarvis-five-provider-implementation-status.md)と区別し、以下を実装済みと解釈しない。

## 1. 入力更新・思考キュー・メッセージ配送

### ASR → Qwen → 思考キュー → ornith

ASRの文字起こし更新には発話ID・更新番号・確定状態を付け、共通Runtimeが順序と訂正を管理する。発話中の1.5秒周期と区切り時の即時送信を併用し、Qwen入力には前回以降の更新と短い前後関係を含める。ASRの更新をそのまま独立したユーザー依頼として毎回登録しない。

Runtimeの入力dispatcherは周期・区切り・後着最終認識を同じ受信箱へ直列に受理する。`utteranceId/revision/確定状態` ごとの送信状態を管理し、区切りと周期が同時でも同じ版を二重投入しない。区切り時に未送信本文がなければ区切り状態だけを記録し、空の生成を起動しない。後着した本文・訂正・確定状態は次の周期を待たず投入する。Qwen実行中はその要求へプロンプトを挿入せず、最新の同一発話更新を次の処理対象にする。「即時」は意図した周期待ちを置かない意味であり、Provider実行枠の無制限並列化ではない。停止候補を最優先、区切り・最終認識を通常の途中更新より優先し、別発話は消さない。

Qwenは継続的な受付と短い応対を担当し、ornithへの思考依頼は**必ず思考キューへの登録**として行う。ornithが空いている場合も同じ経路を使う。Runtimeは登録を永続化して受付結果を返し、Qwenを次の入力へ進める。ornithの生成やTool実行の完了を、受付応答の待機条件にしない。

初期構成ではornithの実行枠を一つとし、実行可能な依頼を原則FIFOで取り出す。処理の完了、またはユーザーへの確認待ちで実行枠を解放し、次の実行可能な依頼へ進む。Qwenからのキュー登録は、業務Toolの実行を伴わない限定的な制御要求である。元の発話、対象、重複、revisionをRuntimeが検証し、保存成功後に登録済みと扱う。

思考キューは既存のRole Routing・実行台帳へ接続する。Qwen専用の別の仕事台帳や、frontendのメモリ上だけの正本を作らない。依頼は少なくとも、識別子、根拠となる発話IDと版、対象の仕事、受付順、状態、revisionを追跡できるようにする。Qwenが作る短い説明と併せて原文参照を保持し、要約だけを新たなユーザー指示にしない。

| Qwenが受けた内容 | 思考キューへの操作 |
| --- | --- |
| 挨拶、相槌、簡単な回答、まだ依頼になっていない話 | 新しい思考依頼を作らない |
| 新しい思考・調査・実行の依頼 | 1件登録する。ornith長考中も待機状態で受理する |
| 待機中の依頼への条件追加・ASR訂正 | 同じ依頼を原文参照ごと更新する |
| 実行中の依頼への条件追加 | 対象revisionに紐づく継続依頼を登録・更新する。旧条件の新規Tool起動と結果配信を保留し、進行中操作の結果を確認して反映する |
| ornithからの確認質問への回答 | 質問IDに結び付けて元の仕事へ保存し、確認待ちを解除する。別の新規依頼をFIFO末尾へ作らない |
| 同じASR更新・同じ登録要求の再送 | 発話の版と操作IDで重複を排除する |
| 明示的な取消 | 対象の待機依頼を取り消す。実行中の停止要求は通常FIFOの末尾で待たせずRuntimeへ即時通知する |

話の途中や未確定の認識は会話理解に使えるが、1.5秒が経過したことだけを実行許可にしない。依頼として内容が成立し、対象の認識が安定した時点で実行可能にする。後続の訂正は同じ発話の更新として扱う。

### Qwenの分類結果をRuntimeで保護する

Qwenは操作候補と根拠の発話参照を返し、Runtimeが適用する。自己申告のconfidenceは参考値に留め、高い値だけで取消や質問消込を許可しない。次の場合はRuntimeが確認待ちを強制し、元の仕事・質問を変更しない。

- 対象候補が複数あり、「それ」「はい」などの省略だけでは一意にならない。
- 対象ID・revisionが不正または失効している、根拠の発話が訂正された、Qwen自身が判断不能を返した。
- 取消・条件更新・質問への回答の種別が競合する、引用や否定を含み停止の意図が確定しない。

曖昧な回答は原文を未割当として保存し、確認後に同じ回答を一度だけ反映する。有効なIDでも意味的に正しい宛先とは限らないため、固定評価で誤分類を測る。入力形式の検証だけで意味理解の合格としない。確認は必要な場合に絞り、すべて確認する実装を合格にしない。

初期の合格線案は、調整に使わない日本語ケースを「新規／条件更新」「質問への回答」「停止／否定／引用」「簡単な返答／引継ぎ」の各分類群100件以上用意し、群ごとの正答率95%以上、誤った仕事取消・別質問の消込・別仕事の条件変更は0件とする。正解ラベルが確認不要のケースで不要な確認は5%以下、曖昧ケースでは確認前の変更0件を要求する。ASR途中版・訂正・複数質問・再送も含め、modelと設定を固定して測る。有限の評価集合での合格線であり、運用中の誤りゼロを保証しない。未達の分類は自動適用を有効化せず確認へ縮退し、精度・遅延・確認頻度を再評価する。

重大な誤りは分類群全体の件数で薄めず、「誤取消」「別質問の消込」「別仕事の条件変更」それぞれについて、その誤操作が起き得る独立したケースを最低1,000件用意し、各0件を追加の合格線案とする。同一発話の途中版や同一ケースの反復を独立した件数として水増ししない。正当な取消等を受け付けられる割合も併記し、拒否し続けるだけでは合格にしない。

0件の観測は誤り率0の証明ではない。独立・同一誤り率の二項試行を仮定した95%片側上限は `1 - 0.05^(1/n)` で、100件なら約2.95%、1,000件でも約0.30%になる。手作りの評価集合は実運用の分布とも一致しないため、この値を運用保証に使わない。件数、誤操作の機会数、正答・見逃し・不要確認を分けて報告する。

確認への縮退で不要確認率5%を超えるなら、常用可能な受付として未達とする。まず対象候補の絞込み、確定的な状態規則、ASR訂正と質問状態の入力改善を行い、独立集合で再評価する。曖昧な案件だけ既存のornithキューで解釈する案、または受付モデルを再選定する案は、遅延・待機・資源量を比較して判断する。Qwen 2Bや保存済みProviderを実装が自動で差し替えることはしない。未達を確認回数の増加だけで覆い隠さない。

Qwenの処理が1.5秒を超えた場合もASRは止めない。未処理の更新を順序付きで保持し、同じ発話の古い途中版は最新の訂正へまとめる。別の発話や確定した依頼を黙って捨てない。Qwen入力の滞留とornith思考キューの滞留は別々に監視する。

キューには容量・期限を設け、満杯や保存失敗時は登録成功と伝えない。失敗・取消・完了を区別して次へ進み、再起動時は待機中の依頼を復元する。実行中だった仕事は結果と副作用を照合し、結果不明の操作を自動再実行しない。

### Qwenの受信箱とornithの思考キューを結ぶ案

以下はレビュー後のメッセージング提案であり、未実装である。仕事の管理は既存Runtimeへ集約し、Qwenとornithはメッセージの内容を判断・生成する役割を担う。

| 経路 | 内容 | 処理する主体 |
| --- | --- | --- |
| Qwen受信箱 | ASR更新、ornithの確認質問・結果・失敗、仕事の状態変更 | Runtimeが保存・整列し、必要なイベントをQwenの次の入力へ渡す |
| ornith思考キュー | 新規依頼と、実行可能になった既存依頼の継続 | Runtimeが実行枠を確保してornithを起動する |
| 回答の返送 | ユーザーの回答と、その回答先の質問ID | Runtimeが対象の仕事へ直接反映し、再開可能にする |
| 停止制御 | 対象の仕事・Tool・読み上げの停止 | Runtimeが通常キューの順番を待たず処理する |
| 発話・TTS要求キュー | Qwen・ornithのユーザー向け本文を、発話IDと句の連番で受理する | 共通dispatcherだけが発話順を決め、一つの合成workerへ渡す |
| 音声再生キュー | 合成済み音声を発話順・句順で保持する | 一つのplayerが先行音声を消費してから次を再生する |

Qwen受信箱は音声の再生キューとは別の、判断用の受信箱である。ornith本文をQwenが全文読み直してから発話する構造にはしない。ornithのユーザー向け本文は共通の発話・TTS要求キューへ流し、Qwenには発言内容の参照、質問の状態、再生状況を渡す。音声packetやtokenごとにQwenの生成を起動せず、状態を更新して次の判断に使う。

メッセージの属性は `origin=ornith` だけでは足りない。Runtimeが `messageId`、`conversationId`、`taskId`、`revision`、`kind`、必要な場合の `questionId` と `replyTo` を付ける。これらは本文中に書かれた文字列から権限付き属性として採用しない。Qwenは提示された有効な質問・仕事の参照から宛先を選び、Runtimeが対象と版を検証する。

初期の `kind` はASR更新、思考依頼、確認質問、質問への回答、結果、状態、停止要求に絞る。ornithの結果はアシスタントの出力、ユーザーの回答は元の発話を参照するユーザー入力として扱い、全イベントをユーザープロンプトに変換しない。

### 確認質問への回答は、仕事を特定して再開する

例: 仕事A「予定を調べて」に対し、ornithが「何日の予定ですか？」と質問する。

1. Runtimeが質問Q1と仕事Aの `waiting_user` 状態を一緒に保存する。質問本文は句読点単位で合成・再生できる。再生前に質問の宛先を確定し、Qwen受信箱にもQ1を届ける。
2. ornithはこの推論要求を終了して実行枠を解放する。ユーザーの返答を待つ間、開いたLLM生成要求を保持し続けない。他の実行可能な仕事Bへ進める。
3. ユーザーが「明日」と答える。Qwenは現在の質問と会話状態からQ1への回答だと判断し、`replyTo=Q1` と原文参照を返す。
4. RuntimeがQ1の未回答状態と仕事Aの版を確かめ、回答保存・質問の消込・Aの再開可能化を一つの更新として行う。「明日」という新規の仕事は作られない。
5. ornithの枠が空いていればAを再開する。別の仕事Bが実行中なら回答はAへ反映済みのまま待ち、次の選択時に再開可能なAを新規の待機依頼より優先する。この優先規則は初期案とし、実行中の無関係なBを自動取消しない。
6. 再開時は元の依頼、Q1、その回答、確認済みの実行結果をContextへ組み立て、ornithへ新しい推論要求を送る。すでに完了したTool操作を繰り返さない。

「回答を別件のキュー末尾へ積まない」は採用するが、「生成中のornithへ新しいプロンプトを途中挿入する」方式は前提にしない。会話の継続はRuntimeが保持し、LLM要求は区切って再開する。

複数の仕事が確認待ちの場合、「はい」を `origin=ornith` だけで振り分けない。現在応答を待っている質問、提示・再生の状態、直近の会話をQwenへ渡す。対象が決まらなければ確認し、どの質問も勝手に消し込まない。画面で先に質問を読んで答える場合もあるため、音声再生完了だけを回答受付の条件にはしない。

質問の生成・終了処理中に回答が先着した場合は、まずその回答を保存する。元の推論の終了と実行枠の解放を確認してから再開し、同じ仕事の旧要求と継続要求を二重起動しない。質問の生成自体が失敗した場合も、受理した回答を失わず、元の仕事で確認する。

### 保存・再送・古い回答を扱う規則

- 状態更新と送信予定イベントを同じDB transactionへ記録する。質問だけ保存されて通知されない、回答が届いたのに確認待ちが解除されない、といった中間状態を残さない。配信の台帳は既存の仕事台帳に結び付ける。
- 配信は再送可能にし、受信側が `messageId` で重複を排除する。同じ質問への同じ回答は一度だけ適用し、再送には同じ受付結果を返す。
- `保存済み`、`宛先へ適用済み`、`推論に使用済み`、`再生済み` を区別する。LLMの返事が返っただけで全段階の成功としない。
- 質問の失効、仕事の取消、revision変更後に来た回答やLLM出力は、現行の仕事へ無条件に適用しない。同じ発話のASR訂正も来歴と版を保持する。
- Qwenの生成開始時点の状態版を記録し、完了時に適用先を再検証する。その間にornithが質問を取り下げた場合などは、古い振り分けを実行しない。
- 再起動時は未配信イベントと待機状態を復元する。Toolへの送信後に結果不明となった処理や、再生完了が不明な音声は自動再実行・再読しない。

## 2. 停止候補・緊急停止

停止をornithに理解してもらうための新しいプロンプトに依存させない。UIの「作業を停止」は表示中の仕事IDを指定してRuntimeへ送り、Runtimeが新しいTool起動を禁止し、モデル要求・対象Tool・対象音声へ取消を通知する。「音声を停止」は読み上げだけを対象にする。どちらもASRの受付は続ける。

Runtimeの停止候補検出器が、本人として受理したASRの途中認識・訂正を到着時に正規化し、「やめて」「止めて」「キャンセル」等の辞書で照合する。1.5秒周期もQwenも待たない。検出は取消決定ではなくAlertであり、発話ID・版・一致範囲を添える。否定や引用を含んでも候補として検証できるが、単語一致だけでは仕事を取り消さない。同じ版の再送は重複Alertを作らず、訂正で候補が消えた場合も新版を渡して再判定する。

通常の発話開始でpause済みでも、Alertは「停止意図の判定が終わるまで自動再開しない」という保留理由を追加し、Qwen受信箱の最優先へ送る。未停止なら直ちにpauseする。これが音声活動検出に対する追加効果である。Alert単独では新しいTool起動を一律保留せず、停止の意図と対象が検証された時点で、その仕事の新規起動禁止・取消通知へ進む。確定までの間にToolが進む可能性は残るため、即時停止には対象ID付きUIボタンを設ける。

引用・否定で停止不要と判断した場合はAlertの保留理由だけを解除し、本人発話終了・最新revision・他の保留理由も確認して再開する。対象不明なら保留したまま短く確認する。確認発話には別の発話IDを付け、旧音声のpause確認後に再生する。判定期限を超えても停止候補を自動解除しない。ASRの訂正で仕事取消を自動撤回したり、取消済みToolを再起動したりしない。

| 対象 | Runtimeが行うこと | 停止確認の意味 |
| --- | --- | --- |
| 待機中の仕事 | 待機解除・取消を記録し、取り出し不可にする | 以後起動しない |
| ornithの推論 | 取消通知を送り、ストリームと後続Tool要求の採用を止める。Providerに取消APIがあれば利用する | ローカル処理の停止と、サーバー計算の停止は分けて観測する |
| 実行中Tool | Tool adapterの取消処理へ通知し、終了結果を回収する | 通信切断だけを外部操作の停止成功とみなさない |
| TTS・再生 | 対象音声の世代を失効させ、player停止・未再生音声の破棄を行う | 実playerから停止を確認する |

Toolには停止能力を明示する。開始前なら止められるもの、途中で協調停止できるもの、外部へ送信後は取消不可のものを区別する。送信済みメールなどは取り消せず、結果不明ならそのまま結果不明として報告する。

仕事の状態は停止要求の受理時点で `cancel_requested` とし、実行系の応答を見て `cancelled`、完了済み、結果不明等へ確定する。Qwenは受理時に「停止を要求しました」、停止確認後に「停止しました」と伝えられる。通常の依頼も、音声は即合成しつつ、登録成功・完了の表現はRuntimeが確認した状態に基づかせる。

条件変更は緊急停止と同一視しない。変更先を特定したら、その仕事の新規Tool起動と旧版の音声を保留し、実行済み・実行中の結果を照合して継続する。停止できない途中操作があれば、その事実を含めて次の判断へ渡す。

## 3. Contextの組立

Qwen用には、現在の発話とその更新、短い直近のやり取り、ユーザーが確認済みの呼称、実行中・待機中の依頼、回答待ちの質問ID、音声の再生済み範囲を上限付きで渡す。読み取り用の小さな投影とし、長期記憶の検索や全Tool定義を持ち込まない。追加の思考が必要ならornith用キューへ登録する。

ornith用には、現在の原文指示と制約を優先し、関連する履歴・Memory・World・Tool結果を予算内で組み立てる。根拠には出典、適用範囲、時点を残す。必須の訂正や未完了操作は、速度のために黙って落とさない。

Context Windowはその推論のための一時的な入力、Memoryは根拠を持つ長期的な理解、World Modelは現在の状況についての投影、実行台帳は仕事の進捗の正本である。embeddingの索引はこれらから再構成できる検索用データとする。

## 4. embeddingと検索

まず「どの消費先に接続するか」を決める。既存のTool検索を最初の対象とし、同じ入力集合でローカルworkerとの取得品質と遅延を比較する。その後、Memory・records検索への導入を必要性に応じて評価する。5番目のProviderが接続済みという理由だけで、全検索を一括移行しない。

索引にはモデルの識別情報、次元、前処理・query/passageの方式、対象sourceの版を持たせる。モデル変更時は別世代の索引を構築し、互換性のないベクトルを混ぜない。検索時のScope・削除状態を確認し、忘却後の古い索引から内容が復活しないようにする。

queryは会話に必要な優先度、文書の再索引は背景処理の優先度で動かす。利用不能時は、利用先が定義するFTS等の縮退を明示し、検索できていない状態を「該当する記憶がない」と答えない。

## 5. LLMストリーム・TTS・再生

**ユーザー指定の方針: LLMのユーザー向け応答ストリームに句読点が届いたら、そこまでを共通TTSキューへ直ちに渡す。合成枠が空いていれば即合成し、全文の完成、最終回答の採用、文ごとの採用審査を待たない。** Qwenとornithの双方に適用する。合成枠を使用中の場合は順番を待ち、再生には別途Runtimeの発声許可を適用する。先行合成した音声は到着順ではなく本文の順序で再生し、後続のLLM生成と重ねる。

分割単位はHTTP/SSEの受信chunkやtokenそのものではなく、連結した本文の句読点である。「確認します、続いて予定を調べます。」なら、「確認します、」が届いた時点で最初の合成を始める。句点だけでなく読点も区切りとして使い、最初の句の後に続く文を待たない。

1. ユーザー向け本文のdeltaを順に蓄積する。内部のreasoning、Tool引数・結果、制御JSONは本文から分ける。
2. `、。！？` などの句読点を検出したら、前回の区切りの次からその句読点までをTTSキューへ渡す。一つのdeltaに複数の句が含まれていれば、それぞれ順に取り出す。句読点で区切れた句を、最低文字数や次の文待ちで保留しない。
3. 共通dispatcherが発話と句の順序を確認し、合成workerへ一件ずつ渡す。再生可能になった音声から共通playerで本文順に再生する。先行音声の再生中に後続句の生成・合成を進められるようにし、合成と再生のキューには上限を設ける。
4. LLMが正常終了したら、句読点のない末尾も一度だけ合成する。最終回答の保存・完了イベントで、すでに送った本文を再投入しない。
5. 条件変更・取消等で対象のrunやrevisionが失効したら、未送信の本文と未再生音声を破棄し、必要な再生停止を行う。遅れて届く合成結果も再生しない。取消時は残りの本文をflushしない。

英語等の句読点も対象にする場合は、小数点やURL中の記号との区別を分割規則に含める。句読点のない長い出力には上限長による分割を補助として設けるが、通常の句読点到着を待たせる条件にはしない。

短い句の韻律、要求あたりの固定コスト、1秒あたりの合成件数・キュー滞留をベースラインで測る。初期は最低文字数による待機を入れない。worker取得時点で同じ発話の隣接句がすでに到着済みなら、追加待機なしで結合する最適化を比較できる。結合しても元の句との対応を残す。最低文字数や待機時間を導入する場合は、遅延と音質の比較を伴う方針変更として扱う。

### 読み上げ本文の公開契約

Runtimeは生成要求の開始前に許可する出力用途とイベント順序を指定し、Provider adapterはその契約と構造化されたイベント種別から配信先を決める。モデル本文中の「公開」「final」などの自己申告タグで権限を切り替えない。以下の名称は新設する契約案であり、現在のProviderがすべて対応済みという意味ではない。

| 出力用途 | TTSへの経路 |
| --- | --- |
| `internal`：推論、候補比較、Tool呼出し・結果、採用審査 | 接続しない。通常contentに見えるTool前の前置きも、内部用途の要求なら読まない |
| `user_speech`：回答、質問、確認済み状態の説明 | Runtimeが発行した公開枠に紐づく本文deltaだけを即時分割する。公開枠はtask/revision、発話種別、speechIdを固定する |
| `control`：キュー操作、質問登録、取消要求 | 構造化要求として検証・適用する。JSONやTool引数をTTSへ渡さない |

ornithのTool実行・候補比較は内部用途とする。Tool結果を受け取った後、実行計画上ユーザーへ回答する次の要求をRuntimeが公開用途・Toolなしとして開始できる場合は、そのストリームを使う。Toolの必要性が未確定の要求は内部用途に留める。単に通常contentが来たという理由で公開へ切り替えず、内部要求の全文を必ず別モデル要求で言い換える方式にも固定しない。内部で完結した候補から回答を作り直す必要がある場合だけ追加要求を行い、追加回数・実行枠占有・prefill・後続依頼の待機を計測する。すべての推論要求は同じornith実行枠を使い、ユーザー待ちでは枠を解放する。

Qwenの初期契約は、1要求の中で次の順序を保証する。

1. 制御ヘッダーを独立した構造化レコードとして完結させる。操作候補、Runtimeが提示した対象参照、根拠の発話版、発話種別を含み、Provider adapterが重複キー・形式不正を拒否する。自由文のタグを制御として解析しない。
2. Runtimeが対象・版・曖昧性を検証し、必要な保存を行って公開枠を確定する。ヘッダーは確定後に変更できず、後続の制御追加・差替えを拒否する。ヘッダーで完結した操作は後続本文の失敗によって自動撤回しない。
3. 同じ要求の本文deltaを逐次デコードする。保存完了前の本文は上限付きで保持し、成功後に句読点単位でTTSへ渡す。成功していれば次の句を待たない。保存失敗・宛先失効・形式不正・buffer超過では公開せず、生成を取消してRuntimeの確認済み状態に基づく短い定型応答または画面表示へ縮退する。本文のためだけに二度目のQwen推論は起動しない。

本文はあくまでヘッダーの処理が成功した場合の表現であり、未来の完了結果を先取りしない。停止要求の受理時点では「停止を要求しました」までとし、「停止しました」は別途停止確認後のRuntime通知で伝える。保存時に変化し得るキュー順や進捗も、先に生成した本文へ確定情報として埋め込まない。

既存の `kind/reply` は、そのままで上記のレコード境界や順序を保証するものではない。Provider adapterで保証できる形式へ変更し、ヘッダーが遅れる・書き換わる・制御と本文が混在するケースを受入試験に含める。対応不能なProviderはこの早期読み上げ契約を未対応として表示する。最終文面の完成・採用審査や、句ごとの意味審査を待つ設計にはしない。

現在の `BufferedRoleStepSink` はユーザー向け本文も最終採用まで保持しているため、この方針との差分になる。ユーザー向け本文を逐次TTSへ流す経路と、内部の推論・比較候補を保持する経路を区別する。Toolの操作許可や実行結果の確定は既存Runtimeで管理し、音声合成の開始を操作成功の証拠にはしない。

### 早期発話の後で却下・失敗・訂正が起きた場合

先行して聞こえた本文は取り消せない。公開用途を分けても内容の正しさまでは保証できず、「採用前に話す」と「却下される内容は一切聞こえない」は同時に保証しない。Role Routingの最終採用と、実際に公開した発話は別に記録する。

1. 却下・生成失敗・訂正をRuntimeが受理したら、該当speechの世代を失効させ、残りの合成と再生を停止する。停止確認まで次の音声を重ねない。
2. 未再生なら古い本文を再生せず、必要な新回答だけを流す。再生済みまたは出力済みか不明な部分があるなら、確実に再生終了した句と途中の句を履歴へ残し、全文を未発言として消さない。
3. 意味を撤回する必要がある場合は、Runtimeが訂正イベントを一度だけ保存する。確認済みの訂正があれば「先ほどの〇〇を訂正します。正しくは…」、まだ確定できなければ「先ほどの回答は確認が取れていません。確認し直します」と伝える。単なる音声障害では内容が誤りだったと断定せず、読み上げの中断として扱う。
4. 訂正は対象speechへの参照を持ち、次の再生選択で通常の待機回答より優先する。無関係な再生中発話は取り消さず、音声停止中は勝手に発声を再開しない。本文・訂正待ち状態は画面にも残し、次のQwen・ornith Contextへ渡す。

公開記録は推論結果の採用状態を上書きしない。Toolの成功・Memoryへの事実採用は、音声で述べたことを根拠に確定しない。以上は今後の実装方針であり、この文書更新ではランタイムを変更しない。

### Qwen・ornith共通のキューで合成と再生を管理する

LLMの生成は並行してよい。初期構成では共通TTS workerを一つ、使用中の出力デバイスに対するplayerを一つとし、**同時合成要求数は1以下、同時再生数も1以下**にする。合成と再生は別工程なので、句Aを再生しながら句Bを合成できる。これにより早期出力を維持しながら、両モデルによるTTSの同時呼出しと二重再生を防ぐ。

キューに入れるだけでは排他は保証されない。Qwen・ornith・再試行処理からTTSやplayerを直接起動する経路をなくし、共通dispatcherだけが取り出しと起動を行う。worker再接続時も一つの実行所有者だけが有効になるよう、世代と実行枠を管理する。既存の並列合成設定をそのまま二モデル別々に動かす構成にはしない。

| 段階 | キューに保持するもの | 次へ進む条件 |
| --- | --- | --- |
| 発話受付 | `speechId`、発話元、仕事・revision、発話種別、受付順、本文の句 | 有効な公開枠と最初の句があり、発話順が回ってきた |
| TTS要求 | `speechId/chunkSeq`、本文参照、世代、要求ID | 有効な世代で、前の合成要求が終了している |
| 音声待機 | 合成した音声、発話ID、句の連番、音声長 | Runtimeの発声許可があり、同じ発話内の先行句に続けてplayerへ投入できる |
| 再生 | 現在の発話・句、消費frame数、再生済みの句 | playerが先行音声を消費してから次の音声を再生する |

最初の句は合成して再生可能になり、Runtimeの発声許可があれば直ちに出力する。後続の句は先行音声の再生中にも合成し、同じplayerのFIFOへ追加する。playerが音声を連続して消費するため、句ごとの別playerの起動や、想定音声長のtimerによる再生切替えは行わない。

### 回答の句が交互に混ざらない発話順

再生の所有権は句ごとに取り直さず、`speechId` 単位で持つ。最初の合成可能な句が来た時点で発話順を確定し、その回答の後続句も同じ発話に追加する。先に生成を始めたが本文がまだないモデルのために音声出力を予約しない。同時到着はRuntimeが付ける受付順で一意に決める。

たとえばQwenの回答QがQ1・Q2、ornithの別件回答OがO1・O2に分かれ、Q1を再生中にO1とQ2が届いた場合は、Q1→Q2→O1→O2の順に流す。受信順のQ1→O1→Q2→O2にはしない。Qwenは音声の順番待ち中もASR更新を受け取り、思考キューの登録・回答返送を続ける。

再生の所有権を解放する通常条件は、LLMの発話終了を受理し、末尾を含むすべての句の合成と実再生が終わったこととする。一時的にplayerのbufferが空になっても、LLMが後続句を生成中なら別の発話を割り込ませない。ただし生成の停止・通信断で無限に占有させず、進捗期限超過を音声失敗として処理し、取消・停止確認後に次の発話へ進む。失敗した古い発話の続きを後から混入させず、画面の本文・仕事の状態は別に保持する。

ユーザーの割り込みによる一時停止は、上記の通常終了とは別の遷移とする。playerのpause確認後に再生位置と未再生分を保持する。相槌・非発話音から同じ回答へ戻る間は所有権を保持し、確認発話が必要な場合だけ退避して所有権を解放する。確認質問は新しいspeechとして再生できる。旧発話は最新入力との整合確認後にだけ再開候補となり、訂正・取消なら破棄する。確認のために停止した旧発話がキュー先頭を占有し続ける状態を作らない。合成workerの実行枠は合成終了・取消確認まで保持し、再生所有権の解放とは混同しない。

確認が必要な場合は、旧発話の未着手の合成も保留し、実行中の1要求が終了・取消確認された次の合成選択で確認発話を優先する。旧発話の全文生成・全句合成の完了を待たせない。旧発話の後続deltaは上限内で保持し、上限到達時は既定の抑制・音声失敗へ進む。この割り込みと訂正以外では、通常の発話順を維持する。

合成の位置と再生の位置は別に持つ。先行発話のLLM終了と末尾までの合成が確定したら、その音声を再生中でも次の発話の先行合成は可能とする。合成workerは一件ずつ処理し、次の発話の音声は再生キューで待つ。これにより発話の切替え時に、次の最初の句の合成待ちを減らせる。

### 相槌の失効、停止、再送

- 同じ依頼に対するornith回答の最初の句が届いたら、その依頼の待機用相槌を失効させる。後から届くQwen相槌にも同じ失効を適用する。別件のQwen回答や確認質問を、発話元がQwenという理由で捨てない。
- 相槌が再生中なら、対象の合成・playerへ取消を通知し、未再生bufferを破棄する。対象の合成が終了または停止し、playerも停止したことを確認してからornithへ再生の所有権を移す。停止未確認のまま次の要求・再生を重ねない。すでに先行合成したornith音声は有効な世代なら利用できる。
- 明示的な読み上げ停止・仕事取消は通常の発話順を待たず制御する。停止対象の世代を更新し、遅着した合成結果や再生終了通知を無視する。古い終了通知で新しい発話の所有権を解除しない。
- 同じ `speechId/chunkSeq/世代` の再送は一度だけ受理する。全文完了イベントでも、すでにキューへ渡した句を再投入しない。
- 必要な句の合成に失敗した場合は、黙ってその句を飛ばして後続を読まない。その発話の音声を失敗として終了し、停止確認後に他の発話へ進む。再生済みか不明な音声を自動再読しない。

再生位置は、`speechId/chunkSeq`、playerが消費したframe数、最後まで再生した句、待機中の音声量で管理する。`合成済み`、`player投入済み`、`再生開始`、`再生終了` は別イベントにする。出力デバイスのbuffer遅延を含むため、frame消費は出力進捗の指標であり、ユーザーが聞き取ったことの保証とはしない。

一時停止では同じplayerの未消費PCMと再生位置を保持し、resume時にその位置から続ける。世代を失効させてbufferを破棄するcancelとは別の状態にする。pause/resumeを保証できないadapterは相槌後の自動再開を未対応とし、句の先頭から黙って再読しない。

途中で破棄された句は途中として記録し、単語ごとの時刻対応がないのに「ここまでの文字を読んだ」と断定しない。ユーザーが再開を求めた場合は、その句の先頭から等の明示した方針で再生成できる。キュー件数・本文量・合成済み音声量には上限を設け、満杯なら受信を抑制するか、その発話の音声失敗を明示する。音声の滞留を理由にASRやQwenの仕事受付を停止しない。
