# SAAA：5種類のProviderで実現するJarvis型アシスタント

作成日: 2026-09-26  
状態: コンセプト案（2026-09-26の作業ツリーを部分照合）／提案の実装・実機受入は未実施

## 1. 目指す体験

SAAAは、呼びかけにすぐ応じ、必要なことを覚え、現在の状況を踏まえて仕事を進める、ユーザー専属の常駐アシスタントを目指す。

会話の入口はQwen 2Bが担当する。ASRは常時聞き取りを続け、ユーザー本人の発話だけを文字起こしする。発話中はその更新を1.5秒ごと、発話の区切りでは周期を待たずQwenへ渡し、簡単な問いにはその場で答える。思考が必要な依頼はQwenがキューへ登録し、ornith 1.5が順に取り出してContext Window、World Model、Memory、Toolを使って仕事を進める。TTSはLLMの応答ストリームを句読点で区切って順に音声へ変える。embeddingは必要な情報や能力を探すために使う。

ユーザーには一人のアシスタントとして振る舞う。モデルの切り替えを意識させず、前の話、進めている仕事、新しい条件がつながっていることを重視する。

当面は本人とアシスタントの応対に集中し、受理した本人の発言はすべてアシスタント宛てとして扱う。呼びかけ先の分類、会議録音、他の用途の文字起こしは今回の設計対象に含めない。

**Qwenの役割は、ornithの準備や思考にかかる時間の中でも、会話を途切れさせないこと。ornithの役割は、根拠と実行結果に責任を持つこと。** 発話量を増やして待ち時間を隠すことは目標にしない。

### この文書の根拠と範囲

方針と受入基準は本書を正本とする。キュー、停止、出力用途、TTSの詳細は[Runtime契約](saaa-jarvis-five-provider-runtime-contract.md)、コードで確認した現状と調査の限界は[実装状況と根拠](saaa-jarvis-five-provider-implementation-status.md)に分ける。3文書とも提案と既存実装を区別し、実機性能は未検証である。

実装の着手範囲、既存コードへの接続先、段階別の作業と完了判定は[初回実装計画](saaa-jarvis-five-provider-implementation-plan-v1.md)を参照する。

この作業では文書だけを追加・改訂する。ランタイム、Provider設定、DB、凍結対象は変更しない。本書は次の設計・実装の判断基準であり、既存の実行権限や回答採用条件を自動的に変更するものではない。

## 2. 5種類のProviderの役割

ここでの5種類は論理的な役割である。別々のサーバーやGPUを5台用意するという意味ではない。接続先を共有しても、準備状態、容量、タイムアウト、障害は役割ごとに扱う。

| Provider | 主な役割 | 渡す情報・返すもの | 境界 |
| --- | --- | --- | --- |
| Qwen 2B / `backchannel` | 挨拶、相槌、簡単な回答、思考依頼のキュー登録・更新判断 | 定期・区切り時の文字起こし更新と軽量な会話・キュー状態から、応答と受付操作を返す | 業務Toolを実行しない。キュー操作はRuntimeへの制御要求とし、未確認の進捗や完了を語らない |
| ornith 1.5 / `llm` | キューから依頼を取り出し、主思考、調査、計画、Tool利用、Memory・World Modelを使う応答を行う | 原文の依頼、制約、関連Context、実行結果から回答・操作要求を作る | 操作許可、結果採用、永続化はSAAA Runtimeが管理する |
| ASR / `asr` | 常時聞き取り、ユーザー本人の文字起こしを継続する | 話者を確認した途中認識・確定発話を更新として返す | 他人の声・TTSの自声をQwenへ流さない。1.5秒の区切りを依頼完了とみなさない |
| TTS / `tts` | 回答を早く、自然に読み上げる | ユーザー向け応答ストリームの句読点到着で、それまでの本文を合成する | 全文完成・回答採用を待たない。内部の思考過程、Tool引数、制御JSONは読まない |
| embedding / `embedding` | 関連する記録・記憶・Tool候補を絞る | テキストをベクトルへ変え、検索に利用する | 類似度は事実の証明や操作権限ではない。検索・索引管理はSAAA側の責務 |

キュー操作は、Runtimeが提示した仕事・質問への限定的な制御要求であり、外部サービスや業務データを操作するToolとは区別する。QwenにTool実行権限を与えず、Runtimeが検証・永続化する。

Qwenはtoken生成速度を重視し、思考出力を無効にし、入力と出力を小さく保つ。ただし採用判断はtok/sだけでは行わない。最初のtokenまでの時間、構造化出力の完成時間、最初の可聴音までの時間、振り分けの正しさを合わせて評価する。

ornithには、単に長い履歴を渡すのではなく、今回の仕事に必要なContextを渡す。Context Windowの組立、検索、接続、prefill、生成、Tool待機を別々に計測する。「ornithが重い」という一つの説明にまとめない。

## 3. 会話として守る振る舞い

### 常時聞き取り、1.5秒ごとにQwenへ渡す

音声入力を有効にしている間、ASRはQwenの応答中、ornithの長考中、TTSの再生中も聞き取りを続ける。ユーザーが明示的に停止・ミュートした場合は止める。登録した話者との照合とTTSの自声除去により、ユーザー本人の文字起こしだけを会話へ入れる。話者未確認の音声を本人として通さず、照合不能や聞き取り障害を状態として示す。

**1.5秒は発話中の文字起こし更新をQwenへ渡す基本周期とする。** 話し続けている間も、その時点の新規テキストや訂正を渡す。送信は無音1.5秒や発話全体の確定を待たない。認識途中か確定済みか、どの発話のどの版かを付け、Qwenが続きや訂正として理解できるようにする。

音声の区切りを検出したら、その時点の未送信更新を周期を待たず送る。最後の認識がまだ届いていなければ、後着した最終認識・訂正も即時に追送する。本文が同じでも途中から確定への状態変化は届ける。同じ発話ID・版・確定状態の再送は重複処理せず、定期送信と即時送信から同じ仕事を増殖させない。

更新のない周期には同じ本文や空の入力で生成を繰り返さない。ASRは継続し、次の新規・訂正または確定状態の更新を、定期・即時送信の規則に従って送る。1.5秒ごとの入力は毎回返事を発声する指示でも、毎回ornithへ依頼を作る指示でもない。Qwenは話の途中なら続きを待ち、必要な短い応対だけを行う。

### 受信・生成・合成・発声のタイミングを分ける

Qwenへの送信は発話中の1.5秒周期と区切り時の即時送信を併用し、本文の合成は句読点到着で進める。実際に声を出す許可はRuntimeが管理し、Qwenの判断だけでは再生を始めない。合成済み音声は必要な間だけキューで待つ。

初期の再生許可は、本人の音声活動がなく、音声から検出した発話区切りを満たすこととする。区切りは無音300msを暫定値として実機で調整する。ASRの確定テキストだけでは、話し続けているユーザーへの割り込みを許可しない。明確な質問が途中認識に現れても、それだけでは発声しない。読み上げ開始直前に最新の音声活動と本文の有効性を再確認する。

本人の発話開始を検出したら、音声bufferと再生位置を保持して一時停止する。単なる音量変化を本人発話とみなさず、自声・他人・咳などとの区別を入力経路で行う。判別中は暫定pauseできるが、非発話音と確定した場合は区切り後にQwenを呼ばず再開できる。判別不能を「咳だった」と推測して再開しない。ASR・生成・仕事受付は継続する。

回答を聞きながらの「うん」は、回答待ちの質問や停止候補がなく、最新入力をQwenが変更不要の相槌と判定した場合に自動再開する。質問への「うん」は回答として処理する。相槌の再開は発話終了からp95で1秒以内を初期目標とし、区切りから1.5秒を判定待ちの期限案とする。期限超過では保留状態と再開UIを示し、時間切れだけで再開したり同じ確認を繰り返したりしない。遅着した有効な判定で再開できる。

通常の一時停止では保持した音声位置から続け、句の先頭へ巻き戻さない。訂正・明示停止・取消で破棄した音声とは区別する。判定の版が古い、停止候補が未解決、または認識が不確かな場合は保留し、必要な確認発話だけを別途許可する。

アシスタントがユーザーの発話中に返す相槌は任意の会話方針として独立させ、初期は無効にする。有効化する場合もRuntimeが相槌専用枠を与え、同じユーザー発話につき短い相槌を最大1回に制限する。通常の回答・確認質問・Tool結果をこの例外へ混ぜない。この調整は再生の許可に限り、句読点での即時合成は維持する。

### 自声除去と話者照合の前提

再生中の本人発話による割り込みを有効にする前に、段階2で実スピーカー・マイクを使い、TTSだけでは停止・ユーザー入力・思考依頼が発生せず、TTSに重なる本人発話は受理できることを確認する。話者照合だけで自声除去を代用しない。本人照合・非発話音の区別に要する時間も割り込み遅延へ含める。

自声除去が未成立なら、段階4の模擬試験・キュー開発は進められるが、音声割り込みを含む実機受入は未完了とする。暫定運用では自動割り込みを無効にし、UIで音声を止める。ASRの取得は続けても、再生中に本人と確認できない認識は会話入力へ流さず、UIに「再生中の音声受付に制限あり」と示す。自声から新規依頼を作らない。この縮退では本人の発話を取りこぼす可能性があり、常時応対の達成とは扱わない。設定の保存値を勝手に変更せず、実効状態として表示する。

### 推論回数と低遅延の方針

Qwenの初期構成は、各入力更新に対し1回の生成要求で制御ヘッダーを先に確定し、その後に本文を流す方式とする。Runtimeの検証・保存中に届く本文は上限付きで保持し、成立した公開枠へ句読点単位で渡す。制御と本文を別々に再推論する方式は標準にしない。後着したASR訂正による別要求は、1回答のための二段階生成とは別に計測する。

ornithも、内部用途と公開用途の分離だけを理由に毎回答の追加生成を義務付けない。既存のToolループで結果を受け取った後の回答要求を公開用途へ指定できるなら、そのストリームを使う。実行中の内部要求を本文タグだけで公開へ変更しない。候補審査などで追加要求が必要な経路は、実行枠1つを引き続き使い、追加要求数・prefill・キュー待ちを含めて比較する。短い確認済み進捗はRuntimeの定型文で通知できる。全内部出力の再文章化は初期構成に含めない。

契約を満たさないProviderで黙って二重推論や公開範囲の緩和へ切り替えない。Qwenは確認済み状態の定型応答、ornithは早期読み上げ未対応として状態を示し、Provider adapterの対応後に速度と品質を再評価する。2回生成を採用するなら、p95の体感遅延と処理量の比較を伴う設計変更とする。

### 簡単な会話はQwenで完結する

「おはよう」「ありがとう」「1+1は？」のように、現在の発言だけで確かな短い答えを返せる場合はQwenで完結する。ornithや検索を毎回呼ばない。

短文でも「明日の予定は？」「前に決めた設定は？」は、現在の情報や記憶の確認が必要なのでornithへ渡す。文の長さや特定キーワードだけでは分類しない。曖昧な発言を都合よく完結扱いせず、確認または引継ぎにする。

### 重い仕事の開始を短く伝える

「明日の予定と移動時間を調べて」の場合、Qwenが思考依頼をキューへ登録し、短い受付応答を返す。ornithが空いていれば直ちに取り出し、長考中なら待機させる。どちらの場合もキューを経由し、Qwenはその完了を待たず次の音声入力へ応対する。受付の音声再生とornithの準備・処理は重ねられる。

受付、実行待ち、実行中、完了を区別する。「調べています」は実際に処理が開始している場合に限る。Qwenの返答は、ユーザーの原文や条件を置き換える要約には使わない。

長い仕事の後ろに短い依頼が並ぶ場合は、受付時に「今の調査が終わったら確認します」と待機を伝える。以後は開始・失敗などの状態変化か、ユーザーの問い合わせに応じて知らせる。残り時間を推測せず、Runtimeの待機時間・順番を使う。初期は通常FIFOを維持し、短そうな依頼をQwenの予測だけで追い越させない。待ち時間の実測をもとに優先度や中断・再開の導入を別途判断する。

### 考えている間にも話を受け取る

目標は、ornithの仕事を維持したまま、追加発言へ適切に反応できること。「うん」で再推論を始めず、「徒歩でお願い」は既存依頼の条件変更、「別件だけど」は別依頼、「やめて」は停止要求として扱う。指示対象が不明なときは確認する。

QwenはRuntimeから渡された短い状態を使って応じる。たとえば「予定を取得中」「次の依頼は待機中」は使えるが、モデルが進捗率を推測してはいけない。独立した別件は次の思考キューへ登録する。条件追加は対象の依頼を更新し、実行中なら変更を反映した継続依頼をキューへ登録する。その時点で旧条件の未再生回答を保留し、同じ依頼を1.5秒ごとに増殖させない。

### 声は一つ、結果は一度

Qwenとornithは同時に回答を生成できるが、音声は共通の発話キューへ集める。ornithのユーザー向け応答が最初の句読点まで届いたら合成対象として登録し、同じ依頼の待機用相槌より優先する。未再生の古い相槌を捨て、必要なら再生中の相槌を停止してから回答する。別件のQwen回答は保持し、順番に再生する。ornithの結論をQwenに書き直させない。

ユーザーの割り込みには、音声停止と仕事の取消を分けて対応する。「読み上げを止めて」で仕事まで取り消さず、「その作業をやめて」なら対象の実行も止める。ASRがTTSの自声を新しいユーザー発言として受理しないことも受入条件にする。

沈黙が自然な場面では黙る。初回の短い受付に加え、意味のある状態変化やユーザーからの問いに応じて進捗を伝える。一定間隔の「はい。」を会話継続の代わりにしない。

## 4. 資源配分と待ち時間

会話の低遅延処理と背景処理を分ける。ASR、Qwenの応対、最初のTTS音声が、ornithの長い生成やembeddingの再索引に押し出されない配置を目指す。ただし、resourceGroupの名前を分けるだけではGPUの並列能力は増えない。

必要なモデルの準備状態を把握し、起動時・復帰時に有限の準備処理を行う。重い全サービスclaimによって、すでに使えるQwenやASRまで待たせない。常駐は、無言の間にLLMへ繰り返し生成要求する意味ではない。

| 測定点 | 判断したいこと |
| --- | --- |
| ユーザーの発話終了 → 最初の可聴応答（主要指標） | 音声上の終了時刻から測り、ASR・周期待ち・発声許可・全キュー待ちを含む体感遅延を把握する。受付相槌と内容への回答を分ける |
| ユーザー音声 → 話者照合 → ASR更新 → 定期／区切り時のQwen送信 | 話し続けても更新が届くか。本人以外の混入と、Qwen入力の滞留がないか |
| 受付保存 → Qwen要求 → 最初のtoken → 検証済み返答 | 共通処理、接続、prefill、decode、JSON完了のどこで待つか |
| Qwen返答 → 最初の可聴音 | TTS要求、合成、音声転送、playerの待ちがどれだけあるか |
| 思考キュー登録 → 受付保存 → ornith取り出し | Qwenが登録後すぐ受付に戻れるか。キュー長・最古の待機時間・失敗を追えるか |
| ornith開始 → Context準備 → 接続・lease → 最初のtoken | Contextとモデルの準備コストを分離できるか |
| ornith生成・Tool・回答採用 | 実作業と回答公開の待ちを分離できるか |
| 応答本文の最初の句読点受信 → TTS要求 → 最初の可聴音 | 全文完成・回答採用を待たずに合成と再生が始まるか |
| 発話受付 → TTS枠取得 → 合成終了 → player再生 | 同時合成数・同時再生数がそれぞれ1以下か。合成待ちと再生待ちを分離できるか |
| 追加発話受付 → Qwen応答、停止要求 → 実音声停止 | 思考中の応対と割り込みが成立しているか |
| embedding query / 再索引中の上記各時間 | 検索や背景処理が会話を妨げていないか |

各値は温間・冷間、単独・同時稼働を分け、p50/p95を記録する。モデル、量子化、機器、入力tokens、出力tokens、同時負荷をそろえて比較する。Qwenのdecode tok/sは初回待ちを除いて別途測り、体感遅延と混同しない。

主要指標の初期目標案は、温間・先行音声なしの簡単なQwen応答で、ユーザーの発話終了から可聴開始までp95で2.5秒以内とする。実録音で最後の本人音声の終了を注釈し、VAD・ASRの終了通知時刻との差も記録する。無応答・失敗は集計から隠さず件数を併記する。重い依頼は受付応答までとornithの有用な回答までを別に測る。短い相槌だけで回答遅延の目標達成としない。これは未測定の目標案であり、区切り即時送信・後着認識・計算時間を含めて成立するかをベースラインで判断する。

工程別の補助目標案は、先行音声がなく合成・再生枠が空き、発声が許可された温間条件で、応対する入力のQwenへの更新送信から可聴開始までp95で2秒以内、応答本文の最初の句読点受信から可聴開始までp95で1秒以内、Runtimeが音声停止要求を受理してから実停止まで500ms以内とする。現状の実測値ではなく、最初のベースラインを見て採用可否を決める値である。同時生成時はこの値に混ぜず、発話順の待機を含む全体遅延も必ず報告する。音声による停止は、ユーザーの停止発話開始から停止候補検出・実停止までの時間も別に測り、ASR認識前の遅延を隠さない。設定のtimeoutを伸ばしただけで達成としない。ASR処理時間、1.5秒周期による待ち、Qwen入力の滞留、ornithのキュー待ち、TTS合成待ち、再生待ちはそれぞれ別に報告する。

5種類の同時動作が資源上難しい場合は、どの組合せで待つかを表示する。Qwenを使える状態とornithで仕事を実行できる状態を一つの「接続済み」にまとめない。

## 5. 現状からの改善順序

| 順序 | 作業 | 完了と判断する条件 |
| --- | --- | --- |
| 1. 実効構成とベースライン | 5役割の設定、実model、接続経路、容量、flag、起動buildを記録し、通常の音声入口で計測する | どの段階で待つかを数値と相関IDで説明できる。設定表示と実効経路が一致する |
| 2. 常時ASRとQwenの即応 | 本人登録・話者照合・自声除去の既存経路を調査し、不足分を整備する。発話中は1.5秒周期、区切り・後着最終認識では即時に渡し、発声許可と1回生成を検証する | TTS・ornith稼働中も更新が届く。簡単な応答でornith呼出0。発話途中の無許可再生0。凍結対象の変更時は[検証手順](saaa-jarvis-five-provider-implementation-status.md)に従い、指定回帰後に該当domainだけ理由付きacceptと凍結チェックを完了する |
| 3. 思考キューと継続応対 | Qwenの登録・更新・取消要求を永続キューへ接続し、ornithの取り出しと結果配信を分ける | 長考中も受付・登録できる。FIFO・待機通知・重複排除・条件更新・停止・再起動復元が成立し、Qwen分類の固定評価が合格する |
| 4. 共通キューによる早期TTS | 公開用途を分離し、両モデルの本文deltaを共通worker・playerへ接続する。発話所有権・末尾flush・取消・訂正を整備する | 実機で音声割り込みを有効化する前に段階2の自声除去・本人照合を合格させる。未成立なら制限表示付き暫定運用に留める。空き枠で最初の句読点から合成。発声許可時は全文完了前に音声開始。合成数・再生数は各1以下。内部出力の読み上げ・句の混在・重複・失効音声の再生0。却下後の停止・訂正が追跡できる |
| 5. embeddingの利用先を接続する | Tool検索から品質・負荷を比較し、必要ならMemory等へ広げる | Provider診断に加えて実検索の利用証跡がある。索引世代、Scope、忘却、障害時の縮退が成立する |
| 6. 継続利用を受け入れる | 長い会話、別件、取消、接続断、復帰、再起動を反復する | 会話、仕事、記憶、声が整合する。再起動で操作を二重実行せず、新しい発話を受け取れる |

各段階を既存Runtimeへの小さい変更として進める。新規基盤や全体リファクタリング、別のMemory正本、常時ループする自律エージェントの追加は今回の改善の前提にしない。

## 6. 受入シナリオと検証方法

各表は該当段階の完了に必須とし、後段でも回帰対象として維持する。段階1は第5章のベースライン記録を完了条件とする。段階4の実機受入には段階2の自声除去・本人照合合格が必要だが、模擬試験の先行を妨げない。任意の発話中相槌は、有効化する場合だけ追加で受け入れる。

### 段階2：音声入力とQwen即応

| シナリオ | 必須の結果 |
| --- | --- |
| ユーザーが話し続ける | 無音確定を待たず1.5秒周期で文字起こし更新がQwenへ届く。周期ごとに同じ依頼を作らない |
| ユーザーの発話途中・ASRだけが先に確定 | 生成・合成は進められるが、通常回答は再生しない。相槌の例外は明示的に有効化した枠だけ。音声区切り後も本文の有効性を再確認する |
| 簡単な応答の体感遅延 | 実音声上の発話終了から可聴開始まで測り、ASR・周期・発声許可の待ちを含める。失敗数と受付相槌／実回答の区別を記録する |
| TTS再生中・ornith長考中のユーザー発話 | ASRの聞き取りとQwenへの更新が続く。他人の声とTTSの自声は除外する |
| 無音・話者未確認・更新なし | 同じ本文を再送して生成や思考依頼を繰り返さない。話者確認不能を本人扱いしない |
| 挨拶・お礼・確かな簡単な質問 | Qwenのみで短く返す。Toolとornithを呼ばない |
| 「旅行を考えているんだけど」など話の途中 | 勝手に調査・実行を始めない。続く発言を失わない |
| 区切り直前・直後の周期、遅れて届く最終認識 | 区切り時の未送信更新と後着最終認識を周期待ちなしで送る。同じ版の重複推論・仕事登録をしない。本文なしの区切りで空の生成を起動しない |
| TTS単独／TTSと本人発話の重なり | TTS単独による入力・誤停止・思考依頼は0。本人の重なり発話を受理する。未成立なら自動割り込みを有効化せず制限表示し、段階4の実機受入を通さない |
| Qwenのヘッダー遅延・保存失敗・後続差替え | 正常応答は1生成要求。保存前本文は公開せず、後続ヘッダー変更を拒否する。失敗時は本文を捨てて確認済み状態の定型表示へ進む。本文用の追加推論0 |

### 段階3：思考キュー・回答返送・停止

| シナリオ | 必須の結果 |
| --- | --- |
| 長い依頼の後ろに短いornith依頼が並ぶ | 待機を正しく伝え、FIFOで処理する。推測の進捗・残り時間や定期的な相槌を出さない |
| 曖昧な回答・停止の引用や否定・無効な宛先 | Runtimeが必要な確認を強制し、質問消込や仕事変更を行わない。分類別の固定評価と不要確認率が合格線を満たす |
| ornithが依頼Aを実行中に依頼B・Cを受ける | QwenがB・Cをキューへ保存して応対を続ける。通常時はAの後にB、Cの順で処理する |
| 待機依頼への訂正・ASR更新の再送 | 同じ依頼を更新し、重複した思考依頼や副作用を作らない |
| ornithの質問にユーザーが回答する | 質問IDで元の仕事へ結び付け、新規依頼を作らず再開する。確認待ちの間は他の仕事を実行できる |
| 複数の確認質問・質問終了前に届く回答 | 宛先を取り違えず、回答を保存する。元の推論終了前に同じ仕事の継続を二重起動しない |
| 保存直後の配信失敗・回答再送・再起動 | 未配信を復元し、質問消込と再開は一度だけ行う。取消・失効した質問を復活させない |
| Qwen遅延・キュー満杯・保存失敗 | ASRを止めず、更新の滞留を追跡する。登録できなかった依頼を登録済みと伝えない |
| 予定確認・過去の判断・World状態への質問 | ornithが必要な出典を参照する。Qwenが記憶や最新状態を推測しない |
| ornith思考中に「うん」 | Qwenは必要な応対ができ、既存の仕事は再起動しない |
| ornith思考中に「やっぱり徒歩で」 | 対象の仕事へ条件を追加し、旧条件の回答を公開しない |
| 「声だけ止めて」／「作業を中止して」 | 読み上げ停止と対象作業の取消を区別する |
| UI停止・音声停止候補・取消不可Tool | UIはモデル判断を待たず停止制御へ進む。音声は意図と対象を検証し、停止要求と停止確認・結果不明を区別する |
| 停止語を含む途中認識・否定・引用・訂正 | Runtime検出器が周期を待たずAlertを作り、Qwenへ優先配送する。再開保留と仕事取消を区別し、単語一致だけで全Toolを止めない |
| 分類精度未達・確認過多 | 重大操作別の評価母数と誤りを報告する。不要確認率超過を未達とし、入力・規則の改善またはモデル構成の比較へ戻る |

### 段階4：早期TTSと割り込み再生

| シナリオ | 必須の結果 |
| --- | --- |
| 再生中にユーザーが話し始める | 本人発話を検出してpauseし、ASRを継続する。非発話音は確定後に再開、相槌は有効な判断後に保持位置から再開する。確認発話が必要なら旧音声を退避する |
| Tool前置き・内部推論・比較候補と公開本文が届く | 内部用途の出力は読み上げ0。公開枠の本文だけが句読点でTTSへ渡る。本文中の偽のチャネルタグは無効 |
| 読み上げ開始後の採用却下・内容訂正 | 残りを停止し、再生済み・途中・未再生を記録する。必要な訂正を重複なく配信し、次のContextへ反映する |
| 短い句の連続と合成待ち | 最低文字数待ちを入れず、要求数・滞留・韻律を測る。到着済み句の結合を比較する場合も、追加待機・順序変更・重複を発生させない |
| 長文回答・読点で続く文 | 最初の読点または句点でTTS合成開始。全文完成・回答採用を待たず、本文順に音声が聞こえる |
| deltaをまたぐ句・一度に届く複数の句・句読点のない末尾 | 受信chunkの境界に依存せず分割し、正常終了時の末尾を一度だけ合成する |
| Qwenとornithの同時生成・短い句の連続 | 共通dispatcherが合成を直列化し、同時合成数と同時再生数がそれぞれ1以下。各モデルの直接TTS起動0 |
| Q1再生中に別回答O1と後続Q2が届く | Q1→Q2→O1の発話順を維持する。bufferが一時的に空でも回答途中で別回答を挟まない |
| 先行発話の再生中に次の発話を合成する | 合成は先行できるが、次の発話の再生は先行発話終了後。実際の再生位置と未再生bufferを追跡できる |
| 発話途中の生成停止・合成失敗・停止未確認 | 無限占有・欠けた句を飛ばした再生を防ぐ。停止未確認のまま二つ目の要求やplayerを起動しない |
| 先行合成後の取消・生成失敗・最終完了イベント再送 | 遅着音声を再生せず、失敗時に残りをflushしない。最終イベントで冒頭を再読しない |
| ornith回答が同じ依頼の相槌の合成中・再生中に到着 | 相槌を失効させ停止確認後に回答を優先。後から生成された同じ相槌も再生0。別件のQwen回答は失わない |
| 回答を聞きながら「うん」／確認質問への「うん」 | 前者は条件を満たせば自動resumeし、再推論による仕事再起動・句の再読をしない。後者は質問への回答として消込を検証する |
| 咳・短い非発話音・判別不能・判定遅延 | 確定した非発話音はQwenを呼ばず再開できる。判別不能や期限超過で勝手に再開せず、再開UIを示す。pause/resume未対応なら自動再開未対応を表示する |
| ornithのToolループと公開回答 | 結果後の公開用回答要求を使い、単なる用途分離で毎回言い換え要求を追加しない。必要な追加要求と後続依頼の待ち時間を記録する |

### 段階6：継続利用と復旧

| シナリオ | 必須の結果 |
| --- | --- |
| Qwen障害・ornith容量不足・TTS障害 | 段階別に表示する。完了していない仕事を完了と言わず、TTS障害で確定本文を失わない |
| 接続断・アプリ再起動・同じイベント再送 | Toolと最終回答を二重実行・二重再生しない |
| 連続会話と自声 | TTS音声をユーザー発言として再投入しない。受付不能やキュー上限を黙って隠さない |

まず模擬Providerと実Runtime入口で決定的に確認し、次に実機で確認する。既存の `butler_route_tests.rs` は、簡単な回答、Qwen初回の共有lease非依存、frontend失敗、draft非公開、待機発話などを検証する資産として使える。テストが現在の挙動を固定している場合は、コンセプト変更に合わせて期待値も明示的に改訂する。

Qwenの分類評価は[Runtime契約](saaa-jarvis-five-provider-runtime-contract.md)の分類別合格線に従う。会話の実機試験とは別に固定集合を保存し、分類器・model・設定変更時に再実行する。

変更領域ごとの回帰コマンドと凍結更新手順は[実装状況と検証手順](saaa-jarvis-five-provider-implementation-status.md)を参照する。

実機受入では固定の日本語ケースを繰り返し、30発言・10往復以上に思考中の追加入力、割り込み、再起動を含める。`utteranceId → run/root/revision → provider request → message/公開部分 → speech` を追跡し、実model、build、設定fingerprint、失敗件数、遅延を記録する。認証情報や私的な会話本文は通常の診断ログに含めない。模擬試験と過去のLAN疎通結果を実マイク・実TTSの合格に代用しない。
