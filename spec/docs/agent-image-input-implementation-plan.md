# エージェント画像入力の実装計画

作成日: 2026-09-23。状態: **実装済み（実機 canary は未実施）**。

採用した初期上限: 入力 12_000_000 bytes、12_000_000 画素、一辺 8_192 px。長辺 2_048 px 以上は 1_920 px。WebP 品質は 75、65、60 の順で最大 4 回。下限の追加縮小は長辺 1_280 px。WebP は 1_500_000 bytes まで。画像付き request はテキスト用 96_000 bytes とは別に 3_000_000 bytes まで。provider の送信形式は `confirm_image_input` で endpoint と model と `webp` / `png` / `jpeg` を記録するまで送らない。LARM 実機の読字比較は推論サーバーに接続できないため未記録。

## 1. 目的と成功条件

部分スクリーンショットをエージェントの質問に添付し、Gemma が画像そのものを判別できる経路を作る。文字や UI の色を読める状態で画像を有界に処理し、元 PNG を永続化しない。通常のテキスト会話には画像処理の負荷を加えない。

成功条件は、画像付きの質問が実際の推論サーバーに届き、画像中の文字と UI 状態に基づく回答を返せること、元 PNG と Base64 が DB・ログ・永続ファイルに残らないこと、画像を受け付けない経路では送信前に明確に失敗することである。

## 2. 現状と前提

- `StartTurnInput.content`、`conversation_messages.content`、`chat_completions::world_body::build_messages` は文字列中心であり、画像の入力・保存・送信契約はまだない。
- 現行の provider request は 96,000 bytes、必須 context がある場合の保守的な入力枠は 64,000 bytes。画像の Base64 を既存枠へ押し込むために画質を落とさない。
- LARM は `openai.chat-completions.v1` の経路を使う。ただし実配備のモデルと推論サーバーが画像パートを受け付け、Gemma の画像プロセッサーまで到達するかは未検証。モデル名だけで対応と判定しない。
- Gemma 4 の画像解像度と視覚トークン予算は推論側の設定にも依存する。SAAA 側のピクセル縮小だけではモデルの読字精度を保証できない。

## 3. 範囲と非目標

### 範囲

- チャット入力欄への画像ドラッグ＆ドロップ、一回の質問につき一枚の添付、入力契約、ドロップ直後の前処理、送信、失敗表示。
- 画像の一時保管と、将来または設定で履歴に画像を残す場合の WebP 一枚のみの保管契約。
- ローカルと LARM の各 provider 経路で、画像対応の有無を確認したうえで送信する。
- 文字の読み取り、容量、遅延、保存物の固定テストと実機検証。

### 非目標

- フルスクリーン撮影、画面監視、動画、複数画像、画像生成、OCR 文への事前置換。
- 元 PNG の永続保存、Base64 の会話履歴保存、画像の自動的な長期記憶化。
- ASR 経路の変更。画像と無関係な provider や会話ランタイムの全面改修。

## 4. 入力画像のライフサイクル

1. チャット入力欄へドロップされた PNG を一時入力として受け取る。**ドロップした時点で**前処理を開始し、送信ボタンが押されるまで処理を遅らせない。ファイル名・拡張子を信用せず、実データを復号して形式、寸法、画素数、入力 byte 数を検査する。巨大画像や復号不能な画像は処理前に拒否する。上限値は代表サンプルの最大値を測って決め、画素数・入力 byte 数・変換後 byte 数を別々に制限する。
2. 長辺が **2,048 px 以上**なら、縦横比を保って長辺 **1,920 px** へ縮小する。それ未満の画像は原則として寸法を変えず、拡大もしない。文字の高さが小さい実例を含め、縮小後の読字精度を確認する。
3. 色を保持し、標準経路では白黒化・コントラスト補正・シャープ化を行わない。補正で読字が改善するかは別途評価し、採用する場合も実測結果と対象を明記する。
4. 処理済み画素を **非可逆 WebP** に変換する。圧縮率は保存ファイルの大きさだけで選ばず、実際の provider 送信形式へ変換した後の最終 request byte 数を基準に選ぶ。まず画質を変えて容量を下げ、それでも送信上限を超える大きな画像だけ追加縮小を試す。画質の下限・縮小の下限・最大試行回数は §8 の読字評価で固定し、収まらなければ画像を送らず超過を通知する。変換結果を再復号してから元 PNG の一時データを破棄する。
5. 初期実装では WebP はドロップ後の送信待ちと当該ターンの間だけ保管し、添付取消・送信完了・ターン中断・画面離脱・失敗時に削除する。後続ターンから同じ画像を再参照する必要が確認された場合に限り、明示的な保持操作と削除操作を設け、保持するのは処理済み WebP 一枚と参照 ID・寸法等のメタデータだけとする。保持しない画像は後続ターンで再送できないことを UI に示す。

画像の一時ファイルはアプリ管理領域に閉じ、推測可能なパスを外部入力として受け付けない。ログ、診断イベント、例外、トレース、会話本文には画像 bytes や data URL を含めない。処理中のメモリ上の一時バッファも、送信完了または中断時に参照を解放する。

### チャット入力欄での操作

- 既存の `ChatPage.tsx` の composer 全体をドロップ領域にする。画像ファイルをドラッグ中だけ受け入れ表示を出し、通常の文字ドラッグやファイル以外のドロップを妨げない。画像を入力欄へドロップした場合はブラウザーのファイル表示への遷移を防ぐ。
- ドロップ直後に「処理中」を表示し、Rust 側の画像処理へ渡す。処理が成功したら、**処理済み WebP から作ったプレビュー**、寸法、容量、削除操作を composer に表示する。元 PNG のプレビュー URL や Base64 を UI 状態に保持しない。
- 前処理が完了するまで送信を無効にする。失敗した画像は添付済みとして扱わず、理由を表示して元の入力文は残す。質問文だけ、または画像だけでも送信可能にする。画像だけの場合は既定の短い質問「この画像の内容を説明してください」を送信本文として明示する。
- ドロップは**添付と前処理の開始**であり、自動送信はしない。利用者が送信操作をした時点の質問文と、処理完了済みの画像参照 ID を一つの turn に結び付ける。送信時点の参照を固定し、送信中の再ドロップや会話切替で別画像が混入しないようにする。
- 初期実装は一枚だけを受け入れる。既に画像がある状態で別画像をドロップした場合は、先の前処理を中断し、先の一時 WebP を削除して新しい画像に置き換える。複数ファイルが同時にドロップされた場合は黙って一枚を選ばず、対応外であることを表示する。
- 送信待ちの画像は添付取消、会話切替、コンポーネントの終了時に削除する。アプリ強制終了で残った一時画像は次回起動時の期限付き掃除で削除する。

## 5. Gemma への送信契約

- 画像付き user message の `content` を、画像パートと質問文パートの配列にする。通常のテキスト turn は従来の文字列形式を維持する。Gemma 4 の推奨する画像→テキストの順序で送る。
- 送信直前に WebP を読み、対象 provider が WebP を確実に受け付ける場合だけ `image/webp` を送る。未対応または不明なら、その provider で確認済みの PNG または JPEG へメモリ上で変換する。JPEG への再符号化は追加の画質損失があるため、対応形式ごとの最終 request 容量と読字結果を比較して選ぶ。送信用画像と Base64 は永続化しない。
- provider の `openai.chat-completions.v1` 表記だけを画像対応の証拠にしない。画像対応の能力情報、または実配備サーバーに対する固定画像の疎通結果を必須にする。非対応なら文字だけで画像質問を送らず、利用者に理由を示す。
- 画像込みの最終 JSON byte 数を測る。従来の 96,000 byte 枠とは別に、画像一枚と request 全体の上限をサーバー側の制約と実測で決める。Base64 の増分と再符号化後の大きさを含めて判定する。上限に収めるための画質調整と追加縮小は §4 の定めた範囲だけで行い、それでも超過する場合は画像を欠落させて送らず失敗を返す。
- 画像がある turn の context 組み立てでは、送信した質問と画像の対応を保つ。画像を履歴に保持しない既定動作では、後続 turn へ画像の参照だけを残して再送したふりをしない。必要なら前回の回答テキストを通常の会話履歴として使う。

## 6. 実装順序

| 段階 | 作業 | 完了の判定 |
| --- | --- | --- |
| 0 | LARM とローカル provider の画像入力を小さな PNG で実測し、上限・形式・Gemma 側の視覚設定を記録する。既存のテキスト turn と画像サンプルの容量・時間を基準値として保存する | 配備別の画像対応と失敗形が明確になる |
| 1 | PNG 検査、条件付き縮小、非可逆 WebP 化、一時データ削除を独立した画像処理経路にする | 元 PNG が残らず、圧縮試行は有界で、同じ入力と設定から同じ画像ができる |
| 2 | composer のドラッグ＆ドロップ、ドロップ直後の前処理とプレビュー、IPC 入力契約を加え、本文と画像参照を別に運ぶ | 送信前に画像が処理され、処理中・準備完了・失敗・取消が UI で区別できる |
| 3 | provider 能力確認、画像パート送信、確認済み形式への一時変換、画像用 request 上限を接続する | 実際の Gemma 回答が画像内容に依存する |
| 4 | 会話履歴と削除の整合、容量・読字・レイテンシの評価を行う | §8 の受入基準を満たす |

`models.rs`、`runtime/turns`、`providers/chat_completions`、`ipc_contract`、`src/features/chat`、必要な永続化層を候補とする。既存作業ツリーには他タスクの変更があるため、実装時は差分を確認して本計画の変更だけを加える。凍結対象を変更する必要が生じた場合は該当 domain の回帰テストと `freeze:accept` を実行し、理由を変更記録に残す。

## 7. 設計判断と代替案

- **非可逆 WebP を選ぶ理由:** 送信容量を優先する。元 PNG を破棄するため、圧縮による読字の悪化を固定評価で抑え、限界を超えた場合は無理に送らない。
- **明暗補正を標準にしない理由:** 読みにくさを自動判定できないことは、全画像を補正すべき根拠にはならない。補正で細い文字や淡い表示を消す可能性がある。
- **白黒化しない理由:** 色は警告、選択状態、グラフなどの意味を持つ。
- **WebP 保管と provider 送信形式を分ける理由:** 画像形式の対応は Gemma 自体でなく推論サーバーのデコーダーで決まる。未確認の WebP 直接送信を前提にしない。
- **画像を既定で残さない理由:** 普段のスクリーンショットを長期保存しないという利用方針に合わせる。後続 turn での再参照が必要なら保持を明示する。

## 8. 検証と受入基準

### 固定ケース

部分スクリーンショットを、(1) 明るい UI、(2) ダークモード、(3) 小さい日本語・英数字、(4) 警告色と選択色、(5) 写真を含む UI、(6) 長辺 2,047 / 2,048 / 2,049 px、(7) 復号不能・偽装 MIME・巨大画素数、(8) 送信取消・provider 非対応・容量超過、で用意する。期待する寸法、色の保持、拒否理由、削除状態を定義する。UI ケースとして、ドロップ直後の処理開始、処理中の送信抑止、画像だけの送信、再ドロップによる置換、複数ファイルの拒否、添付取消、会話切替、処理中と送信中の競合を加える。

### 品質比較

同じ実スクリーンショット群で「原寸 PNG」「条件付き縮小のみ」「条件付き縮小＋複数の WebP 画質設定」「上限超過時の追加縮小」を比較する。画像中の指定文字列の完全一致率、UI 状態の正答率、保存 byte 数、**実際に送る形式での最終 request byte 数**、処理時間、推論時間を記録する。文字や色に意味があるケースの正答を犠牲にして平均容量だけを改善しない。固定した Gemma モデル・推論サーバー・視覚トークン予算で比較し、異なる予算は別系列として測る。採用する初期画質、下限、追加縮小の下限、画像と request の容量上限を結果とともに記録する。

### 自動検証と実機確認

| 実行項目 | 期待結果 |
| --- | --- |
| 画像処理の Rust 固定テストと IPC 契約テスト | 閾値、再復号、破棄、異常入力、Base64 非保存、拒否理由が全件成功 |
| composer の UI テスト | ドロップ直後に一度だけ前処理を始め、完了まで送信不可。画像だけの送信、置換・取消・会話切替時の一時画像削除、複数画像拒否、通常の文字ドラッグが期待どおり |
| provider 模擬 HTTP テスト | 画像→質問文のパート順、MIME、圧縮・追加縮小後の最終 request 上限、非対応時の送信拒否を確認 |
| `bun run spec:check` | 本文書に新たなリンク・形式エラーがない |
| `bun run freeze:check` と変更範囲の型・品質テスト | 凍結対象の意図しない差分がなく、テキスト会話が回帰しない |
| LARM 実機 canary | 画像内だけに書かれた短い文字を回答し、画像なし対照では答えられない。送信形式、時間、容量を記録 |

凍結対象を実際に変更する場合は `critical-path-freeze.json` 指定の該当回帰コマンドを追加する。全体 gate に既存作業ツリー由来の失敗がある場合は、その差分と本件の失敗を分けて報告する。ライブ推論が使えない環境では模擬 HTTP テストまでを固定の合否とし、実機受入は未完了として残す。
