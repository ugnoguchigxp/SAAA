# SAAA × L-Lang 動的拡張 — 初期実装計画

作成日: 2026-09-19  
状態: 初期計画案 v0.2 / 実装未着手  
基準: [動的能力コンセプト](saaa-llang-dynamic-capability-concept.md)

実装担当者は[詳細実装手順・契約・試験仕様](saaa-llang-dynamic-capability-implementation-guide.md)を併読する。本書は目的と段階を示し、詳細手順書は作業順、ファイル、内部API、状態遷移、失敗時の処理を定める。実装上の具体的な判断は詳細手順書を優先する。最初の依頼範囲はM0/M1のままであり、後続段階を一括実装する指示ではない。

## 1. 最初に作るもの

**画面を持たない、小さな判定機能を動的に登録し、SAAAの会話とMCPから利用し、更新後も実行した版をTypeScriptで検査できるところから始める。**

最初の対象は、L-Langの既存`predicate-i32-v1` profileで表現できる、副作用のない判定処理とする。第一の接続確認には既存の受付可否fixtureを使い、その後、別の要求から生成した候補と更新版でも同じ経路が動くことを確かめる。実際の認証・認可判断には利用しない。

例として「有効かつ停止中でないレコードを対象とする」を生成・登録し、後から条件を変更する。これはRuntimeの動作確認用であり、SAAA自身の権限判定を書き換える機能ではない。

世界時計は後続の表示連携の候補にする。先にツールとしての能力追加を成立させれば、OpenUI連携も同じ呼び出し口へ接続できる。世界時計から始める場合に必要となる別ABIへの対応と画面連携を、最初の登録・実行基盤から切り離せる。

本計画は最初の実装を複数のレビュー可能な作業単位に分ける。最初の着手はM0、最初に通常Runtimeへコードを追加する単位はM1とする。M1〜M3を既存生成物による利用経路の成立、M4をLLMによる動的作成まで含めた成立として扱う。M3だけで「動的生成が完成した」とは報告しない。

## 2. 調査で確認した現在地

ソース確認時のSAAA HEADは`1b595ffd10c3c77adb19c8d3f9f47c536aa3fe54`、L-Lang HEADは`7fb1a7bb639b18d29055fe032b7ffc5dc6f5ee15`。L-Langには未コミット変更がある。以下はコードと既存検証記録の確認結果であり、この計画作成時にRuntimeテストを再実行した結果ではない。

| 領域 | 確認した事実 | 計画への反映 |
| --- | --- | --- |
| SAAAからのWasm実行 | `src-tauri/src/wasm_host_poc/`にinspect・verify・invoke、期限、取消、出力上限、子プロセス回収がある。`lib.rs`ではモジュール全体が`cfg(test)` | 実行処理を再利用するが、通常運用への公開は新規作業 |
| 実行キットの信頼 | `wasm_host_poc/kit.rs`はruntimeコードと候補を同じkitに含め、固定hash、clean provenance、fixtureであることを要求 | 単にfixture制約を外さず、信頼済みruntimeと動的candidateを分離する |
| package世代 | SAAA同梱fixtureはmanifest version 1。L-Langにはversion 2 packageのhost-kit試験がある。host protocol名は`llang-host-v1` | package version、host protocol、Wasm profileを別々に交渉・検査する |
| TypeScript inspection | L-Langの`llang-capability-inspection.ts`と`llang-predicate-projection.ts`に実装があるが、確認時点では未追跡ファイル。関連CLI等も変更中 | 完成済み依存として扱わず、取り込む版と提供方法をM0で固定する |
| inspectionの意味 | reportにはhashとTypeScriptがあり、`semanticEquivalence: not-checked`を返す | 表示・出力と意味の同値性証明を区別する |
| 会話ツール | `runtime/agent_tools.rs`、`providers/stream/dispatch.rs`が既知ツールを組み立て、振り分ける | 共通会話Runtimeの既存経路へ動的定義と実行を加える |
| Capability Registry | 構想文書はあるが、今回確認した呼び出し経路に汎用の動的登録実装は見当たらない | 最小の永続catalogから作り、検索・学習機構を一度に実装しない |
| MCP提供 | `services/reasoning-mcp/src/lib.rs`に固定のreasoning toolを提供するHTTP実装がある | 認証・制限・試験の実例として参照。汎用動的MCPサーバーが存在すると見なさない |
| UI | `generative_ui/`に保存・版・状態管理、`SemanticRenderer.tsx`に表示がある。`@openuidev/react-lang`の直接利用は確認範囲ではspike側 | 既存UIを尊重し、OpenUI本体が通常表示経路で使われていると決めつけない |
| 永続化 | `persistence/sqlite/`にreader・single writerがある | catalogと実行記録を既存writer経由で保存する |
| 世界時計 | L-Lang exampleは`world-clock-i32-v1`。既存predicateとは別ABI | 初回対象に混ぜず、複数profile対応と表示連携の検証候補にする |

根拠となる既存記録: [Wasm接続PoC検証結果](verification/llang-wasm-host-poc-20260916.md)。この記録の成功は開発用接続試験の範囲であり、配布アプリや動的登録の成功を意味しない。

## 3. 最初の範囲と境界

初期対象は開発環境のローカル実行とし、対応profileと入力型を明示する。すべての機能に汎用effectを許す仕組みはまだ作らず、外部effect要求は拒否する。生成に必要なモデル接続は生成側だけに与え、生成物の実行側へ認証情報を渡さない。

範囲に含めるもの:

- 既存packageの取込み、検証、永続登録、有効化、呼び出し。
- 用途、適用しない場面、入力、出力、制限を含む使い方の登録。
- 会話とMCPからの同一実行サービス利用。
- 小さな条件変更による新しい版への切替、停止、以前の版への復帰。
- 実行版に対応するTypeScriptとhashの取得。
- 対応profile内に限定した、LLMによる新しい候補の作成と更新。

後続に分けるものは、世界時計・オセロ・テトリス、OpenUIとのstate/action binding、外部書き込みeffect、無制限の自己修復、汎用Capability検索・ランキング、配布用Bun同梱・署名、公衆ネットワークへのMCP公開、保存物の自動物理削除である。既存の会話、記憶、UI、Coding Agentの全面改修は含めない。

## 4. 実行と登録の共通境界

```text
既存packageの取込み / 制限付きLLM生成
                  ↓
          未有効の候補を保存
                  ↓
   契約・整合性・許可範囲・テストを確認
                  ↓
   Capability Catalogへ有効版を登録
                  ↓
      会話ツール      MCP接続口
             ＼      ／
          共通実行サービス
                  ↓
       信頼済みL-Lang Host
                  ↓
         指定hashの候補を実行
                  ↓
       結果・実行版・検証参照を保存
```

SQLiteを登録状態・有効版・検証結果の正本とし、package本体はSAAA管理下の変更されない保存領域へ取り込む。hashは整合性の確認に使い、生成物自身が提示したhashだけで信頼済みとしない。信頼する実行コードの版はHost側で管理する。

論理的に必要な情報は、能力ID、用途と利用条件、入力・出力契約、profile、package版、package/program/artifact hash、生成元とruntime版、テスト結果、状態、有効版への参照、inspection参照である。初期テーブルと内部APIは詳細手順書で定める。

状態は少なくともcandidate、validated、active、suspended、retiredを区別する。新しい候補の失敗は現在の有効版を変更しない。有効版の切替は原子的に行い、更新競合を検出する。

一回の呼び出しには能力IDと解決済みの版・hashを結び付ける。会話で提示した定義と実行する契約が途中で変わらないよう、要求単位で固定する。MCPも契約を特定できるツール識別子を使い、古い一覧を使う呼び出しを新しい非互換版へ黙って転送しない。停止済みの版は、提示履歴があっても実行時に拒否する。

## 5. 実装単位と着手順

### M0 — 対応するL-Lang契約を固定する

**成果物:** 小さな接続契約書、固定した検証用package、依存の状態一覧。

1. SAAAのv1 fixtureとL-Langのv2 packageの差を確認し、初期対象をv2の`predicate-i32-v1`として接続可能か検証する。
2. Hostのinspect結果・verify結果をRustがどこまで受け入れられるか比較する。protocol名が同じという理由で互換と判断しない。
3. TypeScript inspectionの提供版と入口を固定する。現在のhost operationにinspection出力があると仮定しない。必要ならL-Lang側への最小の接続契約変更を別項目として定義する。
4. 信頼済みruntimeを起動し、別の候補packageを渡す契約を決める。候補がruntimeコードや起動コマンドを差し替えることは許さない。
5. SAAAとL-Lang双方の採用commitまたは検証用snapshotの全ファイルhashを記録する。未コミット作業ツリーへの暗黙依存を避ける。

完了条件は、固定した候補についてinspect・verify・invoke・TypeScript取得の経路と不足が根拠付きで確定すること。実行接続のM0-Rと、inspection接続のM0-Iを別判定する。M0-Rが合格すればM1へ進める。M0-Iが未達ならM3のinspectionを保留し、M0全体は未完了と報告する。SAAA内でLLMに代替コードを推測生成させない。

### M1 — 最小Catalogと通常実行サービスを作る

**成果物:** 管理packageを登録し、指定した版を実行できる通常Runtime。ここが最初のコード実装単位。

- PoCのprocess管理・構造検証・期限・取消を再利用し、test専用から通常Runtimeへ必要部分だけ分離する。
- 固定runtimeと候補保存領域を分け、candidateの取込み、verify、active化、停止を実装する。
- catalogは既存SQLite writerに接続する。LLMへ任意ファイルパスやコマンドの実行を許す入口を作らない。
- 入力・出力検査、非対応profileと権限要求の拒否、timeout時の回収を実装する。既存の実行上限を維持し、メモリ等の未対応制限は明記する。
- 検証前には公開せず、異常終了と正常な`false`を区別する。

完了条件は、固定fixtureと別内容の候補を、アプリの再ビルドなしに登録・実行でき、再起動後も登録と版が復元されること。候補を替えるたびにHostコードや信頼済みruntimeを生成し直す構造にしない。

### M2 — 会話とMCPから呼び出す

**成果物:** 登録済み能力が、使い方とともに発見され、両経路から実行できる。

- `providers/stream/dispatch.rs`のツール提示・実行へ接続する。別の会話Runtimeは作らない。
- 初期は明示的に有効化した少数の能力だけを、件数・説明サイズの上限内で提示する。検索ランキングは作らない。
- MCP接続口はSAAAと同じcatalogと実行サービスを使う。初期案はローカル限定の認証付きHTTPとし、既存reasoning MCPの試験・制限を参考にする。reasoning専用サービスへ別の正本catalogを追加しない。
- 登録後、再ビルド・再起動なしの再一覧取得で新しいツールを利用できることを最初の動的公開条件とする。自動的な一覧更新通知は、接続契約を確認して採用可否を決める。
- MCPは初期段階では有効化済み機能の呼び出し口とする。生成・有効化・権限変更の管理操作を外部へ一括公開しない。
- テスト用providerで会話ツール呼び出しを再現し、実モデルによる疎通は別に確認する。

完了条件は、同じ版・同じ入力に対して会話とMCPが同じ値または同じ分類のエラーを返すこと。無認証、未知ツール、不正入力、停止済み版は拒否し、Runtimeを迂回する別実装を置かない。

### M3 — 更新・停止・TypeScript検査をつなぐ

**成果物:** 二つの版を切り替え、過去に使った版を検査できる。

- 新しい候補を別の版として検証し、成功後に有効版を切り替える。失敗時は旧版を維持する。
- 実行記録に対象版とhashを残し、更新と競合しても実行対象が曖昧にならないようにする。
- 停止、retired化、旧版への復帰を実装する。初期の廃棄は選択・実行対象から外す操作までとする。
- 実行記録から、その版に対応するTypeScriptとinspection reportを取得できるようにする。既存のファイル表示や成果物表示を利用し、専用管理画面は必須にしない。
- 有限のテスト入力で、TypeScript表現とWasmの結果を比較する。比較成功を一般的な意味同値性の証明と表示しない。比較用の実行は隔離した検証環境で行い、生成TypeScriptを通常実行のfallbackにしない。

完了条件は、v1実行後にv2へ更新してもv1の検査出力が取得でき、非互換な古い呼び出しを拒否し、v2の停止・v1への復帰ができること。

### M4 — 制限付きのLLM生成・変更を接続する

**成果物:** 要求から新しい能力を作り、登録して利用し、小さな変更を反映する一連の実証。

- 対応する要求・入力契約を明示し、SAAAの既存モデル呼び出し経路を使ってL-Lang入力を生成する。候補packageとテストの作成には既存L-Lang側の機能を利用できるか確認する。
- L-Langのdevelopment入口が、採用するv2 package生成に対応するかを先に確認する。別世代の生成機構をそのまま接続しない。
- 一要求あたり生成1回を初期値とし、時間・出力・token予算を設定する。失敗を報告して候補を未有効のまま保持し、自律修復ループは追加しない。
- 生成されたテストだけで合格を決めず、SAAA側で事前固定した独立の受け入れケースを実行する。
- 合格した候補は、許可済みの副作用なしprofileに対するHost policyで有効化できるようにする。毎回の人間コードレビューを必須条件にしない。
- 条件変更の要求から新しい版を作り、M3と同じ更新経路を使う。

完了条件は、事前に用意したpackageの選択だけではなく、少なくとも一つの新しい要求と一つの変更要求から実生成した成果物が、会話・MCP利用・TypeScript検査まで到達すること。fixtureによる再現試験と実モデルによる実証を区別して報告する。

## 6. 受け入れ試験

| ID | 必須となる段階 | 観測する結果 |
| --- | --- | --- |
| AC1 | M1 | 異なる二つのcandidateを再ビルドなしに登録・実行できる |
| AC2 | M1 | package改変、未知profile、契約不一致、テスト失敗ではactive化しない |
| AC3 | M1 | 権限要求・未知importを許可せず、正常なfalseと実行エラーを区別する |
| AC4 | M1 | 無限実行fixtureのtimeout・取消後、子プロセスを回収し次の呼び出しが動く |
| AC5 | M1 | 再起動後にcatalogを復元し、復元だけでは候補を実行しない |
| AC6 | M2 | 用途・入出力が会話ツール定義とMCP一覧に反映され、同じ版を呼べる |
| AC7 | M2 | 登録・停止が再一覧取得に反映され、無認証・不正入力・停止済み呼び出しを拒否する |
| AC8 | M3 | 更新中の呼び出し対象が固定され、新候補失敗時には旧版を維持する |
| AC9 | M3 | 過去の実行hashに対応するTypeScriptを取得でき、照合不能なら明示的に失敗する |
| AC10 | M3 | 有限ケースで投影とWasmを比較し、比較範囲と未証明部分を報告する |
| AC11 | M4 | 実モデルで新規候補と変更版を生成し、独立ケースを通して会話・MCPから利用できる |
| AC12 | 全段階 | 関連する既存会話・永続化・UI・MCP試験に回帰がない |

実装開始時に変更前baselineを採り、段階ごとの対象試験を実行する。既存コマンドとして、`cargo test --manifest-path src-tauri/Cargo.toml wasm_host_poc --no-fail-fast`、`bun run typecheck`、`bun run size:check`、`bun run ipc:check`を利用できる。モジュール移動後は対応する試験名へ更新する。各実装単位の統合時には`bun run check:local`を実行し、MCPサービスを変更した場合はそのcrateの試験も行う。L-Lang側の試験は固定した提供版の手順を採用する。

liveモデル試験はAPI費用と環境依存があるため通常の再現試験から分け、モデル、要求、生成物hash、検証結果を記録する。秘密情報やrequest全文を無条件にtelemetryへ保存しない。

## 7. 想定する変更先と失敗時の扱い

| 対象 | 主な作業 |
| --- | --- |
| `src-tauri/src/wasm_host_poc/`と通常Runtimeの新モジュール | 信頼済みHostの通常利用、候補との分離、process管理の再利用 |
| `src-tauri/src/persistence/`とCapability用の新モジュール | catalog・版・検証・実行参照、既存writerへの接続 |
| `src-tauri/src/providers/stream/dispatch.rs`と関連契約 | 動的ツール提示・版固定・実行振り分け |
| SAAA内のMCP adapter（新規候補） | 共通サービスへの接続。配置はM2着手時に確定 |
| L-Lang側の提供contract | 固定したpackage・inspection・生成入口。不足分は別変更として管理 |
| 既存artifact/file表示 | TypeScriptとreportの取得・表示に必要な最小接続 |

機能を無効化した状態から導入できるようにし、問題があれば新規呼び出しを止めて既存会話を継続できるようにする。登録失敗、DB更新失敗、package欠落、runtime不在は区別して記録する。ファイル保存後・DB登録前に中断した候補はactiveとせず、再起動時に未完了として回収または再検証できるようにする。

この計画では既存テーブルの破壊的変更や既存データの削除を前提にしない。runtimeと候補の差し替え、同一OSユーザーからの改変、配布アプリでの実行保証は、それぞれ対応範囲を明示する。ローカルPoCの成功を完全なsandboxの成立として扱わない。

## 8. 次の実装へ渡す単位

最初の実装依頼は**M0の契約固定と、M1の最小Catalog・通常実行サービス**に限定する。成果物は、固定依存の記録、既存PoCを再利用した実装、二候補での登録・実行試験、失敗時の拒否試験とする。M2以降の接続口を用意しつつ、M1で会話・MCP・UIまで同時に実装しない。

M4まで達した後に、世界時計による複数profile・表示連携、stateを持つ機能、外部effectへ進む順序を再検討する。その判断には、能力追加に必要だった手作業、生成と検証の失敗理由、更新時の互換性、TypeScriptで原因を調べられたかという実証結果を使う。
