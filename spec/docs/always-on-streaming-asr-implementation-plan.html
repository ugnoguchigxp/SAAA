本文書は、実装担当が追加の方式選定をせず、記載順にtestを書いて実装を完了できることを目的とする。 定数、wire format、IPC、状態遷移、失敗時挙動、変更file、test名を本文書で固定する。 本文書と既存のChat音声仕様が競合する場合、常時ASRとpartial表示については本文書を優先する。

「常時」は、Chatの待ち受けが有効で、MeetingまたはSAAA自身のTTSへ音声deviceを引き渡していない間を指す。 その間はVADのspeech判定前も含め、取得PCMを欠落なくASR coordinatorへ渡す。 VADはASR開始条件に使わず、沈黙後に現在発話を確定するtriggerとしてだけ使う。 Meeting ASR、TTSのhalf-duplex既定、LLM completion契約は変更しない。

長時間soak、30分以上の連続運転、長時間実マイク検証は、ユーザー指示により本計画のGateへ含めない。 短いfixture、mock transport、5分以内のdesktop確認で完了判定する。

1. 採用方針

AudioWorklet (16 kHz mono Float32)
        ↓ VADより先に100 ms packet化
Frontend serial raw-IPC sender
        ↓ sequence付きPCM16LE
Backend AsrSessionManager
        ↓
Optional local target-speaker gate
  ├─ all-speakers   : raw PCMをそのまま通す
  └─ target-speaker : 本人blockだけ通し、その他は同長silenceへ置換
        ↓
  ├─ Preferred : Harness v2 / saaa.asr-stream.v1
  └─ Fallback  : whole-prefix batch decode + Anchored Local Agreement
        ↓
stableText + replaceable unstableText
        ↓
Chat live transcript

VAD silence / 30 s limit ── commit ── final ── utteranceIdで一度だけLLM送信
  1. 現行の1〜5秒非重複chunkと単純文字列連結は完成形に残さない。
  2. Native streamingはProvider Harness v2だけで実装する。
  3. 個別Cloud ASR、Harness v1、stream非対応Harness v2はbatch agreementへ送る。
  4. partialは会話履歴へ保存せず、同一発話の表示projectionとして置換する。
  5. finalだけを会話入力にし、同じutteranceIdを二度送らない。
  6. ASRや話者filterのためにOS側の音量、出力音、周囲音を変更しない。

3. 要件と不変条件

3.1 Functional requirements

  • F-01: 待ち受け中は全AudioWorklet frameをVAD判定前にpacketizerへ渡す。
  • F-02: 録音中はpartialを継続更新し、stableとunstableを区別する。
  • F-03: 設定済み沈黙時間または30秒上限で現在発話をcommitする。
  • F-04: commit後もmicrophoneを閉じず、次発話packetを同じsessionへ送る。
  • F-05: finalだけをLLMへ送り、partialとdiscarded utteranceは送らない。
  • F-06: all-speakersでは取得した全PCMを認識対象にする。
  • F-07: target-speakerでは本人判定blockだけを外部ASRへ渡す。
  • F-08: native streamが失敗しbatchが使えるときだけ一度degradeする。
  • F-09: microphone制約のAEC、noise suppression、auto gainをfalseのまま保つ。
  • F-10: ASRはsystem output volume、audio ducking、他application音量を操作しない。

3.2 Correctness and privacy invariants

  • packet sequenceはsession内で0から始まり、成功したappendごとに1増える。
  • duplicate、gap、out-of-order packetはProviderへ送らず、sessionをfatal errorにする。
  • packetを静かにdropしない。queue overflowはASR_BACKPRESSUREとして失敗させる。
  • Backend mutexを保持したままawaitしない。
  • 同一発話のstable textは後退しない。finalだけが表示全体を差し替えられる。
  • Frontendはsession ID不一致、古いrevision、重複finalを無視する。
  • batch partial requestは最大1件、待機snapshotは最大1件、仮説は最大3件とする。
  • nativeからbatchへのdegradeはsessionあたり最大1回で、nativeへ自動復帰しない。
  • target-speakerのraw PCMはlocal gate決定前に外部Providerへ送らない。
  • target-speakerの判定error、timeout、profile不整合はrejectとして扱う。
  • PCMとtranscript本文を診断log、error message、metric labelへ含めない。
  • PCMは送信、確定、取消、session stopのいずれでも所有bufferからzeroizeする。

4. 実装architectureと所有権

4.1 Frontend capture

  1. Chat captureだけnew AudioContext({ sampleRate: 16_000 })で作成する。
  2. 作成後のaudioContext.sampleRateが16,000でなければsession開始を中止する。
  3. AudioWorklet frameをVoiceAsrPacketizerへ先に渡し、その後VADへ渡す。
  4. packetizerはFloat32を1,600 sampleずつPCM16LEへ変換する。
  5. VADのshouldFinalizeでserial senderへcommit barrierを追加する。
  6. 300 packet到達時もmax-duration理由でcommitし、VADをresetする。
  7. barrier前のaudio、commit、barrier後のaudioは同じoperation queueで必ずこの順にinvokeする。
  8. commit受付を待つ間もWorklet frameは最大10 audio packetまでbarrier後へ蓄積できる。

VoiceAsrPacketizerは1,600 sample未満の端数を次frameまで保持する。 通常commitでは端数を次発話へ持ち越す。session stopでfinalizeする場合だけzero paddingして1 packetにし、 実音声長ではなくProviderへ送ったsample cursorを発話endとして扱う。追加silenceは最大99.94 msである。 

type VoiceAsrSenderOperation =
  | { type: "audio"; sequence: number; bytes: Uint8Array }
  | { type: "commit"; reason: "silence" | "max-duration" }
  | { type: "stop"; finalizeCurrent: boolean };

// enqueueCommitはoperationをaudio列の末尾へ同期的に追加し、
// その後にappendされたaudioは必ずcommitより後ろへ入る。
enqueueCommit(reason: CommitReason): Promise<void>;

capacity 10は未送信audioだけを数える。commit/stop control operationは各1件まで許可し、 同種controlの重複enqueueは同じPromiseを返す。sequenceはaudio invoke成功後にだけ確定する。

  • Chat ASR sessionはprocess内で最大1件とする。二重startは拒否する。

5.1 Provider Harness v2 descriptor

v1 fieldを変更しない。v2は各serviceにoptionalなstreamingだけを追加する。 ASRのbatch descriptorはv2でも必須とし、Native failure時の同一service fallbackを保証する。

    "baseUrl": "http://private-host/v1",

    "healthUrl": "http://private-host/health",

#[derive(Clone, Deserialize)]
#[serde(tag = "contractVersion", deny_unknown_fields)]
enum HarnessDescriptor {
    #[serde(rename = "saaa-service-harness.v1")]

    #[serde(rename = "saaa-service-harness.v2")]
    V2 { revision: String, services: Vec<ServiceDescriptorV2> },
}

#[derive(Clone, Deserialize)]
#[serde(rename_all = "camelCase", deny_unknown_fields)]
struct ServiceDescriptorV2 {
    capability: String,
    protocol: String,
    base_url: String,
    model: String,
    language: Option<String>,
    voice: Option<String>,
    health_url: String,
    #[serde(default)]
    streaming: Option<AsrStreamingDescriptor>,
}

#[derive(Clone, Deserialize)]
#[serde(rename_all = "camelCase", deny_unknown_fields)]
pub(crate) struct AsrStreamingDescriptor {
    pub(crate) protocol: String,
    pub(crate) url: String,
    pub(crate) sample_rate: u32,
    pub(crate) encoding: String,
    pub(crate) packet_milliseconds: u64,
}
  • v1 validationは現行のまま通す。
  • v2のLLM/TTSはstreamingを持ってはならない。
  • v2 ASRのbatch fieldは現行ASRと同じ制約を満たす。
  • streamingはASRにだけ許可する。protocol、sampleRate、encoding、packetMillisecondsは 上記literalへ完全一致させ、URLは次項のpolicyで検証する。
  • WebSocket URLは2,048 byte以下、credential、query、fragmentなし、Harnessと同じhostとする。
  • HarnessがHTTPSならwssだけを許可する。private HTTP Harnessはwsを許可する。
  • unknown field、unknown contract、unknown protocolはdescriptor全体を拒否する。
  • resolveのASR statusはstreaming宣言があればsaaa.asr-stream.v1、 なければbatch protocolを表示する。health probe成功だけでNative接続済みとは表示しない。

既存resolve_serviceはLLM/TTS利用者のため変更しない。 新規resolve_asr_serviceがResolvedAsrService { batch, streaming }を返す。

5.2 saaa.asr-stream.v1 wire protocol

ClientはWebSocket subprotocol headerへsaaa.asr-stream.v1を指定する。 redirectとHarness credentialは使わない。WebSocketはmessage順序を保証するため、binary frameへdesktop sequenceを重ねない。

5.2.1 Client messages

{
  "type": "start",
  "contractVersion": "saaa.asr-stream.v1",
  "sessionId": "voice_asr_uuid",
  "utteranceId": "utterance_uuid",
  "model": "descriptor-model",
  "sampleRate": 16000,
  "encoding": "pcm_s16le",
  "packetMilliseconds": 100,
  "language": "auto"
}
{
  "type": "commit",
  "utteranceId": "current-id",
  "nextUtteranceId": "next-id",
  "endSample": 48000
}
{ "type": "stop", "sessionId": "voice_asr_uuid" }
  • ready後のbinary frameは3,200 byteのraw PCM16LEである。
  • commitより前のbinaryはcurrent、後のbinaryはnext utteranceに属する。
  • Providerは前発話finalの生成中も次発話binaryを受け付ける。

5.2.2 Server messages

type ProviderStreamEvent =
  | { type: "ready"; sessionId: string; utteranceId: string }
  | { type: "partial"; sessionId: string; utteranceId: string; revision: number;
      startSample: number; endSample: number; stableText: string; unstableText: string;
      language: string | null }
  | { type: "final"; sessionId: string; utteranceId: string; revision: number;
      startSample: number; endSample: number; text: string; language: string | null }
  | { type: "noSpeech"; sessionId: string; utteranceId: string; revision: number;
      startSample: number; endSample: number }
  | { type: "error"; sessionId: string; utteranceId: string | null;
      code: string; message: string; recoverable: boolean }
  | { type: "stopped"; sessionId: string };
  • revisionはutteranceごとに1から単調増加する。
  • stableTextは前partialのstable prefixを完全に含み、後退してはならない。
  • startSample <= endSampleで、送信済みaudio cursorを超えてはならない。
  • text messageは65,536 byte、各transcriptは16,000文字を上限とする。
  • serverからのbinary frame、invalid JSON、unknown event、session不一致はprotocol fatal errorにする。
  • 音声なしは空finalではなくnoSpeechで返す。
  • pingにはpongを返す。readyは5秒以内、commit finalはmin(route timeout, 15秒)以内とする。

      scope: "all-speakers" | "target-speaker" }
  | { type: "partial"; sessionId: string; utteranceId: string; revision: number;

      language: string | null }
  | { type: "final"; sessionId: string; utteranceId: string; revision: number;

  | { type: "utteranceDiscarded"; sessionId: string; utteranceId: string;
      reason: "no-speech" | "target-speaker-empty" | "cancelled" }
  | { type: "degraded"; sessionId: string; from: "native";
      to: "batch-agreement"; reasonCode: VoiceAsrFailureCode }
  | { type: "failed"; sessionId: string; utteranceId: string | null;
      code: VoiceAsrFailureCode; message: string; recovery: string; fatal: boolean }
  | { type: "stopped"; sessionId: string };

Commandは次の4つだけを追加する。

  1. start_voice_asr_session(input, on_event) -> Result<(), String>
  2. append_voice_asr_audio(request: Request) -> Result<(), String>
  3. commit_voice_asr_utterance(input) -> Result<(), String>
  4. stop_voice_asr_session(input) -> Result<(), String>

append_voice_asr_audioはraw bodyと次のheaderを完全検証する。

Table: Raw IPC headers
Header Value
x-saaa-asr-session-id validate_identifierを通るstart済みID
x-saaa-asr-sequence 先頭0のない10進u64。最初は0
x-saaa-asr-sample-count 常に1600

bodyは常に3,200 byte、little-endian i16である。 commandはsequence確認後にtry_sendし、成功した場合だけmanagerのnext sequenceを増やす。

  • startはProviderまたはbatch engineがreadyになるまで待ち、ready event送信後にreturnする。
  • commitはactor queueへの受付でreturnし、finalはChannelだけで返す。
  • stopはactorがstop状態を受理したackを最大2秒待つ。 finalizeCurrent=trueのfinalはChannelへ非同期に返り、Frontendは stoppedまでChannelを保持する。
  • stop ackが2秒で返らない場合だけcancellationを通知し、sessionをmapから除去する。

6. State machineとruntime sequence

6.1 Backend state

absent
  └─ start ─▶ resolving ─▶ connecting-native ─▶ streaming-native
                         └─────────────────────▶ streaming-batch

streaming-* ── commit accepted ─▶ finalizing(old) + streaming-*(next)
streaming-native ── recoverable transport failure ─▶ degrading ─▶ streaming-batch
any active ── fatal failure ─▶ failed ─▶ removed
any active ── stop(false) ─▶ stopped ─▶ removed
any active ── stop(true) ─▶ finalizing current(max 15 s) ─▶ stopped ─▶ removed
  • Backendがcurrent/next utteranceIdを生成する。
  • commitはcurrent PCMをmoveし、空のnext bufferを作ってからProvider I/Oを行う。
  • 前発話final待ちに次発話PCMを混ぜない。
  • 空またはno-speech finalはutteranceDiscardedにし、LLMへ送らない。

6.2 Frontend state

type AmbientAsrState =
  | { kind: "idle" }
  | { kind: "starting"; sessionId: string }
  | { kind: "listening"; sessionId: string; protocol: EffectiveProtocol;
      currentUtteranceId: string; revision: number }
  | { kind: "stopping"; sessionId: string }
  | { kind: "failed"; message: string };

VoiceSessionのcapture lifecycleは残し、ASR protocol stateは別reducerへ分離する。 一つのbooleanへ統合しない。古いsession eventはreducerで無視する。

6.3 Native normal path

Frontend                 Manager/session             Harness stream       Conversation
   | start + Channel            |                         |                     |
   |--------------------------->| start/handshake         |                     |
   |                            |------------------------>|                     |
   |<------ ready(native) ------|<--------- ready --------|                     |
   | PCM seq 0..N               |                         |                     |
   |===========================>|========================>|                     |
   |<------ partial revision ---|<-------- partial -------|                     |
   | serial commit barrier      |                         |                     |
   |--------------------------->| move current/create next|                     |
   |                            |----------- commit ----->|                     |
   | PCM for next utterance     |                         |                     |
   |===========================>|========================>|                     |
   |<------ final old ----------|<---------- final -------|                     |
   | dedupe utteranceId         |                         |                     |
   | submitPrompt(final) ----------------------------------------------------->|

6.4 Native failure

  1. session taskがnative failureをtyped codeへ変換する。
  2. serverのutterance付きrecoverable=true errorはその発話だけ失敗させ、Native sessionを継続する。
  3. transport、protocol、timeout、recoverable=falseはdegrade対象にする。
  4. batch descriptorがあり、degraded_once == falseならnative taskを閉じる。
  5. currentとpending finalのsanitized PCMは保持したままbatch engineを作る。
  6. degraded eventを一度送る。
  7. pending finalを優先decodeし、その後current partial scheduleを開始する。
  8. 同じsessionで二度目のProvider failureは再degradeせず、対象発話またはsessionを失敗させる。

6.5 Start and stop policy

start_voice_asr_sessionは次の順序を変えずに実装する。

  1. session ID、conversation ID、16 kHzを検証する。
  2. DB lock内でconversation存在、ASR route、voice settings、profile modeを読む。
  3. target modeなら同じlock内でprepared verifierを作り、以後のwarm pathでDBを読まない。
  4. DB lockを解放してからHarness resolve、health、WebSocket handshakeを行う。
  5. bounded actor channelを作り、manager mapへgeneration付きhandleを登録してからtaskをspawnする。
  6. task終了時は同じgenerationのhandleだけをmapから除去する。
  7. ready eventを送り、start commandへsuccessを返す。spawnまたはready失敗時はhandleを除去する。
Table: Stop callers and finalization
Caller finalizeCurrent Reason
User pauses listening true 取得済み発話をdeliverする
Input device changes true 旧deviceの発話を確定して新sessionを開始する
TTS starts false 既にLLM inputは確定済みで、自己音声loopを作らない
Meeting handoff false Chat conversationへ曖昧な途中発話を送らない
Conversation change / unmount false 別conversationへ誤配送しない
Fatal error / app shutdown false 即時zeroizeとcleanupを優先する

7. Native streaming event normalization

  1. Provider revisionはadapter内で検証し、FrontendへはBackendのlocal revisionを送る。
  2. 古いProvider revision、unknown utterance、final済みutterance eventは破棄しmetricだけ増やす。
  3. Provider stable textが前回stableをprefixとして含まない場合はprotocol errorとする。
  4. unstableは追加連結せず、eventごとに全置換する。
  5. finalはallowed languageを検証し、通過後だけFrontendへ送る。
  6. commit timeout時は保持PCMをbatch finalへ一度だけ回す。batch失敗時はその発話をfailedにする。

8. Anchored Local Agreement batch fallback

8.1 Snapshot policy

  • 一つの発話内の全partial requestは同じutteranceStartSampleから始める。
  • 最初のrequestは1,800 ms到達時、その後は600 msごとに作る。
  • request audioは[utteranceStartSample, latestPacketEndSample)のwhole prefixである。
  • 開始位置の異なるrolling tail同士は比較しない。
  • in-flightは1件。処理中に複数hopが来た場合、最新end sample一つだけをpendingにする。
  • 完了仮説は同じutterance、同じstart sample、増加するend sampleのものだけ最大3件保持する。
  • 30秒commitで計算量とmemoryを上限化する。
  • batch成功またはno-speechでconsecutive failureを0へ戻す。partial/finalを通じて3回連続で失敗した場合は asr-provider-unavailableのfatal eventを送りsessionを停止する。 
struct BatchEngine {
    generation: u64,
    in_flight: Option<InFlightDecode>,
    pending_partial_end_sample: Option<u64>,
    hypotheses: VecDeque<BatchHypothesis>,
    result_rx: mpsc::Receiver<BatchDecodeResult>,
}

struct BatchDecodeResult {
    generation: u64,
    utterance_id: String,
    kind: DecodeKind,
    end_sample: u64,
    outcome: Result<BatchDecodeOutcome, AsrFailure>,
}

HTTP/network decodeはsession actorからtaskへspawnし、actorをawaitで止めない。 commit時はgenerationを増やしてpartial cancellationを通知し、final taskを最優先で開始する。 旧generationのresultは内容を適用せずzeroizeする。final完了後に次発話の最新pending partialを開始する。 

Request 1: audio [0 ms, 1800 ms] ─▶ H1 "クロードコ"
Request 2: audio [0 ms, 2400 ms] ─▶ H2 "クロードコード"
Request 3: audio [0 ms, 3000 ms] ─▶ H3 "クロードコードを使う"

開始点はすべて0 ms。末尾だけが伸びるためprefix agreementが意味を持つ。

8.2 Comparable text

unicode-segmentationとunicode-normalizationを使い、次の純粋関数をRustへ実装する。 unicode-normalizationはlockfileにtransitive dependencyとして存在しても、直接dependencyへ明記する。 

struct ComparableTranscript {
    raw: String,
    units: Vec<ComparableUnit>,
}

struct ComparableUnit {
    key: String,
    raw_end_byte: usize,
}

fn comparable_transcript(raw: &str) -> ComparableTranscript;
fn longest_common_prefix(left: &[ComparableUnit], right: &[ComparableUnit]) -> usize;
  • raw全体をNFC化してからgraphemeへ分割する。
  • 連続するUnicode whitespaceは比較key一個のASCII spaceへまとめる。
  • 英字case、数字、句読点、記号は変更しない。
  • 表示文字列は最新仮説のNFC rawからbyte境界で切り出す。
  • LLM、辞書、fuzzy edit distanceを重複除去へ使わない。

8.3 Exact agreement algorithm

on hypothesis Hn:
  1. stale utterance/start/endならdiscard
  2. latest 3へHnを追加
  3. HnとHn-1のLCPを求める
  4. Hn-2があればHnとHn-2のLCPも求める
  5. 現stable unitsをprefixに含むcandidateだけ残す
  6. 最長candidateを選ぶ。同長ならHn-1とのcandidateを優先
  7. candidateがHn全文と同じなら末尾2 graphemeをstable化せずunstableに残す
  8. candidateがHnの途中で終わるならcandidate全体をstableにする
  9. Hnが既存stableをprefixに含まない場合はeventを出さずagreement_conflictを増やす
 10. unstable = Hn rawのstable境界以後。前回unstableへ連結しない

手順7は、まだ音声が続いていない時点で「クロードコ」の末尾を確定しないためのguardである。 次仮説が「クロードコード」へ伸びれば、共通prefixの後ろに新しいtailが存在するため手順8で確定できる。 

H1 "クロードコ"              → 初回はstable "" / unstable "クロードコ"
H2 "クロードコード"          → LCP(H2,H1) "クロードコ" / unstable "ード"
H3 "クロードコードを使う"    → LCP(H3,H2) "クロードコード" / unstable "を使う"

禁止: "クロードコクロードコード" のような結果連結

8.4 Batch finalization

  1. commit受理時にpartial requestのcancellationを通知する。
  2. 同じ発話のsanitized whole PCMを一度だけbatch decodeする。
  3. verbose_jsonのtext、language、segment start/end、no-speechをtyped outcomeへparseする。
  4. no-speechまたは空textはutteranceDiscardedにする。
  5. allowed languageを検証し、通過したtextをfinalの正本にする。
  6. partial agreement textをfinal失敗時の代用としてLLMへ送らない。
  7. final decode失敗は対象utteranceIdのfailed(fatal=false)として通知し、 consecutive failureが3未満なら次発話を継続する。

9.1 Mode resolution

9.2 Prepared verifier

warm audio pathでDB、Keychain、embedding fileを読むことを禁止する。 profile/streaming_verifier.rsへ次を追加する。 

pub(crate) struct PreparedVoiceVerifier {
    extractor: SpeakerExtractor,
    references: Vec<Zeroizing<Vec<f32>>>,
    threshold: f32,
}

impl VoiceProfileRuntime {
    pub(crate) fn prepare_streaming_verifier(
        &self,
        connection: &Connection,

filter disabledならOk(None)、enabledだが準備不能ならtyped start errorを返す。 scoreはcandidate embeddingと各referenceのcosine similarity最大値を返す。

9.3 Block voting

  • 1 blockは100 ms、windowは連続15 block、window startは5 blockごととする。
  • window RMSが現行vadSensitivityの閾値未満ならspeaker modelを呼ばずfail voteにする。 閾値はhigh 0.006、medium 0.008、low 0.012を既存実装と共有する。
  • window scoreがprofile threshold以上ならpass voteである。
  • 各blockは、それを含むwindowがすべて完了した時点でreleaseする。
  • 通常blockは3票中2票以上でacceptする。
  • session先頭にはstart -1,000 msと-500 msのvirtual windowを置き、範囲外sampleをzero paddingする。
  • 端点を含む全blockを常に3窓で評価し、2票以上でacceptする。
  • speaker inference errorまたはtimeoutのwindowはfail voteとして数える。
  • commit時は沈黙timeout分の後続audioがあるため、speech末尾を含むwindowを先に処理してからflushする。
  • accepted/rejected blockの時刻とscoreをlogしない。countと処理時間だけmetric化する。

gateは判定までraw blockをlocal memoryへ保持する。判定後、accepted blockはProvider queueへmoveし、 rejected blockはzeroizeして同長silenceを生成する。batch final bufferにもsanitized PCMだけを保存する。

score計算はspawn_blockingへ出し、同時実行は1件、timeoutは1,000 msとする。 timeout後はsessionをfail closedにし、native worker上に残った計算結果を再利用しない。

このgateは「本人が含まれる時間block」を選ぶtemporal filterであり、同時発話から本人の波形だけを 分離するtarget-speaker extractionではない。本人と他人が同じblockで同時に話し、そのblockがacceptされた場合、 両者の波形がASRへ渡る。厳密な同時発話分離を出荷要件にする場合はspeaker separation modelを別計画で導入し、 それまではこのmodeを本人認証または完全分離と表示しない。

10. Frontend projectionとLLM delivery

10.1 Transcript projection

  • stateは{ stableText, unstableText, utteranceId, revision }で保持する。
  • partial eventのrevisionが現在値以下なら無視する。
  • 同じutteranceのunstableを全置換し、文字列を追加連結しない。
  • finalでstable/unstableを消し、final textを一度表示してdelivery queueへ渡す。
  • discardedでそのutteranceの表示を消す。
  • screen readerのaria-liveはstatusだけに使い、全文更新を毎回読み上げない。

10.2 Exactly-once delivery

type FinalVoiceUtterance = {
  sessionId: string;
  utteranceId: string;
  conversationId: string;
  text: string;
};

class VoiceFinalDeliveryQueue {
  // capacity 2; seen/inFlight/deliveredをutteranceIdで管理
  push(value: FinalVoiceUtterance): "accepted" | "duplicate" | "full";
  shift(): FinalVoiceUtterance | undefined;
  clear(): void;
}
  1. final受信時にpushし、duplicateなら何もしない。
  2. conversation runが空なら既存submitPrompt(text, { inputOrigin: "voice" })を呼ぶ。
  3. conversation run中なら既存pending voice promptへsourceId: utteranceIdを追加してqueueする。
  4. capacity 2超過はerror表示し、3件目を送らない。重複finalでcapacityを消費しない。
  5. markはsubmit前にinFlightへ移し、成功または既存retry UIへの移行後にdeliveredへ移す。
  6. session stop後も受信済みfinalはdeliverする。unmountまたはconversation changeではdeliverせずclearする。

ASR sessionはprocess再起動後に復元されないため、exactly-onceの範囲は一つのdesktop process内である。 persistent idempotency migrationは本計画に含めない。

10.3 User-visible states

  • 接続中、ストリーミング文字起こし中、互換モード、発話確定中を区別する。
  • stableは通常text、unstableは既存のstreaming styleで表示する。
  • target-speakerでは本人確認後に文字起こしと表示し、追加latencyを隠さない。
  • degradeはerror bannerではなくnon-blocking statusへ出す。
  • fatal errorだけ待ち受けを停止し、一つのrecovery actionを表示する。

Native完成にはHarness server側のsaaa.asr-stream.v1実装と短時間test endpointが必要である。 Desktop repositoryだけを変更できる場合の完成範囲はbatch agreementまでである。 server repositoryが不明でもASR-00〜10のbatch部分は止めない。

RollbackはHarness v2のstreaming宣言を外すか、Desktopを直前releaseへ戻して行う。 新DB columnとSettings schemaを追加しないためdata rollbackは不要である。 Nativeだけを無効化する場合も新Frontendとbatch agreement coordinatorは維持する。

15. Definition of Done

  • 待ち受け中のPCMがVAD判定前にsequence付きでASR coordinatorへ届く。
  • Native対応Harnessでは持続WebSocketからpartial/finalが返る。
  • Harness v1と個別Cloud ASRではanchored batch agreementが動く。
  • 「クロードコード」の途中境界fixtureでfinal欠落と重複が0件である。
  • partialはstable/unstableへ分かれ、unstableが追加連結されない。
  • 沈黙または30秒上限でcommitし、次発話captureを止めない。
  • 同一utteranceIdのLLM submitが1件である。
  • all-speakersとtarget-speakerの外部送信PCMが仕様どおり異なる。
  • target-speakerの非本人raw PCMが外部adapterへ渡らない。
  • OS microphone DSPがfalseで、ASR codeが音量またはaudio duckingを操作しない。
  • production codeから非重複chunk単純連結とlegacy staged Chat ASR IPCが削除されている。
  • Section 13の自動Gateと短時間GateがすべてPassする。
  • 実装後に本文書へ実測値、利用可能Harness revision、未対応事項を追記する。
