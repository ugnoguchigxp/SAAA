# アーティファクト WebView 改善計画

作成日: 2026-09-23
状態: 実装前・再レビュー反映済み（実機での原因確定待ち）

## 目的と受入結果

Webサイトをアーティファクト領域で読めるようにし、SAAA のタブとサイト自身のナビゲーションを区別できる表示にする。LLM の最終回答に含まれる複数の URL は、最初の1件を表示し、残りを選択可能なタブとして示す。マウス、キーボード、音声のいずれからも同じ WebView 操作へ到達できるようにする。

受入時には、サイトのハンバーガーメニューやサイト内タブの**上**に SAAA のタブ列が常時見え、どのサイトを表示中か分かることを確認する。SAAA のダークテーマはサイト本文の配色を決めない。

## 調査で確認した現状

- `ArtifactDrawer.tsx` にはタブ列、選択、個別閉鎖が既にある。`artifactTab.ts` は最大8件を保持する。ただしスクリーンショットでは SAAA のタブを認識できず、見えている `Summary / News / Chart` は Yahoo Finance 側のタブである。
- `SourceWebsite.tsx` は別のネイティブ子 WebView を作り、ホスト要素の `getBoundingClientRect()` をその位置と大きさに使う。`artifact-panel-body` はスクロール可能で余白と見出しを持ち、`artifact-webview-host` には最小高さ240pxがある。現在の矩形判定は画面内との交差だけを見ており、タブ列・パネル本文の可視領域でクリップしない。この組合せは重なりの有力な原因だが、実機の矩形ログで確定する。
- `ChatPage.tsx` は実行中の最初の `sourceAvailable` だけを自動で開く。`ChatMessages.tsx` は回答内のリンクをクリックしたときだけ `openSource` を呼ぶ。回答内の全 URL を順序付きでタブへ展開する処理はない。
- `source_web.rs` は会話に保存済みの `web_fetch` または `web_search_result` URL のみを許可する。遷移は最初の URL と同じホストに限定し、新規ウィンドウとダウンロードは禁止する。サイトの配色を書き換える処理は見当たらない。したがってスクリーンショットの暗いサイト表示を SAAA のテーマ強制と断定しない。
- SQLite の tool selection catalog は `CatalogEntry` と `UsagePage` を保存する。一方、現在の backend router は `llang`、`mcp_http`、`records` のみを実行できる。SQLite に説明を登録するだけでは WebView 操作は動かない。会話モデルへ公開する定義と、実行結果を UI へ届ける経路も必要である。
- 回答確定時には `messageCompleted` イベントが届く。回答の表示コンポーネントは履歴の再描画にも使われるため、そこで自動タブ展開すると過去の回答やページングでも開き得る。
- `artifactTab.ts` は新規タブを開くと古いタブを削除して最大8件にする。このままでは回答内 URL の全件提示を保証できない。

## スコープ

対象は Webサイトのアーティファクト表示、回答 URL のタブ化、WebView 専用の操作とその SQLite ツール登録。既存の semantic UI と interactive preview はタブ共通部の回帰確認対象とし、表示内容の再設計は行わない。一般ブラウザ化、任意サイトの自動巡回、ダウンロード、サイトへの認証情報の共有は対象外。

## 設計

### 1. タブと WebView の表示境界

SAAA のタブ列と URL/操作バーをパネル上部の固定領域に置き、サイト表示領域を独立した残余領域にする。サイト表示時の本文余白と見出しは廃し、見出しはアクセシビリティ名として残す。選択中タブは背景・境界・文字の差と `aria-selected` で示し、横幅が狭い場合はタブ列だけ横スクロールさせる。

子 WebView はスクロールしない固定のサイト表示領域に配置し、その領域とアプリの可視領域の交差から矩形を決める。親領域のスクロールを WebView の位置調整に使わない。非表示・ゼロ面積なら WebView を隠す。リサイズ、タブ切替、ウィンドウ可視状態の変化で矩形を更新し、古い非同期更新が新しい位置を上書きしないようにする。ネイティブ WebView が DOM の `z-index` に従うことは前提にしない。

サイト自体には SAAA のダークテーマ用 CSS や `prefers-color-scheme` の上書きを注入しない。サイトが自分で暗色を選ぶ場合は、その表示を保持する。

### 2. 回答 URL の提示

確定した assistant 回答の本文から、表示対象の Markdown リンクと文章中のプレーン URL を出現順に抽出する。コードブロック、画像 URL、非表示の構文は自動表示対象に含めない。HTTP(S) のみを構文検証し、URL の表記差を正規化して重複排除する。表示ラベルはリンク文字列またはホスト名を使い、長い URL は省略表示しつつ完全な URL を確認できるようにする。**最終回答の URL 順をタブ提示の正本**とし、最初の URL を選択して表示し、2件目以降を背景タブとして追加する。

自動展開の起点は新しい回答の `messageCompleted` とし、メッセージ ID 単位で一度だけ適用する。履歴の読み込み、ページング、再描画、アプリ再起動時には自動選択しない。ストリーミング途中の URL や失敗・取消しで未確定の回答も対象にしない。ユーザーが履歴中のリンクを押したときは通常のタブ選択として扱う。タブ状態の正本はアーティファクトワークスペースとし、回答の提示順と選択状態を別の独立した状態へ二重保存しない。

実行中の `sourceAvailable` は出典の記録・表示用メタデータとして扱い、WebView タブを自動で開かない。回答が確定するまでは既存タブの選択を変えない。確定した回答に URL がない場合は新規タブを開かず、既存タブの選択も変えない。回答中のリンクをユーザーが押した場合は、その URL のタブを選択する。この規則に合わせ、現在の `ChatPage.tsx` にある `sourceAvailable` からの自動 `openSource` を廃止する。

現行の WebView は、Web検索・取得で保存された URL だけを開ける。一方、LLM の最終回答には、その保存済み出典に存在しない URL も含まれ得る。新しい許可条件として、ホストに保存された**確定済みの assistant メッセージ**の URL と、会話 ID・メッセージ ID・URL をマウント時に照合する。フロントエンドから任意の URL を「回答にあった」と登録する方式にはしない。保存済み出典の照合は引き続き利用できるが、回答 URL の表示に必須とはしない。回答表示側とホスト側の URL 抽出結果が異ならないよう、同じ抽出仕様の契約テストを設ける。

有効な回答 URL の1件目は自動ロードする。回答 URL の出所照合と URL 構文検査は維持する。公開 Web 向けの既存ポリシーで拒否される宛先はタブに理由を表示し、ロードしない。外部ブラウザでの明示的な操作を認めるなら、その認可を別途定義して実装する。自動ロードを取りやめる条件として、ページの JavaScript が存在すること自体は使わない。

回答に含まれた有効な URL は既存の8タブ上限で黙って削除しない。URL タブは全件をタブ一覧に保持し、横スクロールまたは一覧メニューで選べるようにする。タブ状態は会話 ID ごとに分け、会話を切り替えたら前の会話のサイトとタブを表示・音声操作の対象から外す。戻った会話のタブをどう再表示するかは、会話ごとの最後の選択状態で決める。

タブの個数とネイティブ WebView の個数は分ける。ただし毎回 WebView を破棄するとタブへ戻るたびにページが再読み込みされる。実装では、選択済みタブの WebView を少数だけ非表示で保持する方式を先に実機で評価し、メモリ・背後でのスクリプト実行・切替速度を測る。採用できなければ1件のみ保持し、再選択時は再読み込みになることを UI と受入条件で明示する。タブを大量に保持しても、全ページを一斉にロードしない。

**ページ遷移は最初に開いた URL のオリジン（scheme・host・port）へ固定する。** 現行の `source_web.rs` は `on_navigation` でホストだけを比較しているため、同じホストの別ポートや HTTPS から HTTP への移動を許し得る。ホストだけでなくオリジンを比較するよう強化し、JavaScript の `location.assign` / `location.replace`、通常リンク、HTTP リダイレクト、meta refresh が別オリジンへ向かう場合を実機で確認する。同一オリジン内の通常遷移は許可する。`www.example.com` と `example.com` は異なるホストとして扱い、拒否した遷移は SAAA 側で理由を示す。`target=_blank` / `window.open`、非 HTTP(S)、ダウンロード、端末権限も引き続き拒否する。

この制御の対象は WebView の**ページ遷移**であり、ページ内のスクリプト、画像、API 通信などの全ネットワーク要求を遮断するものではない。JavaScript を無効化したり `window.location` を上書きしたりする方式は、サイト機能を壊すうえ完全な境界にもならないため採用しない。別ホストへの通信全体の禁止が必要になった場合は、別のネットワーク隔離設計として扱う。

### 3. WebView 専用の音声操作

操作は `next_tab`、`previous_tab`、`select_tab`、`scroll`、`close_tab`、`close_all_tabs` を基本とする。「次のタブ」「スクロールして」「タブ全部閉じて」などの発話をこの操作へ対応させる。次・前・番号指定は現在の会話の Webサイトタブだけを巡回し、選択中のサイトタブがあるときに使う。`close_all_tabs` もその会話の Webサイトタブだけを閉じ、semantic UI と interactive preview は閉じない。対象がない、番号が範囲外、WebView が読み込み中といった場合は、実行できなかった理由を返す。

スクロールは選択中のネイティブ WebView の内容へ届ける必要がある。親 DOM の `scrollTop` だけを変えて成功と報告しない。まず Tauri の子 WebView で安全に実行できる操作方法と成功確認方法を小さな実機検証で確定する。切替操作はタブ選択の反映、スクロール操作は対象 WebView への命令の適用をそれぞれ確認する。読み込み先ページの JavaScript を成功応答の唯一の根拠にしない。マウス・キーボードの操作と音声操作は同じ操作経路を使う。

ツールの名称、入力 schema、使用例、適用条件と不適用条件を `CatalogEntry` / `UsagePage` として SQLite に版付き登録する。SQLite 上の登録は常設し、会話モデルへの提示は**その会話で Webサイトの子 WebView がマウントされ、選択中で、操作可能な間だけ**行う。選択が他のアーティファクトへ移った時、WebView が閉じた時、別会話へ移った時には次のツール提示から外す。読み込み中や表示失敗時にはスクロールを提示しない。WebView が一つもない会話では、ツールの使い方も会話コンテキストへ載せない。ツール探索の設定に依存せず、この状態による提示判定を毎回行う。

登録時に現在の `register_revision` が source kind を `llang` 固定で保存する点を解消し、専用の `artifact_webview` backend を明示的にルーティングする。会話モデルへ公開する定義は SQLite の現行 revision から生成し、カタログと提示内容の不一致を防ぐ。SQLite の登録はツールの正本だが、提示は tool selection の探索設定に任せず、既存の直接提示経路で稼働状態を条件に行う。実行は提示時に固定した revision、actor、会話 ID を tool selection の検証・監査経路へ渡し、その経路を迂回しない。直接提示から既存の検証・監査へ接続できるかを先に小さな実装で確認し、接続できない場合はこの段階で設計を見直す。

タブ一覧と選択状態は UI ワークスペースが所有し、ホストは会話 ID とマウント済み WebView のラベル、選択の世代番号を操作用に追跡する。呼び出しを受けた時にも対応と操作可能状態を再確認し、提示後にタブが閉じられた呼び出しは副作用なしで失敗させる。LLM 引数に含まれるタブ ID や URL をそのまま権限として使わない。UI 操作を伴う命令は要求 ID と選択世代番号を付けて画面側へ送り、実際の切替・スクロール・閉鎖の確認応答を受けてから成功を返す。応答がない場合はタイムアウトとして扱い、遅れて届いた要求で後続の選択状態を上書きしない。
