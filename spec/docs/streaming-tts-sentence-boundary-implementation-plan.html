Streaming TTS Sentence-Boundary Pipeline 実装計画

0. 文書の役割

  • Status: Proposed。実装・実機計測は未着手
  • Created: 2026-08-30
  • SAAA baseline: 0f0d2cd + working tree
  • Shipping client: macOS版SAAA desktop
  • 親計画: Conversation / LLM / ASR / TTS 品質改善実装計画のCV-05
  • 対象: Conversation Runtime、TTS Runtime、Chat UI、IPC、QA

本文書は、LLMの回答全文が完成してからTTSを開始する現行方式を、自然な句読点単位で 回答生成中から読み上げる方式へ移行するための実装契約である。単に10文字ごとにTTSを呼ぶのではなく、 回答単位のSpeech Session、文境界accumulator、bounded render-ahead queue、単一再生streamを実装する。

計画作成時点ではRuntime、Settings、Database、UIを変更しない。完了の定義はSection 13の実装ticketを 依存順に完了し、Section 14の自動GateとSection 15の実機Gateをすべて通すことである。

1. 採用判断

採用する方式は「10文字固定分割」ではなく、10文字を最初の発声候補になる最小値とし、 自然な句読点でチャンクを確定するadaptive sentence boundary方式である。 

LLM append-only deltas
        ↓
TurnEventSink（UI通知とSpeech Sessionへの一回だけの分岐）
        ↓
StreamingSpeechSession
  ├─ raw Markdown accumulator
  ├─ protected-range scanner
  ├─ sentence boundary chunker
  ├─ speakable-text projection
  └─ render queue（最大2件）
        ↓
chunk N playback + chunk N+1 synthesis
        ↓
one output stream / complete / cancel / fail

最初の自然な文が確定した時点でTTS合成を開始し、LLMのmessageCompletedは待たない。 一方で、語、URL、Markdown、数値、括弧の途中では切らず、最終イベントで残りを一度だけflushする。

2. Goals / Non-goals

2.1 Goals

  1. 回答全文の完成前に、最初の自然な文から読み上げを開始する。
  2. 読み上げ対象の欠落、重複、順序逆転を0件にする。
  3. 句読点、Markdown、URL、数値、括弧を考慮し、不自然な位置で切らない。
  4. 再生中に次チャンクを合成し、チャンク間無音を抑える。
  5. 停止、割り込み、Provider失敗、画面遷移、app終了でsession全体を確実に取消す。
  6. Text回答の成否とSpeechの成否を分離し、TTS失敗で完成済みTextを失敗へ戻さない。

2.2 Non-goals

  • LLM Provider、prompt、回答内容、ASR endpointingの変更は行わない。
  • 単語単位、token単位、10文字固定での逐次発声は実装しない。
  • LLMがまだ出力していない内容を予測してTTSへ渡さない。
  • full-duplexや未検証のbarge-inを同時に導入しない。half-duplexを維持する。
  • ユーザー向けSettings項目、Database migration、Settings schema更新は追加しない。
  • 実Providerのstreaming audio protocolは前提にしない。既存のtext-to-audio契約を使う。

3. 現行Baselineと遅延要因

Table: Current speech path
区間 現状 影響

Speech gate FinalResponseSpeechGateがmessageCompletedだけを受理 回答生成時間の全体が読み上げ開始遅延へ加算される
System TTS 回答全文を一つのsay processへstdin送信 process起動は回答完了後
Cloud TTS 回答全文の音声bodyを全量受信し、WAV保存後にafplay 回答完了後にも合成、download、file syncの待ちが発生
状態所有 FrontendのspeechRunIdとBackendの一つのchild process 複数チャンクのqueue、render-ahead、session取消を表現できない

現行testは「incomplete model deltaを合成しない」ことを成功条件としている。このtestは新契約では、 「自然な境界が未確定のdeltaを合成しない」「確定済みチャンクだけを一度ずつ合成する」へ置き換える。

4. 固定する契約と不変条件

  1. Append-only: 一つのProvider attemptが送るAssistant deltaは追加専用として扱う。 Providerはoutput開始後にfallbackしない現行policyを維持する。
  2. Single ownership: chunk確定位置、queue、active playback、cancel tokenの正本は BackendのStreamingSpeechRuntimeだけが持つ。
  3. At-most-once enqueue: 一つのchunkSeqをrender queueへ二度入れない。
  4. Ordered playback: 再生はchunkSeqの昇順だけを許可する。
  5. Bounded resources: ready audioはactiveを含め最大2件、raw textは64,000文字、 artifactはsession所有directoryだけに制限する。
  6. Text authority: 永続化されたAssistant messageが最終的な画面表示の正本であり、 Speech失敗や取消で書き換えない。
  7. Half-duplex: 最初の音声再生前にcaptureを一度停止し、最後のchunk終了後または session取消完了後に一度だけ再開する。チャンク間では再開しない。
  8. No content diagnostics: metricとlogへ回答本文、chunk本文、音声hashを残さない。

5. Target Architecture

5.1 TurnEventSink

tauri::ipc::Channel<RuntimeEvent>を直接各Providerへ渡す形を、薄い TurnEventSinkで包む。既存の全LLM経路は同じsendを呼び、sinkが UI channelへの通知とSpeech Sessionへの入力を同じ順序で行う。 

struct TurnEventSink {
    ui: tauri::ipc::Channel<RuntimeEvent>,
    speech: Option<SpeechSessionHandle>,
}

impl TurnEventSink {
    fn send(&self, event: RuntimeEvent) -> Result<(), SendError> {
        match &event {
            RuntimeEvent::Delta { text, .. } => self.speech.append(text),
            RuntimeEvent::MessageCompleted { message, .. } => {
                self.speech.finish(&message.content);
            }
            RuntimeEvent::Cancelled { .. } | RuntimeEvent::Failed { .. } => {
                self.speech.cancel();
            }
            _ => {}
        }
        self.ui.send(event)
    }
}

sinkはSpeechへ同じeventを順番に観測させてからUIへ送る。Speech feedはLLM経路へerrorを返さず、 内部の合成・queue失敗は独立したSpeechEvent::Failedとして通知する。UI channel切断だけは現行どおりturn取消対象とし、Speech Sessionも同じgenerationで取消す。

5.2 StreamingSpeechRuntime

AppStateへArc<StreamingSpeechRuntime>を一つ持たせる。runtimeは同時に 一つのactive Speech Sessionだけを許可する。新しいspoken turn開始時は旧sessionの停止完了を待つ。 

struct SpeechSession {
    session_id: String,
    source_run_id: String,
    conversation_id: String,
    generation: u64,
    phase: SpeechPhase,
    accumulator: SentenceAccumulator,
    next_chunk_seq: u32,
    next_play_seq: u32,
    queued: VecDeque<SpeechChunk>,
    rendered: VecDeque<RenderedChunk>,
    cancellation: Arc<RunCancellation>,
}

enum SpeechPhase {
    Buffering,
    Rendering,
    Playing,
    Draining,
    Completed,
    Failed,
    Cancelled,
}

lock保持中にnetwork request、process wait、audio playbackを行わない。lock下ではstate更新と queue操作だけを行い、workerへ所有権を移してから非同期処理する。

5.3 Renderer / Playback worker

  1. chunkerが確定したraw Markdown chunkをtoSpeakableText相当の純関数へ渡す。
  2. 空になったchunkはsequenceを消費せずskipする。
  3. rendererは次の一件を合成し、session所有の一時artifactまたはmemory bufferへ置く。
  4. playback中にrendererが次の一件を先読みする。合成並列数は1、ready queueは最大2件とする。
  5. playbackは一つのoutput streamをsession終了まで保持し、sequence順にappendする。

Cloud TTSは「回答全文の音声を全量受信」から「一つの文チャンクの音声を受信」へ変更する。 System TTSはmacOSのsay -oで次チャンクをartifactへrenderし、Cloudと同じ再生streamへ渡す。 一つのprocessで直接読み上げる現行経路は互換fallbackとして開発中だけ残す。

5.4 Speech lifecycle events

LLM用RuntimeEventへSpeechの非同期完了を混在させず、app-wideの型付き SpeechEventを追加する。Frontendは起動時に一度subscribeし、session IDとgenerationで 古いeventを無視する。 

type SpeechEvent =
  | { type: "preparing"; sessionId: string; sourceRunId: string }
  | { type: "chunkQueued"; sessionId: string; chunkSeq: number }
  | { type: "readyToPlay"; sessionId: string; chunkSeq: number }
  | { type: "audioStarted"; sessionId: string; chunkSeq: number }
  | { type: "completed"; sessionId: string }
  | { type: "cancelled"; sessionId: string }
  | { type: "failed"; sessionId: string; code: SpeechFailureCode };

本文、Providerの生error、endpoint、file pathはeventへ含めない。UIはpreparingから completed | cancelled | failedまで「読み上げ中」と停止操作を表示する。

6. Sentence Boundary Contract

6.1 初期値

Table: Chunking thresholds
値 初期値 意味
firstMin 10 speakable graphemes 最初のstrong boundaryを発声可能にする最小長
steadyMin 24 speakable graphemes 2件目以降の短すぎる断片を抑える目安
target 120 speakable graphemes strong boundaryがない場合にweak boundaryを選び始める長さ
hardMax 240 speakable graphemes 句読点がなくてもboundedにする上限
idleFlush 400ms LLM delta停止時、weak boundary済み断片を早めに確定する時間

文字数はUTF-8 byteやUTF-16 code unitではなくUnicode graphemeで数える。閾値は実機計測前の初期値であり、 Section 15のcorpusを変えずに比較して調整する。ユーザー向け設定にはしない。

6.2 Boundary class

Table: Boundary classification
Class 例 確定規則
Strong 。、！、？、!、?、段落末 firstMinまたはsteadyMin到達後、直ちに確定
Weak 、、comma、semicolon、colon、自然な空白 target到達後、またはidle時だけ確定候補
Forced safe hardMax以前の最後のsafe grapheme 句読点がない異常な長文だけに使用
Completion final messageの末尾 最小長未満でも一度だけflush

6.3 切断禁止範囲

  • Markdown fenced code、inline code、link destination、image destination
  • http://、https://、www.から始まるURL
  • 小数、version、日付、時刻、桁区切りを構成する数値の内部
  • 未閉じの丸括弧、角括弧、波括弧、引用符の内部
  • Unicode grapheme cluster、emoji sequence、combining markの内部
  • 英字、数字、連続する片仮名語の途中

scannerはraw Markdown deltaを連結して状態を保持する。deltaごとに既存の正規表現を独立適用しない。 たとえばcode fenceやMarkdown linkがdelta境界をまたいでも、閉じるまでは発声チャンクを確定しない。 切り出したraw chunkだけを読み上げ用plain textへ投影する。 property testでは各chunkの投影結果をcanonical whitespaceで連結し、完成全文を一括投影した結果と 同一になることを保証する。

6.4 確定algorithm

append(delta)
  1. raw accumulatorへ順番に追加する
  2. scanner stateを更新し、protected range外のboundary候補を記録する
  3. speakable projection後のgrapheme数を計測する
  4. 最初のchunk:
       strong boundaryかつ10文字以上 → そのboundaryまで確定
  5. 後続chunk:
       strong boundaryかつ24文字以上 → そのboundaryまで確定
  6. 120文字以上:
       最後のstrong、なければ最後のweak boundaryまで確定
  7. 240文字到達:
       protected range外の最後のsafe graphemeで強制確定
  8. 確定分だけraw accumulatorから除き、chunkSeqを一つ進める

finish(finalContent)
  1. accumulated raw delta列とfinalContentを照合する
  2. 一致 → 残りを最終flush
  3. finalContentがdelta列をprefixとして含む → 未到着suffixを追加してflush
  4. prefix不一致 → queued/render中を停止しspeech-sync-lostで終了

prefix不一致時に、すでに読んだ内容を取り消すことはできない。修正版全文を自動で最初から読み直すと重複するため、 Textを正本として残し、ユーザーの「読み上げを再試行」で完成済みmessageを最初から読めるようにする。

7. Render / Playback Contract

7.1 Queue bounds

  • raw確定待ちchunkは最大1件、合成中1件、ready audio最大2件、再生中1件とする。
  • LLMが速くqueue上限へ達した場合、本文をdropせずraw accumulator側でbackpressureする。
  • raw accumulatorはLLM契約の64,000文字上限を超えない。超過はLLM側の失敗を優先する。
  • 同一session内のCloud TTS合成並列数は1とし、Providerへのburst requestを防ぐ。

7.2 Render-ahead

  1. chunk 0の合成完了直後に再生を開始する。
  2. chunk 0再生中にchunk 1を合成する。
  3. chunk 1を同じaudio sinkへappendし、再生終了境界でprocessを切り替えない。
  4. chunk 2以降もready queueを最大2件に保ちながら繰り返す。
  5. LLM完了後もrender/playbackが残っていればSpeech SessionだけDrainingを継続する。

7.3 Cancellation ordering

User stop / new voice input / new spoken turn / meeting / unmount / shutdown
  → generationを進める
  → cancellation tokenを発火
  → network synthesisを中止
  → output sinkをstop
  → queued audioとraw accumulatorを破棄
  → session所有artifactを削除
  → Backendがcancelled eventを送信
  → Frontendが必要な場合だけmicrophoneを再開

Frontendはstop_ttsのcommand返却だけで停止済みとみなさず、対象sessionの cancelled | completed | failedをgeneration guard付きで受けてUIを確定する。

7.4 Error policy

Table: Speech failure behavior
Failure Speech Text / LLM
最初のchunk合成失敗 sessionをfailedにし、retry actionを表示 生成を継続し、完成Textを保存
途中chunk合成・再生失敗 残queueを停止し、どこからかを推測して自動再送しない 生成を継続し、完成Textを保存
LLM partial-output / failed activeとqueuedを停止 現行のtyped LLM failureを表示
LLM user cancellation 同じsource runのSpeech Sessionを取消 現行のcancelled状態を維持
UI channel disconnected sessionを取消 現行どおりturnをClientDisconnectedとして終了

8. IPC / Frontend変更

8.1 Turn開始

StartTurnInput.presentationMode = visual-and-spokenをBackendがSpeech Session生成の 明示条件として使う。FrontendはautoSpeakからpresentation modeを決める現行責務だけを持ち、 deltaごとにTTS commandを呼ばない。

8.2 Chat state

  • FinalResponseSpeechGateによる全文待ちを削除する。
  • messageCompletedからのstartSpeech(finalText)を削除する。
  • activeTtsRunIdをBackend発行のspeechSessionIdへ置き換える。
  • 「読み上げ停止」はsource LLM runではなくSpeech Session IDを指定する。
  • Speech失敗時のretryは完成済みAssistant message IDを参照し、全文一括再生を行う。
  • 会話切替やcomponent dispose時は対象sessionを取消し、古いeventをgenerationで無視する。

8.3 Microphone coordination

現行のsuspendVoiceForSpeechとresumeVoiceAfterSpeechはsession単位へ変更する。 SpeechEvent::audioStartedより前にcapture停止を完了させる必要があるため、Backendは最初のaudioをrenderした時点で readyToPlayを送り、Frontend coordinatorのvoiceSuspended ackを待つ。ack timeout時は再生せずfailedにする。

実装は「Frontend suspend → Backend ack → playback」の順を採用する。BackendだけでmacOS microphoneを 停止できると仮定しない。ack timeout初期値は1秒とし、自己音声loop防止を開始速度より優先する。

10. Observability

本文を保存せず、monotonic clockで以下のtimestampとcountだけをsession単位に記録する。

TTS provider、voice ID、locationは既存のbounded identifierだけを記録できる。回答本文、文字数以外の 内容特徴、音声artifact path、URL、error bodyは記録しない。

11. Test Plan

11.1 Chunker unit tests

  • 10文字未満の文は次文と結合し、10文字以上の最初の。で確定する。
  • 日本語の。！？、英語の.!?、改行を自然な境界として扱う。
  • 3.14、v1.2.3、10:30を途中で切らない。
  • URL、Markdown link、inline code、fenced codeが複数deltaへ分割されても途中で切らない。
  • 括弧や引用符の中の句読点を外側の文末と誤認しない。
  • emoji、combining mark、surrogate相当をgrapheme途中で切らない。
  • 句読点のない240文字超をsafe boundaryでboundedに分割する。
  • completion時の短い末尾を一度だけflushする。
  • 空またはMarkdown-onlyのchunkをTTSへ送らない。
  • delta列とfinal contentのprefix一致、suffix補完、不一致をそれぞれ検査する。

11.2 Runtime / queue tests

  • 50 chunkを投入してもready queueが2件を超えない。
  • chunk N再生中にN+1をrenderし、再生順が必ず昇順になる。
  • renderer完了順を意図的に逆転させてもplayback順が逆転しない。
  • 同一delta callbackの再送で同じchunkSeqを二重enqueueしない。
  • 最初、中間、draining中の各cancelでnetwork、process、sink、artifactが残らない。
  • Cloud responseが遅い、過大、非音声、途中切断の場合にbounded failureとなる。
  • System renderer processが失敗してもText turnをfailedにしない。
  • app shutdown後にchild process、audio sink、temp artifactが残らない。

11.3 Conversation integration tests

  • fake SSE serverから文途中deltaを送り、最初の句点まではTTS requestが0件である。
  • 最初の自然な文が確定した直後、[DONE]前にTTS requestが開始される。
  • 全TTS inputを連結した結果が完成済みspeakable textと一致する。
  • Providerがoutput開始後に失敗した場合、Speechを停止しfallbackしない現行契約を維持する。
  • Providerがoutput開始前にfallbackした場合、失敗Provider由来のSpeech Sessionを開始しない。
  • Text完成後にSpeechが継続してもChatはGeneratingではなくSpeakingを表示する。
  • Speech retryはLLMを再実行せず、完成済みAssistant messageだけを一括で読み上げる。
  • meeting開始、conversation切替、Mic interruptで対象sessionだけを停止する。

11.4 Property / invariant tests

固定fixtureを任意のdelta境界へ分割し、どの分割でも最終chunk列が同じになることを検査する。 各caseで、sequence単調増加、欠落0、重複0、順序逆転0、buffer上限内をassertする。

12. Rollout / Rollback

  1. 開発時だけSAAA_STREAMING_TTS_ENABLED=1で新経路を有効化し、未指定時は現行の final-only経路を使う。値は起動時に一度だけ読む。
  2. fake rendererとSystem voiceで自動test、desktop smoke、content-free latency計測を通す。
  3. Cloud TTSを含む実Provider matrixと30分連続再生を実施する。
  4. Section 15の全Gate通過後、新経路を既定にしてfinal-only経路を一releaseだけrollback用に残す。
  5. 次releaseで旧経路、環境変数、旧FinalResponseSpeechGateを削除する。

DatabaseとSettings schemaを変更しないためbinary rollbackにdata migrationは不要である。 rollback時はactive Speech Sessionを停止してから旧binaryを起動し、session artifact cleanupを確認する。

17. Definition of Done

  • 最初の自然な句読点が確定した後、LLM回答完了前に読み上げが始まる。
  • 10文字固定分割ではなく、Section 6のboundary contractが全LLM routeで共通適用される。
  • Backendがsession、chunk位置、queue、playback、cancelの唯一の正本である。
  • System / Cloud TTSで欠落、重複、順序逆転が0件である。
  • チャンク間gap、開始遅延、cancel遅延がSection 15の閾値内である。
  • Speech失敗、LLM失敗、取消、retryが別outcomeとして動作する。
  • 本文を含まないmetricだけで変更前後を比較できる。
  • DB / Settings migrationなしでrollbackできる。
  • 全自動Gate、実機matrix、30分soakがPassする。
  • 旧final-only経路と開発用feature flagを期限どおり削除する。
