SAAA Provider LLM WebSocket Protocol saaa.llm-stream.v1

0. 文書の役割

  • Status: Reviewed / Implementation-ready v2
  • Created: 2026-08-31
  • SAAA baseline: 0ec8019 + working tree
  • 対象: LARM、Provider Harness、Dynamic LAN Provider、SAAA desktop
  • WebSocket subprotocol: saaa.llm-stream.v1

本文書は、SAAAとLLM Provider間の回答data planeをSSEからWebSocketへ完全移行するための normative application protocolである。Provider実装者が別の判断を補わなくても相互接続できるよう、 discovery、handshake、wire message、run state、順序、ACK、resume、tool call、取消、 backpressure、上限値、適合試験を固定する。

本文書の「必須」「禁止」「推奨」はnormativeである。WebSocket transport自体は RFC 6455へ従い、本文書はその上に載せる SAAA固有subprotocolを定義する。

1. 固定する判断

Table: Provider protocol decisions
ID 判断 意味
PWS-DEC-01 controlは1 text message = 1 JSON、hot response.deltaは固定16 byte headerのbinaryにする 低頻度controlの可読性を保ち、小deltaのJSON parse、field名、run ID転送を除去する
PWS-DEC-02 広告同時実行数までconnectionをprewarmし、1 connectionへactive runを1件だけ割り当てる turnごとのhandshakeとrun間head-of-line blockingを同時に除去する
PWS-DEC-03 Provider eventはrun内連続seqを持つ TTSへ渡す前に重複、欠落、逆順を検出する
PWS-DEC-04 累積ACKと最低120秒のresumeを必須にする 再接続後に受理済みdeltaを再発声しない
PWS-DEC-05 tool callは完成済みargumentsを1 eventで送る 分割JSON再構築と本文混在をなくす
PWS-DEC-06 terminalは累積UTF-8 byte数とSHA-256を持ち、全文を再送しない client accumulatorを正本にし、最大262 KiBの重複転送とcopyを除去する
PWS-DEC-07 permessage-deflateをv1では使わない 小deltaの圧縮待ち、CPU変動、同一圧縮contextへのsecret混入を避ける
PWS-DEC-08 SSE bridgeを準拠Providerとして認めない 外側だけWebSocketで包む構成を完全移行と呼ばない
PWS-DEC-09 tool callは回答text開始前に最大4件まで並列化できる 独立toolのwall-clock latencyを直列和にしない

2. Scope / Non-goals

2.1 Scope

  • assistant text delta、tool call / result、usage、正常完了、失敗、取消。
  • 同一client process中の切断、再接続、未ACK event replay。
  • LARM allocation runとProvider Harness direct run。
  • local、LAN、remote Providerに共通するwire contract。

2.2 Non-goals

  • ASR、TTS audio、画像、binary token、reasoning traceのtransport。
  • process再起動後の永続resume。
  • Provider側tool実行、Provider側Markdown render。
  • OpenAI互換SSE eventをWebSocket payloadへそのまま格納すること。

3. Provider discovery

3.1 Provider Harness

Harnessはsaaa-service-harness.v3を返す。LLM serviceでは protocolとstreaming.protocolを共に saaa.llm-stream.v1へ固定し、streamingを必須にする。 

{
  "contractVersion": "saaa-service-harness.v3",
  "revision": "2026-08-31.1",
  "services": [
    {
      "capability": "llm",
      "protocol": "saaa.llm-stream.v1",
      "baseUrl": "https://provider.example/v1",
      "model": "local",
      "healthUrl": "https://provider.example/health",
      "streaming": {
        "protocol": "saaa.llm-stream.v1",
        "url": "wss://provider.example/v1/llm/stream",
        "encoding": "json-control+binary-delta-v1",
        "compression": "none",
        "maxConcurrentRuns": 8,
        "maxConnections": 8,
        "resumeWindowMs": 120000,
        "upstreamTransport": "native"
      }
    }
  ]
}
  • urlはcredential、query、fragmentを含めてはならない。
  • descriptor URLとstream URLは同一hostでなければならない。
  • 非loopback hostではwssを必須とする。
  • upstreamTransportはnativeまたはwebsocketだけを許可する。
  • maxConnectionsはmaxConcurrentRunsと同値にし、1〜8を許可する。
  • target profileのClientはadvertised connection数をProvider readiness時にprewarmする。 一部しか確立できない場合、利用可能slotを減らし、同じconnectionへ二つ目のactive runを載せない。

3.2 LARM

allocation、poll、renew、releaseは現行REST control planeを維持する。LLM data planeは LARM base URLの/v1/llm/streamを使う。HTTPSはWSSへ、literal loopbackのHTTPだけは WSへ変換できる。allocationIdは各run.startへ入れるため、connectionを allocation間で再利用できる。

3.3 Dynamic LAN

Provider descriptorのprotocolをsaaa.llm-stream.v1へ変更し、 credentialなしのstreamUrlを返す。現在の平文HTTP + Bearerはtarget profileで認めない。 非loopback LAN ProviderはTLSを用意する。

4. Transport / Handshake

  1. ClientはSec-WebSocket-Protocol: saaa.llm-stream.v1を送る。
  2. Serverは101 responseで同じsubprotocolをechoする。
  3. 一致しない場合、Clientはapplication messageを送らず接続を破棄する。
  4. 認証が必要ならAuthorization: Bearer <token>をhandshakeへ付ける。
  5. tokenをURL、query、cookie、subprotocol、最初のJSON messageへ入れてはならない。
  6. ClientはWebSocket extensionをofferせず、Serverも選択してはならない。
  7. handshakeとconnection.readyは合計5秒以内に完了する。

connection共有keyは(stream URL, credential fingerprint, subprotocol)とする。 tokenが異なるrunを同じpoolへ混在させない。各connectionは同時に一つのrunだけを所有し、terminal ACK後にだけidleへ戻る。Serverはhandshake時とrun.start時にauthorizationを確認する。

4.1 Heartbeat

  • 15秒application trafficがなければ、どちらかがRFC 6455 Pingを送る。
  • 受信側は5秒以内に同じpayloadのPongを返す。
  • 2回連続でPongがなければ接続を閉じ、Clientはjitter付きbackoff後にresumeする。
  • JSONのping / pong messageは定義しない。

5. Encoding / Limits

  • response.delta以外のapplication messageはUTF-8 JSON objectのtext messageを使う。 JSONL、SSE framing、複数JSONの連結を禁止する。
  • response.deltaはbinary WebSocket messageとし、WebSocket libraryがfragmentを再構成した後、 次の16 byte network-byte-order headerとUTF-8 payloadとしてdecodeする。
  • field名はcamelCase、type値はdot-separated lowercaseとする。
  • unknown field、重複JSON key、NaN、Infinity、末尾dataを拒否する。
  • identifierは[A-Za-z0-9_-]だけで1〜160 byteとする。
  • seqは1以上のJSON integerとする。
Binary response.delta v1（16 byte header + payload）
offset  size  field
0       4     magic = ASCII "SAD1"
4       1     messageType = 0x01
5       1     flags = 0x00
6       2     headerLength = 0x0010
8       8     seq: unsigned u64, big endian
16      N     append-only UTF-8 payload, 1..16,384 byte

binary deltaはconnectionへpinされたrunに属するためrunIdを重複格納しない。magic、type、 flags、header length、UTF-8、payload size、期待seqのいずれかが不正なら該当runを protocolでfailし、Close 1002する。hot pathではDOM型のJSON valueを生成せず、payloadを incremental SHA-256とcanonical accumulatorへ一度だけappendする。

Providerは最初の非empty deltaを待たずに送る。二件目以降は、最初の未送信byteから5 ms経過、 未送信payloadが256 byte到達、またはupstreamがidle / terminalになった条件のうち最も早い時点で 一つのbinary deltaへ結合する。TTSの自然境界を跨いで追加待機せず、16,384 byteを超える前に分割する。 ClientはProvider不良を検出できるよう1 byte × 10,000件のburstにもbounded memoryで対応する。

6. Message model

connection messageはrunIdとseqを持たない。JSONのProvider run eventは 両方を必ず持つ。binary deltaはconnectionのactive runを暗黙のscopeとし、headerのseq だけを持つ。Clientから送るrun commandはrunIdを持つがseqを持たない。

6.1 connection.ready

{
  "type": "connection.ready",
  "protocol": "saaa.llm-stream.v1",
  "connectionId": "conn_01JEXAMPLE",
  "upstreamTransport": "native",
  "limits": {
    "maxConcurrentRuns": 8,
    "maxConnections": 8,
    "maxActiveRunsPerConnection": 1,
    "maxUnackedEvents": 64,
    "maxUnackedBytes": 524288,
    "resumeWindowMs": 120000,
    "heartbeatIntervalMs": 15000
  }
}
  • Serverが最初に送るapplication messageでなければならない。
  • upstreamTransportはnativeまたはwebsocket。
  • maxActiveRunsPerConnectionは必ず1。
  • 同じconnectionで二度送ってはならない。

7. run.start

{
  "type": "run.start",
  "runId": "run_01JEXAMPLE",
  "allocationId": "alloc_01JEXAMPLE",
  "model": "local",
  "messages": [
    { "role": "system", "content": "You are a helpful assistant." },
    { "role": "user", "content": "要点を説明してください。" }
  ],
  "tools": [],
  "reasoningEffort": "medium",
  "maxOutputTokens": 4096,
  "toolTimeoutMs": 60000,
  "maxParallelToolCalls": 4,
  "client": {
    "name": "saaa-desktop",
    "version": "0.1.0",
    "capabilities": ["ack", "resume", "binary-delta-v1", "hashed-final", "parallel-tools-v1"]
  }
}
  • LARMではallocationIdにidentifier、Harness directではnullを入れる。
  • messages.roleはsystem、user、assistant、tool。
  • maxOutputTokensは1〜65,536、toolTimeoutMsは1,000〜120,000。
  • maxParallelToolCallsは1〜4とし、Clientが同時実行できる上限を宣言する。
  • active runがあるconnectionへの別run.startはcapacityで拒否する。
  • 同じrunIdの再送は拒否し、再接続にはrun.resumeを使う。

8. Sequence / Content integrity

  1. run.acceptedをseq = 1とする。
  2. 以後のProvider eventは1ずつ増やし、gap、重複、resetを禁止する。
  3. binary response.delta payloadはappend-onlyで、既送信textを置換・撤回しない。
  4. Clientは期待seq以外をTTS、UI、DBへ配送しない。
  5. contentSha256は、それまでの全delta textを順に連結したexact UTF-8 byte列の SHA-256 lowercase hexとする。
  6. response.completed.contentBytesはdelta連結のUTF-8 byte数と一致し、 finishReasonはstopまたはlengthを許可する。
  7. terminalはrunごとに一つだけ送り、その後のeventを禁止する。

最終回答を修正する可能性があるdecodingでは、確定したprefixだけをdeltaとして送る。 既にTTSが発声したtextをterminalで書き換えてはならない。Clientはcanonical accumulatorを completion後の画面、DB、TTS tail flushへmoveし、全文copyを作らない。

9. ACK / Flow control

{
  "type": "run.ack",
  "runId": "run_01JEXAMPLE",
  "ackSeq": 12,
  "contentSha256": "64-character-lowercase-sha256-hex"
}
  • ACKはそのseqまでを連続受理した累積ACKとし、飛び越しを禁止する。
  • Clientは16 event受理または最初の未ACKから100 msの早い方でACKする。
  • terminalは処理完了後ただちにACKする。
  • ACK hashはackSeq時点のdelta累積hashと一致させる。
  • 古いACKは無視し、未送信seqへのACKはprotocol violationとする。
  • 64 eventまたは524,288 byteで、そのrunの新規送信をpauseする。
  • pauseは別connection、Ping/Pong、cancel、ACKをblockしてはならない。
  • upstreamをpauseできない場合、該当runだけをbackpressureでfailする。

SAAAはdeltaをordered Turn Event Hubのcanonical accumulatorへappendし、TTS branchへの配送結果が 成功またはbounded speech failureとして確定した時点でACK対象にする。UI queue、Channel、React、paintは ACK条件に含めない。UIはcapacity 1のlatest-wins projectionとし、2秒停止してもACKとTTSを止めない。 ACK hashはincremental hasherをcloneしてfinalizeし、累積本文を再hashしてはならない。

10. Resume

{
  "type": "run.resume",
  "runId": "run_01JEXAMPLE",
  "ackSeq": 12,
  "contentSha256": "64-character-lowercase-sha256-hex"
}
  1. Clientは新しいidle connectionのconnection.ready後にrun.resumeを送る。
  2. Providerはrun、authorization、allocation lease、ACK、hash、retentionを検証する。
  3. 成功時はそのconnectionへrunをpinしてrun.resumedを返し、 ackSeq + 1から元と同じseqでreplayする。
  4. Clientはseq dedupeを通し、受理済みdeltaをTTSへ再配送しない。
  5. terminalが未ACKなら同じterminalもreplayする。
  6. terminal ACKまたは120秒経過後にProviderはreplay stateを破棄できる。

拒否codeはunknown-run、resume-expired、 allocation-expired、ack-mismatch、 content-hash-mismatch、not-authorizedとする。出力開始後にresumeできない 場合、Clientは新runや別Providerへ自動再実行せず、partial textをincompleteとして残す。

11. Tool call

{
  "type": "tool.call",
  "runId": "run_01JEXAMPLE",
  "seq": 3,
  "callId": "call_01JEXAMPLE",
  "name": "recall_conversation",
  "arguments": { "query": "previous decision" }
}
{
  "type": "tool.result",
  "runId": "run_01JEXAMPLE",
  "callId": "call_01JEXAMPLE",
  "inReplyToSeq": 3,
  "status": "ok",
  "content": "bounded tool result"
}
  • run.start.toolsで提示された名前だけをcallできる。
  • outstanding tool callはmaxParallelToolCalls以下、最大4件とする。
  • 完成済みarguments objectを一つのeventで送る。
  • 最初のresponse.delta後にtool.callを送ってはならない。
  • Clientはtool callをACKしてからresultを返す。
  • 独立callは並列実行し、resultは完了順に返してよい。Providerは全outstanding callのsettle後に生成を再開する。
  • 同じcallへの同一result再送はidempotent、異なるresult再送はprotocol failure。
  • statusはokまたはerror。
  • Client writer queueの優先順はrun.cancel > run.ack > tool.resultとする。
  • timeout時はrunをtool-timeoutでfailする。

13. Terminal / Error

{
  "type": "response.completed",
  "runId": "run_01JEXAMPLE",
  "seq": 18,
  "contentBytes": 39,
  "contentSha256": "64-character-lowercase-sha256-hex",
  "finishReason": "stop",
  "usage": {
    "inputTokens": 120,
    "outputTokens": 44,
    "totalTokens": 164
  }
}

usage不明ならusage: nullを送る。contentBytesが0、delta累積byte数と不一致、 hash不一致の場合、Clientは保存、Markdown化、TTS tail flushを行わない。terminalに content fieldを含めてはならない。

finishReason=stopだけを正常なMarkdown確定とTTS tail flushへ進める。 finishReason=lengthはcanonicalだが不完全なplain textとして保存し、Markdown化と 未発声tailのflushを行わない。

13.1 Run error code

許可codeはinvalid-request、request-too-large、 response-too-large、authentication、not-authorized、 allocation-lost、capacity、model-unavailable、 tool-arguments-too-large、tool-result-too-large、 tool-timeout、backpressure、upstream、 timeout、protocol、internalとする。

error messageは1,024 UTF-8 byte以下の公開可能な定型文にする。prompt、本文、tool content、 token、内部endpoint、stack traceを含めない。retryableがtrueでも outputStartedがtrueならSAAAはProvider fallbackしない。

13.2 Close code

14. Cancellation / Drain

  • run.cancelはidempotentで、1秒以内にterminalを返す。
  • 既にterminalなら同じterminalをreplayし、新しいcancelledを作らない。
  • cancel受理後はupstream generation、tool待ち、queue済みdeltaを停止する。
  • drain中の新しいrunはcapacityでfailし、active runの完了を待つ。
  • drain期限では各active runをfailしてからClose 1001を送る。

15. Security / Privacy

  • 非loopbackはTLS証明書検証を必須にし、平文WSと証明書無視を禁止する。
  • redirectによる別hostへのcredential転送を禁止する。
  • prompt、delta、final、tool、Authorizationをlog / metricへ出さない。
  • metricはconnection / run数、latency、byte、ACK lag、replay、error codeだけにする。
  • connection、credential、runごとのrate / memory limitを持つ。

16.1 Performance conformance

PWS-C05、PWS-C18、PWS-C19はrelease build、同一hostのcontrolled Harness、 prewarmed connectionで1,000反復以上実行し、p50 / p95 / p99とpeak / settled RSSを保存する。 binary decodeはJSON DOMを生成せず、application overheadはdeltaごとにexact 16 byteとする。 一件でも250 ms、16 MiB、5 msのGateを超えたbuildはconformantとしない。実networkの30 runは Provider生成時間とSAAA内部時間を分けた補助evidenceとし、controlled Gateの代用にしない。 

cargo test --manifest-path src-tauri/Cargo.toml --lib providers::websocket
cargo bench --manifest-path src-tauri/Cargo.toml --bench streaming_hot_path
bun run provider:ws-conformance

conformance runnerはPWS-C01〜PWS-C19とSection 16.1の分布をJSONで出力する。 case欠落、sample不足、0 test、閾値超過は失敗とし、Provider / Desktopのどちらもreleaseしない。

17. Rollout / Compatibility

  1. Providerへ新endpointとconformance testを先行実装する。
  2. Harness v3またはLARM readinessでsaaa.llm-stream.v1を広告する。
  3. SAAA canaryは広告数のconnectionを並列prewarmし、WebSocket未対応Providerをturn開始前にunsupportedとして止める。
  4. WebSocketだけで適合試験とASR/TTS regressionを通す。
  5. SSE client、fixture、text/event-stream routeを削除する。

v1 messageへ意味や上限を変えるfieldを追加しない。変更が必要なら saaa.llm-stream.v2を別subprotocolとして定義する。Clientはtarget releaseが要求する 一つのversionだけをofferする。

18. Definition of Done

  1. ProviderとSAAAが同じgenerated schema / golden fixtureを使っている。
  2. Section 16の全適合試験がrelease buildで成功している。
  3. descriptor、handshake、connection.readyのversionが一致している。
  4. advertised connectionがprewarmされ、active run / connectionが常に1である。
  5. binary deltaのapplication overheadが16 byteで、terminal本文再送が0 byteである。
  6. delta欠落、重複、逆順、TTS再発声が0件である。
  7. tool、cancel、resume、terminal integrityが定義どおり動作する。
  8. 非loopbackはWSSで、secretと本文がlog / metricへ出ていない。
