Codex SDK Realtime Second Opinion 実装計画

0. 文書の役割

  • Status: Proposed — 実装未着手
  • Created: 2026-09-01
  • SAAA baseline: bc4a2d0
  • 対象client: macOS版SAAA desktop
  • 対象: LLM Provider設定、Codex認証、Codex App Server runtime、会話別session、 second-opinion UI、streaming、永続化、性能計測

本文書は、ChatGPT / Codex subscriptionで認証したCodexを、通常会話の回答を置き換えない 「second opinion」として最速で利用可能にする実装契約である。OpenAI API key、Responses API、 usage-based API課金は使用しない。

UI上は既存設定との一貫性を優先してCodex SDK Providerと表示する。ただし実行時の hot pathは、@openai/codex-sdkが利用するCodex executableを配布境界とし、 rich client向けの公式interfaceであるCodex App ServerへRustから直接接続する。 TypeScript SDKのrunごとのprocess起動を会話hot pathには置かない。

0.1 Normative precedence

  1. 通常LLM、UI、TTSのdelta配送と完了後Markdownは Maximum-Performance Streaming Experience 実装計画を正本とする。Codex固有transportだけを本文書で上書きする。
  2. 通常会話のSessionless継続、Context Health、Memory選択は MVP 3 Memory Architecture実装契約を正本とする。Codex sessionへそのContextWindowを再投影しない。
  3. SQLite connection ownershipは SQLite Single Writer実装計画を維持する。deltaごとのDB書込みは禁止する。
  4. Codexのprotocol、認証、thread lifecycleについては OpenAI Codex App Server公式仕様 を正本とし、SDKの適用範囲は OpenAI Codex SDK公式仕様 に従う。

1. Goalと非Goal

1.1 Goal

  • LLM Provider設定内に固定のCodex SDK sectionを追加する。
  • Codex executable、App Server、ChatGPT subscription認証状態を画面で確認できる。
  • 未認証の場合はSAAAからChatGPT browser loginを開始できる。
  • 通常回答に対し、ユーザーが明示操作でCodexのsecond opinionを要求できる。
  • Codexの最初のtext deltaを受信直後に既存Tauri Channelへ流す。
  • 同じSAAA会話では同じCodex threadをresumeし、process再起動後も継続する。
  • Codexの履歴と通常会話の最適化済みContextWindowを相互に汚染しない。

1.2 今回の非Goal

  • Codexを通常会話のprimary providerまたは自動fallbackへ追加しない。
  • いつCodexを呼ぶべきかの自動判定、回答の採点、統合、勝者選択は実装しない。
  • 通常会話の全履歴やMemory projectionをCodexへ毎turn再送しない。
  • Codex内部のContextWindowをtoken単位で削除、並べ替え、要約しない。
  • OpenAI API key、Responses API、Realtime API、SSEを追加しない。
  • 実験扱いのApp Server TCP WebSocket listenerをshipping経路にしない。
  • Codexにwrite、shell、network、web searchを許可しない。
  • second opinionの自動読み上げは行わない。初版はvisual-onlyとする。

5. Local ContextWindowとCodex sessionの分離

Table: Different continuity models
観点 通常local LLM Codex second opinion
継続性の正本 SAAA DB、Memory、毎turn再構成するContextWindow Codex App Serverの永続thread
session Provider sessionを前提にしない 会話ごとに同一threadをresumeする
過去context SAAAが選択、要約、予算制御する Codex自身が保持し、必要時にcompactionする
毎turnのinput system context + projected messages + current input current question + primary answer + optional instruction
回答保存 conversation_messagesとMemory control plane second_opinion_responsesだけ
reset 次turnでContextWindowを再構成できる thread全体を明示的に新規作成する以外は変更しない

初回も過去の通常会話全件はbootstrapしない。ユーザーが対象にした現在の質問とprimary回答だけを self-contained packetとして送る。2回目以降も新しい対象pairだけを送るため、Codex threadの履歴と SAAAの通常履歴が二重に積み上がらない。primary回答を更新して再実行する場合は新しいresponse recordを 作り、同じrequest IDの再送は行わない。

6. Target architecture

User clicks “Codexで確認”
  → React validates completed primary response
  → start_codex_second_opinion(Tauri command, Channel)
  → SQLite single writer creates runtime run + response shell
  → CodexAppServerRuntime gets/resumes conversation thread
  → turn/start over persistent stdin JSONL
  → stdout reader receives item/agentMessage/delta
  → RunSink → TurnEventHub → Tauri Channel
  → frame-coalesced plain-text render
  → item/completed validates canonical text
  → turn/completed → one terminal DB transaction
  → one-time Markdown render

6.1 Runtime ownership

  • AppStateへArc<CodexAppServerRuntime>を1つ保持する。
  • Codexがenabledならapp setup後にbackgroundでeager startする。
  • disabledでも設定画面のstatus確認またはlogin操作でlazy startできる。
  • child generationを採番し、process再起動前のrequest / turn eventを破棄する。
  • app shutdown時は新規受付を止め、active turnをinterruptし、stdin close後にchildを回収する。

6.2 Actor component

Table: Persistent App Server actor responsibilities
component 責務 bounded条件
Lifecycle actor spawn、single initialize、health、restart、shutdown 同時childはgenerationごとに1つ
Writer JSON-RPC requestとnotificationをstdinへ直列化 bounded queue、overflowは即時busy error
Reader 1行ずつJSON parseし、responseとnotificationを振分け 1行1 MiB、control item 256 KiB、本文64 KiB上限
Request registry request IDをoneshot responderへ対応 deadline到達時に必ずremove
Turn registry threadId + turnIdをRunSinkへ対応 1 threadにつきactive turn 1件
Status cache auth mode、plan、rate limit、model catalogを保持 token、email、本文をdiskやlogへ保存しない

現行のMAX_CODEX_STDOUT_BYTESによるprocess全生存期間の累積4 MiB制限は廃止する。 代わりにmessage単位、field単位、turn本文単位の上限を設ける。これにより長時間常駐と memory safetyを両立する。

初版の同時実行はthreadごとに1件、App Server全体で2件を上限とする。上限到達時は latencyが読めない内部queueへ積まず、retry可能なbusy stateを即時返す。status、cancel、 auth notificationはturn枠を消費しない。

7. LLM Provider設定

7.1 Codex SDK固定card

Settings → LLM Providerの先頭に、削除不可のCodex SDK — Second opinion cardを追加する。内部の保存先は既存どおりproviders.agent/codex-sdkとし、 statelessなproviders.model unionへ無理に追加しない。

Table: Codex SDK card fields and actions
field / action 表示・動作
有効化 second-opinion actionの表示とruntime eager startを切り替える
Runtime Codex executable version、App Server ready / starting / failedを表示する
認証 未認証、ChatGPT認証済み、非対応のAPI key認証、確認失敗を区別する
Subscription planTypeを表示し、ChatGPT認証以外は利用不可とする

endpoint、API key、fallback順位、primary route、削除buttonは表示しない。 ServiceConnectionsSectionの通常LLM候補にもCodexを出さない。

7.2 Status contract

CodexRuntimeStatusを次の意味へ拡張する。

  • state: unavailable / starting / signed-out / incompatible-auth / ready / degraded
  • installed、runtimeVersion、processReady
  • authenticatedとsubscriptionEligibleを別fieldにする
  • authMode、planType、checkedAt
  • rateLimitsは取得できない場合nullとし、認証readyを妨げない
  • messageCodeを返し、frontendのja / en翻訳で表示する

statusはruntime stateでありsettings文書へ永続化しない。現行の CodexAgentSettings.healthはschema migrationで削除し、古い値は読込み時に無視する。

8. Subscription-only認証

8.1 利用可能判定

  1. App Serverがinitializedである。
  2. account/read(refreshToken=false)が成功する。
  3. result.account.typeが厳密にchatgptである。
  4. planTypeが取得できれば表示する。未知の将来plan名は拒否せず文字数を検証する。

apiKey、chatgptAuthTokens、Amazon Bedrock、そのほか未知のaccount typeは 認証済みだがSAAAのCodex subscription要件には非対応と表示し、turn開始を拒否する。 SAAAはAPI keyの入力、保存、環境変数fallbackを実装しない。

8.2 Login flow

  1. account/login/startへtype=chatgptを送る。
  2. 返されたHTTPSのauthUrlだけをsystem browserで開く。
  3. loginIdをmemory上で保持し、重複loginを禁止する。
  4. account/login/completedとaccount/updatedを待つ。
  5. 成功後にaccount/readを再実行し、subscription eligibilityを確定する。
  6. 画面を閉じた場合はlogin自体を暗黙cancelしない。明示cancelだけを送る。

access token、refresh token、callback query、account emailはSAAAのDB、diagnostics、logへ保存しない。 token lifecycleはChatGPT managed authを所有するApp Serverへ委譲する。

9. Second-opinion request contract

9.1 UI entry

  • 正常完了したprimary assistant回答のfooterへCodexで確認を追加する。
  • Codexがdisabledまたはnot readyならbuttonから設定cardの状態へ案内する。
  • 同じprimary回答にrunning responseがある間は二重開始できない。
  • 完了後はprimary回答の直下へ独立したCodex second opinion cardを表示する。
  • 取消・再試行・session新規作成をprimary turnとは独立して行う。

9.2 IPC input

新規command start_codex_second_opinionは全文historyをfrontendから受け取らない。 最小入力を次に固定する。

  • runId
  • conversationId
  • sourceUserMessageId
  • sourceAssistantMessageId
  • instruction: optional、最大2,000 Unicode scalar
  • channel: typed second-opinion event Channel

backendは2つのmessageが同じconversationに属し、user → assistantの順で、assistant responseが 正常完了済みであることをDBから検証する。本文はDBから読み、frontendが別会話本文を注入できないようにする。

9.3 Turn input envelope

Codexへ送るtextは固定templateとし、毎turn次だけを含める。

  1. このthreadがSAAAのsecond opinion専用であるという固定instruction
  2. 現在のuser question
  3. primary assistant answer
  4. ユーザーが入力した任意の短い確認観点

過去のSAAA message、Memory summary、agent persona、system contextは含めない。 question 16,000 scalar、primary answer 64,000 scalar、envelope全体96 KiBを上限とし、超過時は 勝手にtruncateせずrequest-too-largeで拒否する。

10. Codex thread lifecycle

  1. 対象会話のpurpose=second-opinion sessionをSQLiteから探す。
  2. 存在しなければ安全なcwdでthread/startし、thread IDとmodelを保存する。
  3. 存在し、現在のApp Server generationで未loadなら、記録済みmodelを維持して thread/resumeする。
  4. 現在のgenerationでload済みならthread/resumeを省き、直接 turn/startへ進む。
  5. turn/start成功後にturn IDをactive registryへ登録する。
  6. turn/completedでregistryを必ず解放する。

coding conversationでは選択済みworkspaceをcwdに使える。通常conversationでは、second opinionを workspace選択でblockしないよう、SAAA app-data配下の空かつread-only用途の専用directoryを使う。 pathはcanonicalizeし、symlink escapeを拒否する。sandboxはread-only、approvalはnever、networkと web searchはfalseを維持する。

設定modelが変わっても既存threadへ一時的なmodel overrideを送らない。UIに 現在のsession: model X / 新規session: model Yを表示し、明示的なsession reset後にだけYを使う。

11. Streamingと性能契約

11.1 Event projection

Table: App Server event projection

11.2 Hot path規則

  • reader threadはJSON decode、field validation、RunSink enqueueまでに限定する。
  • TTS fan-outを行わないため、second opinion deltaはUI laneだけへ送る。
  • UIはcapacity 1のlatest snapshotまたは既存frame coalescerで1 frame最大1回renderする。
  • 生成中はplain text、正常完了時だけMarkdown ASTを一度構築する。
  • deltaごとにSQLite、audit、console log、analytics、React state全文copyを行わない。
  • unknown notificationはbounded metadataだけ記録し、active turnを不用意に失敗させない。

11.3 Latency measurement and budget

Table: Warm-path SAAA-added latency budget

TTFTはTime To First Token、すなわちユーザー操作から最初の表示可能text deltaまでの時間である。 実測ではprovider推論時間とSAAA-added時間を別spanにし、providerの揺らぎでlocal回帰を隠さない。

12. Persistenceとmigration

12.1 Database schema

DB user_versionを15から16へ上げ、transactional migrationを追加する。

  • codex_threadsを再構築し、keyを (conversation_id, purpose)へ変更する。
  • purposeは初版でcoding-assistまたはsecond-opinion。 既存rowはcoding-assistへ移行する。
  • thread ID unique、model、workspace path、compaction count、created / updated / last resumedを保持する。
  • second_opinion_responsesを追加し、response ID、conversation ID、source user / assistant message ID、runtime run ID、Codex thread / turn ID、status、content、failure code、timestampsを保持する。
  • runtime_runs.route_kindへconversation.second-opinionを追加するため、 CHECK constraintを含むtable rebuild migrationを行う。
  • second_opinion_responsesからsource messageへのforeign keyを設定し、conversation delete時はcascadeする。

terminal transactionはcanonical本文、response status、runtime run status、Codex thread metadataを 一括更新する。Memory control planeのrecord_completed_turnは呼ばない。

12.2 Settings schema

Settings schemaを13から14へ上げる。

  • provider="codex-sdk"、sandbox、approval、network、web searchの固定値を維持する。
  • runtimeModeはapp-serverだけへ正規化する。
  • 永続healthを削除する。
  • usage="second-opinion"を追加し、将来のprimary routingへの誤流入をschemaで拒否する。
  • 旧設定は欠落fieldを補い、unknown fieldは既存migration policyに従って除去する。

13. State、取消、回復

13.1 Response state machine

idle → validating → queued → starting-thread | resuming-thread
     → running → completed
               ↘ cancelling → cancelled
               ↘ failed

禁止: completed / cancelled / failed → running
retry: terminal response → new response ID / new runtime run ID

13.2 Failure policy

Table: Failure handling
failure 扱い
not installed / spawn failure Provider cardをunavailableにし、primary回答は変更しない
signed out / incompatible auth turn開始前に拒否し、ChatGPT loginまたはauth変更を案内する
process crash before first delta runtimeを1回再起動しthread resumeを試す。同じturnを自動再送しない
process crash after first delta partial-output failure。本文はplain textで残し、自動retryしない
thread not found / corrupt 明示確認後のnew sessionで回復。過去sessionを暗黙破棄しない
rate limit reset時刻があれば表示し、primary routeへfallbackしない
protocol line / content too large active turnを失敗、runtime generationを隔離して再起動する
UI disconnect turnをinterruptし、terminal DB確定までbackendがownershipを持つ

exactly-once terminal guardはruntime_runs.status='running'の条件付きUPDATEで維持する。 app再起動時にrunningのresponseとrunをinterruptedへreconcileする。

14. Securityとprivacy

  • Codexへ送信する直前に、対象質問とprimary回答が外部serviceへ送られることをUIに明示する。
  • 初版はread-only sandbox、approval never、network off、web search offをhard-codeする。
  • tool call、file mutation、command execution要求をProvider errorでなくpolicy violationとして監査する。
  • stdioはchild pipeだけに接続し、port listenerを開かない。
  • JSON-RPC error本文、path、account情報は既存redactionを通す。
  • prompt / response本文をperformance trace、audit attributes、crash reportへ入れない。
  • auth URLはHTTPS、host allowlist、最大長、control characterなしを検証してからbrowserで開く。
  • SAAAはCodex token fileを読取、複製、backup、diagnostics exportしない。

  4. 既存coding-assist threadが失われないmigration testを追加する。

Phase B — Persistent runtime

  1. CodexAppServerRuntime、writer、reader、request / turn registryを実装する。
  2. status、model list、login、rate limitsを共有runtimeへ移す。
  3. process lifetime総量上限をmessage / turn単位上限へ置換する。
  4. crash generation、restart、shutdown、orphan response回収を実装する。

Acceptance: 100 turnのprotocol harnessでchild spawn 1回、initialize 1回、response leak 0。

  1. CodexSdkProviderCardをProvider tabへ追加する。
  2. auth modeとsubscription eligibilityを分けて表示する。

Phase D — Second-opinion route

  1. source message validationと専用request envelopeを実装する。
  2. conversation × purposeのthread start / resumeとmodel pinningを実装する。
  3. 専用response persistenceを実装し、Memory enqueueを禁止するtestを追加する。
  4. interrupt、partial failure、new sessionを実装する。

Acceptance: 同じ会話は同じthread、別会話は別threadを使い、通常ContextWindowのfixtureが不変。

  1. primary回答footerとsecond-opinion cardを追加する。
  2. 既存plain-text streaming bufferと完了後Markdown pathを再利用する。
  3. latency spans、queue depth、restart count、compaction countをcontent-free metricで追加する。
  4. warm / cold / long response / cancel / 100-turn soakを実行する。

Acceptance: Section 11.3のlocal latency Gateを全て満たし、delta中DB writeとMarkdown parseが0。

17. Rolloutとrollback

  1. 初期値disabledでshipし、Provider cardから明示的に有効化する。
  2. 内部canaryではsettings / authだけを先に有効化し、turn actionをfeature flagで分離する。
  3. 次にexplicit second opinionだけを有効化する。自動呼出しはこの計画に含めない。
  4. failure rate、runtime restart、local latency、rate limitをcontent-free metricで監視する。

即時rollbackはfeature flagでbuttonとeager startを無効化し、Codex session dataは保持する。 DB migration後のbinary rollbackはmigration前に作る既存backupを使う。Codex thread logやtokenをSAAAが 削除するrollbackは行わない。

18. Definition of Done

  • Provider tabにCodex SDK cardがあり、installed、runtime、ChatGPT認証、planを正しく区別できる。
  • API key認証ではsecond opinionを開始できず、OpenAI APIへのfallbackもない。
  • App Serverは常駐し、warm turnごとのprocess spawn / initialize / auth readが0である。
  • 同じSAAA会話は同じCodex threadをresumeし、app restart後も継続する。
  • 通常ContextWindow、conversation messages、Memory jobへCodex second opinionが混ざらない。
  • deltaはSection 11の予算でplain text表示され、正常完了時だけMarkdownへ切り替わる。
  • cancel、crash、partial、rate limit、thread消失が正しいterminal stateになる。
  • read-only、no approval、no network、no web searchがprotocolとtestの両方で固定される。
  • G0〜G10が全てPassし、release evidenceにcontent-free結果が残る。
